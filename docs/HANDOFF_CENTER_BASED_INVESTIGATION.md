## 1. Essential center-based domain primer (so you scope the research correctly)

Internalize this before launching research, or your topic briefs will be mis-scoped. *Verify all of it during research — treat it as a seed, not gospel.*

**What a center-based model is.** A center-based (a.k.a. *cell-centre*, *off-lattice agent-based*) model represents each biological cell as a **point (its centre) at a continuous position `x_i ∈ ℝ²` or `ℝ³`**, usually with a **radius `R_i`** (so it is effectively a soft sphere). There is **no lattice**. Two dominant sub-families differ in how "who interacts with whom" is defined:
- **Overlapping spheres (OS):** cells are spheres; two cells interact when their centre-centre distance `d_ij` is below an interaction cutoff. The force is **repulsive when they overlap** (`d_ij < R_i + R_j`) and **adhesive over a short contact range** beyond that. Neighbours are found by **distance search** (a cell list / spatial hash / k-d tree).
- **Voronoi / Delaunay centre-based** (Meineke–Potten–Loeffler 2001): cells are the points of a **Delaunay triangulation**; two cells are neighbours iff they share a Delaunay edge; spring forces act along edges; each cell's "size" is its **Voronoi region**. Neighbours come from the triangulation, which must be **recomputed (or incrementally updated) as cells move**.

**The dynamics — force-based ODE integration (NOT a CA rule, NOT Monte Carlo).** Tissue mechanics is overwhelmingly modelled as **overdamped** (inertia-free): `η · dx_i/dt = Σ_{j ∈ neighbours(i)} F_ij(x_i, x_j) + F_i^migration`, where `η` is a drag coefficient and `F_ij` is a pairwise force law. It is integrated forward in time with a small timestep `Δt` (usually forward Euler). One "generation" = one integration step (or a fixed number of them). Some models keep an inertial (damped Newtonian) form. **Numerical stability is a real hazard:** too large a `Δt` (relative to the force stiffness) makes positions explode.

**Force laws (`F_ij`).** Common choices: a **linear (Hookean) spring** toward a rest length (Meineke 2001); **cubic / GLS** (Pathmanathan et al. 2009); **Hertz contact**; **JKR** (adhesion + repulsion with hysteresis); piecewise repulsion-then-adhesion with a maximum interaction distance. Repulsion is strong (cells can't interpenetrate); adhesion is weaker and short-range. A separate **random/active migration force** drives motility.

**Cell behaviours = the morphogenesis payoff, and they are *easy* here.**
- **Division (mitosis)** is trivial — *the* draw of this family: when a cell completes its cycle, **replace it with two daughters** placed a small distance apart along a random or oriented axis; repulsion then pushes them to relax. No lattice relabel, no pixel-set split (contrast CPM §2-§6). Division **grows the agent count** `N`.
- **Growth** = increase the cell's target radius/volume over the cycle. **Death** (apoptosis/necrosis) = remove the agent from the population (and recycle its slot). **Differentiation** = change its type/phenotype.
- **Arbitrary per-cell state + sophisticated rules are native.** PhysiCell's model is *exactly* "each agent has a `Phenotype` (cycle, death, volume, motility, secretion, mechanics) + user-assignable `Cell_Functions`/rules" — i.e. the "arbitrary attributes + sophisticated per-cell update rules over many attributes" the user wants, with division genuinely trivial.

**Coupling to a chemical microenvironment (PDE).** Most non-trivial center-based morphogenesis couples the agents to one or more **diffusing chemical fields** on a **separate coarse Cartesian grid**, solved by finite-volume/finite-difference (PhysiCell uses **BioFVM**). Cells act as **sources/sinks** (secretion/uptake) and **sense gradients** (chemotaxis); oxygen/nutrient limitation drives growth and necrosis. This is closer to "must-have for interesting morphogenesis" here than it was for CPM.

**Cell shape: there is none.** Centre-based cells are points/spheres — PhysiCell explicitly "does not model cell morphology." So this family models **population- and tissue-level organization and mechanics**, *not* individual cell shape. (If individual deformable shape matters — folding epithelia, etc. — that is CPM / vertex / subcellular-element territory. State this ceiling as bluntly as the CPM doc stated CPM's.)

**3D is native.** PhysiCell, Chaste, ya||a are 3D-first; the *engine* generalizes to 3D with essentially no new algorithm (only the force/neighbour math gains a z). The *renderer* still needs a 3D path.

**Closest existing GenesisCA machinery — and the gaps (verify these as fit hypotheses, don't assert them):**
- **The per-cell *object* tier is the PRIMARY representation, not an add-on.** A cell is an object: `position (x,y[,z])`, `radius`, type, arbitrary attributes, lineage, cycle state. **This is the same per-cell-object tier the CPM investigation identified as the central new structure** (CPM §5.2) — but here it is *the whole state*, not a second tier over a spin lattice. GenesisCA has no per-agent/object level today (every attribute is per-*site* or a global scalar — confirmed by the CPM audit). **This is THE central data-structure question.**
- **Dynamic adjacency is the user's explicit "dynamic spatiality/adjacency" requirement, delivered natively** — neighbours change every step as cells move/divide. The new structure is a **spatial index (cell list / hash / k-d tree)** or a **Delaunay triangulation**, rebuilt or incrementally updated each step (replaces the fixed neighbour-index table).
- **Variable neighbour count → order-independent aggregates.** A cell has a *variable* number of neighbours (like a graph node, unlike a lattice). The Graph-CA finding applies: neighbour reads must go through **degree-tolerant aggregates** (`GetNeighborsAttribute → Aggregate`), which GenesisCA already has. (Cross-read Graph-CA §2.2.)
- **The compile-to-per-cell-step model may actually FIT** (the counter-intuition vs CPM): each cell computes its **own** net force by summing over its neighbours and then integrates its **own** position — that *is* a per-cell step. If the worker provides the neighbour structure (as it already provides a neighbour-index table), the existing compiler might emit the force/behaviour step with far less violence than CPM required. **Test this carefully — it is the most important and most surprising fit question.**
- **WebGPU is a *good* fit here** (the inverse of CPM): force computation is embarrassingly parallel (one thread per cell, sum neighbour forces), so center-based is a natural GPU target (cf. ya||a on CUDA). Contrast CPM, which was JS/WASM-only because its accept/reject is sequential.
- **Rendering is a from-scratch entity renderer, NOT the lattice blit** — draw N filled circles/spheres at continuous positions, radius ∝ size, colour by attribute; picking = nearest-centre; pan/zoom in continuous coords; 3D via WebGL. **This is the Graph-CA renderer problem, not the CPM one** — reuse Graph-CA §8 (`drawGraph()`, the `screenToCellId`/`cellIdToScreen` picker abstraction, instanced rendering at scale, the "colours buffer on the main thread every frame" perf note). The lattice `ImageData` one-blit path does **not** carry over.
- **Division grows `N`** — the fixed-`total`, allocate-once-at-init assumption breaks. Need a capacity ceiling + free-list (the same `maxCells` hazard the CPM doc raised in §5.2/§12.1 — reuse that analysis).
- **Existence proof / browser feasibility is an OPEN question (and a finding in itself).** CPM had **Artistoo** as a clean pure-JS browser existence proof. Center-based may *not* have an equally clean one — PhysiCell is C++/OpenMP (with cloud/nanoHUB + a "PhysiCell Studio" GUI and some WebAssembly/web efforts), Chaste is C++, CBMOS is Python/GPU, ya||a is CUDA, Tissue Forge is C++/Python. **Find the closest browser/JS/WASM center-based engine — or establish that none is as mature as Artistoo.** Whether a zero-install in-browser center-based engine is proven is load-bearing for feasibility; do not assume it.

## 2. The process that worked — replicate it exactly

### 2.1 ⚠️ THE THROTTLE LESSON (do not skip — it cost two failed runs in the original Graph-CA work)
Web-research agents each fire many WebSearch/WebFetch round-trips, so even a handful running at once can trip a transient server-side rate limit (`API Error: Server is temporarily limiting requests`). The discipline that works:
- **Codebase-audit agents:** run in **parallel but ≤5 at a time** (they read files — fewer API round-trips).
- **Literature research agents:** run **FULLY SEQUENTIAL — one web agent at a time** (a `for` loop with `await`, *not* `parallel()`). Same for the verify pass.
- **Stagger the two waves** (codebase first, then literature) so peak concurrency stays low.
- **Resilience:** `agent()` returns `null` on a terminal API error, so a sequential loop that pushes only truthy results survives partial failures; failed agents just re-run on a resume.

### 2.2 ⚠️ LESSONS THE CPM SESSION LEARNED (new — these will save you real time)
1. **The Workflow validator forbids the literal tokens `Math.random()`, `Date.now()`, `new Date()` ANYWHERE in the script — including inside brief *strings*.** The CPM run failed first launch because a brief contained the text "Math.random()". **Phrase any RNG/timestamp mention without those exact tokens** (e.g. "a uniform random draw", "the JS PRNG"). The script body itself must also avoid them (they break resume).
2. **The result file is wrapped.** The workflow's output JSON is `{ summary, agentCount, logs, result }` — your returned `{ literature, codebase, synthesis, critique }` is under **`.result`**. Don't parse the top level and find everything empty (the CPM session did, once).
3. **Do NOT try to `Read` the giant result as one blob** (it's ~350k+ chars, often effectively one line). Write a tiny **Node extraction script** that `JSON.parse`s the output file and writes each section to its own file (`_synthesis.md`, `_critique.json`, `_codebase.json`, `_lit_summaries.md`, `_lit_works.json`), then Read those. 4. **The synthesis subagent may write the `.md` directly to disk** (it has Write access) and return only a summary. That's fine — but **you are responsible for finalizing it**: read the draft, read the critique, and fold the critique's fixes in yourself. Treat the agent draft as a *draft*, not the final deliverable.
5. **Tune the live demo empirically *before* baking defaults.** The CPM demo's first parameters (temperature, cell size) did **not** visibly sort; the fix was to drive the demo's own controls via `preview_eval`, measure an outcome metric (e.g. interface length over MCS), and iterate the defaults until the behaviour was clearly correct. Budget for this loop — a demo that silently does nothing is worse than no demo.
