PWA, the native exe & offline — explained

Everything that the install / packaging work added to GenesisCA: what a PWA is, how the browser PWA differs from the standalone native executable, when each pop-up appears, and what installing actually unlocks (and what it doesn’t).

30-second version

There is one app (your built dist/ folder). It can run three ways: in a browser tab, as an installed PWA (its own window + icon, works offline), or as a standalone native app you run directly (a portable .exe — no install). Installing gives you offline use, a real app window, and a durable cache — but not more memory. The native (Tauri) build doesn't change that either, as it stands: it wraps the same browser engine, so the memory ceiling is identical. More RAM for huge grids would mean moving the simulation to native Rust — a separate, larger project.

1 · One app, three ways to run it

The same code builds once into a dist/ folder. That folder is delivered to you in three different “shells,” each with a different amount of isolation from your operating system.

The further right you go, the less the OS “sandboxes” the app — and the more it can do.

2 · What is a PWA?

A PWA (Progressive Web App) is an ordinary website that ships two extra ingredients so a browser will treat it like an installable, offline-capable app:

① A Web App Manifest

A small file describing the app’s identity: name, icons, theme colour, and that it should open in its own standalone window (no tabs / address bar). This is what lets the browser offer “Install”.

② A Service Worker

A tiny background script the browser keeps even when the app is closed. It sits between the app and the network and serves files from a local cache — which is what makes the app load instantly and work with no internet.

Every request goes through the service worker. It answers from the cache first, so the app keeps working offline.

In GenesisCA the cache holds the app itself, the simulation engine (the Web Worker), all the icons, the Models Library index, the macros, and the card thumbnails. Individual model files are cached the first time you open them. None of this requires a server — it’s all static files.

3 · The build pipeline

One command builds the web app; the PWA pieces are generated automatically; a second command wraps that exact output into a standalone native exe.

The native exe wraps the same dist/ — so the app is identical; only the shell around it differs.

4 · What we ship: the PWA + a portable exe

The main way to install GenesisCA is the PWA (the browser “Install” button — auto-updating, cross-platform). For when you want a file you can carry, the build also produces one standalone .exe — no installer. Both run the same app.

PWA · the main install

Install from the browser

Open the site in Chrome/Edge → ⤓ Install. Own window + icon, fully offline.

Auto-updates silently on the next launch when a new version ships; works on Windows/Mac/Linux/Android. This is what almost everyone should use.

.exe · portable, for sharing

Standalone executable

GenesisCA-v1.19.0.exe — the raw program; double-click and it runs.

No installer, no shortcuts, nothing to install — runs from anywhere (e.g. a USB stick), handy for tossing to a friend. Published to each GitHub Release. (Unsigned, so the first run shows a SmartScreen “More info → Run anyway” prompt; it does not auto-update.)

We deliberately don’t ship a Windows installer (NSIS or MSI). The PWA already gives a real installed app — own window, icon, Start-menu entry, auto-updates — with zero download, so an installer would mostly add maintenance (publisher / version / signing) for little gain. The portable .exe covers the “give it to someone offline” case.

5 · The one pop-up that’s left

GenesisCA deliberately shows almost no PWA notifications — the earlier toasts ("ready to work offline," "installed," "new version available") were removed because they stated the obvious or had nothing actionable behind them. What remains is the browser’s own install offer.

browser · install offer

“GenesisCA can be installed”

When: the browser detects the app is installable (HTTPS, manifest + service worker) and you haven’t installed it yet.

What it does: offers to install. Use the browser’s own icon, or the amber ⤓ Install button in the top bar (same prompt). The button hides itself once installed — that’s the only feedback (no toast).

removed · and why

The toasts we dropped

“Ready to work offline” — pointless: the app always works offline (no online processing), so it’s never news.

“New version available — Reload” — no in-app update channel to act on; new versions now apply silently on the next launch.

“Installed” — the app opening in its own window already says that.

7 · The key takeaway: storage ≠ memory

what install DOES help

Storage & availability

  • Run fully offline with the whole library.
  • A real app window + icon, launchable from Start.
  • Durable storage — installing makes the browser grant “persistent” storage automatically, so your cached models aren’t evicted when the disk gets full.
  • A generous disk quota (~60% of free space).
what install does NOT do

Memory / performance ceiling

  • It does not give the simulator more RAM. A 5000×5000 grid (25M cells) is bounded by the browser’s memory limits whether or not you install.
  • Durable storage protects data on disk; it never touches the running memory budget.
  • The installed PWA runs in the same browser engine as the tab — no extra compute.

If the wall you hit is memory, installing won’t help — and neither does today’s native build

The Tauri app wraps the same browser engine (WebView2/Chromium on Windows), and the simulation still runs as the same WASM/JS inside it — so the memory ceiling (the ~4 GiB WebAssembly limit) is identical to the PWA. What the native build genuinely adds is true filesystem access with no storage quota, a toggle-free native window, and standalone distribution. Actually raising the memory ceiling would require rewriting the simulation in native Rust to run outside the webview — a separate, larger effort, not something the current shell delivers. (Engine caveat: on Windows the shell is Chromium so WebGPU works; on macOS/Linux it’s WebKit, where the simulator falls back to the WASM/JS engines.)
