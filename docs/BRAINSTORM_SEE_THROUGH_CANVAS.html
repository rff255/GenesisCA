See-through node canvas — editing the model while it plays

Blender's compositor/shader editors let you keep a live render behind the node graph and see every edit land. GenesisCA has the two halves already — a node editor and a simulator that soft-recompiles on every graph edit — but they are mutually exclusive: switching to the Modeler unmounts the simulator's UI and auto-pauses the run. This brainstorm proposes three ways to put the running simulation and the rule graph on screen at once, and the mechanics they all share. Nothing here is built. The mockups below are live HTML: the background is a small Game of Life actually running, so the overlay can be judged with something moving behind it.

What already exists and makes this cheap: (1) SimulatorView is always mounted, hidden by display:none, and its worker survives tab switches; (2) a graph edit is synced to the model after 100 ms and triggers a soft recompile that keeps the grid state (a structural change forces a reinit); (3) every GPU display path presents into a real DOM canvas the browser composites, so stacking the graph over it is CSS z-order, not new rendering. What is missing is only seeing the run while the graph is on screen, and deciding who owns the keyboard and the pointer.

Option A — Backdrop overlay the Blender lookmost "see-through"

The simulator canvas fills the modeler's canvas area, full-bleed. The node graph's pane becomes translucent glass: nodes and wires stay fully opaque, the pane's dotted background becomes a dimming scrim with an opacity slider. The pointer belongs to the graph; holding a modifier (or a toggle) "reaches through" to the simulation, fading the graph so the brush, pan, and orbit gestures land on the board.

Try it: drag the dim slider to change the scrim; tick reach through to see the graph fade while the board takes the pointer (an amber focus ring marks which surface owns input). Nodes keep full opacity at every dim level — legibility comes from the node bodies, not the pane.

What changes on screen

  • A third top-level mode, Live (or a toggle inside the Modeler). The ear-tabs, side panels, graph pills, and macro breadcrumb stay exactly where they are.
  • React Flow's Background dots become the scrim; the pane's --color-bg-canvas fill is replaced by rgba(bg, dim).
  • Node bodies gain a faint frosted backing (no blur — a 2 px shadow + the existing opaque body is enough); comment and group tints get one notch more transparent so they don't wall off the board.
  • A compact transport bar floats at the bottom of the canvas (play/pause, step, reset, FPS, G/F) — the simulator's own bar, re-docked. The mapping viewer tabs collapse into a dropdown on the same bar.
  • The stats overlay and the compile-target chip keep their bottom-right corner; the capture cluster is left out of Live mode (record from the Simulator tab).

Reach-through (input ownership)

  • Default: the graph owns pointer and keyboard. Wheel zooms the graph; RMB pans the graph.
  • Alt held (or the chip's toggle, or a middle-click latch): the graph fades to ~30 % and every gesture goes to the simulator — brush, RMB pan, wheel zoom, 3D orbit. The brush cursor appears; a focus ring shows who has input.
  • Release Alt → graph comes back. The sim's camera and the graph's viewport are independent; a "Fit board to graph viewport" button aligns them once.
  • Nothing dual-purpose is ever active on both surfaces at once — this is how Space (quick-add in the Modeler, step in the Simulator) stops conflicting.

In 3D the sphere/voxel free-mode canvases already sit under gl3d's overlay canvas as layered DOM elements; the graph goes on top of that stack unchanged. Orbit requires reach-through, which is the honest answer — a graph drag and an orbit drag cannot share LMB.

Cost to watch: the browser composites a full-viewport translucent layer over a canvas that repaints at up to 60 fps. On integrated GPUs this is fine for a 2D grid but the Live chip should offer "pause rendering while dragging nodes" (the simulation keeps stepping; only the blit skips), and Live mode should default the sim's FPS cap to 30.

Option B — Split workspace Blender areascheapest, most legible

The canvas area is divided by a draggable splitter: node graph on one side, the full simulator viewport on the other, both fully interactive with no modifier games. This is how most people actually use Blender's node editors — a render viewport next to the graph, not behind it. The graph keeps its opaque pane and full contrast; the viewport keeps its own transport bar, viewer tabs and brush.

Layout menu (top-right of the viewport): dock right / dock bottom / swap / collapse. The splitter position persists like the panel widths. A double-click on the splitter snaps to 50 %.

Why it is the cheapest

  • Both views render in their own box — no transparency, no input arbitration, no z-order across two React trees. The keyboard owner is simply the box under the last click / hover (a 1 px accent border on the focused box).
  • The simulator's right panel (brush, indicators) and the modeler's detail panels compete for width. Live mode collapses the simulator's side panels by default and exposes the brush as a small popover from the viewport bar.
  • Reuses PanelShell's resize handle pattern and the modeler's panel-collapse machinery.

What it gives up

  • Half the width for the graph. Big graphs need the minimap more; a "graph focus" key (F already collapses side panels) can temporarily shrink the viewport to a strip.
  • The "watching the run through the wires" feel — the overlay's real appeal for demos and for cause→effect intuition.

Option C — Live viewport window picture-in-picturebest for multi-monitor

A small floating window over the graph shows the running simulation. It drags, resizes from a corner, snaps to the nearest canvas corner, and expands to full viewport with one click. A pop-out button moves it into a real OS window via the Document Picture-in-Picture API (Chromium, which is what WebGPU already requires), so on a two-monitor desk the simulation lives on the second screen while the graph fills the first.

The window is view-only by default (no brush, no inspect) — it is a monitor, not a workbench. Clicking it is what switches to the Simulator tab if the user wants to interact. A "follow inspected agent" would work here too, since Follow mode already tracks a camera target.

The pop-out is the interesting half. documentPictureInPicture.requestWindow() gives an always-on-top window the page fully controls; the simulator's display canvas can be moved into it (the worker's transferred OffscreenCanvas keeps presenting into the same DOM element), and it returns to the main document when closed. It is Chromium-only and needs a user gesture — the same constraints the app already accepts for WebGPU and the Tauri shell.

Recommendation

Build B as the base, and make A a layout setting on top of it. One "Live" mode with a layout knob: Split right · Split bottom · Overlay. Overlay is Split with the divider pushed to the edge and the graph pane's fill turned to glass — the same two mounted views, the same transport bar, only the CSS placement and the reach-through modifier differ. That way the input-arbitration work is scoped to Overlay and can ship later without redoing the plumbing, and users who dislike the see-through look never meet it. C's pop-out is a follow-up that reuses the same mounted viewport; its floating in-page form is the least valuable of the three and could be skipped.

Mechanics every option shares

1 · The edit → running-rule pipeline (mostly built)

  • Last-good-rule semantics. A half-wired graph compiles with errors dozens of times per minute while the user works. The run must keep the previous compiled function and show the error where it belongs — an amber ! on the offending node (the existing badge) plus a small ● stale state on the transport chip — instead of the red banner that stops everything today. The banner stays for the Simulator tab.
  • Apply policy. A per-session switch on the Live chip: Auto (100 ms) — Blender's behaviour — or On demand (the chip turns amber "● pending", Ctrl+Enter applies). On-demand matters for slow compiles (large WebGPU shaders, big agent graphs) and for deliberate multi-node edits that should land atomically.
  • Structural edits do not silently reset. Adding an attribute, changing grid dimensions, flipping a capability profile → needsFullInit → today's reinit re-seeds the board. In Live mode that should be a prompt on the chip ("Rebuild needed · the board will re-seed · Apply / Later"), so a dozen structural edits cost one reset, and the running board is never lost by accident. If the model carries a saved board, Reset restores the saved board already answers what comes back.
  • RNG / determinism. A recompile mid-run is a new rule from generation N; the shared stream advances continuously. Fine for exploration, but the Overseer must refuse to run while Live is on (a sweep under a moving rule is meaningless) — the same mutual exclusion it already has with manual play.

2 · Mounting both views

  • ModelerView is conditionally rendered and rebuilds React Flow on every mount (its layout state survives via modelerUiState); SimulatorView is always mounted and auto-pauses on visible=false. Live mode renders both with a new visible-like flag that means "shown" rather than "the active tab", so the auto-pause does not fire and the simulator's draw() keeps running.
  • Both views measure their canvas from their container; the splitter / overlay just changes the containers. The direct-render re-attach on resize already exists (it tracks a splitter drag today).
  • The two side-panel systems (modeler ears + detail panel; simulator left/right panels) both push the canvas. Live mode gives the graph the modeler's panels and hides the simulator's, exposing brush + indicators as popovers from the viewport bar.

4 · Performance guards

  • Default the Live FPS cap to 30 and skip the blit (not the step) while a node drag is in progress — draw() is the expensive main-thread part; the worker keeps stepping.
  • Large grids on the CPU path ship a colours buffer per frame; the WebGPU/direct-render paths do not. Live mode changes nothing there.
  • A compile every 100 ms on a 500-node graph is noticeable; the debounce should stretch to ~400 ms while the pointer is down and collapse back when it lifts.

5 · Open questions to decide before an impact map

  • Is Live a third top-level mode (Modeler · Simulator · Live) or a toggle inside the Modeler? A mode is discoverable and keeps the two existing tabs pure; a toggle avoids a third place to be.
  • Should the Agents graph and the Cells graph overlay differently (agents drawn over the graph even at full dim, since they are sparse)? Cheap to try with the overlay's scrim.
  • Does the standalone .html export ever want this? Probably not — it ships the simulator only.
  • Macro scope: editing inside a macro while it runs is the same pipeline, but the breadcrumb and the boundary nodes take vertical space the overlay could use.
