2 Executive summary

The diagnosis in the brainstorm is right, and the conclusion is stronger than it assumes.

A move-into-a-vacancy rule is not fundamentally sequential. What is fundamentally sequential is the implementation GenesisCA offers for it: async mode’s single shared buffer, where “is my target empty?” is answered against a board other cells are mutating. The rule itself needs exactly one guarantee — no two entities land on the same cell — and that is a conflict-resolution problem, not an ordering problem. Conflict resolution parallelises. Ordering does not.

The recommendation is design (A): a two-phase PROPOSE → RESOLVE step. Phase 1 is the user’s existing rule, ending in a new proposeMove node that writes an intent instead of writing the neighbour. Phase 2 is an engine-owned pass in which every cell writes only itself. Both phases are pure functions of the previous buffer — so both are order-independent, and both are ordinary WGSL dispatches.

Three findings that reframe the problem

1 · The usual baseline is inflated

A naive shuffled sweep re-visits a particle that moved into a not-yet-visited cell, so one particle moves 1.61 times per generation at 10 % fill — impossible for a “one cell per step” rule. GenesisCA already ships markCellUpdated to suppress exactly this. Against the marked baseline the parallel scheme is nearly free at the densities most models run at.

2 · Async is already order-dependent

For a packed “train”, a right-to-left sweep advances all K movers and a left-to-right sweep advances 1 — same state, markCellUpdated on. The random-order scheme re-rolls that every generation. The parallel scheme always gives the left-to-right answer: one of the answers async already produces, deterministically.

3 · The prize is the ceiling, not the four shipped models

Every shipped async model is 8 600–10 000 cells, where WASM is entirely adequate. The real constraint is that today a model may have movement with mass conservation, or a grid big enough to need WebGPU — never both. The Accretor ships at 300³ = 27 M cells; a moving-entity model at that scale is not slow, it is inexpressible.

3 The problem, precisely

Two cells want the same empty cell. Sequential execution answers that by making one of them go first. A parallel dispatch has no “first”.

3.2 · What actually needs sequentiality

The six async-only nodes are not one category, and sorting them is the design:

NodeWritesGenuinely order-dependent?
moveSelfToNeighborone target + selfNO — a permutation: at most one payload per cell. A conflict problem.
setNeighborAttributeByIndexone/array of neighboursNO when used as a move (gas_particles, snake); YES if two writers legitimately differ and last-writer matters.
setNeighborhoodAttributeevery cell of a neighbourhoodYES, structurally — a broadcast. N writers per cell is the intent. No arbitration preserves that.
setFacingOrientation · setNeighborOrientationByIndexone neighbour’s orientationSame shape as setNeighborAttributeByIndex.
markCellUpdatedthe scheduler’s _skipped flagN/A — it exists only to patch a sequential artifact. In a two-phase scheme it is unnecessary.
Read the node’s own doc comment: “Async-only. It writes neighbour cells … sync mode’s post-step bulk copy would overwrite those writes.” That is a statement about the buffer discipline, not about the rule’s semantics. Give the rule a mechanism that answers “did I get the cell?” after everyone has asked, and the live buffer stops being necessary.

Both shipped movement models configure the node identically in the load-bearing respect — operation: 'copyTo', nonReceiving: 'defaults' — which is the move-into-a-vacancy idiom: payload to the target, source resets, exactly one vacancy left behind.

The literature’s verdict on the brainstorm’s closing sentence. “The conflict policy needs to be determined somehow” is not an implementation detail — it is the definition of a parallel exclusion process. Two parallel CAs with the same hop rule and different collision rules are different models. That argues for making the policy an explicit, named, per-model setting rather than an engine constant.

Honest limitations. It is not bit-identical to any async run, and cannot be — async’s answer depends on a shuffle. A single generation moves a mover at most one cell, so a packed train advances one cell per generation rather than cascading (the same answer async gives under an unfavourable order). And setNeighborhoodAttribute — a broadcast with N legitimate writers per cell — stays async-only, correctly.

(B) Margolus block partitioning as an update mode

(C) Lattice-locked agents — the brainstorm’s literal reading

This already exists, by hand. Ant Necrophoresis does exactly it: ants on exact integer cell positions, moved one cell per step with Set Agent Position and a hand-written torus wrap, with the engine integrator inert.

Why it does not reach the goalDetail
A GPU resolve needs atomics and gives up determinismThe agent structural phase is CPU/JS on every target by design — draining move requests there forfeits the very residency the brainstorm wants. A GPU-side atomicCompareExchangeWeak claim is conservative but its winner is dispatch-order-dependent, so the model stops being reproducible. Against the project’s exact reproducibility contract that is a visible downgrade.
Population scale is off by orders of magnitudeThe agent engine is measured at ~50 k agents. A 300³ grid is 27 million entities; a 5000² grid is 25 million. Three orders of magnitude past the tested range — and the agent SoA is maxAgents-sized regardless of occupancy.
Every cell attribute must migrateState becomes agent attributes; the substrate becomes a field read through the field bridge; rendering, brushing, indicators, save/load and the cell inspector all change meaning. A model-authoring migration, not a compile-target unlock.

Verdict: right when entities are sparse relative to the grid. Wrong when entities are the grid.

(D) Do nothing; document the workaround

Async on WASM is already the fastest CPU path, and all four shipped async models are ≤ 10 000 cells. The cost of (D) is not slowness — it is the ceiling. Because the gate is a compile-time rejection with a clear message, the failure is at least loud. (D) is correct if nobody wants a large moving-entity model — a product question, and the one question this document cannot answer.

Ship in v1: deterministic-index and per-cell-hash (one biased-but-exact, one unbiased-and-exact), plus swap, since it is nearly free. Attribute-priority and reject are small follow-ons.

7.3 · Order independence — the parallel-safety proof

Self-write-only resolve: 30 generations × 4 random visit orders → 0 mismatching cells.
Target-writes-source resolve: 4 policies × 25 generations × 5 orders → 0 mismatches.
A parallel dispatch may schedule cells in any order; the result is invariant.

7.4 · Determinism

Same seed, two runs, 50 generations, board hashes compared: MATCH for all four policies under the shared xorshift32, and MATCH for all four under the per-cell hash. Being a pure function of (cellIdx, generation, salt), the hash source is independent of dispatch order — which is what makes it the cross-target-reproducible option.

7.5 · Swap needs no arbitration

64×64 at 100 % occupancy, 100 generations: 51 174 mutual-intent swaps (511.7 per generation), occupancy 4096 → 4096 (exact). The only mechanism that mixes a grid with no vacancies at all.

7.6 · The chain extension — and the version that broke

⚠ The naive chain rule BREAKS conservation, and the prototype caught it. “I may enter T because T is committed to leave” is unsound: T’s commitment can be revoked when T loses the arbitration at its own target. Then I overwrite a payload that never left. Measured BROKEN at 35 / 65 / 76 / 90 % fill.

The fix is to make commitment monotone: a destination, once claimed, leaves play, and a claim is only ever granted to the winner of that destination’s arbitration.

7.7 · Margolus, for comparison

200 generations, 2×2 alternating blocks with a random per-block rotation: n₀ 1463 → 1463, min = max = 1463 (exact), 1463 moves/generation, deterministic across runs. Conflict-free by construction; no policy exists to choose.

7.8 · Does it still behave like the same model?

Diffusion. Both rules produce ordinary random walks (MSD linear in t). The parallel one diffuses more slowly, in proportion to its lower accepted-move rate — a time rescaling, not different physics.

Column separation — a Chromatography-shaped fixture (43×200, gravity bias, two solutes of different stickiness, 400 generations, mean unwrapped downward displacement):

8 Recommendation

Build (A). A new proposeMove node plus an engine-owned resolve pass, with the conflict policy as an explicit per-model setting. Keep async mode exactly as it is — this is an additional way to express movement, not a replacement.

Name it honestly. The setting should say what it is — e.g. moverPolicy: 'index' | 'hash' | 'attribute' | 'reject' on ModelProperties, absent ⇒ the feature is off ⇒ every existing model byte-identical. Nothing here should be called “async on the GPU”; it is a different, deterministic semantic.

8.3 · What would kill this

Stated up front, as falsifiers.
  • If the resolve pass costs more than one extra dispatch’s worth of time. Two O(nbrSize) scans is one ordinary gather; if a real GPU at scale says otherwise, the economics change.
  • If nobody wants a large moving-entity model. The four existing ones gain little. P3’s new sample is the test — if it cannot be made compelling, choose (D).
  • If the semantic difference is unacceptable to the owner. The parallel rule is a correct parallel exclusion process — deterministic and exactly conserving — but a model ported across will not reproduce its old trajectory. That is a product judgement, and it belongs to the owner.
