Rule Trace — watch one cell's (or one agent's) rule execute in the graph

Pick one cell or one agent in Live mode and press Trace. From then on the node graph lights up along the path that element's rule actually took, hovering a wire shows the value it carried, a cursor walks the path node by node, breakpoints pause the run before the generation is applied, and a drawer under the graph lists what the element is about to become. Written plan: docs/PLAN_RULE_TRACE.md · design authority: docs/IMPACT_MAP_RULE_TRACE.md · origin: docs/BRAINSTORM_RULE_TRACE.md. Branch debug-mode, base 8c7f6d4.

The one architectural claim. The trace is a re-evaluation, not an instrumented engine. The same graph goes through the same lowering passes and the same JS emitters with a trace option — single-element body, per-node value records, per-flow-node execution records — and runs in the worker, in a write-recording sandbox, against the live state. JS, WASM and WebGPU keep stepping the real grid, unchanged and unaware. That is why this is not a single-target feature: the trace behaves identically whichever engine the model runs on, in 2D or 3D, for cells or for agents.

Vocabulary. The feature is Rule Trace · the button is Trace · the pause point is a breakpoint · the controls are Resume · Pause · Step generation · Step node · Back one node. The mockups use magenta for the trace accent; the final token is picked in P3.

The red dot on Set Attribute is a breakpoint. Get Cell Attribute is dimmed because the compiler sank it into the branch that did not run: no record, and that is the honest picture (D4).

Why the drawer and not a side tab. Live closes the left ActivityBar by policy, so a tab would put the values one click away from the graph they annotate; a floating popover is too small for a values table. The drawer is the IDE convention and it is mounted only while a target exists (D7) — no target, no drawer.

Two independent toggles. ◎ Follow moves the camera; ◉ Trace moves the graph. They compose (follow and trace the same agent), and neither implies the other. Follow already exists — Trace is built on its template, which is why the two chips read as siblings.

One target per graph. A model with both tiers can trace one cell and one agent at the same time; pressing Trace on another element of the same kind moves that target. Closing the popover does not stop the trace — the chip does.

The target keeps its values flowing. The traced element is silently added to the inspect subscription (cells) / the agent poll (agents), so current values keep arriving after the popover is closed — that is what the Values tab compares the trace's predictions against.

3 · The lit graph the path the element actually took, plus values on hover

Game of Life, generation 412, cell (12, 34). The cell is alive with 4 live neighbours, so Compare is true, the then branch runs and the cell dies. Hovering the count wire shows the value it carried; hovering a node shows all of its port values at the cursor. Get Cell Attribute and the whole else arm are drawn exactly as they normally look — the trace adds light, it never greys the rest of the graph.

Tooltips are portalled, and they own no keyboard. A position:fixed popover rendered from inside React Flow's transformed viewport breaks — the tooltip is portalled to document.body (the repo's standing rule). It carries no role: a hover surface that announced itself as a menu would stand the global Enter down just for mousing past it — the lesson the viewer control already paid for.
Values are decoded, not raw. Binary → true/false · a tag → the option name · a neighbour index → (dr, dc) (or (dr, dc, dl) in 3D) · a vector or colour → (x, y, z) reassembled from the component records the composite lowering emitted · an array → [a, b, c, …] (n), copied at record time because the underlying scratch buffer is reused.

4 · The cursor a generation runs in microseconds — the cursor is what makes it followable

a · cursor on If. Lit = everything with a record up to the cursor: the flow so far plus the current node's value cone (Compare, Count Neighbours). The Set nodes have not run yet, so they are dark.

b · one step later (]). The cursor moved to the next flow event, the taken branch wire lit, and Set Attribute became current. The untaken arm never changes.

c · whole trace (⟲). The cursor is cleared and everything the element executed is lit at once. This is what a freshly-landed trace shows — stepping is opt-in.

⏵Resume ⏸Pause ⏭Step generation Space ⤒Back one node [ ⤓Step node ] ⟲Whole trace

The transport row, as it sits at the top of the Trace panel. Resume / Pause are the simulator's own playing state (Enter) and Step generation is the transport's Step (Space) — the trace does not invent a second clock. Step node / Back move the cursor only, and are greyed at the ends of the recorded log with the reason in the tooltip (here: the cursor sits on the first flow event). Whole trace greys out when the cursor is already cleared.

6 · The breakpoint pause pauses BEFORE the generation is applied · fires once per generation

aTracing cell (12, 34)
Playing. A breakpoint sits on Set Attribute. The worker now traces every generation, because it has to decide whether to pause. Gen 411 · 60 fps.
b⏸ paused at Set Attribute
Hit. The traced cell reached the node, so generation 412 is not run: the board on screen is still exactly what the rule read. The cursor lands on Set Attribute, the Values tab shows alive true → false as a prediction.
cTracing cell (12, 34)
Resume ⏵. Generation 412 runs for the whole grid and the cell dies — the prediction becomes the board. The same breakpoint does not re-fire inside this generation.
d⏸ paused at Set Attribute
Generation 413. The cell is traced again and hits the same node again — so the run steps one generation per Resume, which is the loop a user wants when they are reading a rule.

Only the traced cell's change is drawn between frames (c) and (b) — the rest of the board advances too. A breakpoint fires once per generation: the worker remembers the generation it broke on, so the next step message runs that generation through without re-breaking.

Breaking a batch is cancelStep's job description. A break stops the batch mid-flight, so it must drop the queued step messages that have no reqId exactly the way cancelStep does — otherwise they replay the moment the user resumes and the run jumps several generations. Overseer steps are never dropped, and the Overseer never traces (Live excludes it).
Why the pause is before. The trace is of the current state — "the board you see → what it does next" (D2). If the generation had already been applied, the board on screen would no longer be the one the rule read, and every value in the panel would describe a state the user cannot see.

7 · How it works a side computation beside an engine that never notices

The same graph goes down two paths. On the left it is compiled normally and hands JS, WASM or WebGPU the code that steps the real grid — that emit does not change by one byte (proved, not asserted: check-compile-identity --compare). On the trace path it is compiled a second time with the records, run for one element inside the sandbox, and the result is a message. The sandbox reads the engine's live buffers; nothing it writes can get back out.

The cadence — how often a trace runs

Sampled — once per frame

The default while playing. One trace per root at the end of the batch, on the state the next generation will read — i.e. the board on screen → what it does next. On WebGPU that is one readback per frame, which the inspector already pays for.

Every generation — only with breakpoints

The worker must decide whether to pause, so it traces before each generation in all three batch loops. On WebGPU this costs a grid readback per generation — a debugging cost, paid only by a breakpoint session, never by default.

On demand

When the target is set, after a paint, a paste, a Reset, a recompile or a state load, and whenever the simulation is paused. The trace of the board on screen, on request.

GPU-resident agents stand down under breakpoints. A resident agent batch reads the CPU store back only once per frame, so it cannot host a per-generation hook. agentResidentEligible() gains one runtime term: an agent target with breakpoints runs the per-generation path (slower, correct). Sampled tracing keeps residency untouched.

9 · 2D and 3D, cells and agents the trace is dimension-blind; only the mark has two bodies

2D cell. An outline in the trace accent, drawn in the overlay pass next to the inspector's own cell outline.

3D cell. The same target, published through the 3D renderer's inspect-cells channel with a distinct style — a voxel cage rather than a flat outline.

2D agent. A ring in the trace accent — deliberately the same shape as Follow's ring, in a different hue, because they mean different things.

3D agent. The ring becomes an orbit ring with a drop line to the floor, so the depth is readable — the 3D inspector's existing idiom.

The trace itself does not know which one it is. An element is a flat index: idx for a cell (the _layer decode happens inside the body exactly as it does in the engine), an id for an agent. What has two bodies is the mark — the 2D overlay draw and the 3D renderer's inspect channel — and both entry points already open the same popover, so the Trace button is written once. Verified on Game of Life and Wireworld (2D), Life3D and Accretor (3D), Particle Life in both.

10 · What the trace cannot promise stated in the UI, not buried in a doc

Random draws are the trace's own

The trace runs a private RNG seeded from (element, generation) — stable when you re-trace the same generation, but not the draw the engine made. On JS and WASM the shared stream's state at this element depends on every earlier element's draws in the same generation; on WebGPU the per-cell PCG state lives on the GPU.

Asynchronous updates are approximate

The trace evaluates against the start-of-generation state; a real async pass may have updated neighbours earlier in this generation's order. The Values header says so on every async model — "approximate under asynchronous updates".

WebGPU is f32; the trace is f64

A documented, intentional difference of the WebGPU target. Values can differ in the last bits — the shape of the rule and the branch taken do not.

Everywhere else, the trace's "next values" are exactly what the engine writes. The trace is the JS reference compile, and the reference is bit-identical to WASM by contract — so on a synchronous, non-random model the prediction is the value the engine produces. The panel makes that checkable on screen: the previous trace's prediction sits beside the now-current value from the inspect subscription.
And two things it is deliberately not. Not conditional breakpoints, data breakpoints, or breakpoints on value nodes; not editing a value mid-trace and re-running from the cursor; not several elements at once; not a trace history saved to a file; and not the Overseer graph, which is not a per-element rule. Recorded so nobody re-derives them (brainstorm §5).
