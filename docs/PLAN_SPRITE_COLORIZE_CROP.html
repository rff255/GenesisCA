The CPU tint is per-pixel, not a blend mode. The usual 'multiply' + 'destination-in' recipe leaves an anti-aliased edge pixel at (1−a)·Cs + a·Cb·Cs — lightened toward the tint instead of multiplied. The result is cached, so an exact getImageData pass (the same shape applyChromaKey already uses) is affordable and matches both GPU paths exactly.

The cache

agent colour→ quantise 5 bits/ch→ key id|frame|q→ hit? draw it→ miss? bake once, evict oldest

Bounded on entries (512) and total pixels (16 M ≈ 64 MB RGBA). Cleared on every re-decode (SpriteRegistry.onReady) and sprite-set edit, because the cached canvases are derived from ImageBitmaps the registry closes. Dequantised (q<<3)|(q>>2) — exact at 0 and 255, so white art under a pure-red agent is exactly #ff0000.

2 · Crop — for plain images, GIFs and frame sequences

The gap

With a crop

Where the crop happens

sequence · sheet · image→ frames[]→ CROP (per frame, clamped)→ chroma key→ ImageBitmap[]

Decode time, exactly like the chroma key — so ONE change flows to the CPU overlay, the gl3d atlas and the worker atlas through the registry's existing onReady. spriteDecodeKey gains crop, so an edit re-decodes; colorize deliberately does not (it is render-time).
