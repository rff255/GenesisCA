The finding that drives everything: CPM is not a cellular automaton in GenesisCA's sense and cannot be expressed by the engine's defining trick — "compile the node graph to a per-cell step, call it once per generation." CPM is stochastic Metropolis energy-minimization on extended cells: one biological cell spans many lattice sites, and the update proposes copying a neighbour's cell-ID into a boundary site and accepts it with probability min(1, e−ΔH/T). The recommendation is a hybrid: a new worker-side Metropolis driver owns the loop, the per-cell-ID bookkeeping and the accept/reject, while the node graph is repurposed to compute only the scalar ΔH. ~60–70% of GenesisCA's stack still carries over — async single-buffer dynamics, the SoA grid, the colors blit, and the lookupTable type that is the adhesion J-matrix.
Substrate verdict (the user's real question): the goal is cell division + morphogenesis + rich per-cell rules + dynamic adjacency, ultimately in 3D — CPM is a candidate, not the goal. Recommendation: start with CPM (lowest friction for this lattice/SoA/compile stack; free deformable shape and free implicit adjacency; easy division; incremental 3D engine; Artistoo proves browser CPM works) — but keep the per-cell IR engine-agnostic so an off-lattice center-based model (PhysiCell-style) can be the natural second engine for division-heavy 3D populations. CPM is the wrong tool for confluent epithelial sheet-mechanics (that is vertex territory), and its Monte-Carlo dynamics are non-physical (broken detailed balance — Voss-Böhme 2012). CPM-first, not CPM-only.

01 One biological cell = many lattice sites

In GenesisCA today a "cell" is a lattice site: one state per site, updated synchronously. In CPM a lattice site holds a spin σ(x) = the integer ID of the biological cell occupying it, and a biological cell is a connected domain of many same-σ sites. A second map τ(σ) gives each cell a type; σ=0 is medium. Cells are spatially extended and deformable — that is what makes shape, division and morphogenesis expressible.

02 The model is an energy, not a rule

CPM has no transition function. It defines a Hamiltonian H and evolves by minimising it stochastically. The engine never computes global H — it computes a local ΔH for a single proposed copy, summed over independent terms. That ΔH is exactly what a node graph can compute.

03 The dynamics — a Metropolis copy attempt

One elementary move: pick a random target boundary site, pick a random source from its neighbours, propose copying the source's cell-ID into the target, score ΔH, and accept with the Boltzmann gate. N attempts = one Monte-Carlo Step (MCS) = one "generation". It is intrinsically sequential (each accept mutates state the next attempt reads) and stochastic.

Connectivity is a correctness requirement, not polish

A naive copy can split a cell into disconnected islands (biologically meaningless). A local connectivity test on the flipping site's own neighbourhood (Durand & Guesnet 2016) forbids fragmentation at all temperatures, runs faster than the standard algorithm, and is cheap enough to belong in the very first milestone — without it the cell-sorting demo can shatter into specks.

04 Live demo — Metropolis cell sorting

A real (small) CPM running in your browser: ~36 cells of two types in a compact aggregate, an adhesion J-matrix + a volume constraint, the Metropolis accept/reject. With like-cells sticking and unlike-cells repelling, the mixed aggregate spontaneously sorts — the founding Graner–Glazier 1992 result, with no "seek your own kind" rule. Drag T to feel the fluctuation amplitude; toggle colour to see cells by type vs by individual ID.

05 Two-level state — the structure GenesisCA lacks

CPM needs two state tiers: a per-site spin field (which GenesisCA already has — it's an integer cell attribute) and a per-biological-cell object table (type, current/target volume, perimeter, centroid) indexed by cell ID. The second tier does not exist today — every attribute is per-site or a single global scalar. This is the central new data structure.

06 Engine fit — why it must be a hybrid

GenesisCA's whole speed story is "compile the graph to a per-cell step, call it once per generation." A per-site compiled function cannot express a CPM move: it can't read per-cell-ID volume, can't transactionally commit a write + two accumulator updates, and the loop shape is wrong (propose/accept, not sweep-once). The answer mirrors the Graph-CA investigation's "CSR vs dead topology" finding: keep the graph as the authoring surface, add a new engine path to drive it.

07 Is CPM the right substrate? (the user's real question)

The goal is division + morphogenesis + rich per-cell rules + dynamic adjacency, ultimately in 3D — not "CPM" per se. The literature gives a near-perfect head-to-head (Osborne et al. 2017 implement five families in one framework). There is no single winner; the families are complementary. For GenesisCA's specific architecture, CPM is the best first substrate — with a known ceiling.

Why CPM first. It reuses ~60–70% of GenesisCA's lattice/SoA/compile/async stack; it gives free deformable shape AND free dynamic adjacency (two explicit requirements) at the cost of physical rigour; division is easy and 3D is an incremental engine change; and Artistoo is the only proven zero-install browser engine in any family — a behavioural oracle to validate against.

…but know the ceiling

CPM's Monte-Carlo dynamics are non-physical (broken detailed balance → cell extinction without a guard, Voss-Böhme 2012; one T couples many effects). It is the wrong tool for confluent epithelial sheet-mechanics (folding, T1 intercalation — vertex territory). For huge dispersed 3D populations with rich phenotype logic + trivial division, center-based (PhysiCell-style) is the better complementary engine.

Design consequence: keep the node graph + per-cell IR engine-agnostic so the same "per-cell update + per-cell attributes" nodes can later compile to a force-integration step (center-based), not only a lattice copy-attempt. CPM-first does not foreclose the off-lattice second engine — it gets something morphogenetic on screen fastest.

08 Rendering — mostly reused (CPM is still a 2-D lattice)

Unlike Graph CA, CPM keeps the 2-D lattice, so the renderer is ~70–80% reused: the worker fills one RGBA per site into the colors buffer and SimulatorView blits it as ImageData. Colouring a site by its cell-ID or type is just an ordinary Output Mapping. The new work is localised and additive.

Reused as-is

  • colors buffer + ImageData/drawImage blit, zoom/pan, infinity tiling
  • Output-Mapping / viewer-tab pipeline (colour by cell-ID or type)
  • Brush seeding, per-site inspector (cell-ID/type/volume rows appear for free)
  • Recording (captures whatever draw() produces)

New render work

  • Membrane drawing — stroke an edge where a neighbour's cell-ID differs (gridlines are not membranes)
  • Colour-by-cell-ID at scale — a runtime hash-id→RGB mode (the fixed-count categoricalColor can't map hundreds of IDs)
  • Chemical-field heatmap overlay — a composited second blit (follows the glyph-fallback pattern)
  • Centroid / track markers — new; needs the per-cell centroid reduction
  • 3-D renderer — the only wholesale rewrite (Canvas2D is hard-wired), but well-isolated behind draw()/colors

"3D is incremental" — for the engine, not the renderer

The 3-D engine is the same Hamiltonian + Monte-Carlo kernel (only a bigger stencil + parameter rescale). The 3-D renderer is a wholesale new (WebGL/WebGPU) volumetric path. Never quote one half of that without the other.

10 Silent-corruption hazards to pin first

From the adversarial review — these fail quietly (wrong ΔH / corrupt round-trip), not loudly, so they must be contracts decided up front.

paint → accumulator desync (highest priority)

Every mid-run spin mutation — paint, paintManual, importImage, writeRegion, clearRegion, cell paste — must incrementally patch (or re-scan) the per-cell-ID volume/perimeter/centroid, or every later ΔH runs against stale volumes and cells decay/explode. Brush is modify, not reuse.

maxCells lifecycle & overflow

Accumulator arrays are sized once. Default maxCells = clamp(seedIDs×4, 256, cap); a division that would overflow is rejected + surfaced, never silent. Growing it mid-run is a structural reinit — add it to the attrsStructurallyEqual guard (the Amphiphile NI-poisoning class).

accumulator memory location (WASM fork)

JS arrays in Phase 2; from the WASM phase they must be a baked wasmMemory region (so the compiled GetCellVolume reads them at a fixed offset) accessed via views with the copy-into-never-reassign discipline. A JS-only array would strand the WASM target.

ATTR_TYPE_MAP & .gcastate

A missing ATTR_TYPE_MAP entry for an object-tier array silently mislabels it float64 and corrupts the round-trip. And applySimulationState must validate cellCount/maxCells, rejecting mismatches cleanly (no try/catch around deserialize → a throw aborts the whole load).

One source of truth for the mode: drive everything off cpm.enabled; leave the dead topology enum derived/display-only (verified: zero branch sites). Add worker-side mutual-exclusion safety nets (CPM ⟂ WebGPU; CPM forces async) for hand-edited files, mirroring the existing useWasm/useWebGPU net.
