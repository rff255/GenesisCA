Agent engine · architecture proposal

Agent Capability Profiles

Stop baking one paradigm into every agent. Compose the agent from opt-in capabilities so a model carries only what it uses — and GenesisCA's agents become as generic as its grid: particle physics, morphogenesis, vivarium ecologies, and social-network graphs, all from one substrate.

Problem: a center-based soft-body cell is hard-coded into "the agent" Fix: generalize four gating patterns already in the codebase Predecessor: the AutomatosGT plan (FOV + spawn re-slot as capabilities)
⚠️ Pressure-tested — the handoff is authoritative. A 15-agent adversarial audit returned GO-WITH-FIXES and corrected two overclaims inline below: (1) sprites are not conditionally ABI-mirrored (they're always threaded — the real template is hasLookupTables / is3d / agentAccess); (2) the true core is id+alive+position+velocity+force+radius (read every step), so Motion & Body are palette-gated only in v1, and layout is recomputed per profile, not append-only. Build order + shared-infra prerequisite + corrected migration: HANDOFF_AGENT_CAPABILITY_PROFILES.html.
The critique, in one line

The grid is generic; the agent is not. Every agent — in every model — hard-codes velocity · force · radius · age · division axes · bond store · density · lineage whether or not the model uses them, and those intrinsic fields leak into node ports (Behaviour Step always emits myRadius · myArea · myBondDegree · myAge) and the palette (Divide Agent, the whole bond family). A social-network or particle model is handed morphogenesis machinery it will never use. This proposal makes every intrinsic attribute and every engine physics an opt-in capability, driven by a profile the model declares — so universality comes from composition, not from piling every feature onto one fixed agent.

1What's baked in today

Verified in agentEngine.ts: every agent unconditionally carries ~22 Float64 + 5 Int32 + 3 Uint8 intrinsic fields plus the bond store — ~203 bytes before a single user attribute. Even the 3D fields (z, zNext, vz, forceZ, divideAxisZ) sit in the CPU store for 2D models.

The codebase already agrees with the critique. This is its own half-finished trajectory: the built-in agent type was already removed; maxBonds=0 already zeroes the bond store; useBondingPhysics already gates soft-sphere+springs+growth+auto-bond; hasLookupTables / the is3d trailing block / agentAccess already conditionally append params to all three ABI mirrors; hiddenPorts already hides myZ in 2D. The fix generalizes these gates into one profile — no new mechanism. (Pressure-test correction: sprites are not an example — they're unconditionally ABI-threaded; and velocity/force/radius are always-read core, not gate-able in v1. See the handoff.)

2The principle

A model's Agent Capability Profile is the single source of truth. From it derive: which SoA fields allocate, which engine steps run, which palette nodes appear, which ports show, and which Properties panels render. The irreducible core is just: a slot id, an alive flag, a position, and the user's attributes. Everything else is a capability. Presets snap the paradigms; module toggles are progressive disclosure.

7Migration — legacy stays byte-identical

  • Absent profile ⇒ a config-aware inference (corrected: flat "always Full" mis-allocates a bond store for the maxBonds:0 default new models ship): absent + maxBonds:0 ⇒ Particle; absent + maxBonds>0/useBondingPhysics ⇒ Full. Every existing .gcaproj + shipped sample loads unchanged.
  • New models start from a chosen preset (a lean default, not the heavyweight Full).
  • Optional smarter migration: infer a tighter profile by scanning which intrinsic nodes/ports a legacy graph actually wires — only when provably behaviour-preserving; else fall back to Full.
  • The existing customForcesOnly / useBondingPhysics / topologyMode / agentTarget fields fold into (or derive from) the profile with no semantic loss.

8Roadmap

1

Profile schema + presets + port/palette gating effort M · clarity win, low risk

Add the schema + "legacy ⇒ Full" migration; wire capability tags on existing nodes + hiddenPorts on the event roots; build the Properties panel + preset picker + footprint. No engine/SoA change — this alone delivers the "generic & universal" feel: each paradigm shows only its relevant nodes/ports.

2

Conditional SoA + engine-step composition effort L · memory/compute

Extend computeAgentMemoryLayout + the three ABI mirrors per the profile; compose runAgentStep + the structural phase from enabled behaviours. Parity-harness after each capability.

3

New capabilities: Directional FOV (Sensing) + Runtime Spawn (Population) + the AutomatosGT gallery effort M

The predecessor plan's build items, landing as capability members.

4

First-class Social-Graph & Particle-System support effort M

The two paradigms the current engine serves worst: Bonds=Data edge rendering + a force-directed layout Motion mode (social networks); a tuned Motion=Force particle preset (N-body / SPH-lite). Mostly a preset + a small render/layout add once Phases 1–2 exist. Ship sample models alongside the vivarium gallery.

Reframes the agent platform from "one fixed cell that does everything" to "compose the agent you need." Resolves the generality critique at its root — intrinsic attributes and engine physics become opt-in — makes the AutomatosGT features clean capability members, and unlocks paradigms the current engine can't express (social-network graphs, pure particle systems, abstract agent-CA), with morphogenesis as simply the "everything on" preset.
