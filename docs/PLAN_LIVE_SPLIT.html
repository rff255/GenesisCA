Live mode — the rule graph and the running simulation, side by side

GenesisCA already has both halves: a node editor, and a simulator that soft-recompiles on every graph edit while keeping the grid. What it does not have is seeing the run while the graph is on screen. This plan builds that as Option B — a split workspace: two opaque, fully interactive panes and a draggable splitter. No transparency, no modifier games, no pointer arbitration. The overlay (Option A) and the in-page floating window (Option C) are dropped. Design authority: docs/IMPACT_MAP_LIVE_SPLIT.md; written plan: docs/PLAN_LIVE_SPLIT.md.

The boards in every mockup below are a real Game of Life running in this page, so the layouts can be judged with something moving in them.

Zero compiler impact. Live is layout, mounting and input ownership. Nothing under src/modeler/vpl/compiler/** or src/modeler/vpl/nodes/** changes, no schema field, no worker message. The claim is proved, not asserted: check-compile-identity --compare must report 31 models, all surfaces unchanged at the end of every phase.

What is on screen that is new

  • A third mode button — ◐ Live. Greyed with a reason while an Overseer experiment runs.
  • A viewport bar along the top of the simulation pane: model name · viewer picker · apply-policy switch · brush and indicators popovers · the layout menu.
  • A transport chip on the simulator's own transport bar — the four states in §4.
  • A splitter, draggable, double-click to 50 %, position persisted.
  • A focus ring — a 1 px accent inset on whichever pane owns the keyboard.

What is deliberately unchanged

  • The graph pane is the Modeler: same ear tabs, same panels, same graph pills, same macro breadcrumb.
  • The viewport is the Simulator: same canvas stack, same transport bar, same brush, same capture cluster.
  • The Modeler and Simulator tabs behave exactly as today — except two keyboard bugs that Phase 4 fixes (§5).
  • The simulator's own side panels are only collapsed by default in Live; their ears are still there.

2 · The layout menu four actions, all pure CSS

Dock right, dock bottom, swap sides and collapse are flex-direction and a flex fraction on one container. No element moves in the React tree — which is exactly why they are cheap, and exactly why they are safe (see §3).

▥ Dock right / ▤ Dock bottom

flex-direction: row ⇄ column on <main>.

⇄ Swap sides

row-reverse. The splitter stays between them by construction.

⤡ Collapse viewport

The splitter is hidden (nothing to divide — the structurally-impossible rule) and a restore ear takes its place. The sim keeps running.

Persistence — and a correction. The brainstorm said the splitter would persist “like the panel widths do today”. It cannot: panel widths do not persist — both PanelShell and the simulator's own handle mutate inline style.width and the element is unmounted on close (“re-opening starts from the CSS default”, in the code's own comment). So Live gets its own store: a module global with localStorage write-through under genesisca_live_layout — the genesisca_graph_view_settings pattern — holding dock · swapped · split (a 0–1 FRACTION, not pixels) · viewportCollapsed · applyPolicy · simPanelsCollapsed. A fraction survives a window resize and a dock flip; pixels would not.

3 · The one thing that must not go wrong mountinghighest risk

SimulatorView owns the Web Worker, the WASM memory, the WebGPU device, the agent SoA snapshot and the grid state. React reconciles by position in the element tree — so if Live renders it inside a pane wrapper that does not exist in Simulator mode, React unmounts and remounts it, and generation 12 000 becomes generation 0.

✗ The obvious shape — destroys the run

✓ The rule: identical tree, different CSS

The Modeler wrapper is new and must therefore be added in every mode (display:contents outside Live, so today's Modeler is byte-identical) — introducing it only in Live would remount React Flow on every Modeler↔Live switch. And visible splits into two questions: “shown” (a real, non-zero box — true in Simulator and Live; it gates the draw loop, the re-present messages and the 0×0 drawImage crash guard) and “active tab” (owns the keyboard by default — true only in Simulator; it is the only thing the auto-pause may key off).

The proof is a measurement, not a look. Play Game of Life to generation ≥ 500 in the Simulator, switch to Live, and assert the counter keeps climbing and the worker object identity is unchanged. A remount shows as Gen 0.

Why “keep the last good rule” is a gate and not a recovery. The worker's recompile handler does stepFn = stepCode ? eval(stepCode) : null, and the main thread's guarded compile returns an empty step on a throw. So a half-wired graph today does not merely show an error — it replaces the running rule with nothing. The fix is therefore to withhold the recompile message when the compile failed: a message the worker never receives cannot change what it is running. That keeps sim.worker.ts completely untouched.

The four chip states

synced

The last edit compiled and is running. Auto policy, clean graph. Nothing to do.

stale

The graph does not compile. The previous rule is still running; amber ! badges mark the offending nodes. No red banner — that stays the Simulator tab's surface. Tooltip: “3 nodes need attention”.

pending · Ctrl+Enter

On-demand policy: edits are in the model but not yet in the engine. For slow compiles (big WGSL shaders, large agent graphs) and for multi-node edits that must land atomically.

rebuild needed Apply Later

A structural edit (new attribute, grid dims, a capability profile) needs a full reinit, which re-seeds the board. The prompt names what comes back — the saved board, or a fresh seed from the Init Events. N structural edits cost one reset.

Two traps hide in this one feature. (1) setCompileError is not a compile-error channel — it is the simulator's general error surface, and only 6 of its 18 call sites are graph compiles; the rest are failed CSV / GeoTIFF / GeoJSON / preset imports and worker-pushed errors. A blanket “no red banner in Live” would silently swallow a failed GIS import. (2) The rebuild prompt must not advance the model effect's prevModelRef, which is assigned unconditionally at the top of the effect — otherwise the next edit compares against the already-changed baseline, needsFullInit comes back false, and the deferred rebuild is lost while the worker keeps running the old memory layout. A separate appliedModelRef (the last model actually pushed) is the fix, and “N edits, one reset” falls out of it for free.

Apply policy

Auto (~100 ms)

Today's behaviour: the existing 100 ms sync debounce feeds the model, the model effect applies. Blender's feel. The default.

On demand

The model→worker step is held, not the graph sync — so undo, save, and the Modeler's own panels stay live while the engine waits. Ctrl+Enter applies.

A correction to the brainstorm. It proposed stretching the debounce to ~400 ms “while the pointer is down”, framed as fixing a compile storm during node drags. A node position drag never syncs mid-drag — the sync predicate fires on remove, drag-end, dimensions and replace only. What actually storms is a held inline widget inside a node and a comment/group resize. The stretch is still worth having; it just targets a different gesture than the brainstorm assumed.

5 · Who owns the keyboard and two bugs that already exist

Fifteen global keyboard listeners are live at once, because SimulatorView is always mounted — even in the Modeler. Two of them misbehave today, with or without Live:
  • Esc in the Modeler resets the running simulation. The simulator's main key handler has a field check and a capture-modal check, but no visibility gate, and nothing upstream stops Esc. (Backspace shares the same arm.)
  • Ctrl+C/V/X is bound twice — the graph clipboard and the cell/agent clipboard, both bubble-phase on document, neither stopping propagation. In Live a Ctrl+V meant for the node graph would also paste a cell region into the grid.
Phase 4 fixes both. They are corrections, not new-feature scaffolding, and they are testable without Live.

A field check is not enough for “a menu has focus”: the stand-down set has to include the quick-add and connection-drop menus (which own Enter themselves) and every modal.

6 · Guards, and the things that must not be touched

Overseer ⇄ Live

Every model change aborts a running experiment — and in Live every graph edit is a model change. So:
· Live → Overseer: the Experiments tab is hidden (structurally impossible from that panel) and the tab selection is coerced back to Controls.
· Overseer → Live: the Live nav button is greyed with the reason — Abort is visible in the panel, so the working state is reachable.

Performance

· FPS cap 30 as the Live default — the popover stays live and the previous value is restored on exit. A default, never a clamp.
· Skip the blit, not the step, while a node is being dragged: guard the per-stepped draw, keep the worker's cadence, the recording capture and the generation counter.
· The Live viewport is smaller than the Simulator tab's, so per-frame blit cost goes down, not up.

The splitter's hidden cost

A transferred OffscreenCanvas has fixed dimensions, so tracking a drag exactly means one worker pipeline rebuild per frame — measured at 26 attach messages over a 30-move drag before the existing 140 ms settle window fixed it to 2. The Live splitter sits outside SimulatorView, so it must call that machinery through a registered seam. Relying on the ResizeObserver catch-all alone reintroduces both the stretched-stale-bitmap bug and the attach storm.

2D and 3D are one pane, three differences

  • 2D: the composited display canvas plus two cursor-overlay canvases (one mix-blend-mode: difference). A splitter drag blits scaled so the picture stays right-sized.
  • 3D: a worker-presented sphere or voxel canvas underneath, the WebGL2 canvas on top with a transparent clear. Both lower layers are width/height: 100%, so CSS stretches them during a drag.
  • Entering Live re-sends the camera before asking for a re-present — a refresh without it would present the old view.
  • A narrow, short pane puts the 3D gizmo, the axis labels and the 3D View panel in competition for space. Verify on Life3D and Accretor, not by reasoning.

Capture and recording stay

  • They are not structurally impossible in Live, so hiding them would violate the doctrine. The “simulation” capture scope renders the whole world at a fit framing on the main thread — independent of zoom, pan and pane size.
  • The real interlock: the “current view” scope locks the output frame size on the first captured frame. So while recording, the layout controls (splitter, dock, swap, collapse) are greyed with the reason — the mirror of the existing “capture settings are locked while recording” rule.
  • The FPS-cap default is not applied while recording (the recording's frame rate derives from it).

Output-Mapping bar relocation as built · 2026-09-07

The centred top viewer bar is retired in every mode. Its whole job — cell views, agent views, per-mapping tooltips — is now one compact control on the transport bar, between G/F and play/pause. Hovering (or clicking) it opens a vertical popup; the --live-viewer-row-shift machinery the previous round added to keep the row clear of the Live bar is gone with it.

Before · after

Before. A whole strip of canvas for a rarely-pressed control — and in Live it shared that strip with the Live viewport bar, which is why it had to be able to drop to a second row.

After. The canvas keeps its whole top strip. The current view’s name sits between G/F and play, truncated with an ellipsis (the full name is in the tooltip); hover or click opens the list, grouped Cells (A→C) / Agents (A→C) when the model has both, with a ✓ on the current entry.

Two rules the mockup encodes. The popup carries no role="menu": it opens on hover, and overlayOwnsKeyboard() stands the global Enter (play/pause) down while a [role=menu] is in the DOM — the same trap that made the Live bar’s apply-policy popover click-only. And the name is clamped to 108 px: the bar is centred, so an unclamped label would nudge every neighbouring control, the same reason the play button’s width is pinned.

When there is nothing to switch to

A model with one view per layer gets a plain muted readout — no button, no hover, no pointer cursor. Which mapping am I looking at stays answered; nothing that cannot be pressed looks pressable. The predicate is per LAYER (cellOMs > 1 || agentOMs > 1), because one cell view plus one agent view is two entries and still no reachable different state.

What the Live top strip looks like now

Two occupants, not three. The instructions pill is left-anchored and the Live bar is right-anchored behind --live-right-inset; they cannot collide, so the strip needs no arbitration. --live-viewer-row-shift and the .liveOverlayPanels .viewerBarRow override are deleted. The two insets stay — the panel ears and the Live bar both read them.
