Explicit Controls for Macros

Plan · branch explicit_controls · companion to IMPACT_MAP_EXPLICIT_CONTROLS.md and PLAN_EXPLICIT_CONTROLS.md

1  What it is

A macro already externalises connections. Everything else it carries — the inline number/bool/tag boxes, the Expression formula, the op dropdowns, the attribute pickers — is reachable only by opening the macro and understanding its internals.

Explicit Controls let the author promote any of those in-node parameters to a named control on the closed instance, and organise ports and controls into groups — so a ready-made macro is tunable without opening it.

The structural bet: a control is a REMOTE CONTROL, not a copy. It stores a pointer to an existing config key, never a second value — so the whole feature is metadata beside nodes/edges and no compiler learns it exists.

3  The core decisions

DecisionIn one or two sentences
Def-level storage
D1		 The value lives in def.nodes[k].data.config[key] and the control points at it — one storage location, which is the only self-consistent reading of “change either, the other shows it”. Consequence, shown on the instance by the ⛓ badge: two linked copies share the value; per-instance variation is Duplicate Independent, exactly as documented for macro internals today.
The widget kind is derived live
D2		 Nothing about the widget is stored — the resolver reads (nodeType, config, key) at render time. A stored kind would show the wrong editor after a live retype (Set Attribute's value box flips bool↔tag↔number with the picked attribute) and write a wrong-typed value with no error anywhere.
Three eligible classes
D3		 A every inline port widget (~148) · B the ~60 scalar config keys (enums, checkboxes, body numbers, the Expression formula) · C the ~11 model-element pickers. Out: count steppers (they change which PORTS the node has — a consumer must not be able to break the wiring), multi-key editors (gradient stops, palettes, RGB triples), and the two key shapes the machinery renames or permutes.
Chaining, cycle-guarded
D4		 A control may point at a nested macro instance's own control; resolution recurses to the ultimate config key with a seen set and a depth cap of 20, mirroring the three guards already in the codebase. A cycle or a removed inner control resolves to a reason, never to a guess.
Groups are display metadata
D5		 An ordered list on the def; ports and controls carry a groupId. Grouping a port reorders exposedInputs so the handle order matches — and no edge is touched, because the macro bridge matches by portId, never by index. Absent groups ⇒ flat, byte-for-byte today's rendering.
Zero compiler impact
D7		 A control is metadata beside nodes/edges. expandMacros copies internal nodes verbatim and accessor-CSE hashes node configs — a control record is not in a node config at all. Proven, not assumed: a harness tier compiles the same def with and without the records and asserts byte-identical JS / WASM / WGSL.
The one thing most likely to go wrong. cloneMacroWithFreshIds returns a hand-written 6-field literal with no spread — so a new field is silently dropped on every import, paste and Make-Independent-Copy. Forget it and the feature works perfectly in the session that authored the macro and is empty everywhere else, with no error, no badge and no console line. Remap the target's node id wrongly and it is worse: the control resolves to a different node and edits the wrong parameter. Its test and its source-mutation negative control are written before the fix.

4  The sync model — one storage location

An instance-side edit is ONE dispatch (updateMacro(defId, {nodes}), built from live context state). Propagation is free: a model.macroDefs change already re-renders every macro node, so linked instances and any open editor update on the next paint. An in-macro edit reaches the instance through the existing 100 ms write-back, and the shallow UPDATE_MACRO merge preserves the controls key across it.

5  Phases

P1
Schema, resolver, the clone fix, the harness
The four additive types; explicitControls.ts (eligibility, live-derived widget kind, cycle-guarded resolution, the one-dispatch write builder); the cloneMacroWithFreshIds fix; the adaptive-widget extraction so CaNode calls the resolver back. No UI. Harness tiers A–F, six source mutations.
P2
Authoring — the interface editor, pick mode, groups
Explicit-Parameter and Group rows on the boundary node; the pick-mode global (the activeGraphKind pub/sub shape) with in-place class-A outlines and resolver-driven class-B overlays; Esc + auto-cancel; group assignment reordering ports with no edge touched.
P3
Consumption — the closed instance renders its interface
Labelled rows and group headers in the node body, the ⛓ linked badge, every disabled-with-reason state, the orphan roll-up on the amber badge, and the one-dispatch write. Cascade tier + the handle-offset proof (0 px movement).
P4
Class C, chaining UX, M1/M2 interplay, docs
The 32-site model-element picker extraction (one source, so the instance can never offer a list the node cannot use); binding a nested macro's control; verifying macro reference export/import and the cross-tab clipboard need no new pass; the CLAUDE.md + Help sweep; the full gate set.
