## 1. Executive summary

**The ask.** Add a **Center-Based / Off-Lattice mode** to GenesisCA — a new optional model mode (toggled in Properties, like Variegated Cells or Asynchronous update) that **abandons the lattice entirely**. Cells stop being grid sites and become **agents at continuous floating-point positions** `xᵢ ∈ ℝ²` (later ℝ³), each carrying a **radius** so it behaves as a soft sphere. The population is **dynamic** — it grows by **division** and shrinks by **death**. "Neighbours" are computed each step from **distance** (a spatial-hash / cell-list with cutoff `r_max`), not from a fixed offset table. The update is **force-based ODE integration**: each cell sums pairwise mechanical forces from its current neighbours (volume-exclusion repulsion + short-range adhesion) and takes an overdamped step `xᵢ ← xᵢ + (Δt/η)·Σⱼ Fᵢⱼ`. On top of that substrate: cell-cycle growth, division, death, differentiation, and (eventually) a chemical microenvironment and 3D — the morphogenesis end goal.

**The single most important finding (engine paradigm — and it is the *opposite* of CPM's).** GenesisCA's defining architectural commitment is *compile the node graph to a per-cell step function, then call it once per generation over the whole grid* (`fn(...buildLoopArgs())`, [sim.worker.ts:1192](../src/simulator/engine/sim.worker.ts)). For CPM this commitment **broke** — a per-site graph cannot express a stochastic accept/reject Metropolis chain (CPM §1). **For center-based it largely *holds*.** Each agent independently *sums its own neighbour forces and integrates its own position* — that is a genuine, embarrassingly-parallel per-cell step, exactly the shape the compiler already emits and the shape WebGPU wants. **The surprising counter-intuition the handoff asked us to test is confirmed: center-based fits GenesisCA's compile-to-per-cell-step model *better* than CPM did.** But — and this is the load-bearing nuance — "fits the *paradigm*" is not "fits the *current emit*." The audit found that the existing compiled loop body **bakes lattice geometry** (it decodes `(row,col)` from `idx` and writes one RGBA quad at `idx*4`, [compile.ts:1748-1752](../src/modeler/vpl/compiler/compile.ts)), and `buildLoopArgs` ([sim.worker.ts:937](../src/simulator/engine/sim.worker.ts)) supplies a **precomputed fixed-stride lattice neighbour table** ([GetNeighborsAttributeNode.ts:24-31](../src/modeler/vpl/nodes/GetNeighborsAttributeNode.ts)) that does not exist off-lattice. **So the recommendation is a *hybrid that leans heavily on the per-cell compiler*:** a new worker-side **force-integration driver** owns the population loop, the dynamic agent count, the per-step spatial-neighbour rebuild, the position double-buffer, and the division/death structural events; the **node graph is repurposed to compute one agent's net force + behaviour decisions** given a worker-supplied dynamic neighbour list (a new "force/behaviour" event root, sibling to `Step`/`InitEvent`). This is *closer* to the existing model than CPM's hybrid — the per-cell step survives almost intact, only the loop bound, the neighbour-supply, the geometry, and the **force-vector reduction + neighbour-position read** change (the force aggregate is genuinely new emit — see the honesty ledger below and §7.1) — but it is **not** "free reuse of the current step emit."

**WebGPU is a *strong* fit here — the inverse of CPM.** CPM was JS/WASM-only because its accept/reject is an intrinsically sequential Markov chain (CPM §2.6). Center-based force summation is *embarrassingly parallel* — one thread per agent, each gathering its neighbours and summing forces, with no cross-agent write contention in the force pass (this is precisely why ya||a runs on plain CUDA; Germann, Marin-Riera & Sharpe 2019, verified). The force/integration kernel is a near-ideal WebGPU compute dispatch. The *only* part that resists the GPU is the **variable-output structural events** (division grows `N`, death shrinks it), which are handled — as in every GPU center-based engine — by an over-allocated buffer + a CPU/worker-orchestrated append/compaction pass, not inside the per-agent kernel. So WebGPU is in scope as a genuine performance target (deferred to a later wave for engineering-sequencing reasons, not feasibility ones), and the per-cell RNG (PCG) that was *useless* for CPM's sequential stream is *natural* for a parallel per-agent force kernel.

**Why this is *encouraging* news for GenesisCA specifically (the reusable half).** A large slice of the authoring + plumbing layer carries over:
- The **mode-wiring template is a near-mechanical clone** of the `variegatedCells.enabled` sub-object recipe — reducer action, dispatcher, attribute-delete cascade, default-fill, Properties toggle, gated ActivityBar tab, ModelerView auto-switch, init payload, reinit-key, `NodeRequirements` capability gate, worker mutual-exclusion safety net. Every one of these was verified firsthand at the file:line cited in §11.
- The **worker message protocol** (init / recompile / play / step / getState / loadState), **model attributes as global params** (`cachedModelAttrs`, [sim.worker.ts:356](../src/simulator/engine/sim.worker.ts)), the **single sequential xorshift32 RNG** (`rngState`, [sim.worker.ts:367](../src/simulator/engine/sim.worker.ts)), the **play→draw→next-step pipeline shape**, and the entire **value-node math library** (arithmetic/compare/aggregate/interpolation/`lookupTable`) are substrate-agnostic and reused.
- The **force law itself is exactly the kind of node-graph math GenesisCA already compiles** — a piecewise repulsion-then-adhesion curve over centre-distance is `Compare` + `Interpolation`/`ColorScale`-shaped arithmetic. Authoring the force as nodes is GenesisCA's core value proposition applied to mechanics (CBMOS shows the force-function *choice* materially changes emergent geometry — Mathias, Coulier & Hellander 2022 — so making it user-authorable is not a gimmick).
- The **`Structure-of-Arrays` discipline generalizes** — the per-attribute typed arrays stay SoA, just re-indexed by agent-id with `length = maxCells` instead of `total` (the right layout for agents too, per ya||a's GPU SoA).
- The **per-cell-object tier the CPM investigation specified (CPM §5.2) is reused almost verbatim** — but here it is *the whole state*, not a second tier over a spin lattice. The **`maxCells` over-allocation + free-list + reinit-guard hazard (CPM §5.2/§12.1) is inherited unchanged.**
- The **rendering problem is the Graph-CA renderer problem, not the CPM one** — Graph-CA §8 already designed `drawGraph()` (draw N entities at free-floating positions), the `screenToCellId`/`cellIdToScreen` picker abstraction (nearest-entity hit-test), pan/zoom in non-lattice coords, instanced rendering at scale, and the "colours buffer on the main thread every frame disables the direct-render skip" perf note. The center-based renderer *is* that renderer, with positions advanced by physics each step instead of laid out once and cached.

**The genuinely new subsystems (where the work concentrates — and where division/morphogenesis lives):**
1. **A per-agent object store** (continuous `x,y[,z]` + radius + arbitrary attributes + lineage id + cycle phase) replacing the per-site SoA. SoA-per-attribute indexed by agent, length `maxCells` (§5).
2. **A dynamic agent count + capacity ceiling + free-list** for division (births append, deaths recycle slots). This breaks the fixed-`total`, allocate-once-at-init assumption ([initGrid, sim.worker.ts:750-810](../src/simulator/engine/sim.worker.ts)) — the same `maxCells` hazard as CPM.
3. **A spatial neighbour structure (uniform-grid / cell-list / spatial-hash) REBUILT EVERY STEP** from continuous positions — the single biggest genuinely-new runtime cost, and *harder* than the lattice's build-once table or even Graph-CA's static-per-run CSR, because agents move so it is rebuilt per step.
4. **A force-accumulation + overdamped-integration driver loop** that double-buffers **positions** (read old, write new), with a **timestep `Δt` that has a hard stability/monotonicity ceiling** — a genuine silent-corruption hazard unique to this family (positions explode, not crash; Mathias et al. 2020, verified).
5. **Division / growth / death as first-class graph events** executed by the engine as post-step structural events.
6. **A from-scratch entity renderer** (filled circles at continuous positions, radius ∝ size) + nearest-centre picking, replacing the dense `ImageData` lattice blit ([SimulatorView.tsx](../src/simulator/SimulatorView.tsx)). 3D is a wholesale new WebGL renderer (Canvas2D is hard-wired).

**The honesty ledger — what genuinely reuses vs what is new (read alongside §11).** Because "fits the per-cell paradigm" is easy to over-read as "free reuse of the current emit," here is the calibrated split, so the encouraging-reuse story above is not overstated:
- **Genuinely reused:** the mode-wiring template, the SoA state mechanism, the worker message protocol, the single sequential RNG, the bounded-model-attribute sliders, the `lookupTable` adhesion matrix, the index-keyed `colors` buffer→pixels *render* contract, the indicator-reduction *pattern*, and — critically — the **per-pair scalar force-*magnitude* math** `F(d)` (the `Compare`/`Interpolation`/`arithmetic` value nodes, emitted *inside* the new neighbour loop).
- **Genuinely new emit (corrected from a first-pass overclaim):** the pairwise force is a **VECTOR sum** `Σⱼ F(dᵢⱼ)·r̂ᵢⱼ`, which is **not** the existing scalar `GetNeighbors → Aggregate` (that is one scalar array → one scalar, [AggregateNode.ts:10-11](../src/modeler/vpl/nodes/AggregateNode.ts)) — it needs a **2-/3-component vector reduction** *plus* a **`GetNeighborPosition` read of the *other* agent's continuous `(x,y[,z])`**, which `GetNeighborsAttribute` cannot supply (it reads one scalar attribute at a *lattice* neighbour index, [GetNeighborsAttributeNode.ts:24-31](../src/modeler/vpl/nodes/GetNeighborsAttributeNode.ts)). Likewise the **compiled Output-Mapping colour pass** (not just the buffer) bakes lattice geometry and needs the same agent-iteration rework as the Step body (§9). So the **central engine-fit verdict, calibrated:** the per-cell *paradigm* fits and the per-pair *magnitude* math reuses, but the **force vector-aggregate + neighbour-position emit is new on all three targets** — a far thinner change than CPM's bespoke driver, but not zero.

**Recommended scope (see §12 for phasing).**
- **Phase 0–2 (the proof):** a `centerBased` mode forcing single-buffer-position dynamics; a per-agent object store with `maxCells`/free-list; a uniform-grid neighbour rebuild; an overdamped forward-Euler driver; an authorable repulsion+adhesion force graph; JS only → **2D adhesion-driven cell sorting of soft spheres + periodic division** (the visually-compelling headline demo — *easier and more satisfying than CPM's*).
- **Phase 3–4:** WASM target (force kernel + neighbour-bin in WASM); second-order integrator option (midpoint/Adams-Bashforth — ~4-5× larger stable Δt, Mathias 2020); division/growth/death structural events with the free-list; the entity renderer + nearest-centre picking + force/velocity vector overlay.
- **Phase 5–6:** **WebGPU** force kernel (the spatial-hash → sort → offset → gather pipeline, ya||a/NVIDIA-particles style — the *strong* GPU fit) with worker-side division/compaction; chemical **microenvironment** (a coarse reaction-diffusion field cells secrete into and sense, BioFVM-style — chemotaxis + oxygen-limited growth + necrotic cores); **3D** (a dimensionality switch for the engine — same force law gains a z — but a wholesale new WebGL/WebGPU instanced-sphere renderer).
- **Out of scope for v1:** the **Voronoi/Delaunay** neighbour sub-family (a global triangulation that mutates every step — hostile to a per-agent GPU kernel; overlapping-spheres + `r_max` first). And out of scope as a *substrate*: **individual-cell-shape morphogenesis** (folding epithelia, T1 intercalation) — see the ceiling below.

**Center-based's ceiling — stated as bluntly as the CPM doc stated CPM's (§3.3 expands).** Center-based buys trivial division, the richest per-cell phenotype story, native 3D, and a strong GPU fit — but at one decisive cost: **there is no cell shape.** A cell is a point with a radius (PhysiCell explicitly "does not model cell morphology"). So this family models **population- and tissue-level organization and mechanics**, *not* individual cell deformation. It is the **wrong tool for individual-cell-shape morphogenesis** — folding epithelial sheets, T1 intercalation, apical constriction, lumen formation — which is **vertex-model or CPM/subcellular-element territory**. A second honest caveat: **the post-division timestep is a silent geometric-corruption hazard** (daughters seeded overlapping → huge repulsion → forward Euler overshoots unless `Δt` satisfies a *monotonicity* bound stricter than mere stability; Mathias et al. 2020). And a third, on *browser feasibility*: **there is no proven zero-install in-browser center-based engine analogous to Artistoo.** Artistoo (the CPM existence proof) implements *only* CPM + plain CA and explicitly does **not** support off-lattice/center-based models. Every serious center-based engine — PhysiCell (C++/OpenMP), Chaste (C++), CBMOS (Python/CuPy), ya||a (CUDA), Tissue Forge (C++/Python) — is native; their "web" stories are server-side cloud (nanoHUB), not client-side WASM. **A GenesisCA center-based mode would be genuinely novel territory — a first, not a me-too** — which inverts the risk relative to CPM: the risk is *"no reference implementation to copy,"* not *"someone already did it better."* The math is fully documented and bounded, so the risk is engineering, not research.

## 2. Literature foundations (the deep dive)

Center-based (a.k.a. *cell-centre*, *off-lattice agent-based*) models have a 25-year literature in developmental and biophysical modelling. It is organised below by the questions that drive implementation: what center-based *is* (and how it differs from a CA and from CPM), the force mechanics + the timestep-stability hazard, the cell behaviours (division — the payoff), the dynamic neighbour structures, the chemical microenvironment, the software/browser precedent (the Artistoo-equivalent question), and the performance/GPU-fit question. Every citation in this section was independently fact-checked; reliability is summarised in §2.8. **Overall reliability: HIGH** — all anchor works exist with correct venue/volume/pages/DOI; a small number of minor, non-load-bearing caveats are flagged inline.

### 2.1 What a center-based model is — and why it is neither a CA nor a CPM

A **center-based model (CBM)** represents each biological cell as a **point — its centre — at a continuous position `xᵢ ∈ ℝ²` or `ℝ³`**, usually endowed with a **radius `Rᵢ`** so the cell behaves as a soft, deformable sphere. **There is no lattice and no explicit cell-shape boundary**: a cell is a centre plus a size parameter. This inverts *every* spatial assumption of GenesisCA's current engine, and differs from CPM along a different axis:

| | Classical CA (GenesisCA today) | Cellular Potts (CPM) | Center-based (this doc) |
|---|---|---|---|
| **Cell ↔ space** | one cell per lattice site | one cell = *many* lattice sites | one cell = a *point* in continuous space |
| **Cell shape** | none (a site) | emergent, deformable, sub-cell-resolution | **none (a point + radius — a soft sphere)** |
| **Neighbours** | fixed offset template (precomputed table) | sites adjacent on the lattice | **cells within distance `r_max` (a spatial query)** |
| **Update** | synchronous deterministic rule | stochastic Metropolis accept/reject | **overdamped force-ODE integration** |
| **Population** | fixed `total = W×H` | grows/shrinks (division/death) | **grows/shrinks (division/death)** |
| **Time unit** | one synchronous generation | one Monte-Carlo Step (N attempts) | one integration step (or K of them) |
| **Parallelism** | per-cell parallel (sync) | sequential (accept/reject Markov chain) | **per-cell parallel (force sum)** |

The dynamics are **overdamped (inertia-free)**: at cellular scales the microenvironment is an extremely low-Reynolds-number regime, so inertia is negligible (the "inertialess assumption" `m·ẍ ≈ 0`), and Newton's second law collapses from a second-order ODE to a first-order force balance:

> `η · dxᵢ/dt = Σⱼ Fᵢⱼ + Fᵢ^migration` — integrated numerically (commonly forward Euler) as `xᵢ(t+Δt) = xᵢ(t) + (Δt/η)·Σⱼ Fᵢⱼ`,

where `η` is a drag/friction coefficient (often fixed to 1 by convention, folding it into the force scale — CBMOS, Mathias et al.). *(Verified verbatim: Meineke 2001 "motion is overdamped … first-order dynamics"; PhysiCell "we apply an inertialess assumption … to explicitly solve for each cell's velocity.")*

The field splits into **two sub-families** distinguished by how "who interacts with whom" is defined:
- **Overlapping spheres (OS):** cells `i, j` interact iff their centre-centre distance `dᵢⱼ < r_max` (a fixed interaction cutoff, typically ~1.5 cell diameters). Force is **repulsive on overlap** (`dᵢⱼ < Rᵢ + Rⱼ`), **adhesive over a short contact range** beyond that, and **zero beyond `r_max`**. Neighbours come from a **distance search** (cell-list / spatial-hash / k-d tree). Used by PhysiCell, CBMOS, ya||a, BioDynaMo, Tissue Forge, and Chaste's `NodeBasedCellPopulation`. *(Verified verbatim from Osborne 2017: "Two cells i and j are assumed to be neighbours if their centres satisfy ‖rᵢ − rⱼ‖ < r_max.")*
- **Voronoi / Delaunay centre-based** (Meineke–Potten–Loeffler 2001): cell centres are the generators of a **Delaunay triangulation**; two cells are neighbours iff they share a Delaunay edge; a Hookean spring acts along each edge `Fᵢⱼ = μ·(‖rᵢⱼ‖ − sᵢⱼ)·r̂ᵢⱼ`; the dual Voronoi region gives each cell an effective area/shape. The triangulation must be **recomputed (or incrementally repaired) as cells move/divide/die**. *(Verified verbatim from Osborne 2017: "Two cell centres are assumed to be connected if they share an edge in the Delaunay triangulation.")*

**The defining lesson for a GenesisCA mode:** start with overlapping-spheres, *not* Voronoi. The OS per-cell step (range-search neighbours within `r_max`, sum a pairwise force, Euler-step the position) maps directly onto the compile-to-per-cell-step model and is embarrassingly parallel. The Voronoi/Delaunay sub-family's global, every-step-mutating triangulation is hostile to a WebGPU per-cell kernel and to a compiled per-cell step — defer it. *(A documented OS↔VT behavioural difference, verified verbatim from Osborne 2017: "cells in the OS model can have more neighbours than similarly sized cells in the CP, VT or VM models" — OS cells accumulate extra neighbours under compression, changing the emergent mechanics.)*

### 2.2 The force mechanics + the timestep-stability hazard (the load-bearing numerics)

A single cell's net force is the **sum of pairwise contributions over its current neighbours**, each acting along the centre-to-centre unit vector, with a **rest-length / repulsion-then-adhesion / max-interaction-distance** structure: repulsive for `r < s` (rest length — strong volume exclusion, no interpenetration), adhesive for `s < r < r_max` (weaker, short-range), zero at `s` and beyond `r_max`. The field has converged on a small **catalogue of force laws** with known tradeoffs (Mathias, Coulier, Bouchnita & Hellander 2020, verified; CBMOS 2022, verified):

| Force law | Form / character | Software default | Note |
|---|---|---|---|
| **Linear / Hookean spring** | `F = μ(r − s)` | Meineke 2001 / Chaste-style crypt | simplest; over-stiff under strong compression (Pathmanathan 2009) |
| **Generalised linear spring (GLS)** | log repulsion + exp-decay adhesion | Chaste | **most permissive timestep**; tissue elastic-plastic in compression, brittle-elastic in tension |
| **Cubic** | `μ(r − r_max)²(r − s)` | MecaGen | single stiffness param; **most restrictive timestep** |
| **Piecewise quadratic** | independent `μ_R(1−r/r_R)²` repulsion + `μ_A(1−r/r_A)²` adhesion | PhysiCell | the canonical **"strong repulsion, weak adhesion"** tuning (independent strengths) |
| **Hertz contact + JKR adhesion** | from elastic-sphere overlap (Young's modulus, Poisson ratio); JKR adds pull-off hysteresis | Drasdo & Höhme 2005 | most physical, costlier; most meaningful in 3D |

**The numerics are the part most directly load-bearing for a compile-to-step engine, and the post-division timestep is the #1 correctness hazard — not stability, but a stricter *monotonicity* bound.** For a relaxing cell pair, forward Euler has a **stability bound** `Δt*_stab = (r₀ − s)/F(r₀)` (above it positions oscillate/diverge — "blow up") and a stricter **monotonicity bound** `Δt*_mono = (r₀ − s)/(2·F(r₀)) = exactly half the stability bound` (above it trajectories *overshoot* and become unphysical even though they don't formally diverge). *(Both formulas + the "exactly half" relationship verified verbatim from Mathias et al. 2020, Eq. 16.)* The central finding, verbatim from the paper's own section heading — *"Requiring Numerical Stability is Not Enough to Prevent Unphysical Trajectories"* — is that **just-divided daughter cells are placed overlapping (tiny separation ε → huge repulsion), so a "stable" but too-large `Δt` still corrupts post-division geometry and produces population-level error.** Consequences for a default: the bound is **force-function-dependent** (cubic most restrictive, GLS most permissive), and **second-order integrators (midpoint / Adams-Bashforth) permit ~4-5× larger steps at 1% error** (up to ~10× at 0.1%). PhysiCell integrates with second-order Adams-Bashforth at `Δt_mech = 0.1 min` by default (verified). **The failure mode is silent geometric drift, not a crash — so a center-based mode must surface `Δt` prominently and ideally auto-clamp against the monotonicity bound.**

A **migration / active force** and **random motility** make cells more than passive particles: a deterministic bias direction blended with a stochastic random walk (PhysiCell's migration-bias parameter `b ∈ [0,1]`, `0` = Brownian, `1` = deterministic up-bias, with a persistence time — verified verbatim), or a Brownian/Langevin noise term (Drasdo, Van Liedekerke). In the overdamped equation these simply add into the right-hand-side force sum — so they reuse GenesisCA's existing per-cell RNG.

### 2.3 Cell behaviours — division (the payoff), growth, death, differentiation

The four canonical behaviours are **conceptually trivial in a center-based engine** — which is exactly why this family is the natural home for division/morphogenesis:
- **Division (mitosis)** — *the* draw of this family. At cycle end the mother is **replaced by two daughters** placed at `xᵢ ± ε·m̂` along a random or oriented "mitotic unit vector" `m̂` (initially overlapping, a "dumbbell"), each ~half the mother's volume; the rest length / radius then ramps up over ~1 hour of cell-cycle time so repulsion relaxes them apart. *(Verified verbatim from Osborne 2017 and Drasdo & Höhme 2005.)* Division **grows the agent count `N`** — easy off-lattice (append two agents to the pool), awkward on a grid. This is *the* morphogenesis primitive: "rule decides when to divide" + "force relaxation does the rest."
- **Growth** = increase a cell's target radius/volume over the cycle. PhysiCell tracks **seven sub-volumes** via relaxation ODEs and **halves the target solid volume on division** (verified verbatim — the seven sub-volumes and the halving both confirmed against the paper); a simpler variant has daughters start small and grow back.
- **Death** (apoptosis/necrosis) = remove the agent and **recycle its slot**. Trivial off-lattice given a free-list; necrotic cores **emerge** from oxygen consumption + diffusion length (see §2.5).
- **Differentiation** = flip a per-agent **type tag** that re-points which subset of the compiled rules/phenotype parameters apply — a one-attribute write reusing GenesisCA's existing tag-attribute machinery.

**Rich per-cell state + sophisticated rules are native — this is the user's exact goal.** PhysiCell (Ghaffarizadeh et al. 2018, verified) is the reference implementation and the closest analogue: each agent owns an independent hierarchical **Phenotype** (cycle, death, volume, mechanics, motility, secretion) plus a **`Cell_Functions`** object of user-assignable callbacks (`update_phenotype`, `custom_cell_rule`, `update_migration_bias`) and arbitrary `custom_data`. PhysiCell uses **three separated timescales** (`Δt_diff` ~0.01 min ≪ `Δt_mech` ~0.1 min ≪ `Δt_cell` ~6 min — verified verbatim) via operator splitting, and scales to **~10⁵–10⁶ cells** on a desktop. The strategic north star for a no-code IDE is the **PhysiCell rules grammar / Cell Behavior Hypothesis Grammar** (Johnson et al. 2023 bioRxiv → peer-reviewed 2025 in *Cell*; verified): every per-cell rule is *one human-legible sentence* — *"In cell type T, signal S increases/decreases behavior B"* — that compiles to `b(s) = b₀ + (b_m − b₀)·R(s)` with `R` a sigmoidal Hill response (half-max + Hill power) or capped linear, rules combined by bilinear interpolation, edited in **PhysiCell Studio** (a dropdown-driven no-code GUI). *This grammar→math→executable pipeline is conceptually the same "compile a declarative per-cell rule spec to an executable step" pattern GenesisCA already uses* — a node graph in place of a sentence grammar. **GenesisCA being a visual analogue of the PhysiCell rules layer is a strong accessibility differentiator.** *(Minor verification caveat: one cited cycle-transition formula `P = 1 − exp(−r·Δt)` is stated in the PhysiCell paper as its first-order approximation `r·Δt`; the exponential is the underlying Poisson form — not load-bearing.)*

### 2.4 Dynamic neighbour structure — the "dynamic spatiality/adjacency" requirement, delivered natively

In continuous space "who is adjacent to whom" must be **derived from positions and re-derived every step** as cells move, divide, and die. The literature converges on two definitions (the OS distance-cutoff and the VT Delaunay-edge of §2.1), and a crucial implementation fact: **the neighbour search itself is the dominant per-step cost** — "spatial search and reinsertion are frequently reported as the most expensive steps of the simulation" (Dmitrenok et al. 2016, verified verbatim), commonly the bulk of runtime once forces are cheap and local. A naive all-pairs scan is `O(N²)`; the whole engineering problem is reducing it to `O(N)`.

The standard solution, borrowed from molecular dynamics, is the **linked-cell / cell-list / uniform-grid** structure: bin the domain into boxes of edge `≥ r_max`, then each cell only tests its own box + the 8 adjacent boxes (2D) / 26 (3D), giving `O(N)` at biological densities because each box holds `O(1)` cells. This is the unanimous choice of the performance-oriented engines:
- **BioDynaMo's "uniform grid"** (verified verbatim): "divides the total simulation space into uniform boxes … iterating over the assigned box and all its surrounding boxes (27 boxes in total)"; box size auto-derived "based on the largest agent … to ensure all mechanical interactions are taken into account."
- **PhysiCell's** Cartesian "interaction (testing) data structure" gives a bounded candidate list per cell so cost "scales linearly in the number of cells" (verified).
- **Chaste's `BoxCollection`** (box size = the mechanics cutoff, query a box + nearest-neighbour boxes, rebuild on `Update()`/`Clear()` after births/deaths).
- **ya||a's GPU spatial-hashing** (the NVIDIA-particles pattern): hash each cell's position to a cube id via `floor(x/cube_size)`, radix-sort cell indices by cube id, build per-cube start/end offset arrays via prefix scan, then gather over the 27-cube stencil — *"scales linearly in n."* *(Verification note: the exact pipeline phrasing is marked uncertain — the paper exists and the algorithm is the standard NVIDIA-particles pattern, but the bioRxiv full text was access-blocked for verbatim re-confirmation.)*

**Verlet lists** add a skin/buffer `δ` to the cutoff and cache the neighbour list, rebuilt only when a cell moves `> δ/2` (or every K steps) — fewer rebuilds for slow-moving tissue (Allen & Tildesley, the canonical MD reference, confirmed to exist). The **Delaunay/Voronoi** route uses **incremental/kinetic update** (move vertices + local edge-flips / equiangulation, local insert/delete on division/death) rather than full `O(N log N)` recompute, achieving on-average ~linear cost (Schaller & Meyer-Hermann 2005, confirmed) — but with 3D tetrahedralization robustness/degeneracy handling that is far heavier to implement and parallelize, which is why GPU engines pick distance-cutoff over Delaunay.

**The cautionary tale most relevant to an IDE: CBMOS deliberately keeps all-pairs `O(N²)`** because it vectorizes cleanly in NumPy/CuPy and the project targets numerical-method study over scale (a few thousand cells on CPU, ~10k on GPU), explicitly noting the bounding-box (cell-list) algorithm would be faster but harder to express as array operations (verified; default rest length `s = 1.0`, cutoff `rA ≈ 1.5` cell diameters). **The lesson for GenesisCA: build the all-pairs path first as the JS "Debug/Reference" target (easy to compile and verify, fine for a few thousand cells in interactive 2D), and the uniform-grid path as the WASM/WebGPU performance target — exactly paralleling the existing JS-reference-vs-compiled split.**

### 2.5 Coupling to a chemical microenvironment (PDE) — closer to must-have than for CPM

Most interesting center-based morphogenesis — oxygen/nutrient-limited growth, necrotic cores, chemotaxis, secreted morphogen gradients — couples the agents to one or more **diffusing chemical substrates** on a **separate coarse Cartesian grid** (independent of and much coarser than the cells; one voxel holds many cells). Each substrate obeys a reaction-diffusion-decay PDE `∂c/∂t = D∇²c − λc + sources − sinks`, with the key emergent parameter the **diffusion length** `L = √(D/λ)` (for oxygen ~100 µm — it sets the viable-rim/necrotic-core geometry). The canonical solver is **BioFVM** (Ghaffarizadeh, Friedman & Macklin 2016, verified), wrapped by PhysiCell. Cells couple **bidirectionally**: as **sources/sinks** (secretion/uptake, a scatter write into the cell's voxel) and as **sensors** (reading local value + gradient `∇c`, for chemotaxis and oxygen-gated phenotype). The **necrotic core EMERGES** from the physics — cells consume oxygen, the finite diffusion length starves the spheroid centre once its radius exceeds ~2L (the canonical "interesting coupled behaviour"; Macklin et al. 2012 DCIS, verified: proliferation rate ∝ `(σ−σ_H)/(1−σ_H)`, hypoxic threshold `σ_H ≈ 0.2`, viable rim ~80 µm — *do not script the core, let it emerge*).

**The decisive numerical lesson for a Web-Worker engine:** do **not** diffuse with a naive explicit Laplacian — its CFL limit `Δt ≤ dx²/(2·dim·D)` forces many tiny sub-steps. BioFVM uses an **implicit operator-split + Locally-One-Dimensional (LOD) tridiagonal (Thomas) solve** that is **stable even for large time steps** (verified — the paper says "stable even for large time steps"; an implicit scheme is unconditionally stable in the standard numerical sense). The catch for WebGPU: a tridiagonal solve is sequential per grid-line, fighting per-cell parallelism — so the pragmatic web options are **(a) clamped explicit diffusion with K small sub-steps** (simple, GPU-friendly — and GenesisCA's existing Gray-Scott model already proves the node-graph + 3-target compiler can express a Laplacian + reaction on a grid), or **(b) an ADI/LOD solve via parallel cyclic reduction** (stable, large `Δt`, much more complex to emit on three targets). **Recommendation: chemical fields are out of the headline v1 but the first post-MVP addition (Phase 5)** — closer to must-have than for CPM, but cell-sorting + adhesion + division is already a complete, compelling story, and the field is a whole new subsystem (a second grid + scatter-secretion + a diffusion pass). **One honest caveat to surface (Van Liedekerke 2019, verified verbatim):** pairwise center-based contact forces *"lack accuracy in dense cell aggregates under compression"* because they exclude many-body contributions — fine for a v1 spheroid, document the limit rather than silently producing wrong tissue pressures.

### 2.6 Software precedent + the browser-existence-proof question (the Artistoo analogue)

**The headline finding: there is NO mature pure-browser (client-side JS/WASM) center-based engine analogous to Artistoo — and this materially changes the risk calculus relative to CPM.** *(Marked "uncertain" only because it is a negative-existence claim that cannot be positively proven by search; the supporting pillars are all individually confirmed.)*

- **Artistoo** (Wortel & Textor 2021, eLife — the CPM existence proof) is pure-JS, zero-install, Canvas-rendered, and implements **only Cellular Potts + cellular automata**; it explicitly does **not** support center-based/off-lattice models (confirmed: its model-class table lists only CPM + CA).
- Every serious center-based engine is **native**: **PhysiCell** (C++/OpenMP, ~500k cells desktop / millions on one HPC node — verified), **Chaste** (C++; one `AbstractCellPopulation` API spanning CA / CPM / overlapping-spheres / Voronoi / vertex / immersed-boundary — the *swappable-engine* architectural template, verified), **CBMOS** (Python/NumPy + CuPy GPU, ~10k cells — verified), **ya||a** (plain CUDA/C++ GPU, spin-like polarities for epithelium — verified), **Tissue Forge** (C++/Python, real-time Magnum/OpenGL renderer — the closest to "interactive center-based with live visualization," but native desktop/Jupyter, verified), **BioDynaMo** (C++/OpenMP/GPU, ~10⁹ agents — verified), **Biocellion** (HPC, millions–billions). Their "web" stories are **server-side cloud** (PhysiCell on nanoHUB = native binary on a remote server, results streamed to a browser) — **NOT** client-side computation.
- The most conceptually adjacent precedents for GenesisCA's accessibility goal are **PhysiCell Studio** (a PyQt5 dropdown-driven no-code GUI over PhysiCell's XML — verified) and **EPISIM** (a *graphical* multi-scale modelling platform where epithelial cell-behaviour models are authored visually — verified; Java desktop, not browser).

**The conclusion:** a GenesisCA center-based mode that compiles a node graph to a per-cell step on JS/WASM/WebGPU and runs in-browser would be **genuinely novel — a first, not a reimplementation.** The risk is *"no reference implementation to copy"*, not *"someone already did it better."* Because the math is fully documented and bounded (and Artistoo-style behavioural oracles exist for *correctness* even if not for *architecture* — the CBMOS/PhysiCell published results are validation targets), this is an engineering risk, not a research risk.

**Visualization techniques converge on a small, Canvas2D-friendly vocabulary:** cells as **filled circles (2D) / spheres (3D)** at continuous positions, radius ∝ `√volume`, **coloured by type or scalar attribute** ("virtual pathology" colouring); a **microenvironment heatmap underlay** (substrate concentration as a background raster, composited *under* the cells); **force/velocity vectors** as glyphs/arrows; **lineage/clone** structure as dendrograms/Muller plots or spatially-embedded traces (LinG3D — *verification note: the paper exists, DOI correct, but one cited byline was fabricated by the research agent and corrected — cite by tool, not author*). 2D output is SVG (PhysiCell) or Canvas; 3D uses OpenGL/VTK natively — none WebGL-in-browser today, so 3D for GenesisCA is a wholesale new WebGL renderer (the CPM-§9 "3D is easy is true of the engine, not the renderer" caveat applies).

### 2.7 Performance & the GPU-fit question — center-based is a *strong* WebGPU fit (the inverse of CPM)

The central performance fact, and the inverse of CPM's: **center-based force computation is "embarrassingly parallel."** Each cell independently *sums forces from its neighbours and integrates its own position* — no cross-cell write contention in the force pass, no sequential accept/reject Markov chain. So (a) it maps naturally onto **one thread per cell** and is a **strong WebGPU/GPU fit**, and (b) it fits GenesisCA's existing "compile the graph to a per-cell step, run it over all cells" model *better than CPM did*, **IF the worker supplies the (variable-length) neighbour structure the way it already supplies a neighbour-index table.** **ya||a is the proof** (Germann et al. 2019, verified): a plain-CUDA model using **pairwise interactions only** (plus spin-like polarities for epithelial sheets) *specifically to parallelize the whole step on the GPU*, orders of magnitude faster than CPU tools precisely because pairwise-only forces parallelize cleanly one-thread-per-agent. **The single most important architectural lesson: stay PAIRWISE-ONLY in the hot path** — forbid any node needing a global structure (Voronoi areas, all-pairs reductions) so the step stays a local sum over a spatially-binned neighbour list.

The WebGPU pipeline is the proven **ya||a / NVIDIA-particles** design: hash position → cube id, GPU radix-sort cell indices by cube id, build per-cube start/end offset buffers via prefix scan, then a gather kernel over the 27-cube stencil — reusing GPU sort + scan primitives and degrading gracefully to a JS/WASM linked-cell list. **The one part that resists the GPU is the variable-output structural events** (division grows `N`, death shrinks it): every GPU center-based engine handles this with an **over-allocated buffer + a CPU/worker-orchestrated append/compaction pass**, *not* dynamic agent creation inside the per-agent kernel. The per-cell **PCG RNG** that was useless for CPM's sequential stream is *natural* here (per-agent parallel work). The timestep/double-buffer story on GPU is *expected* to reuse the attrsRead/attrsWrite ping-pong GenesisCA's WebGPU target already uses (co-locate positions in the attrs buffer → the ping-pong double-buffers positions) — but this is hedged, not "for free": the existing ping-pong is over a **fixed-`total`** buffer sized once, whereas center-based's premise is a **dynamic count with division/compaction**, so how the swap interacts with worker-side append/compaction (you cannot ping-pong a co-located buffer *and* grow/compact it without a re-upload) is a Phase-5 detail to resolve, not a settled win. **Net: center-based is a genuine, strong WebGPU target — deferred to a later wave for engineering-sequencing reasons (build JS/WASM correctness first), not feasibility ones.**

## 3. Substrate verdict — center-based vs CPM (completes the comparison)

With both deep analyses now in hand, this section gives the honest, decisive comparison the handoff asked for. **There is no single winner — the families are complementary — but for the *specific behaviour* the user wants (division-heavy, rich-phenotype, eventually-3D populations where the interesting thing is the *population*, not each cell's shape), center-based is the better *target*; CPM is the better *first build* for *this codebase*; and a single engine-agnostic per-cell IR can — and should — serve both.**

### 3.1 The candidates, scored against GenesisCA's goal

This reuses and extends the CPM §3.1 table (verified head-to-head: Osborne, Fletcher, Pitt-Francis, Maini & Gavaghan 2017 implement five families in one framework, Chaste).

| Substrate | Cell shape | Division | Adjacency / topology | Rich per-cell state | 3D | Browser precedent | GPU fit | Fit to GenesisCA's lattice/SoA/compile stack |
|---|---|---|---|---|---|---|---|---|
| **Cellular Potts (CPM)** | **emergent, deformable, sub-cell** | easy (split pixels, relabel) | implicit & free | rules over per-site + per-cell-ID state | same kernel, rescale | **Artistoo (proven)** | **poor** (sequential accept/reject) | **highest** — it *is* a lattice CA + Metropolis + per-cell-ID bookkeeping |
| **Center-based / off-lattice** | **none (points/spheres)** | **trivial** (place 2 daughters) | **distance-based / dynamic** | **richest** (PhysiCell Phenotype + Cell_Functions; 10⁵–10⁶ cells 3D) | **native** | **none browser-native** | **strong** (parallel forces, ya||a) | **medium-high** — different driver, but the per-cell step *survives* |
| **Vertex model** | explicit polygons sharing edges | mid (insert edge) | explicit mesh; T1/T2 ops | per-cell + edge state | "most challenging to extend to 3D" (Osborne 2017) | none mature | poor | low — mesh + topological transitions alien to a lattice engine |
| **Subcellular element** | full deformable | duplicate element cloud | distance-based | very rich | native | none | medium | low — many elements/cell under Langevin dynamics; overkill for browser |
| **Phase-field** | beautiful deformable | PDE | implicit (field overlap) | per-field | native | none | poor | low — one PDE field *per cell*; heaviest option |

### 3.2 The two-axis verdict

The CPM and center-based analyses agree on the *shape* of the answer, from opposite directions:

1. **For the user's stated *behaviour goal*, center-based is the more direct match.** The goal is division + morphogenesis + arbitrarily rich per-cell rules + dynamic adjacency, ultimately in 3D. Center-based delivers **all four natively**: division is trivial (append two agents), per-cell state is the richest of any family (PhysiCell Phenotype + Cell_Functions is *literally* "arbitrary attributes + sophisticated rules over many attributes"), adjacency is dynamic and distance-based by construction, and 3D is a dimensionality switch for the engine. Center-based is the substrate the literature *built for* this exact goal — Drasdo/Höhme spheroids, Meineke crypts, Galle regulated epithelium, PhysiCell tumours.

2. **For *this codebase*, CPM is the lower-friction *first* build, and center-based fits the *compile paradigm* better.** This is the subtle, important split:
   - **CPM reuses more of the runtime substrate** (~60-70%): it keeps the lattice, the per-site SoA, the colors-buffer grid blit, `buildNeighborIndices`, and the async single-buffer path. But it **breaks the compile paradigm** — a per-site graph cannot express accept/reject, so CPM needs a *bespoke Metropolis driver* and the graph is demoted to a pure ΔH scalar (CPM §1).
   - **Center-based reuses *less* of the runtime substrate** (it discards the lattice, the per-site index semantics, the grid blit, the build-once neighbour table, and `orderArray`) but **fits the compile paradigm *better*** — each agent genuinely computes its own force + integrates its own position, a true per-cell step that survives almost intact (only the loop bound, neighbour-supply, and geometry change). And it is the **strong GPU fit** CPM was not.
   - So the honest framing is: **CPM is the faster path to *something morphogenetic on screen*** (more of the engine already exists), while **center-based is the better long-term *target*** (it matches the goal, fits the compiler, and is GPU-native). They are not redundant — they are complementary.

3. **A single engine-agnostic per-cell IR can serve both — and this is the recommendation both investigations converge on.** This is the load-bearing design consequence. Keep the node graph and the per-cell-step IR **engine-agnostic at the abstraction level**, so the same "per-cell update + per-cell attributes over a dynamic neighbour set" nodes can compile to *either* a lattice Metropolis ΔH (CPM) *or* a continuous-space force-integration step (center-based). **The center-based audit is the concrete evidence that this abstraction work is real and non-trivial, not a free side effect:** the current IR *bakes lattice geometry into the emit* (§2.9 — `_row`/`_col` decode + `idx*4` color write + fixed-stride neighbour stride). Front-loading the engine-agnostic-IR work (the CPM §3.2 recommendation) is therefore a genuine prerequisite for the second engine, whichever is built first.

### 3.3 The recommendation — and center-based's ceiling, stated bluntly

**Recommendation:** the two-engine future is *CPM-first-OR-center-based-first depending on the user's tolerance for the new neighbour/renderer work*, with a **shared engine-agnostic IR** so the second engine is additive. Concretely:
- If the priority is **the fastest morphogenetic demo on the existing stack** → CPM-first (reuses the lattice/blit/async substrate).
- If the priority is **matching the user's actual end-state (division-heavy 3D rich-phenotype populations) and a GPU-native engine** → center-based-first is defensible *despite* the larger runtime-substrate delta, because it fits the compile paradigm and is the goal.
- **Either way, build the engine-agnostic IR once** so the other engine follows cheaply.

**Center-based's ceiling — hear this before committing (as bluntly as the CPM doc stated CPM's):**
- **There is no cell shape.** A cell is a point with a radius (PhysiCell "does not model cell morphology"). Center-based models **population- and tissue-level organization**, *not* individual cell deformation. It is the **wrong tool for individual-cell-shape morphogenesis** — **folding epithelial sheets, T1 intercalation, apical constriction, lumen/tube formation** — which is **vertex-model (or CPM/subcellular-element) territory**. If the morphogenesis goal drifts toward shape-driven sheet mechanics, neither center-based nor a retrofit onto it is the answer.
- **A behavioural divergence to document:** Osborne 2017 shows OS/VT center-based models reach a *local steady state that is not complete engulfment* when sorting two adhesive populations, whereas the energy-minimizing families (CA, CPM, vertex) reach complete engulfment. So a center-based "sorting" demo looks *more separated* than a CPM one — relevant when comparing the two modes side by side.
- **The post-division timestep is a silent geometric-corruption hazard** (overlapping daughters → stiff forces → forward-Euler overshoot unless `Δt ≤ Δt*_mono`; §2.2). The failure mode is drift, not a crash.
- **No proven zero-install browser engine** (the Artistoo analogue does not exist; §2.6) — novel territory, engineering risk not research risk.
- **CPM's reciprocal ceiling** (for the comparison's symmetry): non-physical Monte-Carlo time, one `T` coupling many effects, broken detailed balance → stochastic cell extinction (Voss-Böhme 2012), and a *poor* GPU fit. Center-based is the better answer wherever those bite — which is precisely the division-heavy 3D rich-phenotype regime.

## 4. Conceptual model — how center-based maps onto the Six Fundamentals, and the engine-paradigm decision

GenesisCA's model definition rests on Six Fundamentals (cells have computing power; N internal attributes = state; cells read neighbour states; writability; discrete space+time; synchronicity). Center-based stretches the *spatial* ones hardest:

| Fundamental | Classical CA reading | Center-based reading |
|---|---|---|
| **1. Computing power** | per-cell rule | per-*agent* rule: sum neighbour forces, decide behaviour (grow/divide/die/differentiate) |
| **2. N attributes = state** | per-site attribute vector | per-*agent* attribute vector **+ continuous position `x,y[,z]` + radius + lineage + cycle phase** — the position is now first-class state, not implicit in the index |
| **3. Read neighbours** | fixed offset template | the agent's **distance-`r_max` neighbour set** (variable size, rebuilt each step) — read via degree-tolerant aggregates (the Graph-CA finding applies) |
| **4. Writability** | sync = own only; async = neighbours too | force integration writes **only the agent's own position** (sync, double-buffered positions); division/death write the *population* (engine-side structural events) |
| **5. Discrete space+time** | grid + generations | **continuous space** + discrete time (one integration step, or K sub-steps, per generation); 2D now / 3D later |
| **6. Synchronicity** | sync (parallel) or async (sequential) | **synchronous** (all agents read old positions, write new — force-sum-then-step), *not* the async single-buffer Markov chain |

**A crucial Six-Fundamentals nuance vs the audit:** the engine-fit audit initially suggested center-based should "force async-like single-buffer dynamics + reuse `orderArray`." **This is the wrong fit.** Async (CPM's substrate) is a *sequential* per-cell sweep where each write is immediately visible to later cells in the same step — correct for a Metropolis Markov chain. **Center-based force integration is *synchronous*:** every agent computes its net force from a *frozen old-position snapshot*, then all positions are written together (forward Euler reads old, writes new). So center-based **double-buffers POSITIONS** (like the sync lattice path's attribute double-buffer, [sim.worker.ts:1233-1235](../src/simulator/engine/sim.worker.ts)) and does **NOT** use `orderArray` (the shuffled-site async schedule, [sim.worker.ts:303,860](../src/simulator/engine/sim.worker.ts)) — `orderArray` dies in this mode. Conflating "agents move and write" with "async single-buffer" imports the wrong buffering model. (CPM *does* reuse `orderArray`; center-based does not — a clean point of divergence between the two modes.)

**The engine-paradigm decision (hard fit question #1).** Three options, evaluated:
- **(A) Pure compile-to-per-cell-step, no bespoke driver.** *Closer to viable than for CPM, but still rejected.* The *paradigm* fits — each agent computes its own force and integrates its own position, a legitimate per-cell step. But three things block reusing the *current* emit/dispatch as-is: (a) `buildLoopArgs` ([sim.worker.ts:937](../src/simulator/engine/sim.worker.ts)) supplies the lattice fixed-stride neighbour table + `total`, not a per-step-rebuilt dynamic neighbour list + live agent count + position arrays; (b) the emitted loop body decodes `(row,col)` and writes `idx*4` colors ([compile.ts:1748-1752](../src/modeler/vpl/compiler/compile.ts)) — wrong geometry; (c) division/growth/death mutate the agent *count* mid-pipeline, which the fixed-arity `buildLoopArgs` and once-at-init allocation ([initGrid, sim.worker.ts:750](../src/simulator/engine/sim.worker.ts)) cannot express.
- **(B) Fully bespoke worker engine, no graph.** Throws away GenesisCA's value proposition. The force law + behaviours *are* naturally a node graph (the force is `Compare`+`Interpolation`-shaped math; CBMOS proves force-choice matters, so user-authorability is real value), so hardcoding wastes the compiler.
- **(C) Hybrid that leans heavily on the per-cell compiler (recommended).** A new worker-side **force-integration driver** owns: the population loop over the live agent count, the per-step spatial-neighbour rebuild, the position double-buffer, the integrator (forward Euler → second-order), and division/growth/death as post-step structural events. The **node graph is repurposed to compute one agent's net force + behaviour** given a worker-supplied dynamic neighbour list — a new "force/behaviour" event root (sibling to `Step`/`InitEvent`), reusing the existing value-node library (reads, neighbour aggregates, arithmetic, `GetRandom`). **This is a *lighter* hybrid than CPM's** — CPM demoted the graph to a pure scalar ΔH and the driver did everything; here the graph keeps doing genuine per-cell work (the force sum + integration *is* the compiled step), the driver only adds the loop bound, neighbour-supply, and structural events. **It is the equivalent of CPM's "node graph stays the authoring surface, a new engine path drives it" — but with far thinner violence to the per-cell step.**

## 5. Data model & file format — the agent object tier

### 5.1 The per-agent object tier (the central new structure)

Per-agent properties — continuous position `(x, y[, z])`, radius, type, arbitrary attributes, lineage id, cell-cycle phase, age — have **no home** in today's two-tier schema (per-site attributes of length `total` / global scalars), and there is **no continuous-position concept at all** (§2.9). This is the **same per-cell-object tier the CPM investigation identified as the central new structure (CPM §5.2)** — but here it is *the whole state*, not a second tier over a spin lattice.

**Recommended shape:** an additive optional **`centerBased?: CenterBasedConfig`** sub-object on `CAModel` (the [`VariegatedCellsConfig` pattern, types.ts:470-483,539](../src/model/types.ts) is the structural template — old files load unchanged when absent), holding `{ enabled, maxCells, dimensions: 2|3, perAgentAttributes, forceLaw refs, … }`, plus worker-side **parallel SoA typed arrays of length `maxCells`** (one per per-agent attribute — `Float64Array` for positions/radius/cycle, `Int32Array` for lineage/type) and a **free-list** for ID recycling on death/division. **SoA, not array-of-structs** — one array per attribute is the right cache-friendly layout for agents too (ya||a's GPU SoA confirms this), and it reuses `createTypedArray` ([sim.worker.ts:710-719](../src/simulator/engine/sim.worker.ts)) with `length = maxCells` instead of `total`. **Continuous positions model cleanly as per-agent `float` attributes** → `Float64Array`, which **already round-trips** (`float64` is in `ATTR_TYPE_MAP`, [fileOperations.ts:383-386](../src/model/fileOperations.ts)) — so no new `ATTR_TYPE_MAP` entry is needed for pure-float agent state. *(The CPM §12.2 hazard only bites if a NON-float kind is introduced — e.g. a `Uint32` free-list or a packed cycle-enum — which must be registered at the same commit.)*

**Critical — the `maxCells` ceiling + free-list (inherited verbatim from CPM §5.2/§12.1).** Because the WASM memory and typed arrays are allocated **once at init** ([initGrid, sim.worker.ts:750-810](../src/simulator/engine/sim.worker.ts)) and never resized mid-run, `maxCells` must be an **over-allocated ceiling** (with a free-list), not true dynamic growth — true growth would require a full reinit (losing run state). **Division appends two daughters** (or reuses the mother slot + one new slot); **death marks a slot free**; the free-list recycles dead-agent IDs. **Overflow is never silent:** a division that would exceed `maxCells` is *rejected* (a no-op) and surfaced through the existing Stop-Event / blue-notice channel — never a wrap into a live ID (the exact Amphiphile-NI-poisoning hazard class). Raising `maxCells` mid-run resizes the baked arrays, so it is a **structural change** that must trip the `attrsStructurallyEqual` reinit guard ([SimulatorView.tsx:241](../src/simulator/SimulatorView.tsx), §13.1), not a soft recompile. Suggested default: `maxCells = clamp(initialAgentCount × growthHeadroom, 256, hardCap)`, user-overridable in the center-based panel. **Concrete policy:** `growthHeadroom` ≈ 4–8× (a run that 10×s the population needs the user to raise it — surfaced as a clear "agent cap reached" notice, never a silent wrap); `hardCap` from a memory budget (≈ a few million agents × the per-agent SoA stride). **Division uses the mother slot + one fresh free-list slot** (the mother becomes daughter A in place; daughter B is appended/recycled) — one allocation per division, not two. **The 2D→3D z-coordinate:** store positions as separate `x`/`y`/`z` `Float64Array`s; in 2D the `z` array is absent (and unserialized). Switching a 2D model to 3D **allocates a fresh `z` array defaulted to 0** (a structural reinit), and serialization writes `z` only when `dimensions === 3` — so a 2D file carries no orphan z column and a later 2D→3D switch is well-defined.

**Where the arrays live (the WASM fork — resolved, reused from CPM §5.2).** Phase 2 (JS-only) keeps them as plain worker-side typed arrays. From the WASM phase they are **promoted to a baked-in `wasmMemory` region** so the compiled force kernel reads positions directly at a fixed offset, with the JS driver touching them through typed-array *views* under the mandatory **copy-into-never-reassign** discipline (the documented "reassigning a view orphans WASM from JS mutations" gotcha — the orderArray/NI-load class of bug). This is a *fork, not a detail*.

### 5.2 Center-based parameters (reuse bounded model attributes + `lookupTable`)

Force-law stiffness `μ`, adhesion/repulsion coefficients, rest length `s`, interaction cutoff `r_max`, drag `η`, timestep `Δt`, cell-cycle durations, migration speed/bias all map onto **bounded `float` MODEL attributes** (`hasBounds/min/max`, [types.ts:39-43](../src/model/types.ts)) → range sliders, live-tunable via `updateModelAttrs` ([sim.worker.ts:171](../src/simulator/engine/sim.worker.ts)). **No new schema for scalar parameters.** A **type×type adhesion/repulsion matrix** (differential adhesion → sorting) maps **directly onto the existing `lookupTable` model attribute** keyed `tagAttribute × tagAttribute` on cell *type* ([types.ts:19-22,71-87](../src/model/types.ts)) — live-tunable via `updateLookupTable` ([sim.worker.ts:164](../src/simulator/engine/sim.worker.ts)) and round-tripped via `SimulationState.interactionTables`. **No new attribute type for adhesion** — the exact CPM §5.3 J-matrix reuse.

### 5.3 The microenvironment field (Phase 5)

A chemical substrate is **an ordinary per-cell `float` attribute on a (coarse) grid** — it reuses `ModelProperties.gridWidth/gridHeight` ([types.ts:207-208](../src/model/types.ts)) for the *field* resolution (**the disambiguation, resolved:** in center-based mode the agent domain is a *separate* continuous **`centerBased.worldBounds`** extent in world units, while `gridWidth/gridHeight` are *repurposed* to mean the **microenvironment field-voxel resolution** — relevant only once the Phase-5 field exists; before then the grid dims are unused/display-only and the agents never read them, so there is no ambiguity at runtime), serializes via the existing per-site path, and is coloured by a Color Scale. The coarse field grid also doubles as the **mechanics broad-phase** (bin agents into the same voxels), unifying two subsystems. *(The constant-boundary `+1` sentinel / 8-byte-alignment hazard re-appears for the field tier, not the agent tier — keep `ATTR_TYPE_MAP` correct.)*

### 5.4 Serialization

- **A new `SimulationState` field** for the variable-length agent table + `liveAgentCount` + `maxCells` + the ID free-list ([types.ts:365-414](../src/model/types.ts) — `SimulationState` only serialises per-site arrays sized to `total` today). The free-list serializes as a base64 typed array via the existing `arrayBufferToBase64` path.
- **Teach `serializeSimState` / `readStateFile` / `applySimulationState` an agent-count dimension** alongside (or instead of) `width*height`. The W×H dim-validation ([SimulatorView.tsx:3484](../src/simulator/SimulatorView.tsx)) and `total = state.width*state.height` ([SimulatorView.tsx:3502](../src/simulator/SimulatorView.tsx)) are the precise points that **silently abort a center-based load today** (no try/catch around deserialize — a throw aborts the whole load = "click load, nothing happens"; CPM §12.3) — they must fail *loudly* on an agent-count mismatch.
- **Bump `SCHEMA_VERSION`** ([schema.ts:10](../src/model/schema.ts)) with an additive migration (old files have no center-based tier).
- **`Variable` is a red herring** ([types.ts:501-518](../src/model/types.ts)): per-cell-*step* scratch that resets every iteration — it cannot store persistent per-agent lineage/cycle-phase. Do not reuse it for the agent tier.

## 6. Engine / worker — the force-integration driver

### 6.1 The new driver loop

Add a `centerBased.enabled` flag and a worker branch in `runStep` ([sim.worker.ts:1097](../src/simulator/engine/sim.worker.ts)) that, instead of (only) calling the lattice per-cell step, runs per generation:

```
# 1. rebuild the spatial neighbour structure from current positions
grid = uniformGrid(live agents in 0..highWater, boxEdge = r_max)   # alive-mask, NOT a dense 0..liveAgentCount range (free-list ⇒ holes)
neighbourList = flatten(grid)            # CSR-like: candIdx[] + perAgent start/len offsets

# 2. force pass (the compiled per-agent step — embarrassingly parallel)
for i in 0..highWater:  if not alive[i]: continue   # one thread per LIVE agent (free-list ⇒ sparse slots ⇒ alive-mask, not a dense bound); GPU-friendly
  Fnet = forceFn(i, positions_old, neighbourList, modelAttrs, lookupTables)   # compiled graph
  velocity[i] = Fnet / eta + migrationForce(i)          # + Langevin noise via RNG
  positions_new[i] = positions_old[i] + dt * velocity[i]   # forward Euler (read old / write new)

# 3. commit positions (double-buffer swap, like the sync attribute swap)
swap(positions_old, positions_new)

# 4. behaviour + structural events (post-step, engine-orchestrated)
for i in 0..highWater:  if not alive[i]: continue
  advanceCycle(i); growRadius(i)
  if shouldDivide(i): divide(i)   # append 2 daughters at x ± eps*m_hat (free-list); reject if would exceed maxCells
  if shouldDie(i):    die(i)      # free the slot
# (Phase 5) microenvironment: secrete/uptake scatter + K diffusion sub-steps

generation++
```

**Reuse:** the sync double-buffer ref-swap idiom ([sim.worker.ts:1233-1235](../src/simulator/engine/sim.worker.ts), applied to position arrays); the shared xorshift32 RNG ([sim.worker.ts:367](../src/simulator/engine/sim.worker.ts), for daughter-plane sampling + Langevin noise + stochastic migration — a *single sequential stream maps cleanly onto a sequential per-agent loop*, the cleanest reuse); `cachedModelAttrs` / `syncModelAttrsToMemory` ([sim.worker.ts:356](../src/simulator/engine/sim.worker.ts)) for the force-law parameters; the per-step transient-flag mechanism as the model for an agent-alive mask.

### 6.2 The spatial neighbour structure (the dominant new cost)

The uniform-grid / cell-list **REBUILT EVERY STEP** (agents move) is the **single biggest genuinely-new runtime cost** — and strictly *harder* than the lattice's build-once `buildNeighborIndices` ([sim.worker.ts:877](../src/simulator/engine/sim.worker.ts)) and than Graph-CA's static-per-run CSR (Graph-CA §2.8), because it is rebuilt per step over continuous positions. Budget a per-step bin-then-flatten (`candIdx[]` + per-agent `start/len` offsets — the continuous-space analogue of the lattice `nIdx_/nSz_` tables, and structurally the Graph-CA CSR ragged adjacency the compiler already needs to support for variable degree). Box edge = `r_max`; gather over the 9-box (2D) / 27-box (3D) stencil; auto-derive box size from the largest agent radius. A Verlet skin (cache within `r_max + δ`, rebuild only on max-displacement `> δ/2`) is a later optimization once the grid path is stable. **Scratch sizing is a silent-overflow hazard here (cross-ref §2.1):** the per-agent neighbour scratch must hold up to `maxDegree` candidates, but OS cells *accumulate more neighbours under compression* (the Osborne 2017 OS-vs-VT finding), so a fixed compile-time `maxDegree` can overflow **exactly when a cluster packs tight** — the worst case. Size it generously (a high multiple of the expected `r_max`-disc occupancy) **and** add a runtime overflow guard (clamp the gathered count + surface a warning) rather than a bare fixed stride — the same NI-poisoning hazard class the lattice path already guards. **The compiled per-agent step receives this ready-made neighbour list** — mirroring how the engine already hands the step its `nIdx_/nSz_` tables — so the node-graph compilation model is unchanged; only the *data* behind "get neighbours" becomes dynamic and variable-degree (the Graph-CA §6 variable-degree aggregate-emit applies verbatim).

### 6.3 The integrator + the timestep-stability guard (hard fit question #8)

Default to **forward Euler** (one pass, the field default). Surface `Δt` and `η` as explicit model parameters, and **implement the Mathias 2020 bounds as a validation guard**: warn/clamp when `Δt` exceeds `Δt*_stab = (r₀−s)/F(r₀)`, ideally the stricter `Δt*_mono = ½·that`. **The dangerous case is a "stable but wrong" `Δt` after division** — the symptom is silent geometric drift, not a blow-up, so surface it in the UI (a CFL-style auto-clamp or a prominent warning). Offer a **second-order option** (midpoint / Adams-Bashforth) from Phase 3 — ~4-5× larger stable steps at the cost of two force evaluations per step (a large constant-factor win for the same per-step force code). Implicit backward Euler is out of scope (needs a linear solve — document as unsupported, not attempted).

**Concrete starting defaults (grounded in the verified literature so the demo does not explode on first run).** Rest length `s = 1.0` (one cell diameter) and cutoff `r_max ≈ 1.5·s` (CBMOS, verified); drag `η = 1` (folded into the force scale — CBMOS/Mathias convention); the **GLS force law by default** (the most permissive timestep of the catalogue); and `Δt` **auto-clamped** to a safe fraction of the monotonicity bound — `Δt ← min(Δt_user, 0.4·Δt*_mono)`, with `Δt*_mono = ½·(r₀ − s)/F(r₀)` computed from the chosen force law's `F` at the closest expected approach and **re-evaluated whenever the force-law parameters change**. PhysiCell's `Δt_mech = 0.1 min` is the canonical mechanical step to seed the default with. A hazard surfaced without a safe default still ships a first-run explosion — so the default *is* the guard.

### 6.4 Division / growth / death as structural events

Post-step, engine-executed, triggered by graph nodes (§8): **division** computes a random/oriented mitotic axis `m̂`, places two daughters at `xᵢ ± ε·m̂` with halved volume and a ramping radius, copies/mutates attributes (lineage id ← fresh, type ← inherited or differentiated), allocates a fresh ID from the free-list, and **rejects + surfaces if it would exceed `maxCells`**; **growth** increments the target radius over the cycle; **death** frees the slot. These mirror the CPM §6.1/§11 post-MCS structural-event machinery. **The free-list + the per-step neighbour rebuild together absorb the dynamic count** — division just appends and the next step's rebuild re-bins; no mid-step structure surgery.

### 6.5 Mutation-handler coupling (a silent-corruption hazard)

The brush/paint/region mutation handlers (`paint` [sim.worker.ts:2500](../src/simulator/engine/sim.worker.ts), `paintManual` [:2591](../src/simulator/engine/sim.worker.ts), `importImage` [:3056](../src/simulator/engine/sim.worker.ts), `writeRegion` [:3327](../src/simulator/engine/sim.worker.ts), `clearRegion` [:3387](../src/simulator/engine/sim.worker.ts)) all map `(row,col) → idx` via `c.row*width + c.col` ([e.g. :2521](../src/simulator/engine/sim.worker.ts)) and write `readAttrs[id][idx]` — **site-addressed**, assuming a 2D grid brush. Two *distinct* center-based operations replace this, and they are **not** the same change: **(a) editing an existing agent** — *"select an agent at a continuous point"* (nearest-agent picking, the Graph-CA §8 picker) → the message envelope + worker-mutates-then-refreshes pattern survive, only `site→idx` becomes `point→agentId`; **(b) placing a NEW agent** — structurally different (it *grows* the population through the free-list), needing a **new `createAgent` worker message + a placement UI mode**, *not* a remap of the existing brush. The Manual-brush `encodeAttrValue` path sets attributes on *existing* cells and cannot birth one — so "place an agent" is closer to ➕new than ✏️modify. After any agent mutation the driver refreshes the display (a force-free render pass or the next step) — the existing refresh-after-mutation discipline applies.

### 6.6 Indicators (reuse the reduction PATTERN, re-point the bound)

`computeLinkedIndicatorsFromBuffer` ([sim.worker.ts:1976](../src/simulator/engine/sim.worker.ts)) bins per-site arrays via `for i < total`. The frequency/total binning logic is substrate-agnostic and **reusable as the template for per-agent reductions** (count agents by type, total mass, mean radius). **The bound subtlety (a correctness trap):** because the free-list leaves *holes* (dead slots interleaved with live ones), the reduction must iterate `0..highWater` and **consult the same alive-mask** the driver loops use (`if !alive[i] continue`) — **not** a dense `for i < liveAgentCount` (that reads the first `liveAgentCount` *slots*, including dead holes, and misses live agents past a hole). `liveAgentCount` is the display tally, not the loop bound — the free-list's sparsity is exactly why "re-point the bound to the live count" is subtly wrong. Spatial (rows/columns) indicators have no clean meaning over continuous positions (or could be re-interpreted as position-binned histograms — a later option).

### 6.7 Initial seeding (a v1 *blocker* — there is no lattice to randomize or paint)

The headline demo cannot start without a population, and **every existing seeding path is per-site**: `reset`/`randomize` fill the per-site SoA arrays, and `InitEvent` exposes *integer lattice* `x`/`y`/`maxX`/`maxY` ([InitEventNode.ts:24-27](../src/modeler/vpl/nodes/InitEventNode.ts)) — none of which births a continuous-position agent. Center-based therefore needs a **new seeding primitive**, and it is a **Phase-1 deliverable, not a footnote** (its own Impact-Map row, §11 #49):
- **A `seedAgents` worker message** that allocates the initial live agents into the per-agent SoA + free-list and sets `highWater`/`liveAgentCount`. v1 modes: **(i)** place `N` agents **uniformly / Poisson-disc** in the world bounds; **(ii)** **lattice-then-perturb** (seed a hex/square packing in a region, jitter positions) — the standard center-based initial condition; **(iii)** **from an image/region** (one agent per occupied pixel, optionally typed by colour, reusing the colour→attribute mapping).
- **A re-purposed `InitEvent`** (or a sibling `SeedEvent`) whose outputs are the **continuous spawn position + per-agent attribute writes**, run once per seeded agent — the procedural-seeding analogue of today's per-cell Init Event.
- **A Structure-panel seeding UI** (count, region/world-bounds, packing, per-type fractions) replacing the W×H field.

Without it Phase 2 has nothing to simulate — which is why it is called out as a blocker rather than folded into "swaps W×H for a seeding spec."

## 7. Compiler — the force/behaviour step on all three targets

### 7.1 The force/behaviour event root

Compile a **new force/behaviour event root** (sibling to `Step`/`InitEvent`, the way the compilers already emit a separate `init` entry). Its compiled function takes the agent index `i`, the worker-supplied dynamic neighbour list (`candIdx[]` + per-agent `start/len`), the position arrays, model attributes, and lookup tables, and produces: the agent's **net force vector** (summed over neighbours) and its **behaviour decisions** (a `shouldDivide`/`shouldDie`/`differentiate` flag set + cycle update). The existing value-node library covers the math:
- **Pairwise force (the part that is genuinely *new* emit, not reuse — corrected).** A mechanical force is a **vector** `Σⱼ F(dᵢⱼ)·r̂ᵢⱼ`, so the per-neighbour loop body must: (i) read the *other* agent's continuous position via a **new `GetNeighborPosition`** node — the existing `GetNeighborsAttribute` reads one *scalar* attribute at a *lattice* neighbour index ([GetNeighborsAttributeNode.ts:24-31](../src/modeler/vpl/nodes/GetNeighborsAttributeNode.ts)) and **cannot** supply an `(x,y[,z])` pair; (ii) compute `Δ = xⱼ − xᵢ`, `d = ‖Δ‖`, `r̂ = Δ/d`; (iii) evaluate the **scalar force magnitude** `F(d)` via the piecewise repulsion-then-adhesion curve (`Compare`/`Statement` for the rest-length break + `Interpolation`/`arithmeticOperator` per branch — ***this*** part is genuine reuse of the existing value nodes, the same shape as `ColorScale`/`Interpolation`); and (iv) accumulate **two/three component streams** `Σ F(d)·r̂ₓ`, `Σ F(d)·r̂ᵧ` (and `·r̂_z` in 3D). That accumulation is a **vector reduction — NOT** the scalar `Aggregate(Sum)` (one scalar array → one scalar, [AggregateNode.ts:10-11](../src/modeler/vpl/nodes/AggregateNode.ts)) — so it is **new neighbour-emit on all three targets**, layered on the *same variable-degree neighbour-loop machinery* the Graph-CA finding prescribes (Graph-CA §2.2/§6). The degree-tolerance carries over; the vector-valued body and the neighbour-position read do not.
- **Migration / Langevin:** add a `GetRandom`-driven noise vector + a bias term into the same force sum.
- **Behaviour:** `Compare` the cycle phase / local density / sampled field value to a threshold → a `DivideCell`/`SetCellType`/`SetTargetRadius` flow node.

The compiler change vs the current emit is bounded: **(a) the loop body iterates agents** (read `position[i]` from a position array, not decode `(row,col)` from `idx`; write a force/velocity, not an `idx*4` color quad — the color write moves to a separate render/Output-Mapping pass keyed by agent id); **(b) the neighbour iteration becomes variable-degree** (data-dependent bound `start[i]..start[i]+len[i]` over `candIdx[]`, the Graph-CA §6 stride→offset emit, with scratch sized to `maxDegree`); **(c) the force-vector reduction + `GetNeighborPosition` read are new emit targets** (per the bullet above). The **per-pair scalar-magnitude math, the RNG, and the `lookupTable` emit are reused verbatim**; the **vector reduction over components and the neighbour-position read are the new emit** — that is the precise, calibrated boundary between reuse and new work on all three targets.

### 7.2 New nodes for the agent tier

`GetSelfPosition`/`GetNeighborPosition` (continuous coords), `GetNeighborDistance`, `GetRadius`/`SetTargetRadius`, a **force-law node** (a parameterised repulsion+adhesion curve — or built-in terms the user composes), `DivideCell`/`SetCellType`/`KillCell` flow nodes, and `GetDegree`/`NeighborDensity` (the Graph-CA variable-degree nodes). The force/behaviour root exposes the agent's continuous position (analogous to how `InitEvent` exposes x/y, [InitEventNode.ts](../src/modeler/vpl/nodes/InitEventNode.ts), unlike `Step` which exposes only `do`).

**Custom-force-contribution node — compile shape (resolving the vector-output problem).** A user-authored per-pair force term outputs a **signed scalar magnitude `F(d)`** (positive = repulsion along `+r̂`, negative = adhesion along `−r̂`), evaluated *inside* the neighbour loop with the neighbour's distance/radii/type as inputs; the **engine/emit owns the direction** — it multiplies the user's scalar by the engine-computed `r̂` and accumulates the component streams. Keeping the user-facing node **scalar-valued** means custom force laws reuse the existing scalar value-emitters unchanged and only the engine's fixed vector reduction is new — the cleanest split, and the reason the force-authoring surface is *not* as hard as a true vector-output node would be. (A built-in term is the same contract with a fixed curve.)

### 7.3 WebGPU — a STRONG fit (the inverse of CPM; hard fit question #7)

Unlike CPM (gated off WebGPU because accept/reject is sequential), **center-based is a strong WebGPU target.** The force pass is one thread per agent, each gathering its neighbours and summing forces — no write contention. The WebGPU pipeline is the proven ya||a/NVIDIA-particles design (§2.7): hash position → cube id, GPU radix-sort by cube id, prefix-scan per-cube offsets, gather kernel over the 27-cube stencil. **The variable-output structural events (division/death) stay on the worker/CPU side** via an over-allocated buffer + append/compaction pass — *not* dynamic agent creation inside the per-agent kernel (the universal GPU center-based pattern). The per-cell **PCG RNG** (useless for CPM's sequential stream) is *natural* here. Positions co-located in the attrs buffer are *expected* to ride the existing attrsRead/attrsWrite ping-pong (double-buffering positions) — but, as §2.7 notes, reconciling that fixed-`total` ping-pong with the dynamic count + worker-side compaction is an unverified Phase-5 detail, not a settled "for free." **WebGPU is deferred to a later wave for sequencing (JS/WASM correctness first), not feasibility** — and the three-target compiler-lockstep rule applies as the wave lands.

### 7.4 RNG & determinism

JS/WASM share the xorshift32 stream (`_rngState[0]`, [GetRandomNode.ts:32-34](../src/modeler/vpl/nodes/GetRandomNode.ts)) — a single sequential stream maps cleanly onto the sequential per-agent loop (daughter placement, motility, noise). WebGPU's per-cell PCG fits the *parallel* force kernel. Document center-based as intrinsically stochastic; WGSL f32 + per-cell PCG diverge from JS/WASM f64 over many generations on this chaotic system (exactly the Gray-Scott tradeoff already accepted) — **validate statistically (spheroid radius, sorting metric, rim thickness), not bit-exact.**

## 8. Node set & capability gating

**New center-based nodes** (`requirements.centerBased`): the force/behaviour event root; `GetSelfPosition`/`GetNeighborPosition`/`GetNeighborDistance`; the parameterised force-law node (repulsion+adhesion); `GetRadius`/`SetTargetRadius`; `DivideCell`/`SetCellType`/`KillCell` flow nodes; `GetDegree`/`NeighborDensity`; (Phase 5) `SecreteToField`/`SampleField`.

**Reused (per-pair scalar math + the neighbour-loop machinery):** the variable-degree neighbour iteration (`GetNeighborsAttribute`'s loop shape, bound to the `r_max` set), `lookupInteraction` (the adhesion matrix), `GetRandom`, `arithmeticOperator`/`Compare`/`Interpolation` (the scalar force-*magnitude* curve `F(d)`), the whole value-emitter library. **New, NOT reused (corrected — see §7.1):** the **vector force reduction** `Σ F(d)·r̂` (a 2-/3-component accumulate, *not* the scalar `Aggregate`, [AggregateNode.ts:10-11](../src/modeler/vpl/nodes/AggregateNode.ts)) and **`GetNeighborPosition`** (the neighbour's continuous coords, which `GetNeighborsAttribute` cannot supply).

**Gated off in center-based mode** (`requirements.lattice` — a new flag, the mirror of `requirements.centerBased`): all offset/position/tag-slot nodes (`GetNeighborAttributeByIndex` offset form, `NeighborIndexFromOffset`, `BreakDownNeighborIndex`, `FlipNeighborIndex`, `GetNeighborAttributeByTag`), the **entire variegated-cells/orientation/facing subsystem** (4-fold rotation + N/E/S/W faces are square-lattice-only), and **spatial (rows/columns) indicators** (no lattice axes).

**The gate is a near-mechanical clone of the `variegated?` flag.** Add `centerBased?: boolean` (and `lattice?: boolean`) to `NodeRequirements` ([vpl/types.ts:79-80](../src/modeler/vpl/types.ts)); `detectCapabilityRequirements` + `isNodeAvailable` ([nodeValidation.ts:447-462](../src/modeler/vpl/nodes/nodeValidation.ts)) drive palette / Add-Node menu / connection-drop filtering + the amber CaNode badge; the compiler reads `def.requirements.centerBased` directly. WebGPU is *not* auto-rejected here (it is a *good* fit) — but it is gated to a later wave, so a model-level "center-based on WebGPU is Phase 5" check + the worker mutual-exclusion safety net (mirror the `useWasm`/`useWebGPU` net, [sim.worker.ts:2390-2399](../src/simulator/engine/sim.worker.ts)) enforce the sequencing on hand-edited `.gcaproj` files.

**Force/behaviour authoring surface (hard fit question #4) — recommendation: built-in-terms-first + a custom force root** (the CPM §12 analogue). Ship the canonical force laws (GLS, piecewise-quadratic, cubic) as **built-in parameterised terms** for the zero-friction path *and* expose the force root so advanced users add custom pairwise-force-contribution nodes the driver sums. This mirrors the Linked-Output-Mappings "auto + override" philosophy and matches GenesisCA's accessibility goal without capping power. CBMOS shows force-law choice materially changes emergent geometry, so making it selectable (with sane GLS default — the most permissive timestep) is not a gimmick.

## 9. Visualization — the entity renderer (the Graph-CA renderer problem)

**This is the Graph-CA rendering problem, NOT the CPM one** (the brief is correct). The split is clean, and Graph-CA §8 already designed it:

**Reused (the index-keyed contract carries over):** the worker's per-agent `colors` buffer is **one RGBA per agent index** ([colorsRef ← msg.colors, SimulatorView.tsx:1196](../src/simulator/SimulatorView.tsx)) — an agent's colour is the same buffer slot the renderer reads, so the **`colors` buffer→pixels *render* contract reuses with zero change**. **But the *compiled* Output-Mapping colour pass that FILLS that buffer is itself a per-cell loop baking lattice geometry** (`colorIdx = idx*4` over `total`, [compile.ts:1748-1752](../src/modeler/vpl/compiler/compile.ts)) — so it needs the **same agent-iteration rework as the Step body** (§7.1; Impact #19/#30). "Zero change" is true of the *buffer*, not of the *pass that writes it*. The `cellIdx`-keyed inspect/paint worker protocol, the screen-space cursor-anchored pan/zoom (`zoomRef`/`panRef`, wheel/drag-pan, [SimulatorView.tsx:2583,2871](../src/simulator/SimulatorView.tsx)), and the screenshot-from-display-canvas path ([SimulatorView.tsx:3244-3252](../src/simulator/SimulatorView.tsx)) all carry over using the agent's array index as the key.

**Replaced (a localized main-thread 2D-geometry cluster):**

|---|---|
| `new ImageData(colors, w, h)` + one `drawImage` ([:780-784,906-925](../src/simulator/SimulatorView.tsx)) | per-**agent** filled-circle at continuous position, radius ∝ size; **instanced/point renderer** at scale |

| geometric brush stamp (`brushShapeOffsets`/`lineStampCells`/Bresenham/silhouette, [:50-134](../src/simulator/SimulatorView.tsx)) | **agent selection / placement** (click nearest / lasso) |

**New render work with no lattice precedent (additive):** nearest-centre or GPU-id picking; **force/velocity vector overlay** (an arrow-glyph primitive — no vector/path primitive exists today; only uniform gridlines + the brush silhouette stroke edges); **lineage/centroid tracks** (polylines, needs per-agent lineage recording — cheap to capture: parent id + birth time per agent, enabling clone-colouring and later Muller/LinG3D-style views without re-running); and the **microenvironment heatmap underlay** — the one exception, a second composited blit *under* the agents that **reuses the existing glyph-fallback double-blit pattern** ([SimulatorView.tsx:877-903](../src/simulator/SimulatorView.tsx)).

**Positions are the new first-class render input the lattice never needed** (a lattice cell's position is implicit in its index): continuous `(x,y[,z])` per agent must ship worker→main-thread **every frame alongside colours** (positions update each step via physics, unlike Graph-CA's static cached layout). This makes the **"colours+positions on the main thread every frame disables the WebGPU/OffscreenCanvas direct-render color-skip"** perf note (Graph-CA §8.4) even more binding — budget an **instanced GPU point/circle renderer or viewport culling from the start**; a naive per-agent Canvas2D fill loop is orders slower at large N.

**3D is a wholesale new WebGL renderer.** Zero WebGL/Three.js exists today (Canvas2D is hard-wired, [SimulatorView.tsx:754](../src/simulator/SimulatorView.tsx)) — 3D instanced-sphere rendering is from-scratch behind the same index-keyed `colors`+positions contract (the WebGPU OffscreenCanvas direct-render seam, [SimulatorView.tsx:1466-1519](../src/simulator/SimulatorView.tsx), proves an alternate renderer can sit there). **"3D is easy" is true of the engine (the force law gains a z), NOT the renderer** — the CPM §9 caveat verbatim.

**Recording** must move from grid-resolution `ImageData` capture ([:1318-1331](../src/simulator/SimulatorView.tsx)) to **display-canvas capture** (no `w×h` source bitmap exists — Graph-CA Impact row 23); the screenshot path ([:3244-3252](../src/simulator/SimulatorView.tsx)) already reads the display canvas and is the template.

## 12. Phased plan (if it were built)

Sequenced so the headline demo — **2D adhesion-driven sorting + division of soft spheres** — lands early; it is genuinely easier and more visually compelling than CPM's. **Currently parked at "research only."**

- **Phase 0 — decisions.** Confirm the hybrid (compiler-leaning) driver, `maxCells` ceiling + free-list, mode flag = `centerBased.enabled` (single source of truth), JS/WASM-first, the §13 hazard contracts, and the engine-agnostic-IR commitment (§3.2).
- **Phase 1 — data model + per-agent tier.** `centerBased` config sub-object; per-agent SoA arrays + free-list in the worker; bounded force-law/`Δt`/`η` model attributes; the type×type adhesion matrix via `lookupTable`; serialization (agent table + free-list) + reinit guard.
- **Phase 2 — force-integration driver + repulsion+adhesion force graph (JS) + uniform-grid neighbours. ★ headline: 2D cell sorting + division.** All-pairs `O(N²)` *or* a first uniform-grid rebuild; overdamped forward Euler with the `Δt` stability guard from the start (post-division overshoot is the hazard); the force/behaviour event root + force-law + DivideCell nodes; a `drawAgents()` circle renderer with nearest-centre picking; colour-by-type. The unambiguous demo: two adhesive types sort into separated domains while a few cells divide into a relaxing cluster.
- **Phase 3 — WASM target + second-order integrator + entity-renderer polish.** Port the driver + force kernel + neighbour-bin to WASM; **promote the agent arrays to the baked `wasmMemory` region** (§5.1); add the midpoint/Adams-Bashforth option (~4-5× larger `Δt`); force/velocity vector overlay; lineage tracking + clone-colouring.
- **Phase 4 — growth + death + richer phenotype + Verlet skin.** `SetTargetRadius` growth, `KillCell` death (free-list recycle), cell-cycle phenotype rules; a Verlet skin to cut rebuild frequency; instanced point renderer + viewport culling for scale.
- **Phase 5 — WebGPU + chemical microenvironment.** The WebGPU force kernel (hash→sort→offset→gather, the strong GPU fit) with worker-side division/compaction; a reaction-diffusion coarse field (clamped-explicit K-substep diffusion, reusing Gray-Scott); secrete/sample nodes; chemotaxis + oxygen-limited growth → **emergent necrotic cores** (validate vs Drasdo/Höhme + Macklin 2012 spheroid compartmentalization); field heatmap overlay.
- **Phase 6 — 3D.** A dimensionality switch for the engine (force law + neighbour bin + daughter-plane gain a z — *incremental*) + a **wholesale new WebGL/WebGPU instanced-sphere renderer** behind the `draw()`/`colors`+positions seam.

Validate each phase against the canonical models as built-in examples (Meineke crypt, Drasdo/Höhme 2D-monolayer→3D-spheroid, Galle regulated epithelium) — published, parametrized rule sets that prove the OS mode and give users a correct starting graph, exactly as the current CA library does. Validation is **statistical** (sorting metric, spheroid radius, rim thickness), not bit-exact (WGSL f32 + per-cell RNG preclude cross-target parity).

## 13. Risks, open questions & decisions to confirm

### 13.1 Silent-corruption hazards (decide up front — they fail *quietly*)
1. **`maxCells` lifecycle.** The per-agent arrays are sized once. A stale `maxCells` after division births past the ceiling → overflow / wrong agent corrupted. Make it derived-on-change, re-uploaded, re-baked into the WASM layout, and add it to the `attrsStructurallyEqual` reinit guard ([SimulatorView.tsx:1916-1930](../src/simulator/SimulatorView.tsx)). A division that would exceed `maxCells` is **rejected + surfaced** (Stop-Event channel), never wrapped — the Amphiphile-NI-poisoning class.
2. **Timestep stability/monotonicity.** A "stable" but too-large `Δt` after division silently corrupts geometry (drift, not crash). Implement the Mathias-2020 monotonicity guard (`Δt*_mono = ½(r₀−s)/F(r₀)`) and surface `Δt` prominently; default GLS (most permissive) + a second-order option. **Concrete defaults + auto-clamp are in §6.3** (`Δt ← min(Δt_user, 0.4·Δt*_mono)`, `s=1`, `r_max≈1.5`, `η=1`) — the default *is* the guard.
3. **`ATTR_TYPE_MAP` omission.** Pure-float agent state is safe (`float64` registered); any non-float agent/free-list array kind missing from `ATTR_TYPE_MAP` ([fileOperations.ts:383-386](../src/model/fileOperations.ts)) silently mislabels to `'float64'` and corrupts the round-trip — register at the same commit (CPM §12.2).
4. **`.gcastate` validation.** `applySimulationState` validates W×H today and computes `total = width*height` ([SimulatorView.tsx:3484,3502](../src/simulator/SimulatorView.tsx)); a center-based snapshot has an agent count + maxCells + free-list — mismatches must be rejected **loudly** (no try/catch around deserialize → a throw silently aborts the whole load; CPM §12.3).
5. **Single source of truth for the mode.** Drive everything off `centerBased.enabled`; leave `topology` derived/display-only; add the worker mutual-exclusion net (center-based forces sync; ⊥ WebGPU until Phase 5) for hand-edited files.
6. **Sync, not async.** Center-based double-buffers **positions** and does **not** use `orderArray` (§4) — do not import CPM's async single-buffer model; that is the wrong buffering for a synchronous force-sum-then-step.
7. **Neighbour-scratch overflow under compression.** OS cells gain *more* neighbours when a cluster packs tight (§2.1/§6.2), so a fixed compile-time `maxDegree` scratch can overflow **silently at exactly the high-density moment**. Size generously + a runtime clamp/warning, never a bare fixed stride — the NI-poisoning hazard class.

### 13.2 Open questions for the user
- **Substrate confirmation (§3).** With both analyses in hand: is the priority the **fastest morphogenetic demo on the existing stack** (CPM-first) or **matching the division-heavy/3D/rich-phenotype/GPU-native end-state** (center-based-first)? Both recommend the **same shared engine-agnostic IR** so the second engine is additive — confirm the IR commitment regardless of order.
- **Neighbour structure.** Overlapping-spheres + uniform-grid `r_max` (recommended v1) vs deferring a Voronoi/Delaunay "mechanical-contact" mode (later). Confirm OS-first.
- **All-pairs vs grid for v1.** Build the all-pairs `O(N²)` JS "Debug/Reference" path first (easy to verify, fine for thousands of cells) + the grid path as the WASM/WebGPU performance target — the CBMOS-validated split. Confirm.
- **Force authoring surface (§8).** Built-in force laws with parameters (GLS/piecewise/cubic) + a custom force-contribution root (recommended hybrid), vs fixed laws. Confirm.
- **Microenvironment (reaction-diffusion).** Out of headline v1, first post-MVP (Phase 5) — closer to must-have than CPM but a whole new subsystem. Confirm in/out.
- **Scope of v1.** Sorting-only spike (Phases 0–2) vs commit through division (in Phase 2) and death/growth (Phase 4). Division is the morphogenesis payoff *and* trivial here — recommendation: include it in the headline.

## 14. Verified bibliography (annotated)

**Confidence:** all anchor works confirmed against arXiv / DOI / PubMed / publisher. Caveats in §2.8 (a no-browser-engine negative-existence claim marked uncertain; ya||a pipeline phrasing + Chaste BoxCollection internals not re-confirmable verbatim; two author bylines fabricated-then-corrected — both papers real).

**Foundations & reviews**
- **Meineke, Potten & Loeffler (2001)** Cell migration and organization in the intestinal crypt using a lattice-free model. *Cell Proliferation* 34(4):253–266. — *The founding Voronoi/Delaunay cell-centre model (overdamped springs along Delaunay edges, Voronoi cell boundaries).*
- **Drasdo & Höhme (2005)** A single-cell-based model of tumor growth in vitro: monolayers and spheroids. *Phys. Biol.* 2(3):133–147. doi:10.1088/1478-3975/2/3/001. — *The founding overlapping-spheres lineage (Hertz/JKR contact, overdamped Langevin; 2D monolayer + 3D spheroid).*
- **Galle, Loeffler & Drasdo (2005)** Modeling the effect of deregulated proliferation and apoptosis on epithelial cell-population growth. *Biophys. J.* 88(1):62–75. — *3D OS model with regulated growth (contact inhibition, substrate-arrest, anoikis).*
- **Van Liedekerke, Palm, Jagiella & Drasdo (2015)** Simulating tissue mechanics with agent-based models. *Comput. Particle Mech.* 2(4):401–444. doi:10.1007/s40571-015-0082-3. — *The canonical taxonomy: lattice (CA/LGCA/CPM) vs off-lattice (center-based/deformable/vertex) vs hybrid; force laws, neighbour methods, mechanics.*
- **Osborne, Fletcher, Pitt-Francis, Maini & Gavaghan (2017)** Comparing individual-based approaches to modelling the self-organization of multicellular tissues. *PLOS Comput. Biol.* 13(2):e1005387. — *The five-family head-to-head in Chaste; the OS vs VT neighbour definitions; OS-more-neighbours-under-compression; OS/VT local steady state vs CA/CP/VM engulfment.*

**Mechanics, forces & numerics**
- **Pathmanathan, Cooper, Fletcher, Mirams, Murray, Osborne, Pitt-Francis, Walter & Chapman (2009)** A computational study of discrete mechanical tissue models. *Phys. Biol.* 6(3):036001. — *Force-law comparison (linear vs GLS), OS vs Voronoi; tissue elastic-plastic in compression, brittle-elastic in tension.*
- **Mathias, Coulier, Bouchnita & Hellander (2020)** Impact of Force Function Formulations on the Numerical Simulation of Centre-Based Models. *Bull. Math. Biol.* 82(10):132. doi:10.1007/s11538-020-00810-2. — *The definitive numerics: stability bound `(r₀−s)/F(r₀)`, monotonicity = exactly half, stability-is-not-sufficient post-division, 4-5× for second-order solvers, relaxation-time matching.*
- **Mathias, Coulier & Hellander (2022)** CBMOS: a GPU-enabled Python framework for the numerical study of center-based models. *BMC Bioinformatics* 23:55. — *Pluggable force functions + ODE solvers; deliberate all-pairs `O(N²)` for vectorization; `s=1.0`, `rA=1.5`; ~10k cells GPU.*
- **Lötstedt & Mathias (2022)** Adaptive time integration of mechanical forces in center-based models. arXiv:2206.00339. — *Adaptive/multirate stepping; smaller steps in high-gradient regions (just after division) — removes manual `Δt` selection.*

**Cell behaviours, phenotype & the rules grammar**
- **Ghaffarizadeh, Heiland, Friedman, Mumenthaler & Macklin (2018)** PhysiCell: an open source physics-based cell simulator for 3-D multicellular systems. *PLOS Comput. Biol.* 14(2):e1005991. — *The reference center-based simulator: Phenotype (cycle/death/volume/mechanics/motility/secretion) + Cell_Functions; piecewise-quadratic force; three timescales; 10⁵–10⁶ cells; "does not model cell morphology."*
- **Johnson, Stein-O'Brien, Heiland, Kurtoglu, Bergman, Metzcar, Fertig, Macklin et al. (2023/2025)** Digitize your Biology! / Human interpretable grammar encodes multicellular systems biology models. bioRxiv 2023.09.17.557982 → *Cell* 188(17) 2025. — *The cell-behavior grammar ("In cell type T, signal S increases/decreases behavior B"); Hill/capped-linear response; the no-code rules layer.*
- **Heiland, Bergman, Lyons, Waldow, Cass, Rocha, Ruscone, Noël & Macklin (2024)** PhysiCell Studio: a graphical tool to make agent-based modeling more accessible. *GigaByte* gigabyte128. — *The dropdown-driven no-code GUI over PhysiCell — the accessibility precedent.*
- **Macklin, Edgerton, Thompson & Cristini (2012)** Patient-calibrated agent-based modelling of DCIS. *J. Theor. Biol.* 301:122–140. — *Oxygen-driven growth/death thresholds; emergent necrotic core + ~80 µm viable rim from `L = √(D/λ) ≈ 100 µm`.*

**Neighbour structure & data structures**
- **Dmitrenok, Drobnyy, Johard & Mazzara (2016)** Evaluation of spatial trees for simulation of biological tissue. arXiv:1611.03358. — *"Spatial search and reinsertion are frequently reported as the most expensive steps" (BioDynaMo prototype).*
- **Breitwieser et al. (2022)** BioDynaMo: a modular platform for high-performance agent-based simulation. *Bioinformatics* 38(2):453–460. — *Uniform-grid environment (27-box stencil, box size from the largest agent); ~10⁹ agents.*
- **Schaller & Meyer-Hermann (2005)** Kinetic and dynamic Delaunay tetrahedralizations in three dimensions. *Comput. Phys. Commun.* 162(1):9–23; and Delaunay-Object-Dynamics (2008). — *Incremental/kinetic Delaunay (move + local flip; local insert/delete on division/death); ~linear neighbour provider.*
- **Allen & Tildesley (2017)** Computer Simulation of Liquids, 2nd ed. OUP. — *The canonical source of the linked-cell (`O(N)`) and Verlet-list (skin + rebuild-on-displacement) algorithms.*

**Microenvironment / PDE**
- **Ghaffarizadeh, Friedman & Macklin (2016)** BioFVM: an efficient, parallelized diffusive transport solver for 3-D biological simulations. *Bioinformatics* 32(8):1256–1258. — *The diffusion solver PhysiCell uses: implicit operator-split + LOD/Thomas tridiagonal; stable for large `Δt`; linear in voxels/substrates/cells.*
- **Van Liedekerke, Neitsch, Johann et al. (2019)** A quantitative high-resolution computational mechanics cell model for growing and regenerating tissues. *Biomech. Model. Mechanobiol.* 19:189–220. — *The dense-packing caveat: pairwise center-based forces lack accuracy under compression (exclude many-body contributions).*

**Software, GPU & browser**
- **Germann, Marin-Riera & Sharpe (2019)** ya||a: GPU-Powered Spheroid Models for Mesenchyme and Epithelium. *Cell Systems* 8(3):261–266. doi:10.1016/j.cels.2019.02.007. — *Pairwise-only forces + spin-like polarities specifically to parallelize on the GPU (CUDA) — the WebGPU-fit blueprint.*
- **Sego, Sluka, Sauro & Glazier (2023)** Tissue Forge: Interactive biological and biophysics simulation environment. *PLOS Comput. Biol.* 19(10):e1010768. — *Interactive particle-based engine with a real-time Magnum/OpenGL renderer (native, not browser) — the interactive-CBM UX reference.*
- **Cooper, Baker, Bernabeu, Bordas … Osborne, Pitt-Francis, Maini & Gavaghan (2020)** Chaste: Cancer, Heart and Soft Tissue Environment. *J. Open Source Softw.* 5(47):1848. — *One `AbstractCellPopulation` API spanning CA/CPM/overlapping-spheres/Voronoi/vertex — the "swappable spatial engines" precedent.*
- **Wortel & Textor (2021)** Artistoo, a library to build, share, and explore simulations of cells and tissues in the web browser. *eLife* 10:e61288. — *The pure-JS browser existence proof — for **CPM + CA only**; explicitly **does not** support center-based/off-lattice models (the "no browser center-based engine" finding).*
- **Sütterlin, Kolb, Dickhaus, Jäger & Grabe (2013)** Bridging the scales: semantic integration of quantitative SBML in graphical multi-cellular models (EPISIM). *Bioinformatics* 29(2):223–229. — *A graphical multi-scale modelling platform — the closest precedent for node-graph-to-model in the agent-based space (Java desktop, not browser).*
- **Delile, Herrmann, Peyriéras & Doursat (2017)** MecaGen: a cell-based computational model of early embryogenesis coupling mechanical behaviour and gene regulation. *Nat. Commun.* 8:13929. — *Center-based (cubic force) embryogenesis coupling mechanics to gene-regulatory state — the "mechanics + genetics → morphogenesis" template.*
