1 Executive summary

CompuCell3D (CC3D) and GenesisCA aim at overlapping biology — tissue morphogenesis: adhesion, sorting, chemotaxis, division, chemical fields — but from fundamentally different engine paradigms. "Make GenesisCA simulate everything CC3D can" is not a feature or a milestone: it decomposes into three genuinely-new engines/tiers, a large energy-term library, and a scientific ecosystem, layered on plumbing GenesisCA already has.

The single most important framing: a surprisingly large fraction of CC3D's actual biology is already reachable through GenesisCA's shipped bond-graph agent engine — via a different (rigid-sphere, off-lattice) substrate. The irreducible CC3D-only core is just two things: (a) Cellular-Potts deformable-shape phenomenology (sorting/engulfment by surface tension, membrane fluctuation, compartmental cells) and (b) the subcellular SBML/ODE multiscale tier. Those two are the honest definition of "parity."

2 What CompuCell3D is

A mature (20+ year), open-source multiscale virtual-tissue framework built on the Cellular Potts Model. ~1,090 C++ core files, ~233 Python files, ~309 validated demo projects; it underpins a large literature (tumour growth, angiogenesis, somitogenesis, gastrulation, branching morphogenesis, immunology, tissue engineering).

2.1  The paradigm — the Cellular Potts Model Potts3D / metropolisFast

A biological cell is a connected domain of many lattice pixels sharing one cell-ID (medium = ID 0). The tissue evolves by Metropolis Monte-Carlo energy minimization: each of ~(sites) attempts per step, propose copying a random neighbour's cell-ID into a boundary pixel, and accept with probability min(1, exp(−ΔH/T)). The "temperature" T is a fluctuation amplitude that sets membrane jiggle / effective motility. There is no hard-coded Hamiltonian — ΔH is a sum over registered energy-term plugins. Parallelism is OpenMP checkerboard (CPU-only; the Potts core has no GPU path — GPU is reserved for the diffusion solvers).

2.3  The authoring workflow & ecosystem

  • A model is a project folder (.cc3d): declarative CC3DML XML (or a PyCoreSpecs Python spec) for the Potts params + energy plugins + PDE steppables + initializers, plus imperative Python "steppables" (start/step(mcs)/finish) — the open-ended escape hatch that can express anything.
  • Visualization: a Qt Player (VTK) renders cells by type/ID, cell/cluster borders, FPP link overlays, scalar-field heatmaps, vector fields, in 2D and full 3D, plus live plots.
  • Output: .vtk snapshots, PNG, PIF cell layouts, full restart/serialization (including pickled per-cell SBML state).
  • Batch/scans: template with {{vars}} + a JSON spec → the Cartesian product runs resumably across nodes; a headless CLI runs GUI-less on HPC.
CC3D's own limitations — relevant because they are exactly where GenesisCA is strong: Monte-Carlo "time" is not physical time; a single T couples adhesion + motility + roughness + effective size; the modified-Metropolis dynamics break detailed balance; CPM is the wrong tool for confluent epithelial sheet mechanics (vertex-model territory); and authoring is two-language desktop software (XML + Python, conda install) — a barrier for the non-programmer audience GenesisCA targets.

3 The substrate difference

GenesisCA's two engines bracket the Cellular Potts model but neither is it. Classic CA is below it (no extended cells); center-based agents are beside it (extended but rigid, off-lattice). CC3D's deformable-membrane phenomenology sits in the gap.

5 Where each is ahead

◤ GenesisCA is already ahead / different

  • Accessibility. Visual node graph, no code, zero-install browser — vs conda + XML + Python desktop. CC3D itself names non-programmers as underserved.
  • Multi-target performance for the cell engine: WASM default + WebGPU. CC3D's Potts core is CPU/OpenMP only.
  • Built-in experiment orchestration — the Overseer already does CC3D's parameter-scan job (sweeps, replicate stats, run-until-stop, export) inside the tool.
  • One-file shareable output — the presentation HTML export has no CC3D equivalent.
  • The agent engine's WebGPU fit — force summation is a near-ideal GPU dispatch; CPM's sequential accept/reject is not (why CC3D never GPU'd its Potts core).

◥ CompuCell3D is fundamentally ahead

  • The CPM deformable-cell substrate and everything that depends on shape: sorting/engulfment by surface tension, membrane fluctuation, precise volume/surface/length constraints, compartmental cells.
  • The subcellular ODE/SBML multiscale tier — a validated stiff ODE integrator per cell, SBML/Antimony import, Boolean networks. GenesisCA has nothing here.
  • The mature multi-field PDE suite — 13 solvers, per-type diffusion, secretion/uptake kinetics, per-face BCs, steady-state, adaptive stability.
  • The ecosystem — VTK/standard I/O, full reproducible restart, ~309 validated demos, decades of peer-reviewed models.
  • The Python escape hatch — arbitrary logic the declarative layer can't express. A node graph trades expressivity for accessibility.

6 Gap-closure roadmap

Seven workstreams. Effort is T-shirt-sized so that "the entire shipped agent-engine milestone" ≈ XL. This is a general draft — each workstream gets its own Impact Map + PLAN + HTML mockup before implementation.

WS-1The CPM engine (a third engine)XLpriority 1

A per-cell-ID accumulator tier (the agent object-store is the template) · a worker-side Metropolis driver (a 'cpm' update mode — the async single-buffer + orderArray machinery is structurally already the substrate) · a new ΔH "energy" event root (the graph computes one scalar ΔH per proposed copy) · a connectivity guard · membrane rendering + colour-by-ID. Fully pre-scoped in INVESTIGATION_CPM.md (~60–70% plumbing reusable; Artistoo is the in-browser-CPM proof). JS + WASM; WebGPU out of scope (sequential accept/reject).

WS-2The CPM energy-term library (plugins as nodes)Lpriority 1

Contact/adhesion → the existing N-D lookup table (no new type needed) · Volume/Surface/Length → λ·(x−target)² over the accumulators · Chemotaxis → −λ·Δfield · FocalPointPlasticity/Elasticity ≈ the agent bond system. The first five terms are the 80/20 that unlock most published models; the other ~28 plugins are incremental.

WS-3The PDE reaction-diffusion field solver suiteLpriority 2

You have the primitive (Gray-Scott + field bridge); missing is the parameterized abstraction: named multi-fields, per-cell-type diffusion & decay, secretion/uptake kinetics, per-face boundary conditions, steady-state, stability auto-scaling. WebGPU is an ideal fit (double-buffered field with halo = a ping-pong storage-buffer kernel) — the one place GenesisCA could out-perform CC3D.

WS-4The subcellular ODE / SBML tierXLpriority 3

Net-new; zero exists today. A per-cell stiff ODE integrator (RK4 baseline; CVODE-class for stiff circuits) + a reaction-authoring path — either an SBML/Antimony importer (reuse the huge existing corpus) or a node-graph reaction editor (on-brand, no parser) + coupling. Start with the smaller Boolean-network cousin to prove the "logic inside each cell" tier.

WS-5Cell lifecycle parity (division / differentiation / compartments)M–Lpriority 2

Division/growth/death already shipped for agents. CPM needs a pixel-set split along an orientation (part of WS-1's structural phase). Compartmentalized cells (clusters of sub-cells with internal-vs-external adhesion) are genuinely CC3D-only and net-new — lower priority.

WS-6The scientific ecosystemL (spread)priority 3

Parameter scans ≈ already shipped (Overseer). Add a VTK exporter (ParaView / CC3D interop) + PIF import/export, reproducible restart of a running experiment (RNG + ODE state), a ported validated-model library, and a constrained expression/script escape-hatch node (extend the Expression node — bounded expressivity without abandoning no-code).

WS-7Scale & performance parityMpriority 3

Mostly present (3D rendering, large grids, O(N) agents via spatial hash, WASM/WebGPU). The one CPM-specific item is an efficient boundary-edge sampler so the Metropolis loop isn't dominated by interior no-op attempts.

7 Strategic recommendation

Name the goal honestly. Literal parity = a CPM engine + a PDE field-solver suite + a subcellular ODE/SBML tier + compartmental cells + the ecosystem — a multi-year, multi-engine program, each of WS-1 and WS-4 comparable in scope to the entire bond-graph agent milestone that already shipped. CC3D is two decades and ~1M lines of specialized computational biology; feature-for-feature cloning is the wrong target.
  • Separate "reachable today" from "irreducible." Much of CC3D's applications — adhesion aggregation (qualitatively), chemotaxis, secretion/morphogen fields, division, mechanical links, 3D — is already expressible in the shipped agent engine. The irreducible CC3D-only core is exactly (a) CPM deformable-shape phenomenology and (b) the subcellular SBML/ODE tier.
  • Recommended sequencing: Phase A (CPM engine + 80/20 energy → 2D cell sorting) → Phase B (PDE suite on WebGPU + CPM division) → Phase C (subcellular tier, Boolean first) → Phase D (ecosystem + long tail).
  • Keep GenesisCA's identity as the differentiator. The winning move is not "reimplement CC3D in the browser" — it is "bring CC3D's biology into a zero-install, no-code, visually-authored, WASM/WebGPU-accelerated tool." A GenesisCA that runs a CPM sorting model and a chemotaxis model and a Delta-Notch multiscale model — as node graphs, in a browser, shareable as one HTML file — is a genuinely new point in the design space, not a clone.
  • Immediate next step (low-cost, high-value): port 3–5 canonical CC3D models to the existing agent engine (cell sorting, bacterium-macrophage chemotaxis, a growing-tissue/tumour model). This measures how far the current substrate reaches, surfaces the concrete gaps that most block real biology, and produces the credibility artefacts that would justify the CPM investment — turning this roadmap into an evidence-driven build order.
