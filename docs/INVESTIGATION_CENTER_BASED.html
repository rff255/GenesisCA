The finding that drives everything (and it is the opposite of CPM's): for the Cellular Potts Model, GenesisCA's defining trick — "compile the node graph to a per-cell step, call it once per generation" — broke (a per-site graph can't express a stochastic accept/reject chain). For center-based it largely holds: each agent independently sums its own neighbour forces and integrates its own position — a genuine, embarrassingly-parallel per-cell step, and a strong WebGPU fit. The honest nuance: "fits the paradigm" ≠ "free reuse of the current emit" — the compiled loop body bakes lattice geometry (colorIdx = idx*4, decode (row,col)), and the pairwise force is a vector sum Σ F(d)·r̂ that is genuinely new emit (not the scalar Aggregate). Recommendation: a hybrid that leans heavily on the per-cell compiler — a new worker-side force-integration driver owns the dynamic population, the per-step neighbour rebuild, and division/death; the node graph computes one agent's net force + behaviour.
Substrate verdict (completing the comparison with CPM): the user's goal is division + morphogenesis + rich per-cell rules + dynamic adjacency, ultimately in 3D. Center-based is the more direct match to that goal — division is trivial (append two agents), per-cell state is the richest of any family (PhysiCell Phenotype + Cell_Functions), adjacency is dynamic/distance-based by construction, 3D is a dimensionality switch. CPM is the lower-friction first build for this codebase (it keeps the lattice/blit/async ≈ 60–70% runtime reuse); center-based reuses less of the runtime substrate but fits the compile paradigm better and is GPU-native. Both recommend one shared engine-agnostic per-cell IR so the second engine is additive. Ceiling, stated bluntly: there is no cell shape (points + radius — wrong tool for folding epithelia / T1 intercalation = vertex territory); the post-division timestep is a silent geometric-corruption hazard; and no zero-install browser center-based engine exists (Artistoo is CPM/CA-only) — so this is novel territory, an engineering risk, not a research one.

01 There is no lattice — cells are points in continuous space

In GenesisCA today a "cell" is a grid site (its position is implicit in its index row·W+col). CPM keeps the lattice but spreads one cell over many sites. Center-based abandons the lattice entirely: a cell is a point xᵢ ∈ ℝ² (later ℝ³) with a radius — a soft sphere. total = W×H becomes a dynamic agent count that grows by division.

02 The dynamics are a pairwise force law, not a rule

Two cells interact through a repulsion-then-adhesion force over their centre-distance d: strong volume-exclusion repulsion when they overlap (d < s), weaker adhesion over a short contact range, and zero beyond the cutoff r_max. Differential adhesion (like-cells stick more) is all you need for sorting.

03 The overdamped step — sum forces, move

At cellular scales inertia is negligible (very low Reynolds number), so Newton's law collapses to a force balance: η·dxᵢ/dt = Σⱼ Fᵢⱼ. Integrated by forward Euler: xᵢ ← xᵢ + (Δt/η)·Σⱼ Fᵢⱼ. Every agent reads the frozen old positions and writes a new one — synchronous, double-buffered positions (NOT CPM's async single buffer).

04 Live demo — soft spheres that repel, adhere, sort & divide

A real 2D overlapping-spheres engine running in your browser: ~N soft cells of two types, integrated by overdamped forward Euler over a uniform-grid neighbour search, with a per-type adhesion matrix. Differential adhesion alone makes the two colours sort into separated domains; turn on division to watch the cluster grow. (This is the headline demo a Phase-2 implementation would target — easier and more visually compelling than CPM's.)

05 Dynamic adjacency — computed every step from positions

"Who is adjacent to whom" is derived from positions and re-derived every step as cells move and divide — the user's "dynamic spatiality/adjacency" requirement, delivered natively. The standard solution (from molecular dynamics) is a uniform grid / cell-list: bin the world into boxes of edge ≥ r_max, test only the home box + neighbours — O(N) at biological densities. This per-step rebuild is the single biggest genuinely-new runtime cost.

06 The agent object tier — the central new data structure

Per-agent state — continuous position, radius, type, arbitrary attributes, lineage, cycle phase — has no home in today's two-tier schema (per-site arrays / global scalars). This is the same per-cell-object tier the CPM investigation specified — but here it is the whole state. Stored SoA (one typed array per attribute, length maxCells) with a free-list that recycles dead slots on division/death.

07 Engine fit — a hybrid that leans on the per-cell compiler

The recommendation: a worker-side force-integration driver owns the population loop, the per-step neighbour rebuild, the position double-buffer, and division/death; the node graph computes one agent's net force + behaviour. This is a lighter hybrid than CPM's (which demoted the graph to a pure scalar) — but the force emit is genuinely new, not free reuse.

08 Substrate verdict — center-based vs CPM vs vertex

With both deep analyses in hand: there is no single winner — the families are complementary — but for the user's specific goal (division-heavy, rich-phenotype, eventually-3D populations where the interesting thing is the population, not each cell's shape), center-based is the better target, CPM is the better first build for this codebase, and one engine-agnostic IR should serve both.

When center-based wins

Division-heavy populations, rich per-cell phenotype logic, 3D, GPU scale, sorting/spheroid/crypt morphogenesis. It is the substrate the literature built for the user's goal.

When CPM wins

Fastest morphogenetic demo on the existing lattice/blit/async stack; deformable shape on a budget; the only family with a proven browser engine. CPM-first ships something sooner.

Center-based's ceiling (blunt)

No cell shape. Points + radius can't fold an epithelium, do T1 intercalation, or apical constriction — that is vertex/CPM territory. And the post-division Δt is a silent geometric-drift hazard.

The browser finding

No Artistoo-equivalent exists. Every center-based engine (PhysiCell, Chaste, CBMOS, ya||a, Tissue Forge) is native; their web stories are server-side cloud. A GenesisCA mode would be a first, not a me-too — engineering risk, not research risk.

10 Silent-corruption hazards — decide up front

Like the CPM and Graph-CA investigations, the dangerous failures are the ones that fail quietly — wrong geometry or stale state, not a crash. Four to pin down before any build.

① Timestep / monotonicity

A "stable" but too-large Δt after division (overlapping daughters → stiff forces → forward-Euler overshoot) silently corrupts geometry. The default is the guard: auto-clamp Δt ← min(Δt_user, 0.4·Δt*_mono), GLS force law, s=1, r_max≈1.5, η=1. (Mathias 2020.)

② maxCells lifecycle

The agent arrays are sized once. A stale maxCells after a division burst → overflow / wrong agent corrupted. Derived-on-change, re-baked into the WASM layout, in the reinit guard; overflow rejected + surfaced, never wrapped (the Amphiphile NI-poisoning class).

③ Neighbour-scratch overflow

OS cells gain more neighbours under compression — so a fixed compile-time maxDegree overflows exactly when a cluster packs tight. Size generously + a runtime clamp/warning, never a bare fixed stride.

④ Sync ≠ async & alive-mask

Center-based double-buffers positions and does not use orderArray — don't import CPM's async single-buffer model. And the free-list leaves holes, so every per-agent loop (force, behaviour, indicators) must consult an alive-mask, not a dense liveAgentCount bound.
