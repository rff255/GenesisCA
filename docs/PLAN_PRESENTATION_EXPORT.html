Presentation Export → standalone .html

Share the Simulator + one model as a single self-contained HTML file — no server, no install, no network. The web rewrite's replacement for legacy Genesis's standalone .exe export. plan runtime already fits

AWhy the runtime already fits

① No binary assets

WASM bytes & WGSL are generated in-JS from the model graph at load time and instantiated from memory. Nothing is fetched — WebAssembly.instantiate(bytes) works under file://.

② The file is the graph

A .gcaproj is plain JSON of the CAModel graph; code is recompiled at load. Embedding the model JSON alone is enough to run.

③ Simulator ⟂ Modeler

SimulatorView takes no data props — it reads ModelContext and auto-restores an embedded simulationState. The runtime is self-contained.

⚠ The one blocker

The worker is code-split (new Worker(new URL(…))). A single file must inline it — solved with Vite's ?worker&inline (base64 Blob worker).

One self-contained file — no folder. Sprites (dataUrl/frames), the thumbnail, presets, and the initial board (simulationState) are ALL already base64 inside the CAModel JSON, so the whole thing inlines into a single .html. And because that JSON is the complete model graph, the file is a dual artifact — it runs, and it's a recoverable model source (download the .gcaproj back, or load the .html into GenesisCA to edit). The model's nodes/logic are never lost.

BExport data-flow (runtime, in the running app)

The running app never stitches hashed chunks — it fetches a pre-built, fully-inlined template and injects one <script>.

CTwo builds: the app, and the viewer template

unchanged the main IDE build. new a second, tiny build with vite-plugin-singlefile that inlines everything (incl. the worker) into one HTML the app ships and fetches at export time.

FRisks & how they're handled

Inlined type:module worker under file:// — the highest risk. De-risked first in a throwaway PR0 spike across Chrome/Firefox/Safari before anything else is built; fallback is a classic worker.format:'iife' viewer build.

WebGPU under file:// graceful

May not init from a bare file — the worker already falls back to WASM/JS automatically. WASM from in-memory bytes is fine under file://.

File size toggle

Grid state (base64) can dominate (Elementary CA 1D ≈ 10.8 MB). "Include board state" defaults OFF past a threshold; dialog shows the estimate.

Template staleness version-stamp

The template is a build artifact — rebuilt by npm run build. A version marker surfaces a mismatch instead of silently exporting old runtime.

No COOP/COEP needed confirmed

Engine uses a non-shared WebAssembly.Memory + typed arrays — no SharedArrayBuffer, so no cross-origin-isolation headers (which file:// can't provide).
