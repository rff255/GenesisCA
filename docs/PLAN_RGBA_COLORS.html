RGBA colours — alpha through the colour-producer chain Illustrated companion to PLAN_RGBA_COLORS.md · precondition: IMPACT_MAP_RGBA_COLORS.md

1 · The premise, corrected

The engine is half RGBA-ready. The sink takes alpha; every producer upstream of it is RGB-only. Adding alpha to the pickers alone would produce a value with nowhere to flow.

The work runs sink-backwards: schema → producers (ports + emit × 5 compilers) → linked-OM wiring → then pickers.

2 · The invariant that makes this safe

Absent alpha ⇒ 255 ⇒ opaque ⇒ behaviour-identical.

Every alpha field is optional (a?: number); every parser defaults to 255 — exactly what setCellLooks' inline default already writes today. No .gcaproj migration. Same additive-optional discipline as coords3d, vectorDims, agentCapabilities.

3 · The load-bearing decision — how the a port avoids polluting every existing emit

A multi-output node emits all its ports together. An unconditional const _v<id>_a = 255; adds a dead line to every model with a linked float/integer OM — harmless at runtime, but it turns check-compile-identity.mjs red across ~10 models and burns the cheapest safety net we have.

4 · The pickers — one shared ColorField

First: can the native picker just do alpha? — measured, not assumed

No. <input type="color" alpha> is specced, but it is Safari 18.4+ only — 12.58% global support; Chrome ✗ through 150, Edge ✗, Firefox ✗ (caniuse). Probed live in a Chrome 148 renderer:

idlAlphaPresent: false
value = '#ff000080' → '#ff0000'   // silently TRUNCATED, no error
colorSpace IDL: ABSENT

It lights up in exactly the wrong browser. WebGPU and the Tauri shell are Chromium-bound (macOS/Linux Tauri uses WebKit → the simulator falls back to WASM/JS). Native alpha would work only where GenesisCA is least capable, and stay dark for the Chromium users who are the actual audience. A progressive-enhancement branch would give ~87% of users a different control and still require the fallback to be built — more code, worse consistency.

The better answer: one ColorField component, not an alpha box welded beside seven swatches. A checkerboard-backed swatch rendering the true rgba() composite, opening a popover with the native picker (RGB) + an alpha slider. Follows the existing BrushColorPopover.tsx precedent.

Seven bespoke picker layouts collapse to one — less code than the status quo — and the three divergent hex-helper pairs (including the 24-bit mask that silently corrupts 8-digit hex) collapse to one alpha-aware pair.

5 · ⚠ The highest-risk subsystem — the _a runtime slot

A colour model attribute is split into scalar slots. Adding _a appends a 4th — across six mirror sites that must agree exactly, or the baked offsets desync.

The library cannot test this. colorAttr = 0 across all 23 shipped models — no model has a colour attribute at all. The highest-risk subsystem has zero regression coverage from the library.

⇒ A synthetic model (scripts/test-rgba-colors.mjs) is mandatory, plus a new scripts/audit-modelattr-layout.mjs asserting all six sites agree — the model-attr split has no equivalent of the agent side's audit-agent-layout.mjs.

7 · Steps

  1. Schema + hex wideningRGB.a?, ColorStop.a?; parsers accept #rrggbb and #rrggbbaa. No behaviour change.
  2. The _a slot + a new layout audit ⚠ highest risk — all six mirror sites in one commit, with the synthetic test, because the library cannot cover it.
  3. JS node ports + emit (Option A)hiddenPorts gating; compile-identity on the representative 6 stays green.
  4. The four non-JS compilerslockstep; cross-target compile via the dev harness; parity-agent-wasm.mjs green.
  5. Linked OM conditional wiringcell + agent; 4th edge only when the palette carries non-255 alpha.
