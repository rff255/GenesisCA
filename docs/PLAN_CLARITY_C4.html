C4 — One Engine selector: Auto | WebAssembly | WebGPU (+ Debug JS)

Proposal item P1 · phase C4 · plan: PLAN_CLARITY_C4.md

The user declares an intent (Auto) or an engine. One pure function resolves the intent, and the radio, the compile paths, the compatibility readout, the chip and the worker all read that single answer.

1 · The radio — before / after

Before — two booleans, three peers

Properties › Execution
WebAssembly (default) Hand-compiled WASM module — typically several times faster than JS on dense neighborhoods.
WebGPU (sync only) WGSL compute shaders on the GPU — designed for very large grids…
Debug / Reference (JS) Plain JavaScript compile target. Slower but human-readable in Show Code…
Targets are mutually exclusive. Switching restarts the simulator.

Every model picks by hand. The library's own policy — “WebGPU where the gates pass, else WASM” — exists only in a docs paragraph and in 29 hand-set flags. JS looks like a peer.

After — an intent, resolved and shown

Properties › Execution
Auto → WebGPU
Auto (recommended) Picks the fastest engine this model can use, and re-picks as you edit.
Every WebGPU gate passes, so Auto picks the GPU.
WebAssembly Exact and seedable (f64, one shared stream) — bit-identical to the JS reference.
WebGPU sync only WGSL compute shaders. Statistical parity — f32 + per-cell RNG.
▸ Advanced

JS is one disclosure away, labelled for what it is. The badge is the resolution, never a promise — it is computed from the same gates that enforce it.

The mirror is not dead weight. useWasm/useWebGPU stay as the resolved representation every existing consumer already reads — the worker init message, both layout builders, the WebGPU/WASM node gates, the CaNode badge. That is what makes this phase byte-identical, and what lets an older build open a file written by the new one. The removal schedule lives in CLAUDE.md.
