Parameterized Input Mappings

An Input Mapping (C→A) declares its own named parameters instead of the hardcoded R/G/B. Each parameter becomes an output port on the mapping's event root and a type-adaptive widget in the brush panel. Cells and agents use the same machinery. A mapping with no declared parameters is the legacy colour mapping, byte-for-byte.

1 · The core model — a parameter has CHANNELS

One abstraction carries the whole design: the flat channel list is simultaneously the port list, the compiled argument list, and the paint payload. color → 3 channels; every other type → 1.

the legacy case, unchanged

A mapping with no declared parameters resolves to one color parameter whose channels are literally r, g, b:

ports   →  output_value_r · output_value_g · output_value_b   ← existing wires intact
JS ABI  →  (_r, _g, _b, idx, total, W, H, …)                  ← byte-identical
WASM    →  (i32 idx, i32 r, i32 g, i32 b)   TYPE_IDX_IDX_RGB  ← byte-identical
payload →  values: [r, g, b]
the sharp edge
parameters: undefined→ legacy colour
parameters: []→ deliberately none (a stamp)

They are different. Any parameters?.length ? … : legacy test mis-classifies the empty list. The distinction lives in one resolver (inputParamsOf) and nothing else may read the field.

5 · Image → cells: the channel→parameter step

Shown only when the chosen mapping declares parameters. A legacy mapping gets today's dialog, verbatim. imageMapping.ts is not touched — pixel sampling (average / invert / binarize) stays exactly where it is; the assignment is a consumer of its output.

Sources: Pixel R / G / B / A / luminance, or a Constant seeded from the brush panel's current value. Defaults: the first three channels take R/G/B, the rest take constants — so an unedited dialog reproduces the classic behaviour for a 3-channel mapping.

What binarize means now: it is still a pixel-space operation, so it is most useful through the luminance source — which is why lum is offered as a first-class source rather than making the user binarize and then read R. The binarize mask continues to serve the Manual path only.

6 · The paint payload — cells and agents become the same shape

before 
// cells — colour repeated on EVERY cell
{ type:'paint',
  cells:[{row,col,layer?, r,g,b}, …],
  mappingId, activeViewer }

// agents — colour at the message level
{ type:'paintAgentsColor',
  ids:[…], r,g,b, mappingId, activeViewer }

Two shapes for one idea. The per-cell colour is dead generality: all five producers read the same brushColorRef once per stroke, and there is exactly one type:'paint' producer in the codebase.

after 
{ type:'paint',
  cells:[{row,col,layer?}, …],
  mappingId, values:[40, 2, 1, 232, 161, 58], activeViewer }

{ type:'paintAgentsColor',
  ids:[…], mappingId, values:[…], activeViewer }

Legacy resolves to values:[r,g,b], so both handlers keep calling fn(...values, ...buildCellArgs(idx)) and wasmFn(idx, ...values) — the emitted code is untouched. Per-cell allocation shrinks.

7 · Where the code runs — three targets, two compiled surfaces

Code-reality finding: there is no WebGPU input-mapping shader. The WGSL emit produces step, init and outputMapping_<id> — nothing else. On the WebGPU target a paint reads attrs back, runs the JS function on the CPU, and patches the touched cells.

the highest-risk change

The WASM entry type is a module constant today:

TYPE_IDX_IDX_RGB = (i32, i32, i32, i32) → ()
paramOutputs = { r:1, g:2, b:3 }      // valtype hardcoded I32, at TWO sites

A parameterized entry mints (i32 idx, f64 ×N) per arity. A stale valtype: I32 does not crash — it reinterprets an f64 parameter's bits and writes deterministic garbage that looks like a modelling mistake. Only a value-asserting harness that runs a real instantiated WASM module and checks that 0.1 arrives as 0.1 catches it. Write that check first.

the safety net
29 shipped models→ parameters absent→ legacy branch→ zero diffs

check-compile-identity.mjs must be green at the end of every phase — not explained, not re-baselined. It is achievable by construction, so any diff is a bug.

Its converse also holds: the library proves nothing about the new path (no shipped model declares parameters), so a synthetic value-asserting harness plus a hand-authored fixture model are mandatory, not optional.

9 · Deferred to v2 (recorded, not planned)

  • Brush-geometry outputs — distance from brush centre, brush radius, normalized falloff as extra event-root outputs, enabling authored falloff. The centre and radius ride the message; the worker computes per-cell distance, so the payload never grows. Compatible with this design by construction: geometry outputs are a separate port group from declared parameters.
  • Image → agent-population initialization — spawn an agent per above-threshold pixel, its parameters fed by the same channel assignment built in Phase 3.
  • A vector parameter type — 2–3 channels, exactly like color.
  • Retire the cell WASM entry, making input mappings JS-on-CPU everywhere like the agent side. Blocked on the full-grid importImage cost.
  • Parameter presets — named value sets per mapping ("Predator brush", "Prey brush").
