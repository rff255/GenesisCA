The problem this fixes

# BEFORE — a false choice Collision ▾ [ Off · Soft-sphere · Positional ] ↑ both ran the SAME soft-sphere force. "Positional" was a label promising a hard solver that was never implemented.
# AFTER — two real behaviours Collision ▾ [ Off · Soft-sphere · Positional ] Positional Iterations [ 2 ] ↑ Soft = a springy repulsion force. Positional = a rigid no-overlap constraint. They now do genuinely different things.

Soft vs Positional — the difference, drawn

Soft-sphere force

A penalty force F = μ_R·(d−s) nudges overlapping agents apart. They can still overlap transiently; a stiffer μ_R only approaches non-penetration. Springy.

Positional constraint

After moving, overlapping pairs are projected apart to exactly touching — zero overlap. Rigid, like billiard balls (position-based dynamics).

Each sweep reads positions from the sweep's start and applies all corrections at once (Jacobi, order-independent) → identical on serial JS/WASM and parallel WebGPU. One pair resolves exactly in one sweep; dense packing converges over a few — hence the Positional Iterations knob. The correction reuses the dead forceX/Y/Z buffers, so no new per-agent memory.

Cross-target & safety

All three targets

  • JS — reference: resolvePositionalCollisions between the force loop and swapPositions (2D + 3D, hash + all-pairs).
  • WASM — a positionalPass export, one sweep per call; bit-parity with JS (f64 + host fmod wrap).
  • WebGPU — an accumulate + apply shader pair per sweep, reusing the force pass's hash + uniform; f32 statistical parity.

Byte-identical for existing models

  • No shipped model uses positional (inference only ever produces soft/off).
  • Soft repulsion re-gated on usesSoftCollision (= true for soft, false for off) — identical to the old gate for every shipped/legacy file.
  • The projection runs only for positional.
  • Verified by the byte-identity audit + parity-agent-wasm + a new positional combo in parity-agent-force + a real-GPU no-overlap check + an adversarial-review workflow.
