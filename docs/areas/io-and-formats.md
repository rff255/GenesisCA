## PWA / Offline Support (installable app + Tauri scaffold)

GenesisCA ships as an installable, offline-capable Progressive Web App (the main install path), with a Tauri v2 shell that builds a standalone portable native exe (no installer — for ad-hoc / USB sharing). Decisions + full subsystem analysis: [docs/IMPACT_MAP_PWA_INSTALL.md](docs/IMPACT_MAP_PWA_INSTALL.md) + [docs/PLAN_PWA_INSTALL.md](docs/PLAN_PWA_INSTALL.md) (illustrated mockup: `docs/PLAN_PWA_INSTALL.html`).

### Build wiring ([vite.config.ts](vite.config.ts))
- `vite-plugin-pwa@1.3.0` (Workbox 7), **`generateSW`** strategy — NOT a hand-written service worker (Workbox revisions the precache from the real build output, so Vite's content hashing can't desync it; a hand-written SW would break on every deploy). Registered LAST in the plugins array so the library plugins' `closeBundle` (`models`/`macros` `index.json` + `*.thumb.*`) runs before the SW precache glob.
- **Base-path is the load-bearing detail** (§B of the impact map). `const base = process.env.GHPAGES ? '/GenesisCA/' : '/'`. The production site is served at the ROOT of the custom domain **genesisca.online** (pinned by [public/CNAME](public/CNAME), which GitHub Pages serves at the apex root), so the deploy now builds with base `/` — [deploy.yml](.github/workflows/deploy.yml) NO LONGER sets `GHPAGES`. `GHPAGES` is an opt-in fallback that rebuilds under the `/GenesisCA/` subpath, needed ONLY if the custom domain is removed and the bare `rff255.github.io/GenesisCA/` project URL is used directly (with the domain set, that URL 301-redirects to genesisca.online). Everything else already used `/`: `npm run dev`, a local `npm run build` + `npm run preview` (both serve at `http://localhost:<port>/`), and the Tauri native shell (its webview loads `dist/` from `tauri://localhost/` at root; release.yml does NOT set GHPAGES). The manifest `id`/`start_url`/`scope` + every icon `src` are built from `base` (`buildManifest(base)`); `index.html` icon links use `%BASE_URL%`. (The `GHPAGES` flag itself replaced an earlier `command === 'build'` + `TAURI_ENV_PLATFORM` heuristic — it's explicit and keeps local preview painless.)
- **Precache EVERYTHING the app needs offline — the WHOLE library, not a lean shell** (user decision, 2026-08-10, reversing the earlier lean-precache policy). `globPatterns` precaches the app shell + `sim.worker` + icons + `viewer-template.html` (via the `.html` glob) + `models/index.json` + **`models/*.gcaproj`** + thumbnails + `macros/index.json` + macros: **79 manifest entries, ~48.8 MB** (models 26.4 · thumbnails 16.9 · shell js/css 3.2 · viewer-template 2.1). **The bug this fixed:** an installed PWA on a plane could not open a library model it had never opened before — models were runtime-cached ONLY, so nothing had populated the cache. The `StaleWhileRevalidate` rules are KEPT as a revalidating fallback, not as the offline mechanism. **The only runtime fetches of a public asset are `models/index.json`, `models/<file>.gcaproj`, `macros/index.json` and `viewer-template.html`** (`spriteRegistry`'s is a `data:` URL and the WebGPU compiler's `fetch` is a local variable name) — all four are precached, so grep for `fetch(` before adding an asset the app loads at runtime. **Overriding `globPatterns` REPLACES Workbox's default `**/*.{js,css,html}`** — the shell MUST be re-listed. `maximumFileSizeToCacheInBytes` (now **20 MB**) is a GUARD, not a filter: the build ERRORS on a glob-matched file above it rather than silently dropping it, which is exactly what you want if a future model outgrows the budget — resolve it deliberately (raise the cap / shrink the model), never by dropping a model out of the offline set. The `models/`+`macros/` globs are gated on `command === 'build'` — they only exist in `dist/`, not `dev-dist/`, so including them under `vite dev` makes Workbox warn "pattern doesn't match any files". (The shell glob `**/*.{js,css,html,…}` is always present and doesn't warn in dev.)
  - **VERIFYING OFFLINE NEEDS A SECOND PAGE LOAD, and the first attempt will mislead you.** Under `registerType: 'prompt'` Workbox sets **no `clientsClaim`**, so on the FIRST visit the SW installs + activates but does **not control that page** — every `fetch` goes straight to the network, so killing the server there makes *everything* fail (`index.html` included) and looks like a broken precache. Reload once (`navigator.serviceWorker.controller != null`), THEN kill the server. Also: `caches.match('/models/index.json')` returns nothing even when cached — precache keys carry a `__WB_REVISION__` search param, so match by iterating `cache.keys()` or pass `{ignoreSearch:true}`. And the precache holds **73 cache entries for 79 manifest entries** — duplicate cache keys, not missing files; diff manifest-vs-cache before concluding anything is absent.
- `devOptions: { enabled: true }`: the SW runs under `vite dev` too, so install / offline are testable straight from `npm run dev` at `http://localhost:5173/` — no `npm run preview` needed. (Combined with the build-only library globs above, dev is warning-free.)
- `registerType: 'prompt'` (NOT `autoUpdate`) **+ a user-confirmed update banner**: a new deploy's SW installs but WAITS, and **never force-reloads a live session**. `autoUpdate` was the earlier setting; it does `skipWaiting`+`clientsClaim`+a `controlling`→`window.location.reload()`, so every open tab self-refreshed a few seconds after load when a background deploy activated — wiping the user's open model mid-session (Pages redeploys on every master push, so users hit it constantly). **Do NOT switch back to `autoUpdate`** — the whole point is that the reload is a CLICK. App.tsx now passes **`onNeedRefresh`** (the earlier "no callbacks" posture left the user with no way to learn an update existed — reported: an installed PWA never offers one), which renders `styles.updateBanner`: *"A new version of GenesisCA is available"* + **Update** (`updateSW(true)` → skipWaiting + reload) + **Later** (dismiss; the waiting SW still applies on the next natural launch). When `isDirty` the banner appends *"save your model first, unsaved changes will be lost"* — the existing `beforeunload` guard is the hard backstop. `onOfflineReady` is deliberately still unused (the app ALWAYS works offline; announcing it is noise).
  - **The banner is NOT the `.toast`** — `.toast` is `pointer-events: none` and auto-dismisses in 3.5 s, both wrong for a prompt with buttons that must not be missed. `.updateBanner` is its own interactive, non-expiring element at `z-index: 1001`.
  - **Update CHECKS: `registerSW({immediate:true})` only checks on page load**, which is fine for a browser tab but not for an installed PWA left open for days — so `onRegisteredSW` adds a `SW_UPDATE_INTERVAL_MS` (1 h) `registration.update()` poll **plus a `visibilitychange`→visible check** (the moment a slept phone regains connectivity), both guarded on `navigator.onLine`. The interval + listener are torn down in the effect's cleanup.
  - **WEB-ONLY, structurally**: the whole `registerSW` block — callbacks and DEV hook — lives in the `else` of the `'__TAURI_INTERNALS__' in window` check, and `setUpdateReady` has no other caller, so the banner is unreachable in the Tauri shell (verified in the shipped bundle: the minified ternary is `"__TAURI_INTERNALS__" in window ? (unregister + clear caches) : registerSW({...onNeedRefresh...})`).
  - **DEV hook `window.__pwaTestNeedRefresh()`** flips the same state — `onNeedRefresh` only fires when a genuinely newer SW installs, which a dev server can't stage on demand. `import.meta.env.DEV`-gated, so it is absent from the production bundle (asserted).

### App wiring ([src/App.tsx](src/App.tsx))
- `registerSW({ immediate: true, onNeedRefresh, onRegisteredSW })` from `virtual:pwa-register` (types via `/// <reference types="vite-plugin-pwa/client" />` in [src/vite-env.d.ts](src/vite-env.d.ts)) — **registered on the WEB ONLY**; its return value is kept in `updateSWRef` so the banner's Update button can call `updateSW(true)`. See the `registerType: 'prompt'` bullet above for the banner + update-check design. The load-confirmation `showToast` (plain `string`, 3.5 s auto-dismiss) is unchanged and separate.
- **CRITICAL — never run the service worker in the Tauri native shell.** In WebView2 the SW caches the whole app into the webview's PERSISTENT profile and then serves that STALE copy on every launch, so a freshly-built exe shows the OLD UI / models / version no matter what it actually embeds (this caused the v1.19.x "stale exe" saga — the exe was always correct; the cached SW was overriding it; the web PWA was unaffected because browsers refresh SWs). So App.tsx's mount effect branches on `'__TAURI_INTERNALS__' in window`: **web** → `registerSW()` + `navigator.storage.persist()`; **native** → unregister any SW (`serviceWorker.getRegistrations().then(r=>r.unregister())`) + clear `caches`, and do NOT register. The native build embeds + serves its own assets, so it never needs a SW. **Debug aid:** if a machine already has the stale SW cached, the new exe alone can't always clear it (the old SW may serve the old bundle before the new code runs) — delete `%LOCALAPPDATA%\io.github.rff255.genesisca\EBWebView\Default\Service Worker` (kill lingering `msedgewebview2.exe` processes for that profile first, or the folder is locked) to break the loop once.
- `navigator.storage?.persist?.()` on mount — auto-granted once installed; protects the offline cache from LRU eviction. **Storage durability only — does NOT raise the memory ceiling** for large grids (renderer heap / WASM32 4 GiB address space). That ceiling is identical in the current Tauri shell (it wraps the same Chromium/WebView2 engine) — only moving the simulation to native Rust would raise it; the native build's real wins are storage/filesystem + a clean window, not compute.
- **Boot splash** ([index.html](index.html) → removed in [App.tsx](src/App.tsx)): a static `#splash` overlay (inline `<style>` + two-cell mark + wordmark + shimmer) painted the instant the page parses so there's no white-screen gap before React mounts; `html`/`body` are set to `#0c0d10` for the same reason (manifest `background_color` covers the OS-launch frame). App.tsx's mount effect adds `.splash-hide` then removes `#splash` after a ~350 ms fade. Pure static HTML/CSS (no bundle dep) — don't let the theme boot `<script>` clobber it. It self-removes, so to screenshot it, re-inject the markup via `preview_eval`.
- [InstallButton.tsx](src/components/InstallButton.tsx) (rendered last in the navbar RIGHT group): captures `beforeinstallprompt` (`preventDefault` + stash), renders the amber "⤓ Install" pill ONLY while installable, fires the native prompt on click, and self-hides on `appinstalled` (no toast — the button vanishing IS the feedback). The shared navbar icon-button style was lifted out of App.tsx to [navStyles.ts](src/components/navStyles.ts) (also used by the keyboard-shortcuts button).
- **No window-controls-overlay (evaluated + dropped).** WCO can't auto-hide the installed PWA's title bar — Chromium shows it by default and only adds a per-app "hide title bar" toggle the user must click (sticky per app). That fails the zero-effort bar, so the PWA stays plain `display: 'standalone'` (own window + icon, no tabs/address bar, but a thin browser title bar remains). The toggle-free clean native header is the **Tauri** build instead (its own OS window). Don't re-add `display_override: ['window-controls-overlay', …]` expecting an automatic clean header — it only surfaces that manual toggle. (The matching `@media (display-mode: window-controls-overlay)` CSS block was removed too.)

### Native shell ([src-tauri/](src-tauri/), Tauri v2)
- Wraps the same `dist/` in the OS webview; `npm run tauri build -- --no-bundle` → a **standalone portable `genesisca.exe`** (the Cargo package name, in `target/release/`) — NO installer. `bundle.active:false` in `tauri.conf.json` (installer bundling intentionally dropped — the PWA is the main install path; the exe is just for ad-hoc/USB sharing); `bundle.icon` is kept so the exe still embeds the GenesisCA icon. Also in `tauri.conf.json`: `frontendDist:'../dist'`, `beforeBuildCommand:'npm run build'`, identifier `io.github.rff255.genesisca`, and **`version:'../package.json'`** so the exe version always matches the web app — package.json is the single source of truth; do NOT hardcode a version in tauri.conf.json (it's no longer one of the version-bump touch points).
- **Release CI** ([.github/workflows/release.yml](.github/workflows/release.yml)): on every `v*` tag (or manual dispatch), `windows-latest` + Rust runs `npm run tauri build -- --no-bundle`, renames `target/release/*.exe` → `GenesisCA-<tag>.exe`, and publishes it to a GitHub Release via `softprops/action-gh-release` (NOT `tauri-action` — that uploads installer *bundles*, and we ship a raw exe). **The job runs a CLEAN build — NO `swatinem/rust-cache`** — on purpose: Tauri embeds the web frontend INTO the binary at compile time (`generate_context!`), so a restored `target/` cache can let cargo skip the recompile that re-embeds it and ship a STALE UI in the exe even when the source is current (the v1.19.0 build hit exactly this — correct source, stale embedded frontend; Pages is immune since it rebuilds `dist/` fresh). Releases are infrequent, so the extra compile time is worth the guarantee. Pages (`deploy.yml`) still deploys on every master push; since the version only bumps at release, the online app and the latest exe always report the same version. Download link for users: `https://github.com/rff255/GenesisCA/releases/latest` (unsigned → first run shows a SmartScreen "More info → Run anyway" prompt). The job needs repo **Settings → Actions → General → Workflow permissions = "Read and write"** so its `GITHUB_TOKEN` can create the Release (else it 403s). **Building needs the Rust toolchain (`rustup`)** + WebView2 (preinstalled Win10/11); the committed `src-tauri/Cargo.lock` carries the `alloc-stdlib` 0.2.2 pin that fixes a transient brotli build break (keep it). `src-tauri/target/` + `gen/` are gitignored; the rest is committed.
- **Native Save As — TEXT *and* BINARY (implemented):** in the Tauri shell the browser blob-download (`<a download>`) is silently dropped by WebView2, so **every** download must go through [fileOperations.ts](src/model/fileOperations.ts)'s `saveTextFile` **or `saveBinaryFile`** — both branch on `'__TAURI_INTERNALS__' in window` → `@tauri-apps/plugin-dialog` `save()` (real OS Save As dialog), else the historical blob download (which now lives in ONE private `browserDownload` helper — `grep -rn "\.download\s*=" src/` must return exactly that one site). App-defined commands need no ACL; the dialog plugin needs `dialog:default` in `capabilities/default.json` (+ `tauri-plugin-dialog` in Cargo.toml, `@tauri-apps/plugin-dialog` in package.json). Load still uses the browser `<input type=file>` (WebView2 opens the native picker natively).
  - **Text** → the `save_text_file` Rust command (`std::fs::write`). `downloadJSON`/`downloadHTML`/`downloadStateFile`/`downloadPresetFile` are `async → Promise<boolean>` (false = user cancelled → FileMenu skips `markSaved`). The standalone presentation `.html` rides this path (it's text), so it was never broken.
  - **Binary** → `saveBinaryFile(data, filename, mime?)`: a **CHUNKED** stream through `save_binary_begin` / `save_binary_chunk` / `save_binary_end` (+ `save_binary_abort`). **The chunk travels as the invoke RAW BODY (a top-level `Uint8Array`), never inside a JSON args object** — verified against the shipped Tauri 2.11 source, not assumed: [`process-ipc-message-fn.js`](file://~/.cargo/registry/src) sends a top-level `ArrayBuffer` view as an `application/octet-stream` fetch body and merges `options.headers`, whereas a `Uint8Array` **nested in a JSON arg** becomes `Array.from(val)` — a ~4× text inflation that would make a large recording pathological; `ipc/protocol.rs` maps octet-stream straight to `InvokeBody::Raw`, and Tauri's own `parse_invoke_request` test asserts the request headers survive. That's why the session token rides in the **`x-genesis-save-token` header** (the raw body leaves no room for a JSON arg) — and why it's a NUMBER: putting the destination PATH in a header would break on any non-ASCII character in it. **`NATIVE_CHUNK_BYTES = 8 MiB`** bounds peak memory on BOTH sides, so file size is limited by DISK, not RAM or any single-message IPC ceiling; the JS side slices the **Blob** per chunk rather than calling one `arrayBuffer()`, so a 1 GB recording never needs 1 GB of JS heap. **Measured throughput ≈ 30 MB/s** through the real WebView2 IPC (12.58 MB in ~0.4 s), i.e. a 500 MB recording takes ~17 s to write — acceptable, but do NOT shrink the chunk size without re-measuring.
  - **Cancel vs failure are distinguishable**: `saveBinaryFile` returns **false** on a cancelled Save As and **THROWS** on a real write error (which also `save_binary_abort`s, unlinking the partial file — a truncated `.webm` masquerading as a recording is worse than no file). `SimulatorView.triggerDownload` maps a throw to a toast; **`saveRecording` additionally toasts "Recording discarded — save was cancelled"**, because on THAT path (the Overseer's `review: false`) the encoder is already finished and the bytes are gone. A cancelled screenshot stays silent (nothing lost, trivially retaken). **From the UI a cancel loses nothing at all** — the capture review dialog still holds the blob and simply stays open (see the capture-cluster section); this toast is now reached only by the unattended path.
  - **The bug this fixed (2026-07-30):** only TEXT ever had a native path, so in the desktop build **recordings (.webm/.gif) and screenshots (.png) were written NOWHERE, silently** — the user's "the desktop installation must be able to record videos too". Two TEXT paths were broken the same way (they predate `saveTextFile` and never got routed through it): the **macro export** (`.gcamacro`, GraphEditor) and the **Overseer results export** (`.csv`/`.json`, ExperimentsPanel).
  - **Verification.** The Rust session logic is split out of the `#[tauri::command]` wrappers into `impl BinarySaves` so it is unit-testable — `cargo test` in `src-tauri/` runs 6 tests (in-order chunk concatenation, empty payload, **abort unlinks** [which only works on Windows because abort drops the `File` handle *before* `remove_file`], unknown/closed token erroring loudly, independent concurrent sessions, `begin()` truncating). The **IPC transport itself** is covered by a reusable native self-test: [src-tauri/ipctest/index.html](src-tauri/ipctest/index.html) is a stand-in frontend built via `npx tauri build --no-bundle --config src-tauri/ipctest.conf.json`; run the resulting exe **from a scratch dir** (artefacts are CWD-relative) and it drives the same invoke calls, then writes `genesisca_ipctest_result.json`. Measured on real WebView2: **12,582,912 bytes over 2 chunks arrive BYTE-IDENTICAL** (sha256 match against an independently regenerated pattern, clean 8 MiB chunk seam), abort unlinks, and a missing header / unknown token are both loud errors. **Rebuild the real app afterwards** — `generate_context!` embeds the frontend at compile time, so `target/release/` otherwise holds the test page. **STILL UNVERIFIED BY MACHINE:** the composition `save()` dialog → chosen path → chunked write *inside the real app* (the dialog needs a human click). Manual recipe: `npm run tauri build -- --no-bundle` → run `src-tauri/target/release/genesisca.exe` → load a model → Simulator → **⏺ Record** → Play a few seconds → **⏹ Stop** → the capture review dialog must appear with the clip playing → **Save…** → a Save As dialog must appear → save → the `.webm` must exist at the chosen path and play; repeat for **📷 Screenshot**; and cancel one recording save to confirm the "Recording discarded" toast.
- Remaining future escape from browser storage limits: move bulk `.gcaproj`/`.gcastate` storage onto `tauri-plugin-fs` (no quota). WebGPU is only guaranteed on the Windows WebView2/Chromium build; macOS/Linux Tauri use WebKit → the simulator falls back to the WASM/JS targets.

## CSV Import — agents from rows, or the CA grid from a table (branch `improvements`, 2026-07-29)

Bring tabular data into a RUNNING simulation, two flavours behind ONE dialog. Plan + illustrated mockup: [docs/PLAN_CSV_IMPORT.md](docs/PLAN_CSV_IMPORT.md) / `.html`. **ZERO compiler impact** — both flavours ride worker messages, so every compile target works by construction (verified on JS / WASM / WebGPU agent targets and WASM / WebGPU grid targets). No new npm dependency.

### The pure core ([src/simulator/csvImport.ts](src/simulator/csvImport.ts), DOM-free)
A ~40-line RFC-4180 parser (quoted fields, `""` escapes, embedded delimiters/newlines, CRLF, BOM, no phantom trailing row; unquoted fields trimmed, quoted whitespace preserved) + **delimiter auto-detection** over `,` `;` `\t` (most consistent field count over the first 20 rows wins) + `detectHeader` + the per-type `decodeCsvValue` + the agent column auto-map + the two builders (`buildAgentSpecs` / `buildGridValues`). **Every decode returns `{value, ok}`** — an unparseable field yields the attribute's DEFAULT and is COUNTED, never guessed. Unit-verified by [scripts/test-csv-import.mjs](scripts/test-csv-import.mjs) (**129** checks asserting VALUES, incl. every negative case).
- **Decode table**: integer → any finite number ROUNDED; float → any finite number; bool → `1/0`, `true/false`, `yes/no`, `t/f`, `on/off` (case-insensitive); tag → the option NAME (case-insensitive exact) **or** a numeric index IN RANGE; anything else → the default with `ok:false`.

### The `none` delimiter — ASCII-art boards, 1 char = 1 cell (GRID only)
Most published CA patterns are written as character art (Life `.`/`O`, Wireworld `.`/`H`/`t`/`#`, a digit grid), so `CSV_NO_DELIMITER` (`'none'`) is a first-class delimiter choice with a **SEPARATE parse path** — `parseCharRows`, NOT `parseCsvRows`, because RFC-4180 machinery is exactly wrong here:
- **No quote handling** (a `"`, a `,` and a `;` are ordinary cells) and **no whitespace trimming** (a SPACE is a legitimate cell — the usual "empty" in ASCII art — so a line of spaces is a row of cells). BOM stripped, CRLF/LF, splits by code POINT (`Array.from`) so an astral char is one cell.
- **Leading/trailing blank lines dropped** (a trailing newline must not create a phantom row) but **INTERIOR blank lines KEPT as zero-length rows**: in a board an empty line most plausibly means a row of empty cells, and dropping it would shift every later row up — silently corrupting the geometry. Such a row pads entirely with the default, and the padding is counted.
- **Header is forced OFF unconditionally** in `parseCsvTable` (a header cannot exist when every character is a cell) — the heuristic AND the override are both bypassed. `detectDelimiter` NEVER returns `'none'`; it is an explicit user choice.
- **GRID-only.** One char per column is meaningless for agent x/y/attribute columns (they need multi-digit numbers and tag names), so the dialog renders the option **disabled with a reason** on the Agents target and a stale `none` selection **coerces back to `auto`** — switching Target can never silently apply a nonsensical parse (verified: the select visibly snaps to auto in Agents mode and restores `none` on switching back).

**The char → value map is the core** (`CsvCharMap = Record<char, string>`, values in the canonical `Attribute.defaultValue` string encoding so they feed `encodeAttrValue` + the existing inline widgets unchanged; an **absent key or `''` = UNMAPPED** → the attribute default). It is also the answer to "the value has to fit in a single char": **any character can stand for ANY value** — `a → 10`, `b → -3`, `a → 2.5` — digits are merely the auto-seed. `distinctChars(table)` lists the characters with counts (most frequent first, SPACE included so it can be mapped); `charLabel` names invisibles (`␣ (space)`, `⇥ (tab)`).
- **`autoSeedCharMap` (conservative, every seed visible + editable; SPACE never seeded):** integer/float/neighborIndex → a DIGIT stands for its own value. **tag** → a digit stands for that INDEX when in range, else a char matching the **first letter of EXACTLY ONE** option stands for that option (`H`→Head, `t`→tail, case-insensitive); **ambiguous initials seed NEITHER**. **bool** → `1 # O o X x *` → true, `0 . - b` → false (Life plaintext `.O`, RLE `bo`).
- `buildGridValues(table, attr, charMap?)` takes the char path only when a map is passed — the DELIMITED path is untouched by construction. Unmapped cells take the default and are reported **per CHARACTER** (`CsvGridBuild.unmappedChars`), not per cell: a 100×100 board with one unmapped background char would otherwise flood the per-cell issue list with 12 identical entries.
- **Dialog surface**: a full-width table below the two columns (the image dialog's manual-brush slot) with one chip per character — `[char] [×count] [value control]`, typed by the attribute: a tag/bool `<select>` carrying an explicit `(default)` entry (`InlineBoolSelect`/`InlineTagSelect` have no unmapped state) or an **`InlineNumberInput` + a clear `×`** for integer/decimal (never a raw `<input type=number>` — the repo rule). Re-seeded whenever the character SET or the target ATTRIBUTE changes; **not persisted** (a char map only means anything for the file it came from).

### Flavour A — Agents (`pasteAgents`, an EXISTING message — no new agent seam)
One CSV row per agent. Each column gets a target (`ignore` / `x,y,z,vx,vy,vz,radius` / an agent attribute / a **vector component** `facing.x`), auto-mapped from the header by normalised name (`Pos X` ≡ `pos_x` ≡ `x`), always overridable. A **vector** agent attribute contributes one target PER COMPONENT keyed by its real `_vx/_vy/_vz` component id (`vectorComponentIds`) — the store never holds a packed vector. **A row with no parseable x AND y is SKIPPED** (an agent without a position is meaningless); every other miss defaults + counts.
- Replace clears first via `clearAgents`; Append does not. Out-of-bounds positions are wrapped/clamped **by the worker** (`pasteAgents` already does it per `torus`); the dialog only reports the count. Overflow past `maxAgents` surfaces the worker's existing `agentOverflow` notice.
- **Compile-target-agnostic BY CONSTRUCTION**: `pasteAgents` allocates through the engine primitives (`allocAgentSlot`/`initAgentSlot`/`applyAgentSets`) and sits in `AGENT_GPU_DEFER_TYPES` (deferred during a GPU batch + invalidates the resident GPU copy).

### Flavour B — the CA grid (`importGridValues`, the ONE new worker message)
**CONVENTION (stated in the dialog): a CSV LINE is a grid ROW (height); a FIELD is a grid COLUMN (width)** — a 12-line × 9-field file gives a **9 wide × 12 tall** grid. Ragged rows pad with the attribute default (counted). One chosen CELL attribute (model attributes excluded; a vector cell attr is offered per component). `Resize` reinitialises the worker to the CSV dims then applies on the next `stepped` (the `pendingImageImport`/`pendingManualImport` pattern, via `pendingGridValuesImport`); `Keep grid` requires an exact dims match (Import disabled + a clear warning otherwise). **3D** gets a **Layer** selector (a 2D table cannot fill a volume); Resize changes W×H and KEEPS depth.
- `paintManual` carries ONE shared value for all cells and `importImage` is colour-mapping-based, so neither fits — hence the new message: `{attrId, width, height, layer?, values: Float64Array (transferred), activeViewer}`. Handler writes `readAttrs[attrId][cellIndexOf(layer,r,c)]` (+ `writeAttrs` in sync mode — the `paintManual` two-buffer discipline), then the `importImage` display tail. In `AGENT_GPU_DEFER_TYPES` alongside `paint`/`writeRegion`.
- **THE WebGPU RULE (verified, not assumed): read back BEFORE writing when `gpuOwnsAttrs`.** After a Play the live state is on the GPU; a partial write + `uploadAttrs` would push the stale CPU mirror of the OTHER attributes (and of uncovered cells) back onto the GPU. A full-attr `patchWebGPUCells` would be equally wrong there (it would copy ALL attrs of those cells from the stale mirror — its `attrIds` written-subset param exists for exactly that hazard). So: `readbackAttrs → gpuOwnsAttrs = false → write → uploadAttrs`.

### EXPORT — the mirror, and the ROUND TRIP is its acceptance criterion (branch `tasks_batch_2026_08`)
**"Export CSV…" is the transport bar's Save State menu item** (see the bullet below) ([CsvExportDialog.tsx](src/simulator/CsvExportDialog.tsx) + the export half of [csvImport.ts](src/simulator/csvImport.ts)), same Target switch, same two flavours. **ZERO worker-protocol change** — it rides the EXISTING `getState`, and **ONE** round-trip carries the WHOLE picture (every cell attribute, all layers, the complete agent store), so the dialog offers any target / attribute / layer without asking again. `getState` also joins the one-shot staleness READERS, so a **free-mode WebGPU** model's GPU state is pulled down first (measured below). It reuses the single-slot `pendingStateSave` callback every other `getState` consumer uses (Save State / preset capture).
- **Format.** **Agents** = a header row + one row per LIVE agent: `x,y[,z],vx,vy[,vz],radius`, then every agent attribute by NAME (a `vector` attribute writes one column per component, `Facing.x` / `Facing.y`). **Grid** = ONE cell attribute, **no header row**, a LINE is a grid ROW and a FIELD a grid COLUMN (the import's own convention; a header would be read back as a row of cells). 3D writes ONE chosen **Layer**. Delimiter comma / semicolon / **tab** (which saves `.tsv`).
- **THE HEADERS ARE THE AUTO-MAP'S OWN VOCABULARY, deliberately** — `agentExportColumns` spells the geometry columns as `GEOM_ALIASES` keys and an attribute as its NAME, and a vector component as `<Name>.<x|y|z>` (which `normaliseName`s to `<name><comp>`, exactly what `autoMapAgentColumns` looks for). So a re-import needs **no manual column fixing**. ⚠ An agent attribute NAMED like a geometry field ("radius") is claimed by the geom alias on re-import — a pre-existing auto-map ambiguity, not introduced here.
- **Values are written in the form `decodeCsvValue` reads back**: tag → the option NAME, bool → `true`/`false`, numbers → `String(v)` (**the shortest decimal that round-trips an f64 EXACTLY** — a position never loses a bit). A **non-finite** value emits an EMPTY field, so a NaN position re-imports as a *skipped row* (the honest outcome) rather than as a defaulted 0. `csvEscape` quotes a field carrying the delimiter, a quote, a newline **or leading/trailing whitespace** (the parser TRIMS unquoted fields, so a padded tag name would otherwise not survive).
- **ONE import-side fix this exposed** ([csvImport.ts](src/simulator/csvImport.ts) `decodeCsvValue`): a tag option whose own NAME carries padding whitespace could never be matched by name (the field is trimmed first) — even from a file this app itself wrote. A **strictly additive** trimmed-name fallback (the exact match still wins first) closes the round trip for such an option.
- **Downloads route through `saveTextFile`** (never a bare `<a download>` — the desktop build writes nothing otherwise).
- **Gates**: [scripts/test-csv-export.mjs](scripts/test-csv-export.mjs) — **63 checks**, most of them export→parse→build→compare rather than string matching: `csvEscape` corners (each proven to survive the parser it was written for), `formatCsvValue` per type + a `format→decode` identity sweep, the header vocabulary asserted against `autoMapAgentColumns`' own output, and full agent (2D + 3D + hostile names + non-comma delimiters) and grid (tag / bool / float / integer / hostile) round trips. `scripts/test-csv-import.mjs` stays green.
- **Real UI, real worker** (0 fresh console errors): **Particle Life** (WebGPU agents, 60 generations then paused in free mode) exported 2000 rows; an independent fresh `readAgents` matched the CSV on **all 2000** agents' geometry exactly; re-imported (Replace) through the real dialog — all 6 columns **auto-mapped with no user action** — and a post-import read matched the pre-export population on **2000/2000 rows, 0 differing** (positions, velocities, radius and the `species` tag, species histogram identical). **Wireworld** (WebGPU grid) exported its `Charge` tag layer at gen 25 (9924 Uncharged / 37 Head / 39 Tail, matching an independent `getState`); the board was then stepped 10 more generations so **166 cells differed** (a no-op import could not pass), and a **keep-grid** re-import restored **10 000/10 000 cells exactly**. **Life3D** exported layer 12 of a 24³ grid — 576 cells, 180 alive, **0 differing** vs the `getState` slice. ## Reset restores the saved board — `ModelProperties.resetRestoresBoard` (branch `tasks_batch_2026_08`)

Some boards are **DATA, not a seeded pattern** — an imported GIS landscape, a hand-painted starting configuration — and **no Init Event can regenerate them**, so a plain Reset wiped them. **`ModelProperties.resetRestoresBoard?: boolean`** (additive, **absent ⇒ false ⇒ today's behaviour**, no migration) makes Reset reseed **and then apply the model's embedded `simulationState` on top**. **UI + orchestration ONLY** — `git status` touches no file under `src/modeler/vpl/compiler/`, no `sim.worker.ts` and no `engine/` file except `overseerRuntime.ts`; the reset / `loadState` / `stateLoaded` machinery it composes already existed.

### THE TWO ACTIONS, and why the flag only sets the DEFAULT
**`reseed`** = the historical `handleReset` (defaults + Init Events). **`restore`** = that, then `applySimulationState(savedBoard)`. The flag decides what a plain ■ click (and **Esc / Backspace**) does; **both are ALWAYS on the button's own menu**, so neither becomes unreachable whichever way it is set — which is what makes a per-model default safe.
- **Order is the mechanism**: the `reset` is posted FIRST and the restore rides on top, because the worker processes messages in order — and **`loadState` SKIPS attributes the snapshot does not carry**, so a partial board restores its own layers (an imported terrain) while every other attribute keeps the values the Init Events just gave it (the fire state, the agent seeding). That is why the GIS generators can omit `state`/`burnTimer` from the board and still get the right starting configuration.
- **`adaptDims: true`**, like a `.gcastate` / preset load: this is an explicit, authoritative user action, so a board saved at other dimensions resizes the grid back to itself rather than being DROPPED (`adaptDims: false` would additionally `setSimulationState(undefined)` — deleting it).
- **`pendingSimStateRestore` is still cleared first.** The `9e464fb` guard is untouched: what changed is that the restore is applied HERE AND NOW rather than left armed to fire on a later `stepped`.

### The ■ button's menu — the Save/Load-State pattern, opening LEFTWARD
Same `.captureBtnWrap` + `.shotMenu` + the single `overlayPopup` union (one popover at a time, outside-pointerdown + Escape dismissal, `data-sim-overlay`, hover OR right-click, opening **flush** upward — measured gap 0 px). It adds **`.shotMenuRight`** (`left: auto; right: 0`) because this trigger sits at the right end of a centred transport bar and its labels are long; growing rightward could overflow. **The menu renders ONLY when the model carries a board** — with none there is exactly one meaningful action, so the historical bare button is used (the enabled-control doctrine). The current default is marked with a ` (default)` suffix.

### "Has a board" is ONE predicate, mirrored in three places
**`embeddedBoardOf(model)`** ([SimulatorView.tsx](src/simulator/SimulatorView.tsx), module scope) returns the snapshot only when it has **all four** fields `applySimulationState`'s own `hasGrid` requires (`width`/`height`/`attributes`/`colors`) — a **controls-only** snapshot ("Save with simulator controls" alone) is NOT a board, and offering to restore one would be an enabled control that does nothing. The Properties panel and the Save dialog gate on the same four fields. **7 shipped models carry a board** (Extended Wireworld, Game of Life, Kelp War, MNCA, snake + the two GIS samples), so the menu is visible on more than the GIS pair — with the flag off its default is `reseed`, i.e. exactly today's behaviour.

### Awaiting a restore — `applySimulationState` now RETURNS its correlation id
It returns the `loadState` reqId when it actually posted a LIVE restore, and `undefined` on every path that posted none (no worker, a dropped stale snapshot, a structural hand-off, a grid-less state, a dimension mismatch) — so a caller can never hang on a restore that never happened. **`awaitStateLoad(id)`** resolves on the worker's own `stateLoaded` ack (the `stateLoadWaitersRef` map, resolved in the SAME handler branch that ends the busy bar, id-matched for the same reason), with the usual 120 s safety net. The new opt **`trackLoad`** allocates the id from the shared `stateLoadSeqRef` **without** raising a bar — deliberately separate from `busyLabel`, because the Overseer awaits every replicate's restore and must NOT flash a bar per run.

### The Overseer follows the model's default
`OverseerDeps.restoreBoardAfterReset(): Promise<boolean>` is awaited by `ovResetBoard` right after the reset ack — a sweep on a data-backed model would otherwise **silently measure an empty world**. It journals `Saved board restored.`. **Verified in the real UI with a decisive negative control** (a throwaway 2-replicate sweep whose board is five 2×2 still-life blocks = 20 alive, sampled one generation after each Reset): flag **ON** → journal shows the restore twice and the series is **20, 20 (std 0)**; the SAME model with the flag **OFF** → no restore line and the series is **1354, 1380** (the reseeded random soup). The await is what makes that difference — an un-awaited restore would have let the run's generation start on the reseeded board.

### A geographic import CAPTURES its board automatically (the discovery path)
`captureImportedBoardAsInitial()` posts `getState` **after** the import messages (the worker processes messages in order, so the reply already reflects them), `serializeSimState(..., { grid: true, controls: false })` — the BOARD, not a UI session, so a later restore leaves the live sliders / brush alone — `setSimulationState(state)` and sets `resetRestoresBoard: true`. Wired at three sites: `applyGridImport`'s **keep-grid** path (inline) and its **resize** path (the layers land on a later `stepped`, so `pendingGridValuesImport.capture` arms it there, via a latest-ref because that handler is declared above), and `applyGeoJsonImport`'s grid burn. The predicate is the gate's own — `gis || r.georef`, i.e. `.asc` (always carries a georef) and GeoTIFF (passes `gis`) and GeoJSON; **a plain CSV board import keeps today's behaviour**. Verified: a fresh 5×4 `.asc` into Game of Life survives a plain Reset cell-for-cell **before anything is saved** (and the menu's *Reseed from rules* wipes it to all-dead — the discriminator), and a second keep-grid import RE-captures.

### Editing the flag
**Properties → Execution** — a checkbox rendered only when the model carries a board. **Save dialog** — a `Use as initial state (Reset restores this board)` sub-row that exists only while *Include board state* is ticked (so `includeGrid` became CONTROLLED state; *Include model presets* is controlled too, for its own warning — only *Include simulator controls* stays uncontrolled). It rides `SaveMetadata` and FileMenu's existing **two-write discipline** (`updateProperties(metaEdits)` AND the local merge into `toSerialize`, because the dispatch is async). `resetRestoresBoard: undefined` in the metadata means *the board is not being saved, so leave the model's value alone* — verified: saving with the grid unticked keeps the flag in the model AND in the file while the menu correctly disappears (the model no longer carries a board).
