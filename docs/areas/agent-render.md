  (a paint gesture queries no neighbours and mutates no topology). The three brush-colour params
  (`_r, _g, _b`) are prepended by the CALLER, exactly as the cell `inputColor` signature does — so
  the DEV arity assertion (the FOURTH ABI pair, `buildAgentInputParams` ↔ `buildAgentInputArgs`)
  expects `descriptor.length + 3`.

- **Every `agentMappings` consumer that assumed A→C now filters**: the direct-render gate's OM count,

- **Every analyzer that enumerates the agent ROOTS had to learn the new one** (an adversarial

  the `input` kind aliases `w_` to `attrRead`, which is EXACTLY why `divisionEvent` is listed, so
  without it a Set Attribute followed by a Get Self Attribute on the same attr was sink-hoisted
  above the write and read the PRE-write value (negative-controlled: 7 before the fix, 42 after);
  `NEVER_INVARIANT` ([loopInvariant.ts](src/modeler/vpl/compiler/loopInvariant.ts)); `ROOT_TYPES` +
  `CONTROL_FLOW` + `NODE_LABEL` ([geometryTaint.ts](src/modeler/vpl/compiler/geometryTaint.ts)) — a
  paint graph's writes were invisible to the C8 taint verdict; and `LOWERED_AWAY`
  ([targetDiagnosis.ts](src/model/targetDiagnosis.ts)) — a value-out wired into the behaviour cone
  would otherwise report the root as an unsupported WASM/WebGPU node type. **When adding an agent
  root, sweep those four files.**
- **Gate**: [scripts/test-agent-abi.mjs](scripts/test-agent-abi.mjs) grew from 28 to **48** checks —
  the `'input'` arg list against a hand-written expectation, the structural claim *input === division
  MINUS the daughter scalars*, the 2D-is-a-prefix-of-3D rule for the new kind, and the `w_` ALIASING
  claim asserted on a **`syncAttrs: true` store**. That last one matters: in async mode `attrWrite`
  ALIASES `attrRead`, so an attrWrite/attrRead mix-up is INVISIBLE — the first version of the test
  passed a deliberate mutation for exactly that reason. **Negative-controlled by SOURCE MUTATION**:
  reverting any of the three widened `singleAgent` branches (the leading `idx`, the bond slice, the
  `w_` aliasing) fails 4-8 checks.
- **⚠ THE LEADING CHANNEL COUNT IS A FOURTH MIRROR, AND IT WAS THE ONE THAT DRIFTED** (user-reported
  2026-08-11: *"[agents] ABI ARITY DESYNC: input mapping '…' fn declares 31 params but the worker
  passes 35"*). The compiled fn's params are `resolved channels + the shared 'input' descriptor`, and
  since Parameterized Input Mappings the channel count is whatever `inputParamsOf(mapping)` resolves
  — 3 only for a LEGACY (absent `parameters`) mapping. The worker's DEV arity assert computed
  `want = buildAgentInputArgs(s, 0).length + 3`, a **hardcoded legacy constant**, so it was the ONE
  site in the chain not derived from the resolver. Any other parameter list fired a **false-positive
  red banner on every load/recompile**: `parameters: []` (0 channels — the reported case, a graph
  that ignores the brush) gives a phantom gap of **4** = 3 channels + the sanctioned trailing
  `_generation` slack of 1. **Nothing was actually shifted** — the compiler and the sender both
  derive from `inputParamsOf`, and the paint was verified correct throughout (`(3,−5) → (6,−10) →
  (12,−20)` on the WASM *and* WebGPU agent targets).
  **THE FIX — ship the number, never guess it**: `inputMappingCodes` entries carry `channels`
  (`imResolved.channels.length`, the SAME resolution the leading params were emitted from), threaded
  through init/recompile onto `agentInputMappingFns`, and the assert adds THAT. The worker keeps no
  model, so it cannot resolve `Mapping.parameters` itself — shipping is what makes it a mirror.
  A missing field falls back to `?? 3` so an old message shape can't silently shorten the prefix.
  **`runAgentInputMapping` now also rejects a payload whose `values.length` disagrees** with the
  compiled fn (skip + one error, never apply): the mismatch is reachable with no bug at all — a paint
  flushed from the main thread's rAF with the NEW channel count can reach the worker before the
  `recompile` that installs the matching fn — and applying it would shift every descriptor arg, the
  exact silent-plausible-garbage mode the assert exists to catch.
  **WHY THE HARNESS MISSED IT, and the rule that now guards it**: `test-agent-abi.mjs` compared one
  ARG list against another ARG list — it never built the compile-side PARAM string, never touched the
  channel count, and never modelled the assert's formula. It grew 48 → **607** checks with two new
  tiers. **T2 pairs `buildAgent*Params(model)` against `buildAgent*Args(store)` for ALL FOUR kinds,
  building the worker side THE WAY THE WORKER DOES — from a real `createAgentStore` + its own
  derivation, never from `agentAbiShapeOf(model)`** (which would compare the compile side with
  itself — the C9 `gates`-missing-from-`agentAbiShapeOfStore` lesson), over a matrix of every
  parameter shape the resolver can produce (0/1/2/3/4/6 channels) × 2D/3D × gates/attrs/fields, plus
  every shipped agent model. Its invariant is stated so the channel count cannot hide in it:
  **`want − declared == args − params ∈ {0,1}`, i.e. INDEPENDENT of how many channels are declared.**
  **T3 pins the shipped source** (T2's arithmetic is necessarily a mirror of the fixed formula, so it
  alone could not notice a revert): the assert must read `im.channels` and contain **no numeric
  addend**, all three sibling asserts must derive `want` from their arg builder alone, the compiler
  must ship the resolved count, and the paint handler must carry the payload guard. Negative-
  controlled by SOURCE MUTATION — reverting the assert to `+ 3` fails 2 checks, shipping a constant
  `3` fails 57, deleting the payload guard fails 1. **`input` was the only kind that COULD carry this
  bug** (the only one with a term outside the shared descriptor); T3 now pins the other three so a
  future kind with its own leading block cannot repeat it.

### 3D agent sprites — the WebGL2 billboard pass (branch `absorb_old_automatosgt`)
The 3D voxel renderer ([gl3d.ts](src/simulator/render/gl3d.ts)) now draws sprite-agents as **camera-facing textured billboards** (the 3D analogue of the 2D `drawAgentsOverlay` sprite blit), so the animated/rotated sprite exhibition layer works in the 3D view — not just 2D (this closes the last Phase-E 3D-renderer gap). Non-sprite agents keep drawing sphere impostors; a non-sprite model is byte-identical (the sprite pass never runs). All additive/gated; touches ONLY [gl3d.ts](src/simulator/render/gl3d.ts) + the SimulatorView atlas wiring (no engine / compiler / ABI change).
- **The atlas** = a `TEXTURE_2D_ARRAY`, one CELL×CELL (128²) layer per (sprite, frame). Each decoded `ImageBitmap` frame is drawn STRETCHED into its square layer; the aspect-shaped billboard quad un-stretches it so the sprite renders at its native aspect with the longest side ≈ the agent diameter (matching the 2D `drawImage` sizing). Built by **`setSpriteAtlas(SpriteAtlasInput[])`** (SimulatorView passes the decoded frames + per-sprite meta from the `SpriteRegistry`), rebuilt lazily in the 3D draw path when the sprite set / decoded frames change (a `spriteAtlasDirtyRef` set on registry `onReady` / a sprite-set edit / a fresh renderer, which also forces a sprite-buffer re-upload). The 2D path draws straight from the registry (no atlas) — the atlas is 3D-only.
- **Per-instance data** ([x,y,z, halfW, halfH, cos, sin, layer, alpha] × 9 floats, a SEPARATE `spriteInstBuf`): `uploadAgents` resolves each sprite-agent's frame (floor+wrap/clamp by the asset `loop`), size (radius·2·scale, aspect-shaped by the frame aspect), facing (the per-agent `spriteRotations` compass degrees, OR the world-XY velocity heading `atan2(vx,-vy)` when the asset `orientToVelocity`, aligned to `defaultDirection` + `rotationOffset` — the SAME resolution as the 2D path), and the atlas layer (`baseLayer + frame`). The billboard VS rotates the quad clockwise-on-screen (matches `ctx.rotate`: x'=x·cos+y·sin, y'=-x·sin+y·cos, with uCamUp = screen-up); the FS samples the atlas layer, multiplies by the agent alpha, and discards fully-transparent texels (chroma-key / aspect-pad friendly). Depth-test on + depth-write off + SRC_ALPHA blend → sprites depth-interleave with spheres/voxels + blend by alpha (drawn AFTER spheres in the agent pass).
- **The sphere buffer stays 8 floats** (byte-identical stride): a sprite-agent is flagged by a NEGATIVE `radius` in the sphere buffer — the sphere DISPLAY FS discards it (`vSkip`), while the pick VS uses `abs(radius)` so a sprite-agent stays pickable (move / inspect / edit) via its invisible pick-sphere. So NO per-target ABI/SoA change — a pure render-layer feature reading the snapshot's existing `spriteIds`/`spriteFrames`/`spriteRotations`/`spriteScales`/`vx`/`vy` (which the 2D path already ships). The velocity + the 4 sprite arrays were added to `AgentSnapshot3D` (length-0 for a non-sprite model → the sprite pass is inactive).
- **Verified** (real GL renderer, driven via `window.__sim3dRenderer()`): a red-square atlas over the 5 Tissue agents → 25.6k red (sprite-textured) pixels at the agent positions, `spriteInstanceCount === 5`; **mixed** (even=sprite/odd=sphere) → both render (`sic 3` + spheres); **zero sprites** → 0 billboards, spheres only (non-sprite path unaffected); a 45°-rotated + a per-agent-rotated arrow render at distinct angles with alpha blending (screenshot-confirmed — the arrows point in the set directions). tsc + `npm run build` clean. **Remaining 3D-sprite gap:** the aspect uses frame 0 only; a per-frame-varying aspect (rare) would fit-pad; refinement, not a bug.
- **Two agents-only bug fixes (same session):** (1) **Agents-only model (Grid Cells OFF) no longer demands a cell Generation Step / shows the empty CA-grid canvas.** GraphEditor's `activeGraph` initial state + the guard effect now switch to the **Agents** graph when `topologyMode.gridCells === false && agents` (was hard-defaulting to `'cells'` → the empty Cells canvas + a "No Step node" feel); and `SimulatorView.compileModel` (+ the init/recompile error re-sets) **suppress the cell compiler's "No nodes / No Step node" error when `gridCells === false`** (the cell graph is intentionally empty; the worker already skips the cell step via `gridCells`). Agent compile errors still surface via the worker `error` message. Verified: an agents-only Boids loads with no compile-error banner, the 260 agents simulate, and the Modeler opens on the Agents graph (Behaviour Step present, no Generation Step). (2) **Agent seed brush "Seed config" now sets agent attributes.** `agentSeedSetsRef` built the `seedAgents.sets` payload by iterating `cellAttrsRef` (the CELL attributes) while the Seed-config `ManualBrushPanel` edits `model.agentAttributes` (a separate id-space) — so the `attrId`s never matched the agent store and `applyAgentSets` no-op'd (seeded agents kept their defaults). Fixed to iterate `model.agentAttributes`. Verified via the worker seed path: an agent seeded with `sets:[{attrId:'energy',value:7}]` reads back `energy = 7`.

### Set Agent Sprite on the WASM agent target (branch `updates`)

`setAgentSprite` was the **single genuine node gap on both agent targets** — it wrote five
PLAIN JS arrays (`spriteIds`/`spriteFrames`/`spriteSpeeds`/`spriteRotations`/`spriteScales`,
the ONE field group C9 described as having "no baked byte on any target"), so it had no WASM
emit and a sprite-driving **Behaviour** graph clamped the whole model to JS. It now emits on
WASM; the generated capability matrix reads **`agentGapsWasm: 0`**.

- **The enabler is the memory, not the emitter.** `computeAgentMemoryLayout` gained a sprite
  block — 4 f64 runs + 1 i32 run, `maxAgents` each — **appended after EVERY existing region**
  and reserved **only when the C9 `sprites` gate is on**. So a sprite-free model's layout is
  byte-identical, and a model that DOES carry sprites shifts no offset already baked into a
  module. `createAgentStore` returns VIEWS over those bytes when `wasmBacked`, plain arrays
  otherwise — which is what makes the WASM write and the JS `advanceAgentSprites` advance the
  same state. `AgentMemoryLayout.spritesReserved` is the emitter's C9 SAFETY CATCH (the shape
  of `layout.f64[name] === undefined`): gate off ⇒ every sprite facet is dropped, while the
  ALPHA facet survives because it writes `colors`, which is always allocated.
- **`env.atan2` is a CONDITIONAL import** (`AGENT_ATAN2_FUNC_IDX = NUM_IMPORTED_FUNCS + 3`),
  added ONLY when a reachable Set Agent Sprite uses the VECTOR rotation mode — the one facet
  needing an inverse tangent, which WASM has no opcode for. **Adding an import shifts the
  module's own function indices**, so making it conditional (and appending it LAST) is what
  keeps every model that does not use it byte-identical — the same conditional-arity
  discipline as `forcePassParamsFor(chargeOn)`. `usesAtan2` is scanned BEFORE emit, exactly
  like `viewerGuardIds`. The host object supplies `atan2` unconditionally (free — WebAssembly
  only looks up imports the module DECLARES).
- **Facet-for-facet mirror of the JS node**, including the two subtleties: an unwired `Agent`
  targets the current-loop agent UNGUARDED (it is live by construction) while a wired one takes
  the range-only guard the other by-id setters use; and the alpha byte is CLAMPED to [0,255]
  before `i32.store8`, because `store8` truncates where the JS `Uint8ClampedArray` clamps.
- **WebGPU clamped at the time, deliberately** — the sprite buffers had no GPU-side mirror,
  and adding one meant new runs + a per-generation round-trip for a pure DISPLAY layer. That
  clamp is **GONE**: see “Set Agent Sprite on the WebGPU agent target” below.
- **Gates**: `check-compile-identity` 29 models byte-identical; a permanent
  `[synthetic] Set Agent Sprite (all facets, self + by-id, vector rotation)` entry in
  [parity-agent-wasm.mjs](scripts/parity-agent-wasm.mjs) with a **VALUE invariant** that
  recomputes the expected state independently (parity alone would pass if BOTH targets wrote
  nothing) — negative-controlled twice by source mutation (a doubled scale write, and forcing
  the layout gate off); the harness's store comparison gained the five sprite arrays;
  `gen-capability-docs --check` regenerated. **Verified in the real UI**: the user's sprite
  boids model's chip flips `agents JS` → `agents WASM`, the bird sprites still render (30
  distinct colours in a 147-px blob — a textured sprite, not a flat disc) and animate, and an
  interleaved A/B shows WASM neutral-to-marginally-faster (2.69/2.71 vs 2.72/2.74 ms/frame at
  100 agents — as documented, the WASM win needs a heavy per-agent rule or a large population).

### Set Agent Sprite on the WebGPU agent target (branch `updates`)

The LAST agent-target node gap. `setAgentSprite` emitted on JS and WASM but not on the GPU
(no sprite mirror there), so a **behaviour-reachable** Set Agent Sprite clamped a
WebGPU-target model to JS — the C1 readout literally said *"the agent graph uses a node the
WebGPU agent shader does not emit (setAgentSprite)"*. It now emits; the generated capability
matrix reads **`agentGapsWebgpu: 0`** and the reject set is the documented fundamentals only.
**There was never a fundamental incompatibility** — sprite state is per-agent, own-slot (or
spawn-handle / range-guarded by-id) writes, exactly the parallel-safe shape every other agent
setter has. It was an effort-scope decision, and this closes it.

- **Five `agentF32` RUNS, no new binding** (`AGENT_GPU_SPRITE_FIELDS` in
  [agentWebgpu/layout.ts](src/modeler/vpl/compiler/agentWebgpu/layout.ts)): `spriteIds` /
  `spriteFrames` / `spriteSpeeds` / `spriteRotations` / `spriteScales`, one run each, **APPENDED
  AFTER every existing run** (including the P3 bond-form request runs) and reserved **only when
  the C9 `sprites` gate is on**. Appending last is what keeps a sprite-free model's bases — and
  therefore its emitted shader — byte-identical; riding `agentF32` is what keeps the Naga
  stripped-binding discipline out of it entirely. `AgentWebGPULayout.spritesReserved` is the
  emitter's C9 SAFETY CATCH (the mirror of the WASM layout's flag): gate off ⇒ every sprite
  facet is dropped, while the ALPHA facet survives because it writes `agentColors`, always
  allocated. **This also wires `agentFieldGating.ts` site 3**, which that file's header had
  claimed (`AgentWebGPUExtras.fieldGates`) but nothing implemented, because the group had no GPU
  run at all. `AgentWebGPUExtras.sprites` defaults to **OFF** when absent — deliberately
  inverting `normalizeFieldGates`' absent⇒on convention, because every other optional block in
  that file is absent⇒off and the two callers that pass no extras (SimulatorView's minimal
  render-only layout, the worker's fallback) compile no shader.
- **f32, and that is honest for this group.** `spriteIds` is a slot INDEX (exact in f32 far past
  any plausible sprite count, rounded on readback) and the other four are DISPLAY quantities the
  renderer already consumes as f32 — a frame counter, compass degrees, a size multiplier. Same
  statistical-parity stance as the rest of the WebGPU agent SoA.
- **THE CPU STAYS AUTHORITATIVE BETWEEN GENERATIONS, so the round-trip is a PAIR.**
  `advanceAgentSprites` ticks `frame += speed` once per generation, `initAgentSlot` clears a
  recycled slot and `divideAgent` hands a daughter its mother's sprite — all CPU. So
  `uploadAgentSoA` **SEEDS** the five runs from the store and `readbackAgentStep` /
  `readbackAgentFrame` copy them back. **Both halves are mandatory together**: the shader writes
  only the TICKED facets, so an un-seeded run would be read back as 0 and clobber the CPU value
  (a `spriteId` of 0 means "no sprite" ⇒ the agents silently render as plain discs). ONE
  predicate — **`spriteRunsActive(rt)`** = `rt.usesSpriteWrite && layout.spritesReserved` —
  gates the plan, the fill, the writeBuffer, both readbacks and the spawn-reconcile overlay, so
  they cannot drift; `buildF32ReadPlan` adds the runs under that SAME predicate, keeping the
  "the plan covers exactly what crosses the bus" invariant `compactBase` throws for.
- **`usesSpriteWrite` is set by a SPRITE-RUN write only, never by the ALPHA facet alone** (alpha
  writes `agentColors`, which every path already round-trips) — so an alpha-only node costs no
  extra traffic and does not block residency.
- **THE SPAWN RECONCILE OVERLAYS SPRITE STATE.** A newborn goes through `initAgentSlot`, which
  CLEARS sprites — so a Set Agent Sprite on a Create Agent handle would be lost. The reconcile
  now copies the five GPU values for `[hw, cursor)` exactly as it already does for the agent
  attributes and `targetRadius`.
- **RESIDENCY IS BLOCKED, narrowly and by DESIGN** (`residencyModelBlockers` key `sprites`,
  mirrored model-side in `residencyFactsFromModel`). A resident batch encodes N generations into
  ONE submit with NO CPU touch point, so the per-generation `advanceAgentSprites` tick could not
  interleave with the shader's writes. The term is `usesSpriteWrite`, **not "the model has
  sprites"**: a model whose sprite state is set in an Agent Output Mapping (or not at all) keeps
  residency exactly as before. Advancing frames GPU-side in `posCommit` was considered and NOT
  taken; the residency-eligible case (sprite state set from a CPU-side OM) instead flags
  `agentGpuUploadPending` after the per-batch tick, so the frames the next batch presents are
  the ticked ones — the animation runs at the right RATE, offset by one batch. (When this was
  written a sprite model could not direct-render at all, so the win was nil; the 2D billboard
  pass changed that, and the flag is what keeps a resident sprite model animating.)
- **DELIBERATELY NOT EMITTED IN AN AGENT OUTPUT MAPPING MODULE** (`agentSubsetSupported`'s new
  `scope: 'behaviour' | 'om'` param). An OM module is dispatched ONLY inside
  `dispatchResidentBatch`, while every other path colours agents through the CPU
  `runAgentColorPass` — and the sprite round-trip is keyed on the BEHAVIOUR flag, so an OM-only
  write would simply be lost. Rejecting it keeps today's OM semantics EXACTLY (an OM with a
  sprite node ⇒ `omSupported: false` ⇒ the CPU overlay, where the node has always worked) and
  costs nothing user-visible: an OM-only usage never clamped the agent TARGET in the first place.

### THE ACTIVE WINDOW — per-generation agent GPU traffic tracks the POPULATION, not `maxAgents` (2026-07-31, user-reported)

**`maxAgents` is a user-set CEILING, and every per-generation CPU↔GPU transfer was sized by it.** A model that grows to ~2 000 agents under a 60 000 ceiling therefore moved **~15 MB of mostly-dead slots EVERY generation**. A bonded / structurally-rewriting model (a GRA rule — rewiring IS the point) can never be residency-eligible, so it *always* pays that per-generation round-trip. Reported as *"on wasm the processing is much faster than on webgpu (roughly 2x)"* — it was worse than 2×, and it got worse with N.

**Measured on the reporter's 3D Cubic GRA, same 60 000 ceiling:** `47.4 ms/gen → 10.9 ms/gen` (**~4.4×**) at a LARGER population (N 1830 → 2486). Confirmed as the cause first by changing ONLY the ceiling (60000 → 4000 gave 47 → 10 ms/gen), with WASM as the control (insensitive: 6.5 → 5.1, since it works in place on `wasmMemory` and has no round-trip). Before the fix the gap widened with N — 1.9× at N≈100, **7.4× at N≈1900** — which is backwards for a GPU and is the tell that the cost was ceiling-bound, not work-bound.

- **`AgentWebGPURuntime.gpuActiveHigh`** ([agentWebgpuRuntime.ts](src/simulator/engine/agentWebgpuRuntime.ts)) is the window; `agentActiveWindow(rt, highWater)` is the ONE resolver every transfer calls. **It only ever GROWS** — a slot the GPU has written must keep being refreshed, or its stale request-queue lanes get read back and **drained** on a later generation. Slots it has never covered are still the zero the buffer was created with, which is exactly the "no requests, not alive" state the reconcile expects. That monotonicity IS the correctness argument; do not "optimise" it by shrinking on reset.
- **It must cover the post-dispatch SPAWN CURSOR, not just `highWater`**: a spawning behaviour bump-allocates slots ABOVE highWater via the atomic cursor and the reconcile reads `[hw, cursor)`. So `readbackAgentStep` reads that ONE u32 **first** (a 4-byte round-trip) and sizes everything else from it. A non-spawn model skips the extra round-trip — its window is exactly `highWater`.
- **Upload**: per-RUN `writeBuffer` of each strided run's live prefix (~30–50 small writes) replaces one whole-buffer write; the CPU zero-fill tails become `[hw, window)` instead of `[hw, maxAgents)`. Same for the alive mask, the colours, and the bond store (`bondStoreUpload`, a reused staging array instead of a fresh `Int32Array(bondStoreLen)` per generation).
- **Readback needs COMPACTION, not a prefix.** The f32 SoA is a set of STRIDED runs (run r at `f32Base[r] .. +maxAgents`), so the live prefixes are scattered across the whole buffer and a windowed readback cannot be one copy. `buildF32ReadPlan` copies each run's prefix into its own slot of a COMPACTED staging buffer and maps only `totalElems`. **EVERY run is planned** (the same field lists the upload walks), not just the ones the reader touches, and **`compactBase` THROWS on an unplanned base** — returning 0 would silently read a neighbouring run's values. Every read site is rebased through `CB(...)`, including the spawn reconcile's attribute read.
- `readbackAgentFrame` (the resident once-per-frame path) gets the same window + plan.
- **Gotcha this exposed in the harness**: `blockAfter(src, /export async function readbackAgentStep\(/)` returned the function's `Promise<{…}>` RETURN TYPE, not its body, so three checks passed vacuously. `blockAfter` now searches for the body brace from the END of the match.
- **Guarded** by the **B13** block in [scripts/verify-agent-render.mjs](scripts/verify-agent-render.mjs) (13 checks: monotonic + ceiling-clamped window; no whole-buffer write/copy remains; the plan covers every run; the unplanned base throws; the cursor-first sizing; every base rebased; the resident path and the bond store windowed). **Negative-controlled** — reverting the window to the ceiling, or making an unplanned base return 0, each fails exactly the check that names it.
- **Verified on the real GPU**: the reporter's model holds the cubic invariant (deg 3/3, `E = 3N/2`), 0 dangling, 0 asymmetry at every sample through 1200 generations of heavy spawning + rewiring; **Game of Life on Agents matches Conway CELL-FOR-CELL over 1024 agents for 3 consecutive generations** on non-trivial boards (234→243→213→171 alive, 0 mismatches — the value-level oracle for the windowed attribute readback); Particle Life (resident path) still shows its **6 species colours**; Growing Tissue keeps 7228 bonds with 0 dangling through division; Boids/2D unchanged. 29 models byte-identical; 14 gates green.

### Why a BONDED model can never be GPU-resident (the two agent GPU paths)

There are **two** WebGPU agent paths, and which one a model gets is the single biggest performance fact about it:

| | resident | per-generation |
|---|---|---|
| submits | **ONE** for the whole gens/frame batch | one per generation |
| CPU work between generations | **none** | upload → dispatch → readback |
| readback | once per FRAME | once per GENERATION |
| eligibility | `agentResidentEligible` | everything else |

**Residency's entire value is that N generations are encoded into ONE queue submit with NO CPU touch point between them.** So *anything* that needs the CPU BETWEEN generations disqualifies a model — by construction, not by omission.

**The structural phase — bond form/break/rewire, division, death, auto-bond, the stale-bond sweep — is CPU/JS on EVERY target by design.** A shader can only *request* those ops (it writes flags into the P4 request queue); applying them is serial data-structure surgery, not per-agent parallel math:
- the bond store is **ragged**, with per-agent capacity, a free list and epoch-stamped slot recycling. Removing a bond compacts by swapping with the last slot (`moveBondSlot`), which moves **both** endpoints' rows.
- **division** partitions a mother's bonds between two daughters via a closed-form eigensolve, then rewires every partner.
- `partner` / `restLength` are **CPU-owned** — the shader never writes them (P3), so they would need uploading + reading back each generation regardless.

Hence the two INDEPENDENT terms in [`agentResidentEligible`](src/simulator/engine/sim.worker.ts): **`s.maxBonds === 0`** (no bond store to sync) and **`agentGraphResidencyClean`** (= `!usesStructural && !usesRadiusWrite`, i.e. no Divide / Form / Break / Rewire / Kill reachable from the behaviour root). The other terms exclude features for the same reason — field bridge, sync-attr swap, positional projection, spawn reconcile, stop drain, indicator accumulation all need per-generation CPU.

**For a GRA rule this is not incidental — THE REWIRING IS THE MODEL** — so `Cubic GRA`, `SDCA`, `Life on Bonds` and every Morphogenesis Tissue can never satisfy either term. They are not "failing" residency; they are a different class of simulation.

**Lifting it** would mean porting the structural phase itself to the GPU: a parallel bond-store allocator/compactor, a GPU division partition, and conflict resolution for concurrent rewires of a shared edge — plus its own answer for invariant **I5** (a rejected op leaves the graph EXACTLY as before), which today is trivially satisfied because the CPU applies ops one at a time. Not scheduled.

**Until then the per-generation path is the middle ground and it is a real one**: behaviour + force still dispatch on the GPU, only the round-trip is per generation — and THE ACTIVE WINDOW (above) made that round-trip's cost track the live population instead of the `maxAgents` ceiling (measured 47.4 → 10.9 ms/gen). At small populations WASM can still win, because a CPU target has no round-trip at all.

### Direct agent render — GPU-side, free-when-idle (A1 + A2 + A1.5 + C + D; branch `optimize`)
The **WORKER renders agents into a transferred OffscreenCanvas**; the main thread just blits it 1:1 (`ctx.drawImage(agentRenderCanvasRef, 0, 0)`, the grid direct-render seam). **A1** feeds the render from the resident/per-gen GPU SoA (WebGPU-target models). **A2** widens this to CPU (JS/WASM) targets: the worker builds a lightweight **render-only** WebGPU surface and uploads the CPU store's positions/colours each frame, then presents on the SAME pipeline — the sim keeps running on the CPU, only the DRAW moves to the GPU (see the A2 subsection below). The per-frame CPU pipeline (readback → snapshot → postMessage → Canvas2D `drawAgentsOverlay`) runs **ONLY while a feature needs it** — free-running cost ≈ one `drawImage`. Additive/gated — every non-eligible model keeps today's CPU-overlay path byte-for-byte. Handoff: [docs/HANDOFF_GPU_AGENT_RENDER_A1.md](docs/HANDOFF_GPU_AGENT_RENDER_A1.md) (+ the master [HANDOFF_GPU_AGENT_RENDER.md](docs/HANDOFF_GPU_AGENT_RENDER.md) / [IMPACT_MAP](docs/IMPACT_MAP_GPU_AGENT_RENDER.md) / [PLAN](docs/PLAN_GPU_AGENT_RENDER.md)). - **FP-1 — the render is a VIEW of engine-owned state.** `AGENT_RENDER_WGSL` reads ONLY `agentF32[x/y/radius]` + `agentAlive` + the packed `agentColors` (r|g<<8|b<<16|a<<24) — fields every agent model has, so **zero compiler changes**, graph-agnostic. - **THE DISC EDGE IS ANTIALIASED — analytic coverage, ALWAYS ON (no toggle).** `fsMain` used to end the silhouette with a bare `if (d > 1.0) { discard; }`, a BINARY edge: **measured on a real device with the shipped shader (radius 12), 0 partial-coverage pixels and 0 distinct partial alphas**, the centre scanline stepping 255 → 0 in one pixel — while the CPU overlay's Canvas2D `arc` fill produced **2084 partial pixels over 54 alpha levels** on the same app. **That inconsistency IS the user-reported "the contours of the agents appear serrated"**: an overlay model looked smooth, a direct-render one (Particle Life, and every E2 composite model) looked jagged. Now `pxw = max(fwidth(d), 1e-5)` and `cov = clamp((1 - d)/pxw + 0.5, 0, 1)` give a one-pixel coverage ramp centred on the true silhouette (cov = 0.5 exactly at `d == 1` — the same half-in/half-out coverage a rasterizer computes), folded into **BOTH the alpha AND the premultiplied rgb** (alpha-only would leave a bright rim fringe). After: **100 partial pixels / 30 alpha levels, and the coverage-weighted area lands on πr² to within 0.02 % (448 → 452.30 vs 452.39)** — proof the ramp is *calibrated*, not merely blurred — with the fully-opaque body **BIT-IDENTICAL** (verified 0 differing pixels, max channel delta 0, at radius 12 and 26, glow on and off).
  - **`fwidth` MUST be taken BEFORE any discard** — WGSL requires derivative builtins in uniform control flow.
  - **THE QUAD CARRIES A ONE-PIXEL PAD, and the pad and the uv rescale are a PAIR.** The quad CIRCUMSCRIBES the disc, so they are tangent at the four axis points and the ramp's outer half would be clipped exactly there (four hard notches). `padded = half + 1.0` grows the geometry and `out.uv = corner * (padded / half)` rescales so `d == 1` still marks the DRAWN radius; **`out.radPx` stays the UNPADDED radius** so the outline band does not move. Padding without the rescale shrinks the disc; rescaling without the pad restores the notches.
  - The **outline band** is feathered with the SAME derivative (`mix(1.0, 0.60, t)`), matching the antialiased `stroke()` the CPU overlay draws instead of a second hard step inside the body. **`fsGlow` needs no ramp** — its falloff already reaches zero continuously at `d == 1`, so the halo was never aliased; its discard just trims the pad ring.
  - **ONE module (`buildAgentDiscPipelines`) feeds A1, A2 and the E2 composite**, so all three inherit the edge policy and cannot drift. **The CPU overlay is untouched** (already coverage-antialiased), and capture rides along for free (view scope reads the display; the simulation scope re-renders with Canvas2D arcs).
  - **3D sphere impostors are NOT covered.** Both `agentRenderSphereWGSL` (worker, free mode) and gl3d's `SPHERE_FS` (frame mode) end the silhouette with `discard`, and **MSAA does not help a discard edge** (the fragment is killed for all its samples), so gl3d's `antialias: true` buys nothing there. The correct fix is **multisampling + alpha-to-coverage** (`alphaToCoverageEnabled` / `gl.SAMPLE_ALPHA_TO_COVERAGE`) — order-independent and depth-write-safe, unlike alpha blending, which would need back-to-front sorting and would halo against `frag_depth`. #### THE SOLID CORE — glow is a core + a halo, not one falloff (branch `updates`)
**The reported problem**: *"the glow shouldn't be a single circle … at least the falloff shouldn't be like that, because it gets impossible to visualize well both clusters of agents AND barely-visible isolated agents. We should be able to have a 'core size' that is a colour that won't be added out or faded out."* A single additive falloff from the centre forces a choice: lower the intensity so clusters stay legible and a lone agent is a dim smudge; raise it so a lone agent reads and clusters blow to white. Both halves of that trade come from the SAME cause — **the agent's own colour was being produced additively**, so it scaled with intensity and accumulated with its neighbours'.
- **THE SHAPE (both paths): an OPAQUE core with the halo UNDER it.** `coreR = radPx + core*glowSize` (`0` = the agent's own disc — the default, and the historical body size), `R = radPx + glowSize`. **`core` spans [-1,1]** — the sub-zero half is the later "dissolve the core" round; see the next subsection. The core is drawn **source-over** (premultiplied on the GPU, a plain fill on the CPU) so it can be neither added out by a neighbour's halo nor faded out by a low intensity. The halo's falloff is **remapped over the BAND** `[coreFrac, 1]` (`t = clamp((1-d)/(1-coreFrac))`, `g = intensity·pow(t, steepness)`) instead of `[0,1]` — the whole dynamic range lands outside the body rather than being spent inside it. #### ACCUMULATE EXACTLY, COMPRESS ONCE — the glow architecture (branch `updates`, 2026-08-07)
**Reported twice.** First: *"Find a better way to blend the glow halos to avoid this oversaturated look and contrast artifacts where there is a high density."* That round replaced pure-additive with **screen** (`1 − (1−p)^N`), which helped. Then: *"it's gotten better but still not good enough. Use as reference the way that our Particle Life reference code solves it. Theirs looks much more well treated both in 2D and 3D."*

**THE LESSON — a per-pair blend is MEMORYLESS, so no operator can fix this.** Additive gives `min(1, Np)`, screen gives `1 − (1−p)^N`; both are functions of the RUNNING RESULT, both live in `[0,1]`, and both exhaust 8 bits after ~4 overlaps for any `p` bright enough to see ONE halo. **The plateau is a property of the ARCHITECTURE, not of the operator.** The reference (studied under `SandboxScience-master/`, technique reimplemented — no code copied) does not blend halos against each other at all: it renders every particle's glow quad **additively into an `rgba16float` HDR target** and compresses the accumulated sum **once**, in a fullscreen compose pass (`assets/particle-life-gpu/shaders/render/particle_render_glow.wgsl` + `.../compose/compose_hdr.wgsl`, wired in `components/particle-life/ParticleLifeGpu.vue`). Both our 2D paths now do the same.

- **THE HALF NOBODY EXPECTED — the clamp WAS the worst artifact.** Under screen the emitted value had to be clamped (`dst = 1 − src`, so `> 1` SUBTRACTS the backdrop), and `min(1, intensity·t^steepness)` gives every agent a hard-edged, fully-saturated **PLATEAU DISC** wherever the profile reaches 1: at the shipped Intensity 3 that is the **outer 42 % of the band radius**, identical on every agent, before any overlap. Removing the clamp is the single most visible half of this fix — and it is only *possible* because the accumulation is no longer where the compositing happens.

**GPU** ([agentWebgpuRuntime.ts](src/simulator/engine/agentWebgpuRuntime.ts)) — three new pieces beside `ensureAgentDepthTex`: `GLOW_HDR_FORMAT = 'rgba16float'` (renderable AND blendable), `ensureGlowHdrTex`/`destroyGlowHdrTex`, and `encodeGlowHdrPass`.
- `fsGlow` emits **unclamped** `colour·g` in rgb and `g` in alpha; the halo pipeline is built explicitly against `GLOW_HDR_FORMAT` with `{one, one}` additive on BOTH colour and alpha — in float that is the EXACT sum.
- `GLOW_COMPOSE_WGSL` is a 3-vertex fullscreen triangle that `textureLoad`s the HDR target and **tonemaps the MAGNITUDE with the hue kept exact**: `mag = hdr.a`, `hue = hdr.rgb / mag`, `t = x/(1+x)` with `x = mag · GLOW_TONE_EXPOSURE`, output `(clamp(hue)·t, t)` — premultiplied by construction. It composites with **screen** (`one / one-minus-src`), so "a halo can only brighten the backdrop" and the source-over alpha that keeps the transparent agent canvas compositing correctly both survive, applied ONCE.
- **A render pass cannot nest**, so `encodeGlowHdrPass` runs BEFORE `enc.beginRenderPass` in **both** `presentAgentsEncode` and `presentCompositeEncode`; a failed HDR build degrades to NO glow (`const glow = … && encodeGlowHdrPass(…)`), never to a wrong one. The compose draw precedes the plain (core) pipeline, so the **solid-core invariant** is unchanged. **Pipeline BEFORE bind group** at each draw — the compose has a different BGL and a pipeline switch invalidates incompatible groups.
- The HDR texture is canvas-sized: `destroyGlowHdrTex` runs on pipeline REBUILD (the old bind group belongs to the old layout) and in BOTH teardown paths, or every re-attach leaks a full-resolution float target.

**CPU** ([SimulatorView.tsx](src/simulator/SimulatorView.tsx)) — Canvas2D has no float target, so the overlay accumulates the **log encoding** of the same sum.
- **`screen` on PREMULTIPLIED colours is `c ← s + c − s·c` for the colour AND the alpha.** So a sprite baked as `1 − exp(−E·g)` makes the buffer's alpha hold exactly `1 − exp(−E·Σg)` — a **bijective, clipping-free** encoding of the exact sum, with the hue in the un-premultiplied colour. The sprite bake is therefore **unclamped**, matching `fsGlow`.
- **THE TONEMAP RIDES THE BLIT AS AN SVG TRANSFER FUNCTION** (`ensureGlowFilter` → `feComponentTransfer`/`feFuncA type="table"`, 256 entries from `glowTransferTable`), applied with `ctx.filter` on the single `drawImage` of the scratch onto the display. SVG filter primitives operate on **un-premultiplied** RGBA, which is precisely what makes the hue/magnitude split work: remapping ALPHA decodes-and-tonemaps the magnitude while the hue passes through untouched. **`color-interpolation-filters='sRGB'` is mandatory** — filters default to linearRGB and would shift every channel.
- **⚠️ THE READBACK IS THE COST, AND IT IS A FLUSH — MEASURED, NOT ASSUMED.** The first version decoded with a typed-array pass and measured **33.9 ms vs 14.6 ms**. Instrumentation blamed `getImageData` (18.9 ms for ONE call), and a synthetic bench showed **`getImageData(0,0,1,1)` costs the SAME 17.5 ms as reading the whole buffer** after ~4 900 blended `drawImage`s: Chromium DEFERS the blend work and the first read forces it synchronously. `willReadFrequently` does not help; `lighter`/`screen`/`source-over` are all similar; the identical blits with no read cost 9–11 ms. **Any readback of a heavily-blended canvas costs the same** — so the only fix was to not read at all. Result: **15.74 ms, +8 % over the pre-rework path.**
- The scratch is sized to the agents' **screen bbox** (a sparse or zoomed-in model pays only for the covered region), cleared with `'copy'` + transparent, and the core sub-pass stays `source-over`.
- **⚠️ `ctx.globalAlpha` is silently IGNORED on a `drawImage` routed through an SVG `url(#…)` filter** (pre-existing Chromium trap, already recorded for the metaball goo filter) — any per-draw alpha on a filtered blit must be baked into the filter chain.

**THE CURVE + ITS ONE DEFINITION** ([src/simulator/glowTone.ts](src/simulator/glowTone.ts)) — `GLOW_TONE_EXPOSURE` and `glowTransferTable` are imported by BOTH paths so they cannot drift.
- **Reinhard `x/(1+x)`, NOT ACES.** ACES-Narkowicz maps 1.0 → 0.80 with slope 0.21 at the origin — it is scene-referred (1.0 is mid-grey) and would darken a sparse field to a fifth. Reinhard has **slope 1 at the origin** (a faint halo passes through untouched) and a **power-law shoulder**, which keeps discriminating far into the highlights (5 overlaps → 0.90, 30 → 0.98, where an exponential shoulder is flat at 1.0 by 5).
- **On the MAGNITUDE, hue exact** — the `c/(1+l)` branch of the reference's `reinhardJodie` taken to its limit. Both the full Jodie mix and per-channel Reinhard DESATURATE the highlights, and desaturating highlights **is** the reported "oversaturated look". Measured on the same dense frame at Intensity 3, halo pixels with a channel pinned at 255: **37 % (old screen+clamp) / 68 % (full Jodie) / 2.5 % (hue-exact)**; near-WHITE 12.7 % / 0.18 % / 0.03 %. It is also the only form the CPU can reproduce term-for-term.
- **`GLOW_TONE_EXPOSURE = 1.6`**: a lone halo at the default Intensity 0.6 lands at ~0.49 display instead of exactly 0.6. The ~20 % an isolated halo gives up is what buys the entire range above it for accumulation — the same trade the reference makes (its intensity slider tops out at 0.5).
- **`glowEncodeScale(intensity) = 0.2 / max(1, intensity)`** — E is chosen PER INTENSITY so the encodable range is a constant number of OVERLAPPING halos (~27) rather than a constant sum; otherwise Intensity 3 would saturate the 8-bit buffer after two overlaps.
- **CPU↔GPU agreement, measured across 1–30 overlaps**: magnitude within **0.4/255 at every N**. Hue is within 11/255 to ~5 overlaps and then desaturates progressively on the CPU (80/255 at N = 30) — the 8-bit encoding's residual, in the regime where both paths are near-white anyway.

#### 3D agent glow — a dual-Kawase bloom over the AGENT LAYER (branch `polishing`)
The 3D half of the Glow option. **Render-layer only** — `git diff --stat` is [gl3d.ts](src/simulator/render/gl3d.ts) + [SimulatorView.tsx](src/simulator/SimulatorView.tsx) + the harness; **no compiler / worker / engine file**, so compile identity holds by construction.
- **WHY NOT THE 2D SHAPE.** A flat additive billboard pasted on a LIT SPHERE reads as a sticker; a bloom blooms the **SHADING** — the specular highlight, the rim, the lit side of every sphere — which is the depth cue 3D actually wants. What IS shared with 2D is the **compression**: `intensity` scales the blurred layer and the result is compressed ONCE with the same Reinhard `x/(1+x)` on the MAGNITUDE with the hue kept exact, at the same **`GLOW_TONE_EXPOSURE`** ([glowTone.ts](src/simulator/glowTone.ts)) — so the Intensity slider means the same thing in both views.

The only unbounded step is `× intensity`, which happens in the composite shader in float immediately before the tonemap. **That deleted the entire float-FBO-probe risk the handoff had costed.** Consequence, correct for a bloom: 3D density reads as **AREA** (more covered pixels), not as the additive brightness stacked 2D halos give.

Re-drawing rather than reading the finished frame back is what buys two things at once: the bloom SOURCE is agents-only (**a grid+agents model never blooms its lattice**) and the existing render is untouched, so bodies / bonds / voxels / overlays are pixel-identical to a glow-off frame with light merely added on top.
- **Occlusion mirrors the main pass exactly.** With `agentsInFront` ON (the default) the main render clears depth before the agents, so the source pass draws them unoccluded too; with it OFF the voxels' depth is laid into the source FBO **colour-masked** — exact occlusion, zero colour contribution.

#### The SAME bloom in the worker's free-mode WGSL sphere pass — the frame pin is gone (branch `polishing`)
`BLOOM3D_WGSL` ([agentWebgpuRuntime.ts](src/simulator/engine/agentWebgpuRuntime.ts)) is the WGSL sibling of gl3d's `renderAgentBloom`, ported **tap-for-tap and constant-for-constant**, so both renderers bloom equivalently and 3D glow no longer forfeits free mode. **Render-layer only** — `git diff --stat` is agentWebgpuRuntime.ts + SimulatorView.tsx + two harnesses; no compiler/engine file, and `check-compile-identity` reports **29 models, all surfaces unchanged**.
- **THE BLOOM SOURCE IS A SEPARATE, SINGLE-SAMPLED RE-RENDER OF THE SPHERES ALONE** (gl3d's level-0 FBO is single-sampled too — the source gets blurred anyway), so `bloom3dSpherePipeline` is a `multisample: {count: 1}` clone of the sphere pipeline off the SAME module. Re-drawing rather than reading the finished frame back buys the two invariants at once: the source is agents-only (**the scene wireframes and the brush plane never bloom** — they are not in the source pass) and the existing render is untouched.
- **THE COMPOSITE RUNS AFTER THE MSAA RESOLVE**, in its own pass over the swap-chain texture with `loadOp: 'load'` and ONE/ONE blending. **That is mathematically the same image as compositing inside the multisampled pass** — the composite quad has FULL coverage, so it adds the same value C to every sample of a pixel, and an MSAA resolve is a linear average: `avg(dst_i + C) == avg(dst_i) + C` (bar 8-bit saturation at already-bright pixels). Post-resolve therefore needs no multisampled clone of the composite pipeline. gl3d composites onto its own multisampled default framebuffer; the identity is why the two agree.
- **ONE 16-byte `BloomParams` uniform serves the WHOLE chain, written once per present** — the per-level half-pixel step is derived IN the shader from `textureDimensions` (the DOWN pass measures its SOURCE, the UP pass measures `prev`, which IS the destination size — exactly gl3d's `(0.5/sw)` and `(0.5/dw)`), so only `offset` / `spread` / `intensity` / `core` cross the bus. No dynamic offsets, no per-level uniform slots. Registered in [verify-render-uniform-layouts.mjs](scripts/verify-render-uniform-layouts.mjs) per the standing rule.
- **`RenderView3D` IS NOT WIDENED.** The glow settings ride the `setAgentCamera` message as new `AgentRenderView3D` fields and are STASHED on `rt.bloom3dGlow` by `uploadAgentRenderView3D` (the `renderClear` / `renderHalf3D` precedent) rather than written into the uniform — so no existing member's byte offset moves and the harness entry is untouched. **`glowSizePx` is the CSS Size slider ALREADY multiplied by dpr** (the main thread applies it; gl3d computes `size * this.dpr`), so the worker needs no dpr of its own.
- **The glow params are in `postAgentCamera`'s 3D DEDUP KEY** — they ride the camera message, so without them a slider move with a parked camera would keep the previous frame's settings.
- **Lifecycle**: the four pipelines are size-independent and built with the sphere pass; only the canvas-sized level CHAIN is lazy. It is freed at FOUR sites — resize (`ensureBloom3DChain`), pipeline rebuild (the sphere-setup commit), **glow switched off** (`uploadAgentRenderView3D`, mirroring gl3d's `setAgentGlow`), and teardown (`destroyBloom3DResources`, both paths). A WGSL/pipeline failure leaves the pipelines null and `bloom3dActive` false ⇒ the model renders exactly as with glow off.
- **⚠️ NEVER PUT A BACKTICK IN A WGSL COMMENT** — this shader is a TS template literal and one in a comment terminates it (hit again here: nine of them, ~50 lines of phantom parse errors away from the cause).
- **VERIFIED ON THE REAL GPU.** *Seamlessness*: an offscreen rig fed the SHIPPED WGSL chain and the SHIPPED gl3d GLSL chain the **identical** source layer + backdrop and compared pixels — **0 differing bytes of 262,144, maxDelta 0, on all five parameter cases** (default / large-soft / tight-bright / core 1 / core 0.5); non-vacuous by 5 mutations (down weight, up denominator, exposure, level count, spread) each producing 61k–107k differing bytes. *Through the shipped worker path* (`setupAgentDirectRender` → `presentAgentsOnce` on a real 3D layout): all four bloom pipelines compile with **0 shader errors**; glow ON takes lit pixels 2,602 → 12,872 and luminance 5.62M → 6.72M with **0 channels darker**; glow OFF is byte-identical present-to-present, and `size = 0` / `intensity = 0` are byte-identical to OFF; **at core = 1, 956 of 956 eroded body pixels are bit-exact (maxDelta 0)** while 15,811 halo pixels land outside; intensity and size are strictly monotone; the chain is freed on glow-off (4 levels / 5 textures → 0). *Wireframes do not bloom*: with bounds+grid+axes on, **0 of 3,305 wireframe pixels far from any agent gained ANY light (max delta 0)** while 7,619 pixels near the agents did — a positive control in the same measurement. *The pin is gone*: on Particle Life 3D the Glow checkbox leaves `directActive` **true** and posts **zero** `setAgentUiSync` messages, and while playing with glow ON the state reads `uiSyncOn: false` with **6 of 6 `stepped` messages carrying no agent snapshot** — free mode, fully intact. 0 console errors throughout.
- **Guarded** by the `[glow-3d]` block in [verify-agent-render.mjs](scripts/verify-agent-render.mjs) (9 source invariants: source-is-spheres-alone, transparent clear, additive composite, post-resolve `loadOp: 'load'`, the shared exposure constant, hue-exact magnitude tonemap, the core mask, the slider→chain mapping **compared against gl3d's own text**, and the four chain-free sites named individually). **Negative-controlled by SOURCE MUTATION — 8 mutations, 8 caught**: the source pass drawing lines, a non-additive composite, the core mask dropped, a drifted level formula, each of the four chain-free sites removed, and the frame-pin gate term re-added.
- **Still frame-mode-only, deliberately**: **alpha blend** (translucent spheres need back-to-front sorting = gl3d's job) and the frame-mode-only shadows/AO. Recording forces frame mode, so captures keep taking gl3d's bloom; a free-mode SCREENSHOT composites the worker's sphere canvas (halo included) under gl3d's overlays, so it gains the glow too.

##### THE PARAMETER ROWS: the geometry must not depend on the VALUE

- The same sweep covered the agent brush's other rows (`.brushFieldRow` + `.brushFieldLabel` replaced inline `width: 54` labels beside UNSTYLED ~170px NumberFields) and `.fieldRow` gained `flex-wrap: wrap` — it only engages on overflow, so wide panels are unchanged. - **The mirror** (built ONLY when `needScan = usesBondingPhysics || usesSoftCollision || agentUsesDensity` — i.e. the force scan actually runs): a `sortedBuf` (field-major, one contiguous `maxAgents` f32 run per **`agentMirrorFields(is3d)`** field = `['x','y','radius','vx','vy']` 2D / `['x','y','z','radius','vx','vy','vz']` 3D; a field's slot `s` is `sorted[k*maxAgents + s]`) + a `sortedId` u32 array (each CSR slot's canonical agent id). Both live in `AgentResidentRuntime` ([agentWebgpuRuntime.ts](src/simulator/engine/agentWebgpuRuntime.ts)), allocated only under `needScan`. Pure-custom-force models (**Boids / Particle Life** — `customForcesOnly`, no collision/density) skip the scan ⇒ `needScan` false ⇒ **NO mirror buffers, NO mirror scatter, NO mirror force** (zero cost; the resident batch uses the shared per-gen `rt.forcePipeline`). `agentMirrorFields` (exported from [forcePass.ts](src/modeler/vpl/compiler/agentWebgpu/forcePass.ts)) is the SINGLE source shared by the mirror scatter emit + the mirror force scan emit.
- **The mirror scatter** (`emitHashScatterWGSL(layout, withMirror)`): the existing GPU scatter EXTENDS to also write `sorted[k*MA + slot] = agentF32[fieldBase + i]` (one extra store per mirror field) + `sortedId[slot] = i` at the SAME CSR `slot` it writes `binAgents[slot] = i` (same atomic cursor) — so `binAgents`/`sortedId`/the mirror stay index-consistent, and the mirror is a strict SUPERSET of the plain scatter (the behaviour shader still reads `binAgents` for `getNearbyAgents`). Runs only in `dispatchResidentBatch`'s hash build (`if hashValid`) — when the world is too small to tile (`hashValid 0`), no scatter runs and the mirror force falls back to the CANONICAL all-pairs branch.
- **The mirror force pass** (`emitAgentForcePassWGSL(layout, usesForceScatter, mirror)` — a **resident-only variant flag**, default `false`): when `mirror`, the hash-stencil branch reads each neighbour's fields COALESCED from `sorted[k*MA + p]` (+ `j = sortedId[p]` for the self-skip; no `agentAlive[j]` check — the mirror holds only alive agents), while the SELF agent + the all-pairs fallback stay canonical (own slot / `agentF32`). **`mirror` false ⇒ the emitted WGSL is BYTE-IDENTICAL to the pre-B1 force pass** (verified: 2D/3D × scatter on/off all byte-identical), so the per-gen `rt.forcePipeline` + `check-compile-identity` are unaffected. `ensureAgentResident(rt, needScan)` builds a SEPARATE `res.forceMirrorPipeline` (bindings 5=sorted / 6=sortedId added) under `needScan`; `dispatchResidentBatch` routes to it when `res.forceMirrorPipeline` is set, else the shared `rt.forcePipeline`. The mirror buffers are added to the destroy path.

#### 2D agent SPRITES on the worker render — the billboard pass (branch `tasks_batch_2026_08`)
A 2D sprite model could never take a worker render path: `agentRenderModelTermsOk` excluded
sprites outright, so it always paid the CPU overlay (the documented "sprite models are
DRAW-bound" regime). The 2D worker render now carries a **sprite billboard pass** — the WebGPU
sibling of gl3d's `renderSprites` — and the exclusion is **2D-only** from here on. Render-layer
only: `check-compile-identity` reports **31 models, all surfaces unchanged**.
- **THE SEMANTICS ARE THE CPU OVERLAY'S, TERM FOR TERM** (`drawAgentsOverlay`'s sprite branch is
  the reference, and gl3d's 3D pass is the second witness): frame = `floor(spriteFrames)` then
  the negative-safe wrap `((raw % fc) + fc) % fc` (loop) or a clamp (once), `fc <= 1 ⇒ 0`; size =
  `max(radius·scalePx, 1.2)` — **the 1.2 px floor FIRST** — `× 2 × perAgentScale`, aspect-shaped
  so the LONGEST side takes that value; facing = the per-agent compass rotation, OVERRIDDEN by
  `atan2(vx, -vy)` degrees when the asset auto-orients and `|v|² > 1e-9`, then aligned by
  `− defaultDirection + rotationOffset`; alpha = the agent colour's **A byte alone** (a sprite is
  never tinted). A sprite ignores the glow **Core** body shrink, exactly as the overlay does.
- **THE TWO CULLS ARE EXACT COMPLEMENTS, and that is the whole mixed-population design.** The
  disc VS culls an agent whose `spriteMeta[slot-1].frameCount > 0`; the sprite VS culls every
  agent for which that is false. So each agent draws exactly one of the two — never both (a
  coloured disc peeking out behind every sprite) and never neither. `frameCount == 0` is also
  the **not-yet-decoded** marker, so an undecoded / deleted / cleared sprite falls back to a
  circle exactly as the CPU overlay's own fall-through does, with no extra state.
- **The pass, its bindings and its buffers exist ONLY when `layout.spritesReserved`** (a static
  model property known at attach), so a non-sprite model keeps the historical 4-binding disc
  module byte for byte. The disc module is emitted in two variants for the same reason — the
  cull text and binding 4 are interpolated only under that flag.
- **THE ATLAS IS BUILT ON THE MAIN THREAD AND SHIPPED AS ONE TRANSFERRED `ImageBitmap`.** Sprite
  decode is main-thread-only by design (the worker never carries the pixels), and transferring
  the registry's own bitmaps would DETACH them from the CPU overlay and gl3d, which still need
  them — while `copyExternalImageToTexture` cannot rescale, so the frames must be resized to the
  square cell somewhere regardless. `buildAgentSpriteAtlasPayload` therefore draws every decoded
  (sprite, frame) STRETCHED into one `AGENT_SPRITE_ATLAS_CELL`(128) tile of a single grid image
  (gl3d's stretch policy, un-stretched by the aspect-shaped quad) and the worker copies each tile
  into one layer of a `texture_2d_array`, **`premultipliedAlpha: true`** so the FS just scales the
  texel by the agent alpha and feeds the same source-over blend the discs use. The contract — the
  cell size, the `AGENT_SPRITE_MAX_LAYERS`(256, WebGPU's guaranteed `maxTextureArrayLayers`) cap
  and the payload types — lives in the dependency-free leaf
  [agentSpriteAtlas.ts](src/simulator/engine/agentSpriteAtlas.ts) (the `sceneWireframe.ts`
  pattern), so importing it from SimulatorView does not drag the worker module's WGSL into the
  main bundle. Truncation past the cap happens on a **whole-sprite boundary** — half a frame set
  would animate wrongly.
- **THE ATLAS MUST BE RE-SHIPPED ON EVERY `agentRenderStatus` ACK.** The worker CONSUMES (and
  closes) the bitmap, so a rebuilt surface — every display-resize re-attach, every recompile —
  has none and cannot ask for one. `shipSpriteAtlas` also fires on a sprite-set change and on a
  decode completing (`SpriteRegistry.onReady`); a monotonic token closes the bitmap of any build
  a newer one superseded. Over-calling is cheap: a no-sprite model returns before building.
- **The runs are UPLOADED for the render even when the shader never writes them**
  (`spriteRunsUploaded` = `spriteRunsActive || (spritesReserved && spriteRenderActive)`) — sprite
  state can be set from a CPU-side Agent Output Mapping. **The READ plan and both readbacks stay
  on `spriteRunsActive`**, so the CPU remains authoritative between generations
  (`advanceAgentSprites`) and nothing reads back a run the shader never wrote. A2's tight upload
  adds the four sprite runs **plus vx/vy** (the orientToVelocity heading), gated the same way.
- **A resident batch flags `agentGpuUploadPending` after ticking frames**, so the next batch
  seeds the ticked values before it presents — right rate, one batch of offset. (A model whose
  BEHAVIOUR writes sprites blocks residency outright, so this only bites the OM-driven case.)
- **⚠ `target` IS A WGSL RESERVED KEYWORD** — it failed the whole module parse on the first real
  device run (the `ref` trap from the voxel line shader, again). The identifier is `span`, and
  the harness pins the reserved set. The failure was at least LOUD: a sprite-module compile error
  fails the entire pipeline build, which is deliberate — it stops the disc cull being left active
  with no pass to draw what it culled, and the model falls back cleanly to the CPU overlay.
- **Verified on the real GPU** (occluded pane ⇒ a worker-side `debugReadAgentPixels` probe, the
  `debugReadCompositePixels` precedent; it returns lit/opaque/distinct counts **and an FNV pixel
  hash**, which is the only thing that can tell two renders apart when a rotation preserves the
  area). **`Boids - Flocking`** (A2, WASM agents) now reports `directActive: true` — previously
  impossible — and a same-frame A/B at generation 10 with all 260 agents carrying slot 1 gives

  cleared). **`Boids - Hemifield Vision`** (A1, `agentEngineActive: 'webgpu'`, 0 fallback events)

## Direct-render resize re-attach: keep the OLD canvas until the ack commits (the panel-resize frozen-frame fix, 2026-07-27)

**The bug (user-reported on Particle Life + Accretor — i.e. every direct-render family):** resizing a simulator side panel (or the window) changes the display size, which forces a canvas RE-ATTACH on all four worker-presented render paths (2D A1 agent render, E2 composite, 3D agent spheres, L1 voxels — a transferred OffscreenCanvas has fixed dims). The old code flipped `*ActiveRef = false` + dropped the canvas ref immediately, so for the whole handshake (transfer → worker setup → ack → commit) the display fell back to the CPU paths — **whose data free mode deliberately let go STALE** (no snapshots / no colours cross the wire), showing a frozen, badly outdated frame. Both UI-sync drivers **early-return while the render is inactive**, so nothing could even request fresh data during the gap; a slow/deferred/failed attach froze the display indefinitely while the sim kept running.

**The fix ([SimulatorView.tsx](src/simulator/SimulatorView.tsx)) — two rules:**
1. **Keep the OLD canvas through the gap.** The worker keeps presenting into the old OffscreenCanvas until the new attach lands worker-side, so the old canvas is LIVE — the resize blocks now call `maybeAttachAgentCanvas(true)` / `maybeAttachVoxelCanvas(true)` (a new `reattach` param that bypasses the is-active guard) WITHOUT flipping the active refs or dropping the canvas: 2D keeps blitting it (briefly mis-sized), 3D keeps compositing it (CSS-stretched). The attach functions therefore NO LONGER remove the prior DOM canvas up front — the **ack COMMIT removes it** (both `agentRenderStatus` 3D and `voxelRenderStatus` commit branches). Dead-canvas paths (runtime rebuild via `agentRuntimeReady`, WebGPU death via `useWebGPUStatus ready:false` — which also now drops the kept voxel canvas) still remove explicitly.
2. **A FAILED attach forces the sync ON.** New `forceAgentUiSyncOn` / `forceGridUiSyncOn` helpers (mirror assigned in the same statement as the post — the B11 mirror invariant; the harness census in [scripts/verify-agent-render.mjs](scripts/verify-agent-render.mjs) sanctions them) are called from the failure ack branches, so a permanent CPU fallback receives fresh snapshots/colours (the worker's OFF→ON handlers ship one immediately) instead of freezing on the ancient frame. Since the normal drivers early-return while the render is inactive, the one-shot ON sticks — which is exactly right for a dead render path.

**Verified live** (real worker + GPU, occluded pane → protocol/structural evidence): Particle Life (A2) — a viewport resize triggers `attachAgentCanvas` → `ack:true`, and an arc-spy shows ~7 arcs total across the gap (cursor ring) instead of the ~1800/frame a stale CPU-overlay fallback would draw; Accretor (L1 voxel, 300³ WebGPU) — resize → `attachVoxelCanvas` → `ack:true`, the voxel layer ends at exactly 1 canvas (commit removed the old), and `stepped` still ships NO colours (stayed in free mode — no spurious readback). Zero console/GPU errors. tsc + `verify-agent-render` + `verify-render-uniform-layouts` green.
