## Target Compatibility readout + resolved-config annotations (C1 — branch `GRA`)

Phase C1 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C1, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P2** + the **P4 core**; plan + mockup [docs/PLAN_CLARITY_C1.md](docs/PLAN_CLARITY_C1.md)/`.html`). **READ-ONLY — zero behaviour change** (`check-compile-identity`: 29 models byte-identical on every surface; the only worker edit is an import swap to shared helpers computing the same numbers).

### The doctrine — four limitation classes, three principles
Every restriction is one of four classes, and the reasons the UI shows carry the class as a tag: **S** semantics (the engine's execution model cannot express it — a blocker), **R** reproducibility (runs, not bit-reproducibly — a note), **F** fast path (runs identically; only ms/generation differ — never an error), **C** capacity (a resource bound, stated WITH its number — a blocker). They derive from three sentences: (1) **sequential vs parallel** — CPU engines run both, the GPU runs only parallel; (2) **CPU is exact, GPU is statistical**; (3) **speed paths are eligibility, not correctness**. The motivating misread this fixes: *"bonds prevent WebGPU"* is FALSE — bonds forfeit GPU **residency** (class F) and `Graph Metrics - Growth Sweep` ships on WASM for **sweep reproducibility** (class R). Two invisible facts reading as one wall.

### `diagnoseTargets(model)` ([src/model/targetDiagnosis.ts](src/model/targetDiagnosis.ts), pure)
Per layer (grid / agents) × per engine (js / wasm / webgpu) a verdict `{ ok, blockers: Reason[], notes: Reason[] }` + the layer's `requested` / `resolved` / `demotionReason`. **THE RULE: every VERDICT is produced by the function that ENFORCES it** — `detectWebGPUIncompatibilities` / `detectWebGPUModelIncompatibilities` / `detectWasmIncompatibilities` (grid), `isAgentGraphWasmSupported` / `isAgentGraphWebGPUSupported` / `agentTargetOf` (agents), `residencyModelBlockers` (the class-F note), `resolveMaxBonds`. This module NEVER re-implements a gate, so the readout cannot drift.
- **A gate that only answers for the CURRENTLY-selected target is asked HYPOTHETICALLY** via a shallow probe clone with that target selected (`{...model, properties:{...properties, useWebGPU:true}}`) — the honest way to answer "could I use WebGPU?" without duplicating its logic. `detectWebGPUModelIncompatibilities` early-outs on `!useWebGPU`, so without the probe the readout would say "no problem" for every non-WebGPU model.
- **REASON TEXTS are a diagnostic layer ON TOP of the verdict.** The agent gates return a bare boolean, so when one says no the module explains it by reading the gate's OWN tables (`AGENT_WASM_SUPPORTED_TYPES` / `AGENT_WEBGPU_SUPPORTED_TYPES`, `AGENT_NEARBY_SCRATCH_SLOTS` = 4, `AGENT_WEBGPU_NEARBY_SLOTS` = 6) plus exact detectors for the documented op-level fundamentals (median / uniform-random aggregate, toggle/next/previous indicators, a cross-agent overwrite aimed at a WIRED non-spawn id — mirroring the gate's own 4 node types / port names / Create-Agent exemption), and falls back to a generic honest sentence otherwise. **A reason can at worst be unhelpfully generic — never wrong about ✓/✗**, because the verdict never depends on it. Swept: all 29 library models satisfy `verdict ⇔ blocker` consistency.
- **Behaviour-SCOPED walks matter** (`walkAgentBehaviourNodes` / `behaviourReachedIds` — flow edges OUT of a reached node + value edges INTO it, exactly the compilers' `behaviourReachableNodeIds`): `divisionEvent` / `agentInit` / `agentOutputMapping` are compiled separately on the CPU on EVERY engine, so a Create Agent in the **Init Event** must NOT read as a residency blocker — **Particle Life spawns its whole population there and IS resident**. Whole-graph scans got this wrong (and named `agentInit` as an unsupported node type on Ant Necrophoresis). The FIELD term stays whole-graph, matching the worker's `agentUsesField`. Following value edges OUTWARD would be wrong too — a value producer shared with the Division Event would drag that CPU-only subtree in.
- All walks are **macro-aware** (the compilers flatten macros up front), and `LOWERED_AWAY` excludes the pre-compile lowering sources (census / periodic step / composites / …) so a lowered node is never reported as unsupported.

### `residencyModelBlockers` ([src/model/agentResidency.ts](src/model/agentResidency.ts)) — the shared residency terms
`agentResidentEligible()` mixed RUNTIME terms (`rt.ready`, the resolved target, `simulateAgents`) with MODEL-derivable ones. The model half moved here and **the worker CALLS it** (`sim.worker.ts` keeps only its runtime terms), so the engine's decision and the explanation the user reads are ONE predicate — the `resolveMaxBonds` single-source discipline; the main thread never imports the worker. Blockers are ordered most-fundamental-first (structural rewriting → bonds → field → sync attrs → positional → growth → spawn/stop/indicators) so a surface showing only the first reason shows the most explanatory one.
- **`ResidencyGraphFacts.bondSlots` is passed IN, not re-derived**: the worker passes its store's real `s.maxBonds` (what was actually allocated), the UI passes the prediction `resolveMaxBonds(cfg)` — the same number by construction (`createAgentStore` calls that resolver), but the worker reports the allocation it HOLDS so a live config edit that has not yet re-allocated can never make engine and readout disagree.

### `effectiveAgentDt(cfg)` ([centerBased.ts](src/model/centerBased.ts)) — the Δt clamp, explained
The Mathias-2020 bound `Δt ← min(Δt_user, 0.2/μ_eff)`, `μ_eff = μ_R + λ`, extracted verbatim from the worker's `clampAgentDt` (which now calls it — same operands, same order, byte-identical engine) and returning `{ requested, dt, muEff, bound, clamped }`. `clamped` is true only when the bound actually REDUCES the value, so a model sitting exactly on the bound reads as unclamped. **Most agent models ARE clamped and never said so** — e.g. Growing Tissue runs 0.0625, not the 0.1 the panel showed (μ_eff = 3.2); Chemotaxis 0.125 from 0.25.

### `capabilityClosureDrivers(profile)` ([agentCapabilities.ts](src/model/agentCapabilities.ts)) — "(required by X)"
DERIVED from `computeCapabilityClosure`, never a hand-written table: close a baseline containing ONLY capability J at the profile's value and record which OTHER keys the closure raised — those are J's requirements; invert to get each row's drivers. `capStrength` ranks the 3-state modes so "did the closure RAISE it?" is decidable for `motion`/`bonds`/`collision` too. Edit the closure and the annotations follow automatically. (Verified: Growing Tissue → `Motion ← Collision, Bonds, Auto-bond`, `Body ← Collision, Growth, Division`, `Bonds ← Auto-bond`.)

## Generation Pipeline panel (C2 — branch `GRA`)

Phase C2 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C2, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P3** + its tempo tags from Appendix A; plan + mockup [docs/PLAN_CLARITY_C2.md](docs/PLAN_CLARITY_C2.md)/`.html`). **READ-ONLY — zero behaviour change**: one new pure module + one Properties section + one harness; nothing in the engine, the compilers or the worker was touched (`check-compile-identity`: 29 models byte-identical on every surface).

**The gap it closes** (proposal §1.3): the CA-grid contract is legible — *the graph is the rule; the engine double-buffers and runs the colour pass.* The AGENT generation is ~20 interleaved phases, only two or three of which are the user's graphs, and NOTHING showed that sequence, which phases were active for their model, or which resolved values each phase reads. The capability work had already made the GATING real; what was missing was making the PIPELINE visible.

### `describeGenerationPipeline(model)` ([src/model/generationPipeline.ts](src/model/generationPipeline.ts), pure)
Returns `PipelinePhase[]` in EXECUTION order — `{ id, title, owner: 'graph'|'engine', tempo: 'generation'|'event'|'frame'|'reset', active, capability?, detail?, group?, presentation? }`. Companion `describePipelineGroups(model)` gives the bracket headers (the force loop's `×N iterations` from `layoutIterationsOf`) and `integrationFormula(cfg)` the resolved `v = m·v + (Δt/η)·ΣF · cap` line.
- **THE RULE (inherited from C1): every `active` bit and every number comes from the function the ENGINE consults** — `usesSoftCollision` / `usesPositionalCollision` / `usesEngineSprings` / `usesEngineGrowth` / `usesCharge` / `chargeParamsOf` / `chargeMaxDistOf` / `layoutIterationsOf` / `resolveMaxBonds` / `cbNum` / **C1's `effectiveAgentDt`** / `sparseSteppingEnabled`. Never a parallel hand-written truth.
- **Where a GRAPH-CONTENT question has an engine usage gate, that gate is called** rather than scanned locally: `agentGraphUsesBondRequests(model)` (the gate that SIZES the request queue) drives the drain row, `dividePartitionTableForModel(model)` (the table the engine INDEXES at runtime) drives the divisions row + its partition/daughter-bond detail, and `periodicParams(config)` (the lowering's OWN clamp) produces the cadence note. **The one deliberate exception, stated in the module header**: "does the graph contain a Kill Agent / a Division Event root / a sprite / an Output Mapping" has no resolver — the engine simply runs the phase and it no-ops — so those come from the macro-aware `walkNodes` scan (the C1 discipline).
- **Phase order mirrors the shipped loops exactly** (`sim.worker.ts` `runAgentStep` → `runAgentStructuralPhase` → `runStep`, the step-message batch loop, the reset handler's `runInit` → `runGridInit` → `runAgentInit`). **Agents step BEFORE cells** (Decision D-FIELD, the closed agent↔grid loop) — a field-using model additionally gets *"reads/writes the cell field here — your deposit is what the cell step below then sees"* on the behaviour row, which is exactly WHY that order holds.
- The canonical order (a grid-only or agents-only model is an ordered PROJECTION of it, asserted by the harness): `init.cell` `init.grid` `init.agent` → `agent.forceReset` `agent.spatialHash` `agent.primeAttrs` `agent.behaviour` `agent.commitAttrs` → [forces group] `agent.charge` `agent.softCollision` `agent.springs` `agent.integrate` `agent.growth` → `agent.positional` → [structural group] `structural.drain` `structural.death` `structural.divide` `agent.divisionEvent` `structural.autoBond` `structural.sweep` → `agent.sprites` → `cell.asyncOrder` `cell.step` `cell.sparse` `cell.swap` → `indicators` → `color.cells` `color.agents`.
- **`presentation?` is RESERVED and never written by C2** — C8 (the geometry taint check) sets it on the force/motion/layout phases so they can render *"presentation only — does not affect your rule"*. Shipping the field now means C8 needs no shape change.
- **Scope**: it answers what the model ASKS FOR, from the model alone. Whether a fast path actually ENGAGED at runtime is C3's diagnostics popover, deliberately not mixed in. The panel is **not editable** (proposal §4 — a user-orderable engine pipeline reopens every cross-target verification).

### Drift guard — [scripts/test-generation-pipeline.mjs](scripts/test-generation-pipeline.mjs)
**3401 checks.** (1) **Activity ⇔ resolver** over a 288-combination synthetic matrix (bonding × collision off/soft/positional × bonds off/data/physics × growth × charge × auto-bond × sync/async × growthRate), the harness re-deriving each truth from the engine's OWN resolver so a drift in EITHER direction fails; (2) **phase ORDER** against a hard-coded list (+ sub-lists must be ordered projections of it); (3) every shipped model produces a pipeline, with the same resolver spot-checks on REAL configs + per-model assertions for the five verification models; (4) **six in-harness negative controls**. ## Fast-path diagnostics + generated capability docs (C3 — branch `GRA`)

Phase C3 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C3, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P4**-rest + **P8**; plan + mockup [docs/PLAN_CLARITY_C3.md](docs/PLAN_CLARITY_C3.md)/`.html`). **Zero simulation-behaviour change** — the worker edits are array pushes, one counter and one new message case; `check-compile-identity`: 29 models byte-identical on every surface.

**The gap it closes.** C1 made Classes S/R/C inspectable before running and C2 made the generation shape inspectable; both describe what the model ASKS FOR. **Class F — fast-path eligibility — was still folklore**: whether GPU residency / sparse stepping / the E1b field bridge / direct render engaged is decided by ~8-term runtime predicates inside the worker, whose only observers were DEV probes (`__e1bCounters`, `sieActive`, `agentRenderStatus`). And when a fast path degraded AT RUNTIME the evidence was a transient banner or a console line. **C2 describes what the model asks for; C3 reports what actually engaged — they are a pair.**

### `getDiagnostics` — a SUPPORTED worker message (not a `__`-prefixed probe)
Request/reply `getDiagnostics` → `diagnostics`, sent when the popover opens plus a 700 ms poll while it stays open — **ON DEMAND ONLY, never per step**. Every field is read from state the worker ALREADY maintains: `agentResidentEligible()`, `sieParamsPresent`/`activeSet`, `agentFieldBridgeGpuEligible()` + the E1b counters, `agentCompositeActive`/`agentRenderActive`/`voxelRenderOn()`/`directRender`, the resolved targets, and the new event log. Additive — no existing message shape changed, `verify-agent-render` green.
- **The residency reason comes from the SAME predicate the engine decided with.** The reply calls **`residencyModelBlockers`** (C1's shared module) with the WORKER's facts — the compiler flags it was handed (`rt.usesSpawn` / `rt.usesStop` / `rt.indicatorsBuf`) and the bond capacity it actually ALLOCATED (`s.maxBonds`). This **replaces C1's node-type approximation** (its own report filed that as C3's job): where the two differ, the popover shows the worker's answer, because it is the one the engine acted on.
- **`residency.engaged` is a real counter, not the eligibility predicate.** `residentBatchCount` bumps where `runAgentBatchResident` actually SUCCEEDS, so a model that qualifies but whose pipeline build failed reads *eligible, not engaged* rather than lying.
- **`sieActiveCount()`** was extracted out of `sendColors`, so the `◩ N active` stats chip and the popover's Sparse row read ONE expression and cannot disagree (verified: both said `1,795`).
- A path that does not APPLY to the model reports **`n/a` with the reason**, never a fabricated blocker — residency on a WASM-agent model is not "blocked by your graph".

### The runtime fallback log
A capped module-level `runtimeEvents` (`RUNTIME_EVENT_CAP = 40`, oldest dropped) of `{ gen, text }`. **`postFallback(message)`** replaces the bare `self.postMessage({type:'error'})` at the **15 ENGINE-FALLBACK sites** — the grid + agent WASM instantiate/compile/run failures, the agent WebGPU build/step/resident-batch failures, both spatial-hash-overflow fallbacks, and every `[webgpu]` grid init failure — posting the transient banner AND recording it. **Ordinary operational errors are deliberately NOT logged** (a failed colour pass, a readback that threw): keeping the log to genuine "we are running something else now" events is what makes an empty Events list a meaningful statement.
- **Two genuinely silent sites were closed**: `startWebGPUInit`'s `!shaderCode` arm set `webgpuGridFailed` with NO message at all, and the shared device's **loss / uncaptured-error hooks were console-only**. The latter lives in `sharedGpuDevice.ts`, which is imported BY the worker and must not import back — so it gained **`setSharedGpuEventSink(fn)`**, a one-line seam the worker installs (absent sink ⇒ exactly the previous behaviour). Uncaptured errors are capped at 3 so one bad dispatch cannot evict the history.
- **Rate limiting reuses the EXISTING warn-once latches** (`agentWasmHashOverflowWarned` / `agentWebgpuHashOverflowWarned`), so a hash overflow logs once, not once per generation.
- **The log is WORKER-scoped**: a model load terminates and recreates the worker, so "this session" means this worker's life and a fresh worker starts empty (measured: 48 reloads of a deliberately-broken model left exactly 1 event). The 40-cap therefore protects a long-lived worker taking repeated per-step fallbacks; a normal session never approaches it.

### P8 — the capability matrix is GENERATED ([scripts/gen-capability-docs.mjs](scripts/gen-capability-docs.mjs) → [src/help/capabilityMatrix.gen.ts](src/help/capabilityMatrix.gen.ts))
Emits a **committed** module HelpView imports, built from the tables the engine enforces with: `AGENT_NODE_REQUIREMENT`, the node registry, `AGENT_WASM_SUPPORTED_TYPES` / `AGENT_WEBGPU_SUPPORTED_TYPES`, `detectWebGPUIncompatibilities`, and the capacity constants. Node-only, using the repo's established esbuild-bundle pattern for importing TS. **`--check` regenerates in memory and fails on drift** (naming the first differing line) — adding a node without regenerating is a red gate, not silent rot.
- **The reject sets are COMPUTED, never listed**: a per-target reject is `registry agent nodes − SUPPORTED_TYPES`.
- **The WebGPU grid reject set is PROBED, not transcribed** — `detectWebGPUIncompatibilities` is an inline switch, not an exported list, so the generator ASKS it: every node × a bare config (catches unconditional rejects) × a candidate-operation list (catches config-dependent ones). The candidate list is the probe's INPUT SPACE; the gate produces every verdict. **The bare-config probe is what distinguishes an unconditional reject from a conditional one** — without it the same reason recurs under every candidate op and a node rejected in all configurations reads as config-dependent (caught by inspecting the first generated output).
- **A node outside a supported set is NOT automatically a gap**, and saying so would be exactly the drift P8 exists to stop. Three DERIVED exemptions: **entryPoint** (`category === 'event'` — the gates walk the behaviour-reachable cone, which never contains a root), **lowered** (**probed**: feed each shipped pre-compile transform — `expandNeighbourCensus` / `expandForceToAgents` / `expandPeriodicSteps` — a one-node graph and see whether the node survives), and **cpuRoot** (`AGENT_WASM_CPU_ROOT_TYPES`). Each row carries `wasmStatus`/`webgpuStatus` = `yes` | `exempt` | `no`. After the exemptions there is **NO genuine gap on either agent target** — `setAgentSprite` was the last one and it now emits on WASM AND WebGPU (see “Set Agent Sprite on the WASM agent target” + “… on the WebGPU agent target”), so the generated counts read `agentGapsWasm: 0` and `agentGapsWebgpu: 0`.
- **Counts stop being hand-typed.** Help said "around 115 selectable node types (42 agent)" while `NODES_REFERENCE.md` said 150 / 53 — both typed by hand, both free to rot. It now renders the generated `150 / 53 / 20`.

## One Engine selector: `auto | wasm | webgpu` (+ Debug JS) (C4 — branch `GRA`)

Phase C4 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C4, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P1**; plan + mockup [docs/PLAN_CLARITY_C4.md](docs/PLAN_CLARITY_C4.md)/`.html`). **`check-compile-identity`: 29 models byte-identical on every surface.**

**The gap it closes.** The grid engine was TWO booleans kept mutually exclusive by the UI (plus a worker safety net for hand-edited files that set both), the agent engine a separate enum, and neither had an "I don't care, pick the fast one" option — so **the library's own compile-target policy ("WebGPU where the gates pass, else WASM") was applied by hand, per model, and was invisible to the user**. JS sat in the list as a peer of the production engines even though it exists to be the readable reference.

### Schema — `engine` is the choice, `useWasm`/`useWebGPU` are its MIRROR
- **`ModelProperties.engine?: EngineChoice`** (`'auto' | 'wasm' | 'webgpu' | 'js'`) and **`CenterBasedConfig.agentTarget`** gains `'auto'` ([types.ts](src/model/types.ts)).
- **`useWasm` / `useWebGPU` are NOT deleted** — they become the RESOLVED MIRROR, which is the representation every downstream consumer already reads (the worker init message, `computeLayoutFromModel`, the WebGPU/WASM node gates, `detectWebGPU*Incompatibilities`). Keeping them is what makes this phase byte-identical AND lets an OLDER build open a file written by a newer one. **REMOVAL SCHEDULE: one release cycle of back-compat, then the mirror goes and `engine` is the only representation.** In-app code should read `resolveEngines(model)`, never the raw flags.
- **Migration** [engineFieldMigration.ts](src/model/engineFieldMigration.ts) (`LOAD_MODEL` + `migrateForHarness`): absent `engine` → the EXPLICIT equivalent of the flags (`useWebGPU → 'webgpu'`, else `useWasm → 'wasm'`, else `'js'`; WebGPU wins when both are set, mirroring the worker's own safety net). **A legacy file NEVER becomes `'auto'`** — that is the whole byte-identity argument. `agentTarget` is deliberately left ALONE (absent already resolves to `'js'`). Idempotent, same-reference when unchanged. **NOT wired into `macroImport`**: a `.gcamacro` carries a `MacroDef`, which has no `properties`/`centerBased` — nothing to migrate.
- Defaults: `EMPTY_MODEL.engine = 'auto'`, `defaultCenterBasedConfig().agentTarget = 'auto'`.

### `resolveEngines(model)` — the single source ([engineResolution.ts](src/model/engineResolution.ts))
Returns per layer `{ selected, requested, resolved, reason, auto }` — **selected** = what the user picked (may be `'auto'`), **requested** = the engine that selection asks for (for Auto, its pick), **resolved** = what will actually run after the gates demote. Every verdict comes from the ENFORCING function (`detectWebGPUModelIncompatibilities`, `detectWebGPUIncompatibilities`, `isAgentGraphWasmSupported`, `isAgentGraphWebGPUSupported`, `agentTargetOf`) — the C1 discipline, so the displayed resolution cannot drift from the engine's decision. **MEMOISED on the model object** (WeakMap): the reducer makes a new model object per edit, so it evaluates once per model version and is shared by every caller — including the per-node CaNode badge, which would otherwise be O(N²).

**Auto policy** — since C5 it is *the fastest engine that satisfies the model's declared reproducibility contract* (see the next section; `resolveEngines` also returns that `contract` and any per-layer `contractViolation`):

| layer | policy, in order |
|---|---|
| grid | **WebGPU** when every grid gate passes · else **WASM**. **Contract-INDEPENDENT** — the GPU grid honours Exact |
| agents | **exact** ⇒ WASM if its gate passes, else JS · **statistical** ⇒ WebGPU if its gate passes, else WASM, else JS |

A new (empty, synchronous) model therefore resolves **Auto → WebGPU**. When Auto picks WebGPU on a model with **Skip Isolated Empty Cells** enabled, the reason says so (the GPU ignores sparse stepping) rather than dropping the fact silently. **C4's two hard-coded `if (overseerConfig.enabled) pick = 'wasm'` branches are GONE** — the Overseer never appears in the resolution now; under Exact the agents already land on CPU (the requirement that special case stood in for), and the grid Overseer sample legitimately ships on WebGPU.

**`withResolvedEngine(model)`** bakes the resolution into the mirror + a concrete `agentTarget`. It bakes the **requested** engine, NOT the resolved one: for an EXPLICIT choice the requested target must still be COMPILED, because that compile's error is what produces the user-visible message and C3's fallback event. Auto never picks a failing engine, so requested ≡ resolved there. Returns the SAME reference when nothing changes (memoisation + effect deps untouched). Applied by **`withPipelineModel`** in [SimulatorView.tsx](src/simulator/SimulatorView.tsx) (the model handed to the compilers/worker at init, soft recompile and Show Code) and inside **`serializeModel`** (so a saved file's mirror always matches the live resolution).

## The declared reproducibility contract: `Exact | Statistical` (C5 — branch `GRA`)

Phase C5 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C5, implementing **P10**; plan + mockup [docs/PLAN_CLARITY_C5.md](docs/PLAN_CLARITY_C5.md)/`.html`). **`check-compile-identity`: 29 models byte-identical on every surface** (a resolution + display property; no compiler, worker or engine file is opened for writing).

**The gap it closes.** Tolerance for run-to-run variance was *entangled with target choice*: picking the WebGPU agent target silently meant "I accept that a fixed seed will not reproduce this run", and the one place it genuinely bites — an Overseer sweep — was handled by a hard-coded `overseerConfig.enabled` special case standing in for a property the model never declared.

**Schema (additive, absent ⇒ `'exact'`)**: `ModelProperties.reproducibility?: 'exact' | 'statistical'`. **Exact** = bit-reproducible trajectories, a fixed seed pins a run. **Statistical** = runs are draws from the same distribution; sweeps use N repeats + aggregates (`ovSeriesStat` already computes mean/std/ci95). **GUARDRAIL (stated in the UI)**: Statistical covers *stochastic variance around the SAME rule* — it never licenses answering a different question.

### THE MEASURED ASYMMETRY — why Exact still allows the GPU **grid** but not GPU **agents**
This is the load-bearing fact of the phase, and it is documented elsewhere in this file rather than assumed:
- **WebGPU GRID** — per-CELL PCG seeded from a global seed, and the `setRngSeed` handler **re-derives those streams** (`seedRngState`). A fixed seed therefore DOES reproduce a grid run *on this device* — measured on a 5-run Overseer sweep (**WebGPU 460.8 ± 15.707 reproducible**). f32 costs comparability with the CPU engines and across devices, not the pinning. ⇒ **honours Exact**.
- **WebGPU AGENTS** — per-AGENT PCG seeded **once at runtime creation**; `setRngSeed` never reaches it, so a sweep does not reproduce across two presses of Run Experiment. ⇒ **cannot honour Exact**. This is exactly why the library's documented sweep exception (`Graph Metrics - Growth Sweep`) is an **agent**-target exception while `GoL Replicate Statistics` — a grid Overseer model — **ships on WebGPU**.

So **Exact keeps AGENTS on a CPU engine and leaves the GRID free**, and the grid Auto reason states the asymmetry where the user meets it.

### The modules
- **[reproducibility.ts](src/model/reproducibility.ts)** — `reproducibilityOf` (absent ⇒ exact), the shared copy (`REPRODUCIBILITY_LABEL/SUMMARY/GUARDRAIL`), `inferContract(resolvedAgentEngine)`, `engineHonoursContract` / `contractViolationFor` (**told what RESOLVED rather than resolving anything** — the caller passes `resolveEngines`' answer, so there is exactly one resolution in the system), and `describeSweepMethodology`. Deliberately import-free of `engineResolution`, which imports `reproducibilityOf` from here — one-way, no cycle (the `engineFieldMigration` precedent).
- **[reproducibilityMigration.ts](src/model/reproducibilityMigration.ts)** — `migrateReproducibilityField`, wired into `LOAD_MODEL` + `migrateForHarness` **after `migrateEngineField`** (whose `engine` field the resolution reads). Infers **`'statistical'` iff the RESOLVED agent engine is WebGPU**, else `'exact'` — it READS `resolveEngines` rather than re-deriving, records what the file already does, is idempotent and stable (an explicit target's resolution is contract-independent, so no flip-flop). A user's declared contract is never re-inferred away.

### THE MIGRATION-COHERENCE REQUIREMENT (and why it holds structurally)
> After migration, **every existing library model resolves to exactly the same engines as before this phase.**

C4's migration deliberately never produces `'auto'`, so every shipped file carries an **explicit** engine on both layers and takes the explicit branch of `resolveEngines` — which the contract does not touch. **The contract only ever changes what Auto picks.** Over the shipped library the inference is **11 statistical / 18 exact**, and the 11 are precisely the models already running their agents on the GPU (Boids ×2, Chemotaxis, GoL on Agents, Life on Bonds, the three Tissues, both Particle Lifes, SDCA). The gate asserts this model by model, both layers, two independent ways (the resolved grid engine vs an independently-computed legacy answer; and stripping the migrated field then re-resolving).

### Violations — exactly one, never a blocker
`resolveEngines` sets `LayerResolution.contractViolation` when the RESOLVED engine cannot honour the contract. **Auto consults the contract, so a violation is always a deliberate EXPLICIT choice**, and the sentence names both ways out (switch the Agent Engine, or declare Statistical). It is an amber **note**, never a blocker — the engine runs; it just delivers a weaker guarantee than the model claims. Surfaced in three places, all off the same string: under the Reproducibility radio, as an `[R]` reason + an amber line in the C1 Compatibility readout, and appended to the simulator `⚙` chip's tooltip (riding C1's existing amber `demotions` channel — one mechanism, no new colour).

**Also corrected here**: C1's grid-WebGPU `[R]` note claimed *"a fixed seed does not reproduce a run exactly"*, which the `setRngSeed` fix had already made false for the GRID. It now states the honest per-device version.

### UI
- **Properties → Execution** opens with the **Reproducibility** radio (above Update Mode / Engine, because it now *governs* them; outside the grid-cells gate, since it matters most for an agents-only model). Two options with the shared summaries + the guardrail line, and the amber violation note.
- **Compatibility readout** — the layer header carries a contract chip; the agent WebGPU verdict carries the violation as an `[R]` note whenever the contract is Exact (so the consequence of picking it is visible *before* it is picked).
- **Overseer Experiments panel** — a one-line **methodology** note under Run/Abort, derived by `describeSweepMethodology(contract, resolvedEngines, violation)`: Statistical ⇒ *"repeats + aggregates; a single run is not a result"*; Exact + a GPU layer ⇒ *"pins a run on this device; f32 numbers are engine- and device-specific"*; Exact + all-CPU ⇒ *"two presses produce identical numbers"*; a live violation replaces it in amber.

## Schema hygiene + update-mode vocabulary + loud fallbacks (C6 — branch `GRA`)

Phase C6 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C6, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P5** + the **P4** completion; plan + mockup [docs/PLAN_CLARITY_C6.md](docs/PLAN_CLARITY_C6.md)/`.html`). **`check-compile-identity`: 29 models byte-identical on every surface** — no resolver's logic or signature changed; the phase adds observation, copy and one message field.

### THE AGENT CAPABILITY PROFILE IS AUTHORITATIVE (P5) — verified, not assumed
The claim P5 rests on is that engine physics has ONE source. Each half was checked rather than asserted:
- **LOAD always seeds it.** `LOAD_MODEL` calls `migrateAgentCapabilities` unconditionally, and the earlier guard `if (topologyMode.agents && !centerBased) centerBased = defaultCenterBasedConfig()` guarantees the object it seeds into exists. A non-agent model has no `centerBased` and needs none. The **viewer** goes through the same reducer (`ViewerApp` calls `loadModel`), so an exported presentation is covered too.
- **SAVE always writes it.** `serializeModel` → `stringifyCompact` is a whole-object walker with **no field picking**; `withResolvedEngine` spreads `centerBased`. So load → save **bakes** the inferred profile into the file (a deliberate one-way bake, not a byte-identical round-trip, for a legacy file).
- **Nothing in `src/` writes `customForcesOnly`.** It is read exactly ONCE, in `usesBondingPhysics` ([centerBased.ts](src/model/centerBased.ts)). Only the generator scripts still emit it into the shipped fixtures they author — left alone (shipped model configs are deliberate; the field is inert once a profile is present).

**`legacyPhysicsFlagsInEffect(cfg)`** ([centerBased.ts](src/model/centerBased.ts)) is the OBSERVATION seam: true iff a capability-gated resolver actually took its legacy arm. It is the **exact union of the two fallback conditions, derived from the same field tests** — `!agentCapabilities` (what `usesEngineSprings` / `usesEngineGrowth` branch on, per-OBJECT) OR `collision` not one of the three literals (what `collisionMode` branches on, per-FIELD — so a PARTIAL profile trips it too). **`usesBondingPhysics` is deliberately excluded**: it has no capability control, so it is not a fallback — it is the only mechanism (see the removal schedule). The worker calls it once per worker (`checkLegacyPhysicsFlags`, latched, after `centerBasedConfig` is assigned in `init` AND `recompile`) and emits the C3 event *"legacy physics flags in effect — … Re-save the model to bake the profile."* **Only a hand-edited / script-built file can trigger it**; every model loaded through the app is migrated first (asserted per shipped model in the harness).

**LEGACY-READ REMOVAL SCHEDULE** (the P5 commitment, recorded so a later phase can execute it):

| field / arm | status | when it can go |
|---|---|---|
| `customForcesOnly` | READ once (`usesBondingPhysics`); **no `src/` write** (gate-asserted) | with the arms below — it has no other reader |
| the `?? legacy` arms in `collisionMode` / `usesEngineSprings` / `usesEngineGrowth` / `resolveMaxBonds` | fire only for a profileless config, which now announces itself | **one release after** the shipped generators emit `agentCapabilities` (6 of 14 agent models still rely on load-time inference) |
| `useBondingPhysics` | **NOT on the list** — still the ONLY control for adhesion `μ_A`, which no capability gates | needs an Adhesion capability first |

**Three distinct fallback predicates coexist** in `centerBased.ts` (per-field literal in `collisionMode`; presence-of-object in `usesEngineSprings`/`usesEngineGrowth`; `!== 'off'` on a possibly-undefined field in `resolveMaxBonds`; strict `=== 'on'` with NO fallback in `usesCharge`). C6 does **not** unify them — that would change resolution for partial profiles, and the byte-identity gate forbids it. `legacyPhysicsFlagsInEffect` covers the first two (the ones a whole model can trip); the divergence is recorded here so the removal phase unifies them deliberately.

### Update-mode vocabulary (P5) — the doctrine at the point of choice
Both radios carry Principle 1's words as a subtitle:

| radio | Synchronous | Asynchronous |
|---|---|---|
| CA grid `updateMode` | *(parallel — runs on all engines)* | *(sequential — CPU engines only)* |
| Agents `agentUpdateMode` | *(parallel — runs on all engines)* | *(sequential — a cross-agent write needs a CPU engine)* |

**The agent row deliberately differs, and the difference is load-bearing.** The runbook proposed the identical pair; verbatim it would be FALSE for agents — an async agent model **does** run on WebGPU (`Morphogenesis - Growing Tissue` ships exactly that way). What the parallel GPU cannot honour is a cross-agent **OVERWRITE**, whose landing order only the sequential CPU engines define (`isAgentGraphWebGPUSupported` rejects precisely that, per the "Cross-Agent Write Semantics" section). The subtitle keeps the vocabulary and states the true consequence. The agent sync hint also dropped its stale *"required by the forthcoming WebGPU agent target"* (PX shipped sync on the GPU; **all three** agent engines honour the mode).
- Reject texts realigned: `detectWebGPUModelIncompatibilities` (the sentence C1's readout shows for an async model) and the WebGPU grid engine hint.
- **The per-node texts in `detectWebGPUIncompatibilities` are LEFT ALONE ON PURPOSE.** They are CAPTURED by `check-compile-identity` as `webgpu.error` (Amphiphile / Chromatography / gas_particles carry them in the baseline), so rewording them would fail the byte-identity gate for a cosmetic gain — and they already carry the doctrine (*"WebGPU runs cells in parallel; …"*). **General rule: a compiler-visible error STRING is a captured surface — treat it like emitted code.**

### Loud fallbacks, UI side (P4; C3 built the worker log)
`postFallback` now posts `{ type: 'error', message, fallback: true, gen }`. The main thread's `error` branch splits:
- **`fallback`** → a ONE-TIME amber toast (the `showAgentNotice` pattern; de-duplicated per DISTINCT message per model by a `Set` ref) + `runtimeFallbackCount`, which keeps the ⚙ chip amber (and its `⚠`) for the rest of the session, with the count in the tooltip. **Not** the red banner.
- otherwise → unchanged (`setCompileError`).
- `pendingStep.current = false` runs in BOTH branches — the step-pipeline unblock is untouched, which is why the `error` type was kept rather than a new message type.
- Both the count and the de-dupe set reset on **`modelVersion`**, alongside `diagnostics`.

**Why a PUSH was needed at all:** C3's `runtimeEvents` is **pull-only** — the main thread requests `getDiagnostics` only while the popover is open, so the chip could never learn about a fallback. The pushed flag drives the toast AND the chip; the Events list remains the durable record. A graceful degradation is also not a *compile error*, so painting the red persistent banner for it was a mis-signal.

**The shared-GPU event sink is promoted** from `logRuntimeEvent` to `postFallback` (`setSharedGpuEventSink(postFallback)`) — a lost device / uncaptured device error is the loudest fallback there is and previously reached only the console plus the pull-only log. Uncaptured errors stay capped at 3.

**Deliberately NOT toasted:** the `webgpuGridFailed` "shader was not produced" arm stays log-only (C3's choice — the compiler already reports that reason through the compile-error path; a second toast would double-report), and **compile-time gate clamps show in the C1 readout only**, per the runbook — they are a property of the model, not an event.

So the destructive confirmation still guards the destructive act, AND cancelling the chooser (Esc / backdrop / Cancel) keeps the current model even though the confirm was already accepted. Ordering it the other way would ask the user to choose something that might then be thrown away.
- **Gate**: [scripts/test-archetypes.mjs](scripts/test-archetypes.mjs) (201 checks) — `'empty'` IS `EMPTY_MODEL` (object identity + deep-equal); per card the topology/dimension/preset-match/engine/contract; a real volume for 3D; the two silent failures above; every seed survives `migrateForHarness` unchanged and resolves with no contract violation; both C1/C2 panels can describe it. Negative-controlled by SOURCE MUTATION (dropping the tissue bond ceiling → `tissue: bond store allocated (resolveMaxBonds 0)`).

### P7 — determinism: every simulation-semantic draw is seeded
**`nextRandom()`** ([sim.worker.ts](src/simulator/engine/sim.worker.ts), next to `rngState`) draws from the SHARED stream with the exact xorshift32 (13/17/5) the compiled code uses. It replaced `Math.random()` at the three **sim-semantic** worker sites: `initAgents`' **`seedPattern: 'scatter'`** placement (2 draws/agent in 2D, 3 in 3D), `initGrid`'s **`asyncScheme: 'cyclic'`** one-time order shuffle, and `runStep`'s per-step **`random-order` Fisher–Yates + `random-independent`** picks. The async order was the bigger hole: P7's own claim ("Reset reproduces exactly on the CPU engines") is *false for every asynchronous model* while the visit order is unseeded.
- **THE TRAP (found by verification, and it is the whole reason the fix works): `rngState` and the WASM memory cell are TWO cells.** The JS-compiled step reads/writes the module-level `rngState`; the WASM-compiled step loads/stores its own `_rs` in `wasmMemory` at `layout.rngStateOffset`. They were synced only at `initGrid` and by `setRngSeed`. A `nextRandom()` that only touched `rngState` therefore ran on a stream **nothing else consumed** on a WASM model — measured directly with a temporary probe: after `setRngSeed(4242)` + one step, `js = 3748443150` while `wasm` was still `4242`. So `nextRandom` READS whichever cell the ACTIVE engine advances (`rngCellView && wasmStepFn` ⇒ the WASM cell, else `rngState`) and WRITES **both** — the same discipline `setRngSeed` already used. `rngCellView` is the module-level view assigned in `initGrid`.
- **`initGrid` publishes the RNG to the WASM cell AFTER the order block**, not before: the cyclic shuffle now advances the stream, and syncing first would leave the WASM cell `total` draws stale for the Init Event that runs next.
- **The behaviour change, stated honestly**: scatter layouts and async visit orders **differ once** from before — they are drawn from the shared stream instead of the platform RNG. They were **never** reproducible before, so nothing that was pinned becomes unpinned.
- **Two things deliberately unchanged.** The module-load seed stays `Date.now()`-derived (a constant would make every user's first run of every stochastic model identical — a far bigger change than P7 asks for; determinism is something you ASK for). And **Reset does not re-seed** — the stream advances across Resets, which is already the documented behaviour of the cell Init Event's `getRandom`; agent scatter now MATCHES the cell side instead of contradicting it. Pinning is `setRngSeed` then Reset — the protocol the Overseer already uses.
- **The async order shuffle is IN PLACE over the running permutation**, so "same seed ⇒ same order" holds from the same starting permutation (a full re-init gives one). Comparing two shuffles taken at different points in a session compares different inputs, not different seeds — a real trap when verifying this.
- **Gate**: [scripts/check-no-unseeded-random.mjs](scripts/check-no-unseeded-random.mjs) — greps `src/` for `Math.random`/`crypto.getRandomValues`, subtracts an explicit **allowlist with a reason per file** (id generation; the 🎲 buttons, which GENERATE a seed the model stores; the agent BRUSH, whose stroke Reset never replays and where seeding would make a *repeated* stroke lay down an identical cluster; the unreferenced legacy `SimEngine.ts`), and additionally fails on a **stale** allowlist entry (a file with no draw left silently protects a future one). Both failure modes proven by mutation.

## Presentational geometry: the taint check + the pipeline label (C8 — branch `GRA`)

Phase C8 of the Clarity & Simplification initiative ([HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C8, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P9**, detection only; plan + mockup [docs/PLAN_CLARITY_C8.md](docs/PLAN_CLARITY_C8.md)/`.html`). **`check-compile-identity`: 29 models byte-identical on every surface** — the phase adds ZERO emit impact (no compiler, worker or engine file is opened for writing).

**The gap it closes.** The scariest chunk of implicit engine behaviour in an agent model is the force / motion / layout block — ~7 phases of repulsion, charge, springs, integration, growth and positional projection the user never wrote. For a large class of models that block decides **only where things sit**; for another it is load-bearing. Nothing said which. C8 decides it statically and labels the pipeline: ***presentation only — does not affect your rule***.

### THE FRAMING — a GRANT of freedoms, not a compatibility gate
A model whose rules read positions into decisions is **fully supported** and stays in today's exact, seeded, lockstep regime. Reading a position is a **PROMOTION**: it moves the layout physics from "how the simulation looks" into "part of what the simulation computes", and the exactness obligations follow from that promotion. So neither UI state is styled as a warning — the presentational case is green + informative, the promoted case is plain grey and carries its witness. **C8 grants nothing yet**: layout cadence/location decoupling and the explicit-consent door are later work; this phase only makes the property visible.

### `analyzeGeometryTaint(model)` ([geometryTaint.ts](src/modeler/vpl/compiler/geometryTaint.ts), pure)
→ `{ applicable, presentational, witness?, witnesses[] }`. `applicable` is false for a grid-only model (no layout physics ⇒ the question is meaningless), and an inapplicable model is never `presentational`. **The module header owns the source / sink / exemption tables** — read it, don't duplicate it. The load-bearing rules:
- **THE CRITERION IS DATAFLOW TAINT, NOT "no position-reading node".** Geometry is presentational iff no path leads from a geometry READ into NON-GEOMETRIC STATE.
- **The closed loop stays clean (the Cubic-GRA-midpoint rule).** Geometry into a position / force / velocity / radius write keeps geometry in a closed loop: `Get Self Position → expression → Create Agent.x` does NOT taint. Implemented as `GEOMETRY_ONLY_SINKS` (applyForce* / setVelocity / setAgentPosition / setAgentRadius / setTargetRadius / setCellLooks / setAgentSprite — these never taint whatever feeds them, INCLUDING under a tainted branch gate) plus `GEOMETRY_ONLY_INPUT_PORTS` (`createAgent.{x,y,z,radius}`, `divideAgent.{axisX,axisY,axisZ,asymmetry}` — geometry slots on an otherwise-tainting verb).
- **THE CONSERVATIVE DEFAULT IS TAINT, and it is an INVERSION**: the module allowlists the geometry-only sinks and the pure control-flow nodes; **any OTHER flow node taints** when its value inputs or its branch gate are tainted. A future state-writing node therefore taints from the day it is added unless someone deliberately allowlists it. Same for an unexpandable macro.
- **Port-level granularity is required**, not node-level: `forEachBond.currentLength` is a distance while `partnerId` out of the same node is topology; `behaviourStep.myX/myY/myZ` are geometry while `myBondDegree` is not.
- **A branch CONDITION taints** (a constant written under `if (density > 3)` is still a geometric decision), and the conditional's `next` chain is NOT inside the branch. Gate taint is carried down the flow walk and re-visited monotonically (flow graphs are DAGs — the documented diamond rule).
- **Local variables are CONDUITS, not sinks** — per-agent per-step scratch, so taint flows *through* the variable id (this is exactly what keeps Boids presentational: geometry → 7 local accumulators → Apply Force). A write under a tainted gate taints the variable, which is why the analysis is a **fixpoint** over (value taint ⇄ flow-gate taint), not a single pass.
- **TOPOLOGY IS NOT GEOMETRY** (bond degree, the bonded 1-ring, bond attributes, `neighbourCensus` with `source:'bonded'`) — but topology BUILT from distance is covered by the auto-bond rule below. **AGE is not geometry** (the engine advances it exactly once per generation).
- **RADIUS is a GATED, deliberate EXTENSION of the runbook's source list**: `getRadius` / `getAgentRadius` / `behaviourStep.myRadius|myArea` / `divisionEvent.myArea` are a geometry source **iff the engine growth ramp is active** (`usesEngineGrowth(cfg) && growthRate > 0`) — because the ramp writes the radius INSIDE the force-iteration loop, the very block P9 decouples. With growth off the radius only changes when the graph writes it, so reading it is an ordinary state read. Resolver-driven, so it cannot drift. It changes no shipped verdict (the three tissues that read `myRadius` are tainted twice over anyway).
- **ENGINE-GEOMETRIC CONFIG taints with no wire to follow**: **auto-bond ON** (resolved with the SAME `springs ∧ autoBond ∧ bonds > 0` expression the pipeline panel uses) and a **REACHABLE `divideAgent` whose resolved partition is `tension`** (via `dividePartitionFromConfig` — the engine's own resolver; `alternate` does not taint, and an UNREACHABLE Divide Agent never runs so it never taints).
- **FIELD DEPOSITS taint UNCONDITIONALLY** (`affectCellsUnder` / `secreteToField`): the deposit LOCATION is the agent's position and the cell rule then reads that cell, so the closed agent↔grid loop is geometry → cell state whatever value is deposited.
- **THE CELL GRAPH IS DELIBERATELY NOT WALKED**: a lattice cell's position is FIXED (`Get Cell Position` indexes an immutable grid), so no cell node is a geometry source; the one place agent geometry reaches cell state is the field bridge, caught at the DEPOSIT on the agent side before it ever becomes cell state.
- **Flattening**: `expandMacros` + `collapseReroutes` (the two structural transforms every compiler front-end runs first) so macro internals and reroute relays are analysed for real. All FIVE agent roots are walked (`behaviourStep`, `periodicStep`, `agentInit`, `divisionEvent`, `agentOutputMapping`).
- **Witnesses are readable**: `Get Nearby Agents · agents → For Each In Array → Form Bond · targetAgent`, classified `dataflow` | `condition` | `location` | `engine-config`. The first step names the PORT that made it geometry, so a multi-output node is unambiguous.

### Integration (UI only)
`describeGenerationPipeline` sets **`PipelinePhase.presentation`** on `PRESENTATION_PHASE_IDS` (the movers: force reset, charge, soft collision, springs, integrate, growth, positional projection — the spatial hash is deliberately NOT one, it is a query structure the RULE also reads) when the verdict is presentational. `PhaseRow` renders a green `presentation` chip + the italic label; the block legend gains an entry. The C1 Compatibility readout gains `GeometryTaintNote` — green "Layout is presentation" or grey "Layout is part of your rule" + the first witness. `PRESENTATION_ONLY_LABEL` / `PRESENTATION_ONLY_EXPLAINER` / `GEOMETRY_PROMOTED_EXPLAINER` are exported so the UI, Help and the harness share one string.

### The shipped library, as hand-audited (the full table is in the C8 Completion Report)
**Presentational (4)**: Boids — Flocking · Boids — Hemifield Vision · Particle Life · Particle Life 3D — all geometry → local variables → Apply Force / Set Velocity only. **Tainted (9, after `Cubic GRA` was retired from the library)**: Ant Necrophoresis + Chemotaxis (field reads/deposits at the position) · Game of Life on Agents (proximity count → attribute) · Life on Bonds (**auto-bond alone — its rule graph is entirely clean**) · Graph Metrics + the three Morphogenesis tissues (tension partition / auto-bond / density+radius → Divide Agent) · **SDCA**.

That is geometry → topology by the runbook's OWN criterion; the three checks the runbook named all pass (census over BONDED ✓, no tension partition ✓, auto-bond off ✓) but none of them covers a proximity-seeded Form Bond. The hand-audit wins, and the verdict is correct: if the layout ticked on its own cadence, the positions at bootstrap time would differ and the K4 could form differently.

### Gate — [scripts/test-geometry-taint.mjs](scripts/test-geometry-taint.mjs)

## Library compile-target policy: WebGPU where supported, else WASM (2026-07-27)

Every shipped library model now sets its compile target(s) by ONE rule — **WebGPU wherever the compile gates accept it, else WASM** — applied to BOTH the grid target (`useWebGPU`/`useWasm`) and the agent target (`centerBased.agentTarget`). Surveyed + applied mechanically (a throwaway script compiled every model with each target forced and read the gates); the matching **gen-\* scripts were updated in lockstep** so a re-run doesn't revert (gen-ant-necrophoresis / -chemotaxis / -boids / -gol-agents / -particle-life / -tissue / -tissue3d gained `agentTarget: 'webgpu'` and/or `useWebGPU: true`; gen-life3d + gen-overseer-stats flipped to WebGPU).
