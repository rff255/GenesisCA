## ⚠ A `recompile` THAT REBUILDS A GPU RUNTIME MUST READ THE GPU DOWN FIRST (2026-09-07)

**THE INVARIANT: no rebuild may re-seed a fresh GPU buffer from a CPU mirror that the GPU has been
overwriting.** Break it and the simulation silently REWINDS to the last time that mirror was synced —
the generation counter keeps its value, no error is raised, and the board looks plausible, which is why
it survived every gate for as long as it did.

**It has bitten twice, on both tiers, and the two fixes are siblings in one place** — the message
dispatcher in [sim.worker.ts](src/simulator/engine/sim.worker.ts), which defers the `recompile`, does a
one-shot readback and replays it (`asyncStepBatchInFlight` + `deferredDuringAsyncBatch` +
`endAsyncStepBatch`, the mechanism the P0 async-batch guard already owned):

| Tier | Authoritative when | Stale mirror | The re-seed | One-shot |
|---|---|---|---|---|
| **Agents** (GPU-resident, free mode) | `agentStoreStale` | the CPU `AgentStore` | `agentGpuUploadPending` → the next resident batch uploads the SoA | `ensureAgentStoreFresh()` (audit M3) |
| **CA grid** (WebGPU target) | `gpuOwnsAttrs` — set by EVERY `runStepWebGPU` | the CPU `readAttrs` | `startWebGPUInit` → `uploadAttrs(rt, readAttrs)` after the rebuild | `ensureCpuAttrsFresh()` |

The grid half was the **user-reported "Live syncs by going back to a previous state"** bug (2026-09-07),
and it **pre-dated Live** — the identical rewind happens on the Simulator tab when you edit in the
Modeler and switch back, because the rewind is entirely in the worker's handling of a message both
paths send. Live just makes it happen dozens of times a minute. Measured, same protocol on both sides of
a `git stash`, Game of Life on WebGPU: mirror synced at gen 20, board run on to gen 59, **one** edit →
the board came back **bit-identical to the gen-20 board** (colour hash `2330622239`, 322 lit, vs
`2342589582` / 393 lit an instant earlier) with the counter still at 59; after the fix the same sequence
leaves the board exactly as it was.

- **The readback is gated on `recompileDropsWebGPUGridState(msg)`, NOT on "is this a recompile".** A
  readback is W·H·D·bytes off the GPU and most recompiles keep the running pipeline (`startWebGPUInit`'s
  shader-hash cache returns early for byte-identical WGSL — a node move, a comment edit, a change in a
  graph the grid shader does not read). Paying for those would be a real cost at 5000².
- **⚠ THAT PREDICATE AND THE PIPELINE CACHE ARE ONE FUNCTION, deliberately** —
  `webgpuShaderMatchesRuntime(shaderCode)`. A re-implementation that drifts is silent in the worst
  direction: the dispatcher skips the readback for a rebuild that then happens anyway, and the rewind is
  back. If you touch the cache condition, you have touched the readback condition.
- **The window between teardown and the async rebuild is already CPU-stepped** (`webgpuRuntime` is null,
  so `runStep` falls through to JS/WASM out of `readAttrs`), which is the second reason the CPU mirror
  has to be right at that moment — those generations were running on stale data too, and the later
  `uploadAttrs` shipped the result to the GPU.
- **WASM is NOT affected and must not grow a copy of this**: `tryInstantiateWasmModule` re-instantiates
  against the SAME `wasmMemory` the worker owns, so the grid state never leaves the module's memory.
- The `setUseWasm` / `setUseWebGPU` handlers already drained GPU→CPU before tearing the runtime down;
  `recompile` was the one teardown path that did not.

## LIVE mode adds NO worker message (2026-09-07)

**Live** (the split workspace — see [`simulator-ui.md`](simulator-ui.md)) is layout, mounting and input
ownership. It introduces **no new worker message, changes no message shape, and `sim.worker.ts` has no
diff**; four existing present-only messages (`refreshDisplay`, `setGridCamera` + `refreshGridDisplay`,
`setAgentCamera` + `refreshAgentDisplay`, and the `attach*Canvas` re-attach) simply fire on a new trigger.

⚠ **The one thing to know from this side is the LAST-GOOD-RULE contract.** `compileFns` does
`stepFn = stepCode ? eval(stepCode) : null` (and the same for `agentBehaviourFn`), so **any `recompile`
the worker receives replaces the running rule — including with nothing, when the compile failed.** That
is deliberate and unchanged. Live keeps the previous rule by **never sending the message**: the main
thread's model effect returns before `postMessage({type:'recompile'})` when the graph does not compile.
So if you ever make the worker tolerant of an empty `stepCode`, or add a recovery path here, know that
the feature relying on this behaviour lives on the *other* side of the boundary and expects a withheld
message to be a no-op — which it is, by construction.

### Simulation Engine (SoA Architecture)
- `src/simulator/engine/sim.worker.ts` — Web Worker owns grid as Structure of Arrays
- Grid storage: one typed array per attribute (`Uint8Array` bool, `Int32Array` int/tag, `Float64Array` float), double-buffered (sync) or single-buffer (async)
- Tag attributes: `Int32Array`, value = index into `tagOptions` string array
- Model attribute bounds: optional `hasBounds`, `min`, `max` fields on `Attribute` type (integer/float model attrs only). When both min & max set, simulator shows range slider alongside spinbox. Values clamped at UI level, no worker enforcement.
- Color model attributes: stored as 3 entries (`attrId_r`, `attrId_g`, `attrId_b`) in cachedModelAttrs
- Neighbor access: pre-computed `Int32Array` index tables (built at init, handles torus/constant boundary once)
- Step function is LOOP-WRAPPED: `(total, r_<attrs>..., w_<attrs>..., nIdx_<nbrs>..., nSz_<nbrs>..., modelAttrs, colors, activeViewer[, order])` — contains the for-loop, called ONCE per step
- Async mode: `order` param is an Int32Array of shuffled/random cell indices; loop uses `idx = order[_i]` instead of `idx = _i`; r_ and w_ params point to same typed arrays (single buffer); copy lines are skipped; buffer swap is skipped after step
- Async schemes: `random-order` (Fisher-Yates shuffle per step), `random-independent` (N random picks with replacement), `cyclic` (one-time shuffle at init)
- InputColor functions remain per-cell: `(_r, _g, _b, idx, r_<attrs>..., ...)`
- **Get Random — EVERY parameter is an input PORT with an inline widget** ([GetRandomNode.ts](src/modeler/vpl/nodes/GetRandomNode.ts)), so a rule can drive the interval / the distribution parameters / the vector reference from a wire (a model attribute, an expression, a neighbour read) instead of a fixed number. Modes: `bool` (`P` port) · `integer` (`Min`/`Max`) · `float` ("Decimal") · `orientation` · `options` (`Options`/`Fallback`) · **`vector`** · **`color`**. `hiddenPorts` gates every port on the mode AND the distribution — the whole matrix lives once on the def.
  - **`distribution` config (DECIMAL only)** — `uniform` (absent/default ⇒ `min + u·(max−min)`, byte-identical to the historical emit) · **`normal`** (`Mean`/`Std Dev`, Box-Muller `mean + sd·(sqrt(−2·ln(1−u1))·cos(2π·u2))`) · **`exponential`** (`Mean`, inverse-CDF `mean·(−ln(1−u))`). Integer stays uniform-only (a discrete Gaussian is a separate feature) and `randomDistribution()` enforces that.
  - **THE DRAW-COUNT CONTRACT — every distribution is FIXED-COUNT, never a rejection loop**: normal = **2** stream advances, everything else = **1** (`randomDrawCount`, exported and asserted by the harness). That is what keeps the shared xorshift32 (JS/WASM) and the per-cell/per-agent PCG (WebGPU) advancing in lockstep. **`1 − u` (not `u`) is the log argument on every target** — `u ∈ [0,1)` so `1−u ∈ (0,1]` and `ln` can never see 0; exponential takes a MEAN rather than a rate so there is no divide, hence no ÷0 guard to keep in step across six emitters (Mean 0 degenerates to exactly 0).
  - **`vector` mode is MULTI-OUTPUT** — `X` / `Y` plus a composite `Vector` port. ONE draw picks an angular offset uniform in ±`Span°`/2, applied as a screen-clockwise ROTATION of the reference unit vector; `Norm` scales it. **Compass convention: 0° = north = −y, 90° = east = +x** (the sprite `atan2(dx, −dy)` heading convention), so a reference unit is `(sin θ, −cos θ)`. The reference is a compass `Angle°` OR (config `refSource: 'vector'`) a wired `Dir X`/`Dir Y`; a ZERO wired direction falls back to north via a single select over an eps-guarded normalise (`1/max(len, 1e-30)` ⇒ `0·1e30 = 0`, never NaN). **ROTATING rather than adding to a computed reference ANGLE is load-bearing: it needs only sin/cos of the OFFSET, so the wired-direction path needs no `atan2` — which the cell WASM module does not import** (and adding an import would shift every module's func indices). Planar (XY) even in a 3D model; a spherical mode is a follow-up. Registered in `isMultiOutput` (config-conditional, like `getModelAttribute`'s `isColorAttr`) + the Overseer's `refFor`; the JS emit also aliases `_v<id>_value` to X so a stale edge from a previous mode can't ReferenceError.
  - **`color` mode is MULTI-OUTPUT too** — `R` / `G` / `B` (integer 0..255) plus a composite `Color` port, and it is the one mode with a draw count > 1 outside `normal`: **THREE draws, in the order R, G, B**, registered in `randomDrawCount` and asserted by the harness. Each channel is `floor(u * 256) & 255`. **The `& 255` mask mirrors orientation's `& 3`**: on JS/WASM `u = _rs / 2^32 < 1` so it can never bite, but the f32 GPU uniform can round to exactly 1.0 — and keeping the mask on every target makes the six emits textually parallel. **NO alpha is drawn, deliberately** (a random opacity is almost never what a rule wants), so the composite `Color` port carries a LITERAL 255 and a rule that wants a random alpha wires its own through Make Color. Colour mode has no numeric parameters at all, so `hiddenPorts` only ADDS the four outputs and hides the scalar `value`. Registered alongside `vector` in `isMultiOutput` + the Overseer's `refFor`; the JS emit aliases `_v<id>_value` to R for the same stale-edge reason.
  - **The composite `Vector` output costs NO extra draw**: `expandComposites`' `vecComponentsOf` lowers it to plain wires back to THIS node's `x`/`y` ports (never to synthesized arithmetic), so both components resolve through the one multi-output emit. **The composite `Color` output works the identical way** — the same arm branches on `config.randomType` and returns wires to this node's `r`/`g`/`b` plus `LIT('255')` for alpha, so a `Color` wire through Break Color still costs exactly the three draws.
  - **BYTE-IDENTITY is preserved by folding at compile time when the range is UNWIRED.** All five compiled surfaces keep the historical constant-fold (`f64Const(max − min)` / the baked WGSL literal) when neither `min` nor `max` is wired, and only take a runtime-span path when one is — so all 29 shipped models are byte-identical on every surface. Wiredness is read from `inputToSource` (WebGPU/agents) or `isInline()` (cell WASM), never from the presence of `inputs[...]`, because an unwired inline port still arrives as a constant ValueRef.
  - **Migration** [getRandomRangeMigration.ts](src/model/getRandomRangeMigration.ts) (LOAD_MODEL + `macroImport` + `migrateForHarness`) re-keys legacy `config.min`/`config.max` onto `_port_min`/`_port_max` across the cell / agent / overseer graphs + every macroDef, value-for-value and idempotent. Without it the UI would show the port default while the compiler used the legacy value.
  - **⚠ PRE-EXISTING (not introduced here, deliberately out of scope): a CELL graph holding SEVERAL RNG nodes where at least one has a WIRED value input assigns the draws in a different ORDER on JS (flow order) than on WASM (sink-analysis topo order)** — reproducible today on the untouched bool + wired-`probability` path, so it is not specific to the new ports. The AGENT compilers are immune (RNG nodes are flow-ordered via the volatile seeding). Fixing it would move the emit order of essentially every existing model, so `scripts/test-get-random.mjs` isolates ONE Get Random per model instead.
  - **Gates**: [scripts/test-get-random.mjs](scripts/test-get-random.mjs) (150 checks — node def + hiddenPorts matrix + draw counts + the migration + CELL JS-vs-REAL-WASM values and bit-parity for every mode + the compass convention + the colour channel range/independence/draw-ORDER + both composite lowerings + the WGSL emit + BOTH agent gates accepting colour and BOTH agent backends emitting it + an Overseer driver run) and the permanent `[synthetic] Get Random …` entry in [scripts/parity-agent-wasm.mjs](scripts/parity-agent-wasm.mjs), whose VALUE invariant is stream-INDEPENDENT (σ=0 ⇒ exactly the mean; span 0 ⇒ an exact direction; |v| = Norm) so a mutation applied identically to BOTH targets — which parity cannot see — is still caught.
- **Mode-dependent dead ports are hidden DECLARATIVELY via `NodeTypeDef.hiddenPorts?(config) => string[]`** ([types.ts](src/modeler/vpl/types.ts)): each node def returns the ids of STATIC ports that carry no meaning under the current config, and BOTH CaNode's render path AND [effectivePorts.ts](src/modeler/vpl/effectivePorts.ts) `getEffectivePorts` apply the SAME hook as a final filter — so the rule lives **once on the node def** and can't drift between the two (this replaced the parallel inline `if`-block filters that previously had to be hand-kept-in-sync). Current `hiddenPorts` users: `getModelAttribute` (R/G/B vs Value by `isColorAttr`), `logicOperator` (hide B for NOT), `updateAttribute` + `updateIndicator` (hide Value for the unary `toggle`/`next`/`previous` ops), `getRandom` (the full mode x distribution matrix: probability only for bool, options+fallback only for options mode, Min/Max only for integer + uniform decimal, Mean/StdDev only for the normal/exponential decimal distributions, the vector block + the X/Y/Vector OUTPUTS only for vector mode -- which in turn hides the scalar `value` output, and swaps Angle for Dir X/Y by `refSource`; the R/G/B/Color OUTPUTS only for color mode, which likewise hides `value`), `statement` + `groupCounting` (hide the upper bound unless a between-family op), `groupOperator` (hide `Position`/`index` unless `max`/`min`/`random`/`weightedRandom` — those are the only ops that pick a real index; the rest emit a constant `-1`, the op set is `GROUP_OPERATOR_POSITION_OPS` in [GroupOperatorNode.ts](src/modeler/vpl/nodes/GroupOperatorNode.ts)), `arithmeticOperator` (Math — hide Y for the unary ops, the set `ARITHMETIC_UNARY_OPS` in [ArithmeticOperatorNode.ts](src/modeler/vpl/nodes/ArithmeticOperatorNode.ts): `sqrt`/`abs`/`negate`/`floor`/`ceil`/`round` + the transcendentals). Hiding is **UI-only** (inputs AND outputs): the compilers ignore the dead port, and any pre-existing edge into/out of it simply goes unread, so it's always safe. **Nodes that ADD or TRANSFORM ports per config — `switch` (case_N + value-widget swap + hide value in conditions mode), `sequence` (then_N), `expression` (slice to visibleCount + relabel) — keep that logic inline in both files** (the hook only REMOVES static ports). When adding a new node whose port set depends on a mode, add `hiddenPorts` to its def rather than a new inline filter. (The audit that produced this — `audit-mode-dependent-ports` workflow — checked all 71 nodes against all 3 compile targets and found Math + Update Indicator were the only un-gated cases.)
- GetNeighborsAttribute uses `_scr_<nodeId>` scratch arrays declared before the loop — never allocate in hot path
- **varName() registration**: Any node whose `compile()` emits a non-default output variable (e.g., `_v${id}_result`, `_v${id}_vals`, `_scr_${id}`) MUST have a matching special case in `varName()` in compile.ts. Without this, downstream nodes reference the wrong (undeclared) variable. Also register scratch arrays in all three locations: main pass, macro inline, nested macro inline.
- NEVER use `fn(...args)` in per-cell loops — V8 megamorphic spread kills performance
- Play pipeline chains from worker message handler (not rAF): receive result → draw → send next step
- Color output: the merged `setCellLooks` node (plain mode, or glyph mode with `setBackground`) writes directly to the RGBA `colors` buffer, checks `activeViewer` for multi-viewer support. See the "Set Cell Looks" major section for the full node shape.
- **`setCellLooks` "Current Simulator Selected"** (`config.mappingId === CURRENT_VIEWER_SENTINEL` = `'__current__'`, exported from [SetCellLooksNode.ts](src/modeler/vpl/nodes/SetCellLooksNode.ts)): writes WHICHEVER output mapping is active instead of one fixed mapping, so one graph can serve several viewers. **Changes compiled CA code on all three targets** — each emits the writes (colors AND/or glyph) WITHOUT the `activeViewer` guard for the sentinel: JS's `_isV_` hoist (`collectViewerRefs`) skips it (no `_isV___current__` identifier emitted); WASM emits `emitWrites()` unconditionally (the sentinel never enters `viewerIds`, so the `viewerInt!` assertion can't fire); WebGPU drops the `control.activeViewer` step-shader guard AND, inside an output-mapping shader, bypasses the `currentMappingId === viewerId` match (every OM shader writes — harmless since each OM pass is dispatched only for its own mapping, so the sentinel's real flexibility is in the Step color pass). `nodeValidation` accepts the sentinel for `setCellLooks` (the `inputColor`/`outputMapping` case still requires a real mapping). Verified byte-shape on all three via dev-server compiler imports.
- Bool constants use `1`/`0` (not `true`/`false`) for typed array compatibility
- Paint: after InputColor writes to writeAttrs, copy back to readAttrs before runStep()
- Worker mutation handlers (paint, importImage, reset, writeRegion, clearRegion): after mutating cell attributes, refresh the display via `if (hasColorPass) runColorPass(); else if (stepFn) runStep(); else writeDefaultColors(); sendColors();`. Without the fallback, users without an Output Mapping see no visual feedback. **NB for verification:** for a no-Output-Mapping model (GoL, Wireworld, Gray-Scott colour-in-step) this runs a STEP, so a `getState` right after a `writeRegion` reads the POST-step cells — use a model with a real Output Mapping (`hasColorPass`) or an immovable cell value to observe the raw written region.
- **Shape-aware cell copy/paste** (Ctrl+C/V/X), **2D AND 3D**: the region is read as the **bounding BOX** of the current brush footprint (so Circle/Ring copy their disc/annulus, the volumetric brush copies its sphere/shell/box; Line at a single cursor point resolves to its width-dot; no special-casing), but a **shape mask** (Uint8, length `w*h*d`, indexed `(dl*h + dr)*w + dc`) travels with the clipboard so **paste writes only the shape's cells**, leaving the surrounding cells at the target intact (a circle pastes a disc, not a square). `clipboard.{mask,hotL,hotR,hotC}` carries the mask + the cursor's offset within the box so paste re-centres on the cursor exactly the way copy did (rect: `hotR/hotC` = the old `halfH/halfW`, so rectangle copy/paste is byte-identical). Cut (Ctrl+X) clears only the masked cells.
  - **ONE clipboard shape serves both dimensions — 2D is simply the `d === 1` case** (`d`/`hotL` stay absent and default to 1 / 0). The three worker messages (`readRegion` / `writeRegion` / `clearRegion`) gained optional `layer?` + `d?`, and `cellIndexOf(0, r, c) IS r*width+c`, so **the 2D path is byte-for-byte the historical single-layer rectangle**. A 2D clipboard pasted into a 3D model lands as one slice at the hovered layer; a 3D clipboard pasted into a 2D model is clipped by the worker. A clipboard carrying attributes the target model lacks skips them (the write loop iterates the MODEL's `cellAttrs` and looks each up in the payload).
  - **In 3D the anchor is the BRUSH-PLANE cursor** (`hover3dRef`), never the 2D `cursorGrid` (an inert fit-mapping in 3D — driving a region write from it corrupted layer-0 cells far from the plane, which is why the shortcut used to be gated off there). **With the brush plane disabled or no hovered cell the shortcut is a no-op + a hint toast**, never a write. The footprint is EXACTLY what the 3D brush would paint at that cell: the same `currentStampOffsets3d()` through the same plane-axis permutation, now factored into the shared **`planeAxisDelta(axis, dr, dc, dl) → [dLayer, dRow, dCol]`** that `mapStampToPlane` also uses (so the copied set cannot drift from the painted set).
  - **The box is measured in ABSOLUTE grid axes and pasted in the same axes whatever the plane is set to afterwards** — the plane only supplies the ANCHOR cell, it never reorients the contents (a plane-relative reorientation is deliberately out of scope). Deltas are taken **UNWRAPPED** (like 2D), so a footprint straddling a torus seam yields a compact box rather than a grid-spanning one; out-of-range cells read as the attribute DEFAULT on copy and are CLIPPED on paste, on every axis — the 2D behaviour, generalized.
  - **In 3D a copy/cut TOASTS what it grabbed** (`Copied 179 cells (7×7×7 box)`). 2D stays silent on purpose: there the silhouette cursor already shows the footprint and the paste is immediately visible, while a 3D volume is occluded and may be deeper than the plane.

- **GIF DELTA FRAMES + identical-frame delay merging** ([gifEncoder.ts](src/simulator/recording/gifEncoder.ts) `encodeFramesToGif`; the encode was lifted out of `stopRecording` into its own module). The old path wrote every captured frame WHOLE — quantize 256 → `applyPalette` → `writeFrame` — consulting nothing about the previous frame, so a frozen simulation cost exactly as much as a churning one. Two optimisations, and **one rule that makes them safe**:
  - **Identical-frame merge**: a run of byte-identical frames is written ONCE with the summed delay. GIF timing IS per-frame delay, so this is exactly equivalent — and it is the biggest single win (a motionless 40-frame recording: **36 039 → 939 B, 38×**). It also *improves* timing accuracy: the centisecond rounding happens once per RUN instead of once per frame (measured 1240 ms vs 1200 ms against a true 1333 ms).
  - **Transparent-index deltas**: pixels already on screen become a reserved index, `dispose: 1` ("do not dispose"). Full-size frames — what shrinks is the LZW payload.
  - **⚠ THE COMPARISON IS AGAINST THE DECODED IMAGE, NEVER THE SOURCE RGBA.** Each frame has its own quantised palette, so an unchanged source colour can land on a different palette entry and therefore a different RGB. `prevRgb` tracks what the decoder actually holds; a pixel goes transparent only when the new frame would paint the identical RGB. **Measured on a palette-drift fixture: a naive source compare would have left 119 570 pixels stale.** With the decoded compare the delta output is **DECODE-IDENTICAL** to writing every frame whole (verified 0 differing channel values, max delta 0, on both the sparse and the drift fixtures).
  - **⚠ A DELTA IS NOT ALWAYS SMALLER, so the choice is MEASURED per frame, not assumed.** The transparent index is a new symbol that FRAGMENTS the runs LZW was already compressing; where changes are scattered the delta comes out bigger — measured on the shipped **Chromatography** (~32 % of pixels change, spread across the column): 194 999 B full-frame vs **204 057 B all-delta, i.e. −4 %**. So each frame is encoded BOTH ways into a throwaway probe encoder (`probe.reset()` + `bytesView().length`) and the smaller is written, making the path **non-regressive by construction** and adaptive *within* one recording. A cheap predictor was evaluated first (adjacent-symbol transition counts called all 11 Chromatography frames correctly) and REJECTED: a wrong prediction ships a bigger file, and the exact answer costs ~2 extra LZW passes — **LZW is ~2.0 ms of a ~6.2 ms per-frame encode**, paid ONCE at Stop (measured 173 → 365 ms for a 30-frame GIF).
  - **⚠ `dispose` MUST be explicit.** gifenc's default `-1` means "you pick", and its pick for a TRANSPARENT frame is 2 = restore to background — it CLEARS, the exact opposite of a delta.
  - **⚠ The transparent slot is appended only AFTER `applyPalette`.** Its nominal colour is `[0,0,0]`; present during palette application, real black pixels would map onto it and silently vanish. Quantisation targets `GIF_DELTA_COLORS` (255) to leave the slot free — one colour of 256, and **nil on CA content** (verified: Chromatography's 5-colour palette re-encodes **byte-for-byte identical** to the 256-colour baseline).
  - **Global-palette reuse**: a frame whose palette equals the first frame's passes `palette: null`, so it carries no local colour table. The common case for CA content (measured 29 of 30 frames on Chromatography, 39 of 40 on GoL).
  - **SUB-RECT frames are NOT expressible and are not attempted**: gifenc's `encodeImageDescriptor` hard-codes the frame position to (0,0), so a changed-region rectangle could only sit in the top-left corner. Emitting one means writing the image-descriptor bytes around gifenc's LZW output, i.e. forking the encoder. The transparent-index delta already collapses the untouched area into one LZW run; what a sub-rect would additionally save is a few bytes of per-frame descriptor.
  - **Measured spread (honest — the win is entirely about WHERE the change is, not how much):** motionless **38×** · settled GoL 300² (5 % of pixels) **1.33×** · synthetic sparse (1 %) **6.9×** · palette-drift fixture **2.03×** · **live GoL soup 300² (20 %, scattered) 1.00×** (all 39 deltas rejected, +0.0007 %) · Chromatography **1.00×** (all 29 rejected, byte-identical) · synthetic dense noise **1.00×**.

All `SimulationState` fields are optional; `applySimulationState` restores grid and controls independently. When making new shared-serialized fields optional, also audit `readStateFile` validation and every consumer that reads them unconditionally.
- **Save-dialog defaults are PER-LOADED-MODEL, not a program-wide last choice** (`deriveSaveOptions(model)` in [FileMenu.tsx](src/components/FileMenu.tsx); replaced the removed global `localStorage['genesisca_save_options']` whose cross-model leakage silently dropped data). **Presets** — checked iff `model.presets?.length` (a durable model property, so a save never drops the presets a loaded model carries [the reported bug: load a model WITH presets, edit its description, save with presets unchecked because a prior save of a *different* model had omitted them] and never offers "include presets" for a model with none). **Board state / simulator controls** — LIVE-session captures, so the rule is snapshot-aware, NOT a blanket "checked iff already present": when the model carries an embedded `simulationState`, reflect its composition (`attributes` present ⇒ grid ON, `modelAttrs` present ⇒ controls ON — `serializeSimState` writes each only inside its own `wantGrid`/`wantControls` block, so their presence records which layers were last saved for THIS model AND respects a prior explicit omission); when there is NO embedded snapshot (fresh/from-scratch model, or one saved definition-only) default **both ON** — matching the historical convenience default so building a model from scratch, evolving its board / tuning its attributes, and hitting Save still captures that live work. **The ON-fallback is deliberate** (`s ? s.attributes !== undefined : true`, not `s?.attributes !== undefined`): a fresh/evolved model never mirrors its live board+controls into `model.simulationState` until a save actually captures them, so deriving OFF there would silently discard the user's evolved board+tuned attributes on the common "build → evolve → Save" path (an adversarial-review-confirmed regression). Every in-session save rewrites `simulationState` to the chosen composition. **The user's CONFIRMED choice is additionally remembered per loaded model (`sim_agent_fixes` batch)**: `ModelState.lastSaveOptions` (in-session only, never serialized; reset by NEW_MODEL/LOAD_MODEL, recorded via `markSaved(fileName, opts)` on a successful save) — the dialog opens with `lastSaveOptions ?? deriveSaveOptions(model)`, so repeated saves keep the explicit choice (all boxes OFF stays OFF — previously a definition-only save left no snapshot and the deliberate ON-fallback re-checked grid+controls every time), while a freshly loaded model still derives from its own content.
- **The Save dialog also EDITS the model's presentation fields (Name / Rule Author / GenesisCA Project Author), and an edit is a MODEL edit — not a file-only override.** The three fields (`SaveMetadata` in [SaveProjectDialog.tsx](src/components/SaveProjectDialog.tsx), labels copied verbatim from the Info panel, which owns the same three properties) are seeded from the LIVE model by `useState` — safe because the dialog is conditionally mounted, so every open re-seeds. `doSave(opts, meta)` diffs them against `modelRef.current.properties` into a `metaEdits` patch and, **when the patch is non-empty**, does BOTH: `updateProperties(metaEdits)` (so the navbar / Info panel / a later save agree) AND a local merge into `toSerialize` — because `updateProperties` is a dispatch, so reading `model` back inside the same handler would still see the pre-edit values. **The local merge is the authority for the file**, which also makes the write-back independent of whether React flushed during the `genesis-capture-sim-state` await; the capture flow and its `wantsAny`/presets composition are untouched (the merge is applied to the already-composed object). **⚠ THE DISPATCH IS DEFERRED PAST THE WRITE, and that ordering is the whole point of the pair**: `doSave` returns at `if (!saved) return;` and only then dispatches, so a **cancelled native Save As leaves the model EXACTLY as it was** — name, authors, `resetRestoresBoard` and `isDirty` all untouched. Dispatching up front (as this used to) renamed the model even though **no file was ever written**, and additionally left it DIRTY, since `UPDATE_PROPERTIES` sets `isDirty` and the `markSaved` that clears it never ran (reproduced in the real UI: the navbar read `RENAMED BY THE CANCELLED SAVE (…) *`). The file is unaffected by the move — the local merge already carried the edits — and a COMPLETED save still ends clean, because the reducer applies dispatches in order and `MARK_SAVED` follows `UPDATE_PROPERTIES`. **Cancelling the DIALOG** (Cancel / Esc / backdrop) was already safe: it is conditionally mounted, so its `useState` seeds re-read the live model on every open. **`modelFilename` reads `toSerialize`, not `latest`**, so the default filename follows the edited name. **An empty name is barred at the dialog** (Save disabled + the Enter handler guarded) rather than silently ignored — a blank name would strip the navbar title and collapse the filename to `model.gcaproj`. **No edits ⇒ no dispatch and no merge**, so a save with the fields untouched is byte-identical to before (verified: two consecutive saves produce the same 857 427-char JSON) and can't flip `isDirty`. `deriveSaveOptions`/`lastSaveOptions` are untouched; the include-what checkboxes gained one visible consequence — **when the model HAS presets and *Include model presets* is UNTICKED, the row shows an amber warning naming the count** (`--color-warning`), because that combination silently drops them from the file. It is never blocking (omitting them is a legitimate choice) and it exists to guard the `lastSaveOptions` remembered-unchecked path, where the derive rule no longer applies.
- Save/load `ATTR_TYPE_MAP` ([fileOperations.ts](src/model/fileOperations.ts)) MUST list every cell-attr runtime type `createTypedArray` (sim.worker.ts) returns. A missing entry silently falls through to `'float64'`, mislabeling int32 buffers. Round-trips fine for some grid sizes, but constant-boundary's +1 sentinel makes attrs N+1 elements long, so 4(N+1) bytes is non-multiple-of-8 for ~half of all grid sizes — `new Float64Array(buffer)` throws `RangeError: byte length must be a multiple of 8` and `applySimulationState` (no try/catch around `deserializeTypedArray`) aborts the entire load silently. Failure mode: "click load, nothing happens" and the grid stays at the default state. When adding a new cell-attr type, register it in BOTH places at the same time.
- Save/load typed-array views: cell-attrs / colors / `orderArray` / `stopFlag` / `rngState` are all initialised as typed-array VIEWS over `wasmMemory` at baked-in offsets (see initGrid). Any restore handler that reads from a load message MUST copy into the existing view (`for i { dst[i] = src[i] }`) — never reassign the JS reference (`orderArray = new Int32Array(...)`). The WASM step reads through the baked-in memory offset, not the JS reference, so reassigning orphans WASM from JS-side mutations. orderArray hit this in 4d82145 and stayed latent until d581232's NI load fix made loads succeed for affected models — symptom was sequential cell iteration in async mode after load, producing strong directional bias in any rule that writes per-cell during the step.

### Busy / progress overlay — one indicator for every multi-second operation (branch `polishing`)

ONE shared indicator so a long operation always says what it is doing and that the app has not frozen. Store: [src/components/busyState.ts](src/components/busyState.ts) (module-level + pub/sub — the `graphState.ts` pattern, so `App`, `SimulatorView`, `FileMenu`, `ModelsLibrary` and any plain module can all call it with no prop drilling); component: [BusyOverlay.tsx](src/components/BusyOverlay.tsx), mounted ONCE in `App`. API: `beginBusy(label, {determinate?}) → { progress(fraction?, detail?), setLabel(), end() }`; `end()` is idempotent and order-independent.
- **THE PAINT-HONESTY RULE (the whole point).** A progress UI is worthless unless it PAINTS. An operation covered here must either be genuinely async (the work is in the worker, or it awaits) or be made to YIELD between chunks via **`yieldToPaint()`** — a MessageChannel round-trip, NOT `requestAnimationFrame` (rAF is part of the rendering steps, so it is suspended in a hidden/occluded tab and would stall a long encode forever *and* make the operation unverifiable in an automation pane). **Wrapping a still-synchronous block in `beginBusy`/`end` buys NOTHING** — the show-delay timer cannot even fire while the main thread is blocked.
- **`BUSY_SHOW_DELAY_MS` (150) applied uniformly**, so an operation that finishes promptly never flashes a bar. Measured in the real UI: a library-model fetch and four short GIF encodes correctly showed nothing.
- **Overlap policy**: entries are a STACK and the MOST RECENTLY begun visible one shows (the innermost, most specific thing). No queueing or merging.
- **`getBusySnapshot` returns a CACHED object** — `useSyncExternalStore` demands a stable reference, and rebuilding the view per call is an infinite render loop.
- **Covered operations.** Recording stop — **GIF is DETERMINATE** (`encodeFramesToGif` became `async`, taking `onProgress` + a `yieldBudgetMs` [default 16 ms]; the bar tracks frames encoded), WebM is indeterminate (streaming stop is a flush; the buffered path encodes at Stop). Worker reinit — `initWorkerWithDimensions` is the single funnel, so ONE handle covers **grid resize / manual Recompile / model load / image-import resize / CSV-import resize**, ended by the first `stepped`|`ready`|`error` from the fresh worker (`beginWorkerBusy`; ends any previous handle first, so back-to-back reinits cannot strand a bar, plus a 120 s safety net and an unmount teardown). Also: model file read/parse (FileMenu, drag-drop, PWA file handler, library card), the `.gcastate` and `.gcapreset` file reads (a board-carrying one embeds the whole base64 grid + agent store), the paste-centred image import and the keep-grid CSV import.
- **BOARD RESTORES ARE COVERED ON THE LIVE PATH TOO, AND THEY NEED THEIR OWN ACK.** A board-carrying preset / `.gcastate` whose dims already match takes the LIVE path — `applySimulationState` posts `loadState`, nothing reinitialises — and on a large grid / population that is seconds of worker work (every cell attribute copied in, the neighbour tables + active set rebuilt, the agent store deserialised, the GPU re-upload). It **cannot ride `beginWorkerBusy`**, which ends on the next `stepped`: while playing those flow constantly, and an in-flight step's `stepped` typically lands BEFORE the worker even starts the restore, so the bar would vanish at once. So `loadState` carries an optional **`reqId`** and the worker answers with a dedicated **`stateLoaded`** post *from the handler itself* — deliberately its own message type, and its own id namespace, because (a) `stepped` is not the restore's ack and (b) the handler may be DEFERRED by an in-flight step batch and replayed later, so only the handler can say when it ran. Posted from every exit including the WebGPU tail's `catch`, so a failure cannot strand the bar. Main-thread side: `beginStateLoadBusy` / `endStateLoadBusy` (id-matched, ends any previous, 120 s safety net, unmount teardown, and `beginWorkerBusy` ends it so a following reinit supersedes rather than stacks).
- **WHICH BAR A RESTORE GETS IS DECIDED INSIDE `applySimulationState`, not at the call sites** — only it knows which of its paths a given state takes. It takes an optional **`busyLabel`**: the STRUCTURAL branch hands off to `beginWorkerBusy` (the reinit funnel then replaces the label with its own), the LIVE board branch raises the ack-ended bar **above the base64 decode** (which is synchronous and cannot paint — but starting the clock there means the bar appears immediately for the worker's share instead of restarting from zero), and every early-out (grid-less parameter preset, dropped stale snapshot, dimension mismatch) raises NOTHING, which is what stops a bar hanging until its safety net. The **deferred embedded restore** (`pendingSimStateRestore`, which fires right after a structural reinit's bar has ended) passes `'Restoring board…'` — that stretch used to go dark. **A live parameter-only preset still deliberately shows nothing** (it posts no `loadState` at all), and the Overseer's `loadPresetLive` stays silent by design (an automated sweep must not flash a bar per replicate).
- **Measured in the real UI** (Game of Life resized to 3000², a board preset): mid-play the bar is up **213 ms** of a 576 ms load and ends from the `stateLoaded` branch; **negative-controlled** by delivering 3 synthetic `stepped` + a `stateLoaded` carrying a MISMATCHED reqId immediately after the click — the bar still appeared and stayed up **588 ms** across 3 further real `stepped`s before its own id-matched ack ended it (the old `beginWorkerBusy` would have died on the first). A 41.6 MB `.gcastate` dropped mid-play shows `Loading "…"` for 440 ms (5 `stepped`s crossing it) then `Restoring simulation state…`; the structural route shows `Preparing simulation…` (285 ms) then `Restoring board…` (**787 ms**, previously dark). A parameter-only preset records **zero** busy entries and posts no `loadState`; an agent model (Particle Life 3D, WebGPU agents) acks in 176 ms with no bar and no errors.
- **GIF byte-identity is STRUCTURAL, not luck** — all encoder state is in locals of `encodeFramesToGif`, the loop never mutates `frames`, and `stopRecording` clears `recordingRef` synchronously before awaiting, so no capture can append mid-encode. Guarded by [scripts/test-gif-encode-yield.mjs](scripts/test-gif-encode-yield.mjs) (21 checks): yield-every-frame AND the shipped 16 ms budget are byte-identical to `yieldBudgetMs: Infinity`, over a fixture that provably exercises the merge / delta-win / delta-reject / global-palette branches, plus a proof the event loop really does run during a yielding encode (and really does NOT without), and two negative controls.
- **⚠ The top-centre slot is SHARED** by the busy card, the load toast and the SW update banner — the latter two take `.loweredForBusy` while a card is up. That rule is **deliberately a doubled class** (`.loweredForBusy.loweredForBusy`): `.updateBanner` is declared later at equal specificity and won on ORDER, so the offset silently did nothing until the specificity was raised.

### Interruptible step batches (the high-G/F responsiveness fix — branch `updates`)

A `step` batch runs `count` generations back to back. At a high Gens/Frame that is SECONDS of uninterrupted work, and measuring it found **three separate costs**, only one of which was where it looked:

| | measured BEFORE | measured AFTER |
|---|---|---|
| Pause latency, WebGPU grid (MNCA 700², G/F 200, batch ≈ 3.2 s) | 1780 / 1595 / 1621 ms | **108 / 93 / 93 ms** |
| Pause latency, CPU grid (Amphiphile 500² async→WASM, batch ≈ 6.9 s) | **> 5000 ms** (probe timed out, 3/3) | **119 / 104 / 117 ms** |
| rAF during a WebGPU batch | **8–14 fps, max gap 2590 ms**, 15 gaps > 200 ms | **97 fps, max gap 94 ms, 0 > 200 ms** |
| Throughput cost | — | WebGPU **≈ +5 %** batch time; CPU **+0.3 %** (6859 → 6879 ms) |

- **RC1 — CONTROL LATENCY (every target).** Pause is main-thread state and a lower G/F is only read at the next `sendNextStep`, so both waited out the whole in-flight batch.
- **RC2 — FRAME STARVATION (WebGPU grid only).** With no stop event the WebGPU loop never awaited, so it ENCODED all `count` generations in a few ms and the GPU queue saturated; the browser could not composite for the entire batch, which is why the nav/transport bar itself felt frozen while **JS was only 4 % busy**. The CPU-target control (same batch length) showed 75 fps / 92 ms worst gap — that contrast is what identifies this half as GPU-specific, and it is why the fix needs GPU backpressure, not just a yield.
- **RC3 — a ~72 ms main-thread React commit per `setGeneration`** (canvas work in it: 11 ms of 5260 ms). NOT the reported regression and deliberately out of scope — it is *worse* at low G/F (67 % blocked at G/F 1 vs 27 % at G/F 200, since the commit is throttled to 10 Hz) — but it is the reason the worst rAF gap lands at ~90 ms rather than ~35 ms. Dev-build figure; a production build will be lower.

**The mechanism.** Every multi-generation batch loop now runs in **time-budgeted chunks** (`STEP_CHUNK_BUDGET_MS = 32`), yielding via `yieldToEventLoop()` — a **MessageChannel** round-trip, chosen over `setTimeout(0)` because it is a macrotask with no timer clamping (~0.05 ms vs 1–4 ms), which is what makes ~100 yields per multi-second batch cost nothing measurable. Four sites: the sync JS/WASM loop, the WebGPU grid loop, the per-gen agent-WebGPU loop, and the GPU-**resident** agent batch (sliced, so residency is preserved *within* a slice).
- **The WebGPU grid boundary is driven by SUBMISSION DEPTH, not wall time.** A wall-clock pacer never fires there (encoding is fast; the batch's whole duration is the GPU draining), so it drains every `gensPerDrain` generations with `device.queue.onSubmittedWorkDone()` — the backpressure IS the compositor fix. `gensPerDrain` is *measured*, not guessed: it extrapolates the previous drain's real cost to the budget, and instrumentation confirmed it converges to 2 generations / 34 ms on the 700² model (so a batch that fits in one chunk never drains at all).
- **A chunk boundary is NOT a batch boundary.** The indicator scan, the colour pass and the single `stepped` all still happen exactly once at the true end of the batch, so nothing an observer can see (chart history, end conditions, recording cadence, the Overseer) changes.
- **G/F 1 takes the literal old fully-synchronous path** (`msg.count > 1` gates the new one) — no promise, no deferral, no chunk bookkeeping.
- The deferral this arms is **not a new restriction**: in the old synchronous loop those same messages simply waited in the event loop until the batch's task ended, and `endAsyncStepBatch` replays them after `stepped` is posted — the same observable sequence.

**`cancelStep`** ([sim.worker.ts](src/simulator/engine/sim.worker.ts)) is the control-plane escape hatch, posted by SimulatorView when the user **pauses** (the single `useEffect([playing])` seam covers button / Enter / Esc / an end condition / a Stop Event) and when **G/F is LOWERED while playing** (only a decrease — raising it asks for more work). Two rules make it safe:
- **It is handled BEFORE the `asyncStepBatchInFlight` deferral guard** — deferring it would replay it after the very batch it was meant to shorten. Safe there precisely because it is pure control plane: it sets a flag the loops poll at chunk boundaries and touches no state.
- **An Overseer batch (`reqId` set) is never cancelled.** `ovRunGenerations` is a FIXED-count run (the ensemble's fixed developmental time point), so a short batch would silently bias the statistics. Verified: the replicate experiment is bit-identical across runs before and after (30 replicates, mean 263.2 / std 70.352 / min 149 / max 374), with 0 cancels posted.

**⚠️ THE NON-OBVIOUS HALF — a cancel must also DISCARD step batches already QUEUED.** The main thread can legitimately have **more than one** batch outstanding: *every* `sendColors()` posts a `stepped` — including ones from init / reset / a colour pass / a mutation — and the play loop's handler treats any `stepped` as "my batch finished", clearing `pendingStep` and issuing another step. Harmless while batches merely run back to back; but once a batch can be cancelled, that stale queued batch is replayed immediately afterwards and runs to completion. Measured symptom: a cancel correctly cut its own batch to 54 generations, then the simulation lurched **200 more generations over a 3.2 s stall** with the worker's event loop fully responsive the whole time (all pings 0 ms — which is what proved it was a queued message, not a block). So `cancelStep` filters `deferredDuringAsyncBatch`, dropping `step` messages **without** a `reqId` (Overseer batches are kept — the runtime awaits that exact reqId and would hang). Filtering *at the moment the cancel is processed* is what makes it precise: it removes exactly the batches issued under the intent the user just revoked, while a step arriving afterwards is the new intent and survives.

## Grid Init Event (global procedural seeding — all 3 targets)

A SECOND cell-grid init entry-point, the free-form GLOBAL counterpart to the per-cell Init Event — the exact analogue of the **Agent Init Event**. The per-cell `initEvent` runs once for EVERY lattice cell (the engine loop is the outer loop, so it can only answer "should THIS cell be seeded?"); the new **Grid Init Event** (`gridInit`) runs **EXACTLY ONCE**, so the user wires a Loop (or nested Loops) inside its DO chain and writes ARBITRARY cells with **Set Cell (at Position)** — imperative seeding the per-cell init can't express (place N random seeds, draw a line/shape, seed the middle box). Additive/opt-in: a model without a Grid Init Event is byte-identical.

### The two nodes ([GridInitEventNode.ts](src/modeler/vpl/nodes/GridInitEventNode.ts) + [SetCellAtPositionNode.ts](src/modeler/vpl/nodes/SetCellAtPositionNode.ts))
- **`gridInit`** ("Grid Init Event") — a white `event` root, SINGLETON (in `SINGLETON_NODE_TYPES`), in `MULTI_OUTPUT_TYPES` (its value-outs resolve via `_v<id>_<port>`). Value-outs: `width` (W), `height` (H), and `depth` (D, hidden in 2D via `hiddenPorts`/`is3dModelLike`) — so seeding is grid-size-independent (seed the middle at `width/2`). `compile()` returns `''` (root; the compiler emits the once-only function). It has NO "current cell", so per-cell reads (Get Cell Attribute / Get Cell Position — which need `idx`) don't apply here — a runtime `idx is not defined` surfaces via the worker if misused (same caveat as the Agent Init Event's per-agent readers).
- **`setCellAtPosition`** ("Set Cell (at Position)") — an `output` flow node: `x`/`y`/`z` (z hidden in 2D) + `value` (the type-adaptive widget — bool/tag/number by the chosen attribute's type, same `effectiveWidget` swap + attribute dropdown as Set Attribute) + config `attributeId`. Its `compile()` evaluates each coordinate ONCE into an int local (a wired getRandom source would else advance the RNG twice), bounds-checks against the grid, and writes `w_<attr>[idx]` — 2D `idx = _cy*W + _cx`, 3D `idx = _cz*W*H + _cy*W + _cx` (picked by `ctx.is3d`). Out-of-range positions are skipped. **JS-only emit** (see below).

### The design — JS-executed once, on EVERY compile target (the Agent Init Event precedent)
`gridInit` compiles to **ONE JS function executed once in the worker (`runGridInit`), regardless of the model's compile target** — exactly like `agentInit`/`divisionEvent` (JS-on-CPU while the behaviour runs on WASM/WebGPU). So there is **NO WASM/WebGPU emitter** for these two nodes and no `expandX`-style lowering, yet the feature works IDENTICALLY on JS/WASM/WebGPU because the WASM/WebGPU **step** compilers only walk the `step`/`initEvent`/mapping roots — they NEVER see `gridInit` (not a root they look for) or `setCellAtPosition` (only reachable from `gridInit`). The seeding is a one-time pass, so nothing is lost by not using WASM/WebGPU. **This satisfies the ALL-TARGET rule** — the feature runs on all three targets; it is not a JS-only clamp of a step-hot feature.
- **Compiler** ([compile.ts](src/modeler/vpl/compiler/compile.ts)): emits `gridInitCode` (the `CompileResult.gridInitCode` field) right after the per-cell `initCode`, using the SAME `omParams` signature (called with `buildLoopArgs()`, like `initFn`) — no loop wrapper. Order: scratch decls → Local Variables (`buildVariableJS(model.variables)` — the scalar `let`s + array fills run ONCE, so a counter persists across the user's Loop) → the `_v<id>_width/height/depth = W/H/D` preamble (emitted BEFORE `preLoopValueLines` so a loop-invariant `width/2` sees them) → `_rs` → value/flow lines.
- **Worker** ([sim.worker.ts](src/simulator/engine/sim.worker.ts)): `gridInitFn` (eval'd in `compileFns`, alongside `initFn`; `gridInitCode` rides `InitMsg`/`RecompileMsg`). `runGridInit()` runs on Reset AND first load, AFTER `runInit()` (so a global seed is the final word), gated on `gridCellsEnabled`. Buffer discipline mirrors `runInit`: it runs right after `resetGrid`/`initGrid` (so `readAttrs === attrsA`), sync mode seeds the write buffer from the read buffer, runs the fn (which writes specific `w_<attr>` cells), then copies write→read; async mode shares one buffer. Under WASM the `r_`/`w_` params are views over `wasmMemory`, so writes land in the right region and the WASM step reads them; under WebGPU **a gridInit model always takes the CPU init path**: `runInit`'s GPU-init shortcut AND the reset handler's `useGPUInit` are both gated on `gridInitFn === null` — the Grid Init's seed is CPU-written, so the CPU must be the init authority end-to-end (per-cell init runs via the JS `initFn`, gridInit seeds on top, then the reset handler's `!useGPUInit` branch uploads the COMPLETE state; the WebGPU-ready handler's `uploadAttrs` covers first load). Without that gate, a model with BOTH events (the Accretor: per-cell `border` + gridInit seed) dispatched the GPU init, skipped the upload, and the seed silently never reached the GPU — Reset showed nothing (a user-reported bug, fixed + verified: Accretor-on-WebGPU Reset seeds asym/sym + grows; Life3D's initEvent-only GPU-init path unregressed). `hadInit`/`loadHadInit` include `gridInitFn` so the post-init colour refresh fires.
- **Gating**: both nodes are in `LATTICE_ONLY_TYPES` (hidden on the Agents graph); `detectMissingConfig` badges `setCellAtPosition` without an attribute; Show Code adds a "Grid Init Event (global, runs once on Reset)" section.
- **Verified** end-to-end through the REAL worker (`getState`): a model seeding the middle (`width/2`,`height/2`[,`depth/2`]) + a Loop-drawn line via a Local-Variable counter produces the EXACT same cells on **JS / WASM / WebGPU × 2D / 3D** (all 6 combinations identical: 2D `[[0,0]..[4,0],[7,7]]`, 3D `[[0,0,0]..[0,0,4],[4,4,4]]`); Reset re-runs it (a painted stray cell is cleared, the seeds return); both nodes render in the Modeler; hidden on the Agents graph; tsc + `npm run build` clean.

## Skip Isolated Empty Cells (opt-in large-grid optimization — branch `sim_agent_fixes`)

The step is normally **O(total cells)** — at 300³ (27M cells) every generation runs the full rule (incl. the 26-neighbour gather) on every cell even though the vast majority are isolated empty cells that provably can't change, and the precomputed neighbour-index tables are `total×nSz×4` bytes (**2.8 GB / ~10 s init at 300³**). This opt-in feature makes the step **O(active cells)** (the growing SURFACE + the structure, not the volume) and replaces the tables with inline neighbour computation. Plan + phase log: [docs/PLAN_LARGE_GRID_PERF.md](docs/PLAN_LARGE_GRID_PERF.md). **OFF by default → every existing model byte-identical** (proven by check-compile-identity per phase). Measured: the Accretor at **300³ inits in ~1.9 s (was ~10 s) with no 2.8 GB table and steps ~10 gens/s** (the remaining per-gen cost is the O(total) bulk copy + linked-indicator scan + colours ship, not the rule).

### The user contract (Properties → Execution → "Skip Isolated Empty Cells", CA-grid models only)
When enabled the user MUST pick: the **empty attribute** + the **empty value** (what "empty" means — tag/bool/int/float, type-adaptive widget), and a **processing range** (a neighbourhood OR a radius+metric). A cell is **ACTIVE** iff it's within the (symmetrized) range of a non-empty cell; only active cells run the Generation Step + the (post-batch) colour pass. **Painting is NEVER gated** — every mutation handler writes directly, then rebuilds the active set (a painted isolated cell activates + is processed next step — verified: painting a border cell at 300³ fired the model's edge-stop from that cell's own step). The range must ⊇ the rule's read-neighbourhood (the user's responsibility — it's opt-in; e.g. the Accretor's radius-1 Moore box covers its face/edge/corner reads because growth requires faceCount ≥ 1).

### Scope + gating
- `ModelProperties.skipIsolatedEmpty?: SkipIsolatedEmptyConfig` ([types.ts](src/model/types.ts)) — `{ enabled, emptyAttributeId, emptyValue, rangeKind: 'neighborhood'|'radius', neighborhoodId?, radius?, radiusMetric? }`. Additive; ModelContext cascades clear/remap on attribute/neighbourhood delete + tagOptions edits.
- **`sparseSteppingEnabled(model)`** ([sparseStepping.ts](src/modeler/vpl/compiler/sparseStepping.ts) — its own tiny module so wasm/layout.ts imports it without a cycle; re-exported from compile.ts) = enabled + **synchronous** + gridCells + **no glyphs**. Async is rejected by design (single-buffer + shuffled order is incompatible with list iteration); **glyph models are excluded** (the per-pass glyph zero-fill assumes a FULL repaint — a sparse loop would erase inactive cells' glyphs; they keep the full loop, correct but not accelerated). **WebGPU ignores the feature** (runs full — correct, since sparse==full; a GPU stream-compaction pass is a possible follow-up). **Any config change forces a FULL worker reinit** (SimulatorView `needsFullInit`) — the config drives the baked layout + step signature. The worker's mirror predicate (`sieParamsPresent` + the initGrid layout flag) matches ALL four terms.
- **Sub-attributes under sparse**: sub-attrs normally skip the bulk copy (their per-cell conditional copy scrubs non-matching cells) — but the per-cell copy only runs for ACTIVE cells, so in sparse mode sub-attrs JOIN the bulk copy on BOTH JS (`sparseBulk` gate in bulkCopyLines) and WASM (`!layout.sparseStepping &&` in emitBulkCopyLines). Active cells still scrub (their conditional copy overwrites on top — identical); inactive cells carry storage forward, which is INVISIBLE behind the parent-match guard (reads, iteration, linked indicators all apply it). Without this, an inactive cell's w-buffer held two-generations-old data after the swap.

### The active set ([src/simulator/engine/activeSet.ts](src/simulator/engine/activeSet.ts) — shared by the worker AND the Node harness)
Reference-counted: `nearCount[idx]` = # of non-empty cells within range; `list`/`member`/`count` + `staleCount`→`compactActiveSet` (so non-monotonic models stay correct — counts go up AND down). `buildActiveOffsets` (neighbourhood coords symmetrized ∪ origin, or a radius ball by chebyshev/manhattan/euclidean), `rebuildActiveSet` (O(total) scan — init/reset/gridInit/loadState/every mutation via `refreshColorsAfterInputJS`), `applyTransition` (per empty↔non-empty flip, ±1 dilation). **`ActiveSet.list` is a VIEW over wasmMemory at `layout.activeListOffset`** — the sparse WASM step reads the live list via the baked offset and the JS step reads the same view through its arg: zero per-step copies. In `runStep`, transitions are detected AFTER the step fn and BEFORE the buffer swap (readAttrs = pre-step, writeAttrs = post-step — true on JS ref-swap AND WASM attrsA/attrsB).

### Compile changes (JS + WASM lockstep; OFF = byte-identical)
- **JS** ([compile.ts](src/modeler/vpl/compiler/compile.ts)): the sync step + the colour pass emit a dual loop — `if (_activeList) { for over the list } else { full 0..total }` — with `_activeList`/`_activeCount` appended LAST to the params. Linked-indicator aggregation is NOT embedded when sparse (it would only see active cells) — the worker runs the full-grid `computeLinkedIndicatorsFromBuffer` instead (the WASM pattern).
- **WASM** ([wasm/compile.ts](src/modeler/vpl/compiler/wasm/compile.ts)): loop entries (step + outputMapping) gain a 2nd `activeCount` i32 param — `>= 0` iterates the active-list region, `-1` = the full loop (the worker's sentinel). The historical loop is extracted into `emitCellLoop` (byte-identical when non-sparse); the body is emitted twice (once per branch — emitBody is re-entrant). A 5th func type `(i32,i32)->()` is appended ONLY in sparse modules.
- **Colour pass**: SPARSE only for the post-step-batch pass (`runColorPass(true)` — inactive cells never step, so their colour inputs are provably frozen); **FULL** for paint / reset / model-attr edit / viewer switch / load (any event that can change an inactive cell's colour) and **always for glyph models** (the per-pass glyph zero-fill would erase inactive cells' glyphs). `buildLoopArgs(useActiveList)` passes a null list to force full.

### Inline neighbours (the 300³ unblock)
When the feature is on, the per-neighbourhood region holds **`nSz` PACKED NIs** (packNI/packNI3 — [wasm/layout.ts](src/modeler/vpl/compiler/wasm/layout.ts) sizes it `size×4` instead of `total×size×4`), filled once by the worker ([sim.worker.ts](src/simulator/engine/sim.worker.ts) `buildNeighborIndices`' sparse branch — one fill serves both targets, the JS arg is a view over the same region; the constant-boundary sentinel fill is kept). Emitters decode each slot inline — **the exact torus-wrap / constant-sentinel math the big table precomputed**, so results are byte-identical: JS via `CompileContext.inlineNbr` + `niCellExprStmts` ([GetNeighborsAttributeNode](src/modeler/vpl/nodes/GetNeighborsAttributeNode.ts) + [GetNeighborAttributeByTagNode](src/modeler/vpl/nodes/GetNeighborAttributeByTagNode.ts)); WASM via `pushInlineNbrCellIdx` (slot's packed NI → the existing `pushNiCellIdx`) at all 6 reachable table-read sites (byTag / groupStatement / random pick / the aggregate main loop / median-scratch / sub-attr-random-scratch / groupCounting-indexes). **Aggregate FUSION is disabled in sparse mode on JS** (the fused builders read the per-cell table; unfused, the gather materialises through the inline-aware scratch fill — negligible on sparse cells). `setNeighborhoodAttribute` is async-only → structurally unreachable in (sync-only) sparse mode. The `_activeList`/`_activeCount`/packed-`nIdx` args are appended/threaded through `buildLoopParams`/`buildCellParams`/the OM params + the worker's `buildLoopArgs`/`buildCellArgs` (ABI-mirror discipline; `sieParamsPresent` is the worker's mirror predicate, and the layout flag rides `computeMemoryLayout(..., sparseStepping)` — set BEFORE `initGrid` from the init message).

### Verification ([scripts/verify-sparse-stepping.mjs](scripts/verify-sparse-stepping.mjs) — run `--wasm` for the full matrix)
The proof standard for any change touching this feature: a feature-OFF compile (classic table) is the REFERENCE; the feature-ON arms — JS sparse-list, JS inline-full (null list), WASM sparse (real instantiated module, list in wasm memory), WASM inline-full (-1) — must produce **byte-identical grids after every step**, on 2D + 3D minimal accretion models that stay genuinely sparse (maxActive ~36-48%), plus a layout-shrink assertion. Also verified END-TO-END through the real worker: Accretor ON == OFF at a fixed RNG seed (identical grid hashes, JS + WASM); a too-small range (corners) ≠ full (proves the gating is real); painting isolated cells works at 300³.

### Gotchas (several found by the adversarial review + fixed)
- The **active set covers the whole STRUCTURE + shell, not just the surface** — a non-empty cell is always active (range 0 of itself). For the Accretor, frozen interior cells still step but short-circuit cheaply (isEmpty gate). Skipping frozen non-empty cells would be a different (model-specific) contract — the feature's name is the contract: only isolated EMPTY cells are skipped.
- **Agent-topology models are EXCLUDED** (in the predicate + both worker mirrors): the field bridge deposits into the cell read buffer OUTSIDE the step, so the active set can never see those transitions — a deposit into an isolated cell would silently never activate it. Agent models keep the full loop.
- **Constant boundary + a NON-empty boundary value on the empty attribute → worker falls back to full** (setupActiveSet sentinel guard): every border-adjacent cell can read the always-non-empty sentinel, a state NO range choice covers. The common empty-boundary configuration (the Accretor) is unaffected.
- **`sieColorDirtyAll`** forces the next colour pass FULL after (a) a `compactActiveSet` (a just-emptied cell removed from the list before the batch-end pass would keep its stale colour) and (b) `updateModelAttrs`/`updateLookupTable` (both are legitimate OM inputs — inactive cells' colours may need recomputing). Cleared once a full pass runs.
- **Incremental linked indicators (the REAL 300³ payoff — found by benchmarking, not review):** the per-gen full-grid indicator scan (`computeLinkedIndicatorsFromBuffer`) costs **~775 ms/gen at 27M cells** — it DWARFED the sparse step (~5 ms) and made the feature look useless end-to-end (OFF 1302 → ON 813 ms/gen, a perceptual wash — the user-reported "no significant difference"). Fixed two ways in [sim.worker.ts](src/simulator/engine/sim.worker.ts): (1) **sparse-incremental** — when EVERY linked def is eligible (plain cell attr, non-spatial, `total` or `frequency` over bool/tag/integer — float-freq bins depend on the global min/max, genuinely non-incremental), the aggregates are maintained from the SAME O(active) diff loop that maintains the active set (`sieLinkedFreq`/`sieLinkedTotal` raw-numeric Maps + `emitSieLinkedResults` producing the scan-identical string-keyed shape; baseline recount in `rebuildActiveSetFromGrid`); exact per-generation values → works at ANY Gens/Frame, accumulated included. (2) **batch-tail deferral** — when incremental doesn't apply and no linked def is `accumulated`, the batch loops pass `runStep(deferIndicatorScan=true)` and the scan+spatial run ONCE at the batch tail (`indicatorScanPending`) — identical observables (the stepped message / end conditions / Overseer all read once per batch); gated to `(callWasm || sieParamsPresent)` so the plain-JS target (which embeds the aggregation in the loop) is untouched. Measured at 300³: **OFF 1302 → ON 40 ms/gen (G/F 20) / 167 ms per frame (G/F 1, now dominated by the 108 MB colours ship + voxel rescan — render, not simulation)**. Parity verified end-to-end: grid hash AND indicator values identical ON-incremental (1-gen batches) vs OFF-scan (5-gen deferred batches).
- **Observability (`sieActive`)**: every `stepped` message carries the live active-cell count (`-1` = feature configured but NOT engaged — excluded combination / invalid config — full loop running); the simulator stats overlay renders **"◩ N active (x%)"** or an amber **"◩ skip-empty inactive"**. This exists because silent fallbacks made "is it even on?" unanswerable — keep it working when touching the feature.
- **Where the feature CANNOT help (tell users, don't debug):** MNCA-class models — dense soups with huge neighbourhoods (the range must cover the LARGEST read-neighbourhood; dilating a soup by radius ~10 covers ~the whole grid → active ≈ 100% = pure overhead, and on the JS target fusion is disabled → measurably WORSE) — and any model on the WebGPU target (documented no-op). The feature's home turf is compact structures growing through a large empty volume (accretion, crystal growth, maze builders).
- **Range size is capped at 30000 offsets** (worker bail + the UI radius max 15): `nearCount` is Uint16 — an oversized range could overflow it in dense regions and a wrap would drop genuinely-active cells at the next compaction.
- Per-gen costs that remain O(total): the sync bulk copy (w←r, ~30 ms/gen at 27M). Per-FRAME (amortized by Gens/Frame): the colours ship (108 MB) + the main-thread voxel-renderer rescan. The indicator scan is NO LONGER per-gen (see the incremental/deferral bullet above).
- `readRegion` read layer 0 only (noted while verifying paint at 300³) — **fixed**: it now takes an optional `layer`/`d` box, absent ⇒ the historical single slice at layer 0 (see "Shape-aware cell copy/paste").
- **Open follow-up / investigation — [docs/INVESTIGATION_HASHLIFE_SPARSE_GRID.md](docs/INVESTIGATION_HASHLIFE_SPARSE_GRID.md)** (+ `.html`): generalising the predicate from ONE "empty" value to a **SET of stable values** (worker-only, no compiler surface — measured **2.08× → 25.19×** on the shipped Wildfire, whose terminal `Burned` state no single value can skip), the quiescence/dirty term, O(active) MEMORY (chunked / unbounded), a HashLife path (measured: **only 3 of the 31 shipped models could even pass its purity gate, and all three are Game of Life** — a live model attribute alone rejects 13), and the WebGPU stream compaction that would end the documented no-op. Also records that **the Accretor is the only shipped model carrying a config and it is `enabled: false`** — the feature has zero users in the library.
