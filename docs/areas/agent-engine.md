## Bond-Graph Agents — Floating Cells (milestone, branch `agents_floating_cells`)

A **second, co-resident engine** the sim worker owns alongside the lattice CA:
floating, continuous-position "cells" (AGENTS) that sense each other (NEIGHBOUR
access), are pushed by **graph-authored forces** (flocking/chemotaxis) AND the
engine soft-sphere, join by **bonds**, **grow**, and **divide along their tension
axis** into a connected tissue, with a **closed agent↔grid feedback** (the cell
CA *is* the morphogen field). The largest net-new subsystem GenesisCA has added.
**The agent ENGINE/driver runs on JS** (Phase F ports it to WASM later); the
**GRID/CELL FIELD has an INDEPENDENT compile target** (Decision D-TARGET, fully
relaxed in Phase 2). A WASM grid shares `wasmMemory` views with the JS agent (no
bridge — the agent reads/writes `readAttrs` directly). A **WebGPU grid** now works
too (e.g. chemical diffusion on the GPU) via a per-step **field-readback bridge**:
when the agent graph uses the field, the worker reads the GPU attrs back to CPU
before the agent gather and uploads the deposit before the cell step — so the grid
gets the GPU fast path while agents stay JS. The independent agent target lives on
`CenterBasedConfig.agentTarget` (`'js'` default; WASM/WebGPU agent loops are
Phase F — `agentTargetOf` clamps to `'js'` until they land). The JS/WASM step loop
is byte-identical (the agent interleave is ONLY in the WebGPU step branch). The
agent COMPUTE is 3D-aware (the engine runAgentStep / divideAgent eigensolve + the
JS *and* WASM neighbour-query emitters all handle a `W×H×D` world), and gl3d.ts
now ALSO renders 3D agents (sphere impostors + bond lines + textured sprite
billboards — see the control-overhaul + "3D agent sprites" sections).
Three shipped samples
exercise the breadth: **Boids — Flocking** (neighbour access + Apply Force +
momentum), **Morphogenesis — Differential Tissue** (asymmetric division +
maturity + contact inhibition = specialization, not a uniform blob), **Chemotaxis
— Aggregation** (the field bridge + WASM-decoupled diffusion). Runbook:
[docs/HANDOFF_AGENTS_FLOATING_CELLS.md](docs/HANDOFF_AGENTS_FLOATING_CELLS.md).

### Generic Agent Platform — separate agent attributes / variables + the comprehensive node catalogue (current)
Agents are now first-class authorable entities with their OWN state, NOT a reuse of the cell attribute set. **This SUPERSEDES the old "cell attrs DOUBLE as agent attrs" framing.**
- **Agent attributes** — a parallel `CAModel.agentAttributes?: Attribute[]` (agent-only per-agent state, a SEPARATE id-space). The agent SoA + the own-agent channel `r_<id>`/`w_<id>` (behaviour/division loops) are keyed by these via **`agentAttrsOf`** ([src/model/attributeScope.ts](src/model/attributeScope.ts), the single source of truth: `agentAttrsOf` / `cellAttrsOf` / `cellFieldAttrsOf` / `cellFieldWriteAttrsOf`). On the Agents tab the Attributes panel lists `agentAttributes` with its own +Add (ADD/UPDATE/REMOVE_AGENT_ATTRIBUTE reducers); Get/Set/Update Attribute + Get Agent Attribute resolve their dropdown against `agentAttrsOf` (graph-aware via `getActiveGraphKind()`). **Master-detail wiring (bug-fixed):** `AttributesPanelContent` already auto-selects a new agent attr on +Add and resolves the `mode='detail'` editor against `agentAttributes`, but `ModelerView.selectedItemName` (which GATES the second detail PanelShell's visibility via `detailItemName != null`) resolved `attr:<id>` ONLY against `model.attributes` — so an agent-attribute selection returned null and the editor never mounted (creating OR clicking an agent attr did nothing). Fixed by making `selectedItemName` graph-kind-aware: `ModelerView` subscribes to `getActiveGraphKind` and, when the Agents tab is active (`attrAgentMode`), resolves `attr:` against `agentAttributes` THEN the shared MODEL attributes (`isModelAttribute` — a cell attr, not listed on the Agents tab, must NOT resolve there) and `var:` against `agentVariables`. Verified in-app: selecting `alive` and +Add both open the detail editor on the Agents tab.
- **Cell-attribute agent-access permission** — `Attribute.agentAccess?: 'none'|'read'|'readWrite'` on CELL attributes gates the field bridge: `_field_<id>` is threaded ONLY for `cellFieldAttrsOf` (agentAccess !== 'none'); field READ nodes (sampleField/fieldGradient/readCellsUnder) require read, field WRITE nodes (affectCellsUnder/secreteToField) require readWrite. CA cells can NEVER read agent attributes (structural — the cell compilers never see `agentAttributes`). Edited via the "Agent access" control in the cell-attribute detail editor.
- **Agent variables** — a parallel `CAModel.agentVariables?: Variable[]`; `buildVariableJS(variables)` takes a list (cell sites pass `model.variables`, agent sites pass `model.agentVariables`); the variable reducer actions carry `target: 'cell'|'agent'`. The agent-WASM array-var gate reads `agentVariables` (the false-positive fix). The JS compiler's **`sourceYieldsArray`** (which decides array-pass-through vs `[_v]`-wrap when a value feeds an `isArray` input like Get Array Element / Array Length / Aggregate) must ALSO look up BOTH scopes — without the `agentVariables` arm an agent Local-Variable ARRAY was mis-classified as a scalar and wrapped as `[_v]`, so `arrayElement[0]` returned the WHOLE array and `arrayElement[≥1]` returned 0 (`[_v].length===1`), silently corrupting read-modify-write accumulators (e.g. a per-agent force-accumulation loop). Fixed to search `variables` then `agentVariables` (ids are globally unique → unambiguous).
- **Migrations** ([agentAttributeSplitMigration.ts](src/model/agentAttributeSplitMigration.ts) + [variableScopeMigration.ts](src/model/variableScopeMigration.ts), LOAD_MODEL): legacy agent models stored agent state in cell attributes/variables. The split migrations MOVE any cell attr/var referenced as agent state by the agent graph into `agentAttributes`/`agentVariables` (DUPLICATE if also cell-referenced); a cell attr used as a FIELD stays a cell attr + gets `agentAccess`. Idempotent (skip when the agent set is non-empty). Verified: Tissue→agentAttributes=[maturity]; Chemotaxis→chemical stays a cell field (readWrite); Boids→accumulators move to agentVariables; lattice byte-identity preserved.
- **ABI-mirror discipline** — `buildAgentLoopParams`↔`buildAgentLoopArgs` and `buildDivisionParams`↔`buildDivisionArgs` both derive `r_`/`w_` from `agentAttrsOf` and `_field_` from `cellFieldAttrsOf`/the worker's `fieldSpecs` (a separate ordered list from the agent `attrSpecs`); `_lookupTables` rides a pinned slot (after glyphColors, before the field block) gated on the model having a lookupTable model attr. ### Agent polish round (branch `polish_agents`)

### The agent engine ([src/simulator/engine/agentEngine.ts](src/simulator/engine/agentEngine.ts))

- **Allocation/lifecycle**: `allocAgentSlot` (free-list first, else grow, else **-1 REJECT** — overflow surfaces an `agentOverflow` notice, never wraps), `initAgentSlot`, `freeAgentSlot` (breaks ALL bonds + bumps the epoch — the dangling-bond ABI), `seedAgents`, `clearAgents`. **Slot hygiene (`sim_agent_fixes` batch)**: `initAgentSlot` zeroes the WHOLE force accumulator (forceX/Y/Z — the per-step reset only fills 0..highWater at the TOP of a step, so a slot (re)allocated MID-step must not carry a stale force) plus the request PAYLOADS (`divideAxis*/divideAsym/bondForm*`), and `divideAgent` rejects a non-finite mother position/radius instead of minting NaN daughters (invisible spheres whose forces poison neighbours). A phantom-agent audit (instrumented worker runs, 10k+ gens, incl. capacity-saturated) found division atomic on reject — no engine path places a daughter away from its mother.
- **Bonds** are SYMMETRIC (both lists): `formBond`/`breakBond`/`hasBond`/`breakAllBonds`/`sweepStaleBonds`/`snapshotBonds`. `partnerEpoch` stamped at form time → a recycled slot reads epoch-mismatch in the force loop + sweep and is skipped. `formBond` is atomic (capacity-checked both sides; overflow → not formed).
- **The force driver** (`runAgentStep` in [sim.worker.ts](src/simulator/engine/sim.worker.ts)): per generation — **reset `forceX`/`forceY` to 0 → build the uniform spatial hash → run the compiled behaviour fn** (it queries the hash via Get Nearby Agents AND adds to `forceX`/`forceY` via Apply Force) → ONE fused neighbour pass that STARTS each agent's force from `forceX`/`forceY` (the graph-authored force) + adds soft-sphere repulsion/adhesion `μ(d−s)·r̂` (unless `customForcesOnly`) + bond springs `λ(l−L)·r̂` + density-for-next-step → **velocity integration `v = momentum·v + (Δt/η)·F; x += v`** (momentum 0 ⇒ the original overdamped step, byte-identical; > 0 ⇒ flocking inertia; optional `maxSpeed` cap) into the xNext/yNext double-buffer → swap → growth ramp → the structural phase. **The hash is now built BEFORE behaviour** (so Get Nearby Agents can query it) and reused by the force pass; its bin edge = `max(soft-sphere cutoff, neighbourQueryRadius)`. **`buildSpatialHash`**: CSR-style, reused scratch, O(N) instead of O(N²); null for a tiny world → all-pairs fallback. **`clampAgentDt`**: the Mathias-2020 monotonicity clamp `Δt ← min(Δt_user, 0.2/μ_eff)`, `μ_eff = μ_R + λ_max`, re-evaluated at init + on every recompile. Density reads one step stale (the fused-pass cost — fine).
- **The agent loop signature gained** (mirrored in `buildAgentLoopParams` ↔ `buildAgentLoopArgs`): `_agentVX`/`_agentVY`/`_agentForceX`/`_agentForceY` + the spatial-hash params (`_hashValid`/`_hashBinStart`/`_hashBinAgents`/`_hashNBinsX`/`_hashNBinsY`/`_hashBinSizeX`/`_hashBinSizeY`). `_fieldW`/`_fieldH`/`_fieldBoundaryTorus` double as the agent world bounds for neighbour-query torus wrap (world IS the grid 1:1).
- **The structural phase** (`runAgentStructuralPhase`, the only place topology mutates — on the SETTLED post-force state): explicit FormBond/BreakBond requests → death (`freeAgentSlot`) → division (`divideAgent`) → division-event per daughter → opt-in auto-bond by distance (hysteresis: form within `formDistance×contact`, break past `breakDistance×contact`, spatial-hashed) → stale-bond sweep.
- **`divideAgent`** (the morphogenesis headline): the axis is the principal eigenvector of `M = Σ_k max(0, λ_k(l_k−L_k))·(r̂_k⊗r̂_k)` over the agent's bonds (closed-form 2×2 symmetric eigensolve — so a glued cluster divides along its MECHANICAL axis); degenerate fallback = the density-gap minor eigenvector; free agents get a deterministic spread axis. Daughters at `centroid ± ½·radius·m̂`, area split by `asymmetry`, each partner bond partitioned to the NEARER daughter by `sign(dot(offset, m̂))`, a daughter-daughter bond added (tissue connected; free agents separate). **Overflow (maxAgents OR either daughter's maxBonds) REJECTS THE WHOLE DIVISION** (never a half-rewired partner — the riskiest single bug).

It is the HOTTEST per-step agent code (the per-neighbour-pair double loop): the 3×3(×3) hash-stencil neighbour pass (soft-sphere repulsion/adhesion + density) → bond springs → velocity integration (momentum, maxSpeed, drag, dt) → `xNext/yNext[/zNext]` → growth ramp. The handoff's PR6 intentionally kept it in JS to minimise the WASM surface; W1 is the deliberate delta.
- **A SECOND export `forcePass` in the SAME agent module** ([agentWasm/compile.ts](src/modeler/vpl/compiler/agentWasm/compile.ts) `emitForcePass`): a faithful byte-for-byte port of `runAgentStep`'s force loop ([sim.worker.ts](src/simulator/engine/sim.worker.ts)), reading/writing the wasmBacked AgentStore at the `computeAgentMemoryLayout` baked offsets — the SAME memory the JS engine reads (zero glue). It runs RIGHT AFTER the behaviour (same step), reusing the in-memory hash already copied in for `getNearbyAgents` (no extra copy). f64 throughout ⇒ JS↔WASM bit-exact. **The structural phase + the hash build STAY in JS** (run once per step, not per neighbour-pair); `swapPositions` (a copy-into under wasmBacked views, B10) commits the new positions as before.
- **2D vs 3D** is a SEPARATE verbatim code path (the `if (is3d)` split mirrors the JS loop — NOT a branchless always-0-dz body — so the 2D arithmetic + stencil count are identical). The hash path skips the alive check (`buildSpatialHash` only bins alive agents); the all-pairs fallback adds it. Density counts regardless of bonding; the soft-sphere force + bond springs + growth-ramp magnitude are gated on the resolved `bonding`/`growthRate` (which the worker already resolves with the `usesBondingPhysics` toggle).
- **Mirrored scalar-config ABI** (`FORCE_PASS_PARAMS` ↔ the worker's `agentForcePassWasmFn(...)` call in `runAgentStep` — the param↔arg pair, the silent-desync class): `(highWater, hashValid, nBinsX, nBinsY, nBinsZ : i32, binSizeX, binSizeY, binSizeZ : f64, dtOverEta, muR, muA, range, momentum, maxSpeed, growthRate : f64, W, H, D : f64, bonding, torus : i32)`. `dtOverEta = dt/eta` is PRECOMPUTED (one division, bit-identical to JS's per-iteration `(dt/eta)` since the operands are step-constant). `bonding` gates BOTH the soft-sphere force (JS `engineForces`) AND the bond springs; `growthRate` carries the bonding gate (0 when off).
- **The torus position wrap uses a host `env.fmod = (a,b)=>a%b` import** — the EXACT JS `%` (fmod). WASM has no f64 rem opcode, and reconstructing `a - trunc(a/b)*b` rounds twice (drift). A "skip the wrap when n ∈ [0,span)" fast path is ALSO not bit-exact (for a non-power-of-2 span, JS's `(n+W)` rounds, so `((n%W)+W)%W ≠ n` in the low bits even for in-range n — verified: it diverged at ~1e-12). The unconditional host-fmod is the only bit-exact path. `fmod` is an 8th func import at funcIdx `NUM_IMPORTED_FUNCS` (=7), appended AFTER pow..tanh (0..6) so those indices are unchanged; the two module funcs are then `behaviour` (funcIdx 8) + `forcePass` (funcIdx 9), exported by name (the funcIdx shift is invisible to the worker, which calls by name). An inline musl-style i64 fmod (avoids the host call) is deferred — it needs ~15 new i64 encoder ops, and the wrap is once per agent, not per neighbour pair.
- **Worker dispatch** ([sim.worker.ts](src/simulator/engine/sim.worker.ts) `runAgentStep`): `instantiateAgentWasm` now returns `forcePass` too (`agentForcePassWasmFn`, null on a behaviour-only module — nulled wherever `agentBehaviourWasmFn` is). After the WASM behaviour ran AND the in-memory hash was copied in this step (`forcePassReady`), the worker calls `agentForcePassWasmFn(...)` INSTEAD of the JS force loop (`if (ranForceWasm) {} else if (is3d) {...} else {...}`). Any WASM force-pass failure → null the fn + run the JS loop this step. The hash-overflow / behaviour-fallback paths set `forcePassReady=false`, so the force pass only runs when its in-memory hash is valid.
- **Verified** (a Node esbuild-bundled parity harness — DOM-free; the worker's force loop copied verbatim as the JS reference): **12/12 bit-parity variants — 0 mismatches, maxAbs 0, 0 NaN** over 60 steps × 200 agents across {2D, 3D} × {hash stencil, all-pairs fallback, torus, clamp, soft-sphere ON/OFF, maxSpeed cap, growth ramp grow+shrink}; an **end-to-end** `behaviour(WASM)+forcePass(WASM)` vs `behaviour+jsForceLoop` test — 0 diffs over 50 real steps (2D + 3D). `tsc -p tsconfig.app.json --noEmit` + `npm run build` clean. Lattice + JS-agent **byte-identity by construction** (only `agentWasm/compile.ts` + `sim.worker.ts` touched — the lattice/JS-agent compilers are untouched; `git diff --stat` = 2 files).
- **HONEST perf finding (the lever is small on this engine).** The plan hypothesised ~2–4× from the force pass. The measured **force-integrator-only** speedup (Node V8, hash build excluded) is **~1.0–1.25×**: ~1.25× in the clamp case, ~1.05–1.09× torus (the host-fmod boundary crossing — once per agent — erases part of the win), ~0.99× (a wash) for 3D-torus 2000 agents, up to ~1.15–1.17× at 10k. V8 already JITs this tight monomorphic numeric loop near-optimally, so the WASM win is modest — consistent with the plan's "neither target fixes a current bottleneck; both raise the ceiling," but BELOW its force-pass hypothesis. The port is bit-exact + zero-regression infrastructure (and worker-V8 / very-large-counts may differ from Node), but it is NOT the CA-grid-level speedup the goal sought for the FORCE LOOP specifically. (NB: the HEAVY-RULE benchmark below shows the boost DOES materialise for a heavy per-agent BEHAVIOUR rule — the force loop is just the wrong place to look.)

### Agent friction/damping IS `momentum` — there is no second knob, and none is needed

User TODO: *"particle life and other models have to manually add some friction damping to avoid
infinite acceleration… shouldn't that be one of the standard offered options?"* **Investigated,
and the answer is that the standard option already exists and was merely unfindable** — so this
shipped as DISCOVERABILITY (a label, a hint, a Help entry, two doc comments), with **no engine,
schema or compiler change**.

- **THE DERIVATION.** Under Motion = Force the integrator is
  `v_{n+1} = m·v_n + (Δt/η)·F_n`, `m = momentum` clamped to `[0, 0.999]` in all three targets
  (the Properties field caps at the same 0.999). For a constant force the fixed point is
  `v_∞ = (Δt/η)·F / (1 − m)` — **finite for every m < 1**, so momentum below 1 already IS
  exponential velocity damping with a bounded terminal speed. "Infinite acceleration" is what
  `m → 1` looks like: at the 0.999 cap `v_∞ = 1000·(Δt/η)·F`, bounded but practically unbounded.
- **POST-FORCE FRICTION IS A REPARAMETERISATION, NOT A CAPABILITY.** The behaviour runs BEFORE
  the force pass, so Particle Life's graph-side `Get Velocity → ×f → Set Velocity` composes to
  `v_{n+1} = (m·f)·v_n + (Δt/η)·F_n` — **exactly momentum `m·f`** (its shipped 0.999 × 0.8
  = 0.7992). The reference implementation's own placement, friction AFTER the force add
  (`(v + kF)·f`), is `f·v + f·k·F` = momentum `f` with `η' = η/f`; `η` is unclamped (unlike `Δt`,
  which the Mathias bound clamps), so that is reachable too. **No qualitative behaviour is
  unreachable.** The empirical control is `Boids - Flocking`: momentum 0.9, no friction node
  anywhere, and it does not run away.
- **THE REAL REASON Particle Life does it in the graph is AUTHORING, not physics**: a model
  attribute is a live *Simulator* slider, while Momentum is a Properties field (still live —
  it is not in `needsFullInit`, so changing it needs no re-init). Documented as such.
- **The other two Motion modes cannot run away by construction**: `velocity` seeds no engine
  force (the graph owns `v` outright — momentum is deliberately not applied there) and `static`
  moves nothing.
- **What shipped**: the Properties row is now **`Momentum (friction)`** with the terminal-speed
  formula and the "agents accelerate forever ⇒ lower it" sentence in its hint; the `momentum`
  doc comment in [types.ts](src/model/types.ts) and the `CENTER_BASED_DEFAULTS` comment carry the
  derivation; HelpView gains a **"My agents accelerate forever — lower Momentum. It IS the
  friction control."** entry spelling out both compositions. **A `velocityDamping` config was
  deliberately NOT added** — it would be a second spelling of one number, exactly the kind of
  false choice the honest-controls doctrine removed from the Collision/Bonds dropdowns.

### Agent action TARGETING — optional id, default self (branch `polishing`)

User report: *"We have no way to 'kill' an agent from its id now? not even the 'self'?? … only
the 'kill agent' that destroys the current evaluated agent? that is very limiting … it should
all be consistent in providing either an id or assuming self, unless there is a strong
technical reason not to."* Plus the same for Set Velocity, *"following the example of the node
'Get Velocity' that the user can provide an agent or leave empty for the 'self'."*

**THE CONVENTION, now uniform: an agent action either takes an OPTIONAL `Agent` id whose
UNWIRED state means SELF, or has a by-ID sibling node.** The id port is always
`{ id: 'agentId', label: 'Agent', dataType: 'integer' }` — literally Get Velocity's port, so
the read and write halves of every pair look the same.

**THE BYTE-IDENTITY DISCIPLINE (inherited from Form Bond's `agentA`, and non-negotiable):
wiredness is read from the EDGE MAP and resolved BEFORE anything is minted** — `em.allocLocal`
changes the WASM module bytes even for an *unused* local, and `fresh()` shifts every later WGSL
name. Unwired therefore emits the historical statement byte-for-byte on all three targets
(`check-compile-identity`: 29 models, every surface unchanged).

#### The three nodes that gained the optional id
| node | unwired | wired | gated? |
|---|---|---|---|
| **Kill Agent** | `_killRequest[idx] = 1` | `_killRequest[target] = 1` — PREDATION ("consume" a neighbour) | **NO** — see below |
| **Set Velocity** | `_agentVX/VY[idx] = …` | writes that agent's velocity (knock-back) | **YES** — cross-agent OVERWRITE |
| **Set Target Radius** | `_agentTargetRadius[idx] = …` | makes ANOTHER agent grow/shrink | **YES** — cross-agent OVERWRITE |

**WHY A WIRED KILL NEEDS NO GATE — the commutativity argument, and it is the load-bearing
reasoning here.** A kill is a **flag set to a CONSTANT** (`killRequest[t] = 1`) consumed once by
the CPU structural phase at the end of the step. Setting the same value is **IDEMPOTENT and
ORDER-INDEPENDENT**: N agents all electing to eat the same target produce the identical result
in any order, and it cannot collide with that target's own self-update (nothing ever writes the
flag back to 0). That is exactly the argument that exempts **Apply Force To Agent**'s
commutative `+=`. So `killAgent` is deliberately **NOT** in `CROSS_AGENT_OVERWRITE`
(compile.ts' synchronous-mode gate) and **NOT** in the WebGPU agent gate's wired-non-spawn
reject set — verified, not assumed: a kill-only model's `isAgentGraphWebGPUSupported` returns
**true** and it runs natively on the GPU. On WebGPU the store is a plain **non-atomic** write of
`1.0` into another slot's `killRequest` run — a benign race, because every racing writer writes
the identical value — and `readbackAgentStep` already rounds it (`>= 0.5 ? 1 : 0`).
**Set Velocity / Set Target Radius are the opposite**: last-writer-wins overwrites, so they join
the same machinery as a by-id Set Attribute / Set Agent Position / Radius (the set is **six**
types in both gates). For an order-independent way to influence another agent's motion, Apply Force To
Agent works in both modes on every target.

**Guards** mirror the by-id setters exactly: range-only (`< _agentMaxAgents`, WASM's shared
`emitGuardedAgentWrite`, WGSL's `< i32(control.maxAgents)`) in the init/behaviour roots — the
unified-spawning relaxation that lets a staged Create Agent handle be configured — and
range+alive elsewhere. For the kill, range-only is *provably equivalent* to range+alive because
the structural phase separately gates on `alive[i]`, and a recycled slot is cleared by
`initAgentSlot`.

**⚠ THE INIT-ABI ASYMMETRY THIS EXPOSED (a real trap):** `deriveAgentAbi`'s **init** kind carries
`_agentZ` but **NOT `_agentVZ`**, and `_killRequest` is **loop-only**. So a wired Set Velocity in
the Agent Init Event (a legitimate "seed a newborn's velocity on its handle" use) would have
emitted an undefined `_agentVZ` in 3D — it now **drops the z half in the init root** (the C9
"no param ⇒ no write" safety-catch shape) rather than widening the ABI. Kill Agent stays
unconditionally init-invalid either way. `nodeValidation`'s `AGENT_SELF_ONLY_WHEN_UNWIRED`
makes that badge WIRING-aware for the two conditional nodes.

- **THE NEW MECHANISM: `hiddenPorts` gained a third argument, the ACTIVE GRAPH KIND.**

  graph rather than on config. `NodeTypeDef.hiddenPorts?: (config, model?, graph?) => string[]`

#### Retiring the `Set Agents Attribute` node — the `Agent` port takes an id or an id ARRAY (branch `polishing`, 2026-08-12)

  **`isAgentIdArraySource`** ([compiler/agentIdArray.ts](src/modeler/vpl/compiler/agentIdArray.ts))

  different targets. It recognises exactly the two source shapes the retired node accepted: a

  agent backends' type-based `AGENT_ARRAY_PRODUCERS` do not list it) — a pre-existing asymmetry

- **⚠ THE TWO WIRED ARMS GUARD DIFFERENTLY, DELIBERATELY** (each keeps its retired node's semantics

### Positional (hard) collision — a genuine second collision model (SHIPPED, all 3 targets, 2D+3D)
`Collision = positional` is a RIGID, no-overlap position-projection constraint — the distinct alternative to `soft` (the springy repulsion FORCE). Plan + illustrated mockup: [docs/PLAN_POSITIONAL_COLLISION.md](docs/PLAN_POSITIONAL_COLLISION.md)/`.html`.
- **Two real models now:** `soft` = a penalty force `μ_R·(d−s)` (transient overlap, non-penetrating only in the stiff limit — needs Motion=Force); `positional` = after integration, overlapping pairs are projected apart to EXACTLY touching (zero overlap, billiard-ball — works under any Motion since it edits positions). Adhesion/springs/growth orthogonal.
- **Algorithm** — `resolvePositionalCollisions` in [agentEngine.ts](src/simulator/engine/agentEngine.ts) (next to `buildSpatialHash`): a **Jacobi** position projection. Each of `positionalIterations` (config, default 2, live-tunable) sweeps reads the sweep-START positions, sums a **half-overlap push** `0.5·(s_ij−d)·(x_i−x_j)/d` per overlapping neighbour (torus-shortest, hash stencil + all-pairs), and applies all corrections at once → **order-INDEPENDENT** (identical across targets). Reuses the dead `forceX/Y[/Z]` buffers as the accumulator (**NO new per-agent SoA**); inlined interaction (V8-optimal, mirrors the force pass); the hash is rebuilt ONCE per step (sub-contact corrections rarely cross bins). A single sweep resolves an isolated pair exactly; dense packing converges over a few (the iteration knob).
- **CPU post-step on ALL targets** — the projection is target-independent CPU/JS, EXACTLY like the agent **structural phase** (bonds/division). ONE implementation, no WASM export + no GPU shader: called in `runAgentStep` between `swapPositions` and the structural phase (JS + WASM run the SAME fn over the wasmBacked memory VIEWS ⇒ **bit-identical**), and in `runAgentStepWebGPU` after `readbackAgentStep` (which already commits GPU positions to the CPU store — no extra readback; the next `uploadAgentSoA` returns the non-overlapping positions to the GPU). WebGPU's f32 force pass ⇒ f32-precision read-back positions ⇒ statistical parity (the documented WebGPU-agent stance, no worse than the CPU structural phase).
- **Gate change:** the soft-sphere repulsion moved `usesEngineCollision` → **`usesSoftCollision`** (`collision==='soft'`) at both force-pass sites, so a positional model runs the projection INSTEAD of the soft force. `collisionMode`/`usesSoftCollision`/`usesPositionalCollision` in [centerBased.ts](src/model/centerBased.ts) are the single source (legacy fallback `usesBondingPhysics ? 'soft' : 'off'`, never `positional`).
- **Byte-identical for shipped/legacy** — the inference only ever produces `soft`/`off` (never `positional`), and `usesSoftCollision` == the old `usesEngineCollision` for those. Only a hand-set `collision:'positional'` file changes (it used to fold to the soft force; now it runs the hard constraint — the intended fix). Verified: [scripts/test-positional-collision.mjs](scripts/test-positional-collision.mjs) (2D+3D torus/bounded resolve 0.01→1.0 exactly; wasmBacked bit-parity 0 mismatches; 0-iter no-op) + browser JS (off leaves overlap 0.7 vs positional→contact 2.0) + real-GPU WebGPU (routes to the webgpu target, 1.577→2.0, 0 errors). UI: the Collision dropdown restores Off / Soft-sphere / Positional + a Positional Iterations field (`AgentCapabilitiesSection`).

### Long-range CHARGE — the force that opens a grown graph (L1, SHIPPED; all 3 agent targets, 2D+3D)
The agent engine had **no force with reach beyond contact distance**, so any model whose bonds rest far past `sij = ri + rj` collapsed. **Measured** on K4 → 1200 nodes grown by triangle split through the real force loop: **99.2 % of nodes had an unrelated node inside contact distance** and unrelated nodes sat ~16× closer than bonded partners. The pair law repels only below `sij` (1.8 for `Cubic GRA`), **ATTRACTS** from there to `interactionRange × sij` (3.96), and is zero beyond — while bonds rest at 5. **Widening `interactionRange` does NOT help** (measured, row 3 of the sweep): it widens the *search*, not the force, and past `sij` the sign flips to adhesion. **This is not a tuning problem.** Design authority: [IMPACT_MAP_GRAPH_LAYOUT_CADENCE.md](docs/IMPACT_MAP_GRAPH_LAYOUT_CADENCE.md) · phase doc [HANDOFF_GLC_L1_CHARGE.md](docs/HANDOFF_GLC_L1_CHARGE.md).
- **The law**: `f_ij = k · (1/(1+d²) − 1/(1+maxDist²)) · (p_j − p_i)` for every pair within `chargeMaxDist`, **in addition to** soft-sphere + springs. `k < 0` repels. The `− min_c` term takes the force continuously to zero at the cutoff instead of stepping.
- **A FINITE cutoff suffices *at L1's measured scale*** (DC1): quality saturates by ~8× the bond rest length and an unbounded cutoff merely INFLATES the layout (bond 3.25× rest) without improving separation, so charge is **one extra term in the fused pair loop all targets already have**, reusing the existing uniform hash. ⚠️ **C10 MEASURED THE OPPOSITE AT SCALE and shipped the tree as an explicit option** — see "Charge RANGE" below. L1's sweep ran at N = 1200 in a very sparse 4000-wide world; in a world scaled to the POPULATION the cutoff law degrades as N grows while the tree does not, and at an 8×-rest cutoff the widened stencil is actually *slower* than the tree. Read the two together: a finite cutoff is right for a small or sparse model, the tree for a growing one.
- **Capability + config**: `AgentCapabilities.charge: 'off' | 'on'` (default **off**; `computeCapabilityClosure` requires `motion: 'force'`, and `applyCapabilityEdit` drops it when Motion falls below Force). `CenterBasedConfig.chargeStrength` (default −3) + `chargeMaxDist` (**absent ⇒ a DERIVED `8 × bondRestLength`**, DC6 — deliberately NOT a world-absolute constant). Resolvers in [centerBased.ts](src/model/centerBased.ts): `usesCharge` / `chargeStrengthOf` / `chargeMaxDistOf` / `chargeBinEdgeOf` / **`chargeParamsOf`** (the precomputed `{doCharge, chargeK, chargeMaxD2, chargeMinC}` — precomputing cutoff² + minC in ONE place, like `dtOverEta`, is what makes JS↔WASM bit-parity hold). `usesCharge` has **no legacy fallback** (charge is net-new, so a pre-L1 file can only resolve to off).
- **THE TRAP — the hash bin edge.** `binEdge = max(range·2·maxR, neighbourQueryRadius)`, and the force pass only ever sees pairs within ONE bin of its 3×3(×3) stencil. **`chargeMaxDist` MUST join that max** or every pair past one bin is invisible and the force is **silently truncated** — plausible-looking, wrong physics, no error anywhere. `chargeBinEdgeOf` (0 when off ⇒ the max is unchanged ⇒ byte-identical) joins it at all THREE hash sites: `runAgentStep`, the per-gen WebGPU `runAgentStepWebGPUInner`, and `computeResidentHashParams` (the resident batch). **Safe for the reserve by construction** — the reserve is computed from the SMALLEST edge and a LARGER edge yields FEWER bins; **`computeAgentMaxHashBins` must NOT be widened** (it is baked into the agent memory layout, so changing it would shift every offset past the hash region). The positional-collision projection keeps the NARROW `collisionBinEdge` (it only needs contact distance).
- **FOUR force surfaces, all of them** (the term goes in BEFORE the soft-sphere's own much-smaller `rmax` cutoff rejects the candidate — riding inside it would clip charge to the contact radius): **JS** [sim.worker.ts](src/simulator/engine/sim.worker.ts) — the SEPARATE verbatim **2D and 3D** arms × (stencil + all-pairs) = 4 sites; **WASM** [agentWasm/compile.ts](src/modeler/vpl/compiler/agentWasm/compile.ts) `emitForcePass`; **WebGPU** [agentWebgpu/forcePass.ts](src/modeler/vpl/compiler/agentWebgpu/forcePass.ts) canonical body; and **the B1 bin-sorted MIRROR body** in the same file — a term added to only one of the two GPU pipelines diverges *only* for models that engage the mirror. The shared `chargeTerm(is3d)` helper emits both GPU bodies so they cannot drift. Charge also joins every **scan gate** (`doScan = doForce || doDensity || doCharge`) — a pure charged gas has no soft-sphere, no springs and no density consumer, so without that the whole neighbour pass would be skipped.
- **The conditional-arity contract (WASM)**: the param list is part of the module's type section, so declaring charge params unconditionally would change EVERY agent model's bytes. `forcePassParamsFor(charge)` **appends** a 4-param block (`doCharge:i32, chargeK, chargeMaxD2, chargeMinC:f64` at indices 26-29) ONLY when `usesCharge`, so a charge-off module is byte-identical; indices 0..25 never shift. The worker **always passes all 30 args** — the WebAssembly JS API ignores arguments past a function's arity, which makes the dangerous direction (a module that DECLARES them while the worker omits them ⇒ `undefined` ⇒ NaN ⇒ poisoned forces) structurally impossible. **Asserted, not assumed** (`parity-agent-force.mjs` checks `forcePass.length` 26 vs 30 and calls the 26-param export with 30 args).
- **WebGPU gates at RUNTIME instead** (`fc.doCharge`): the shader text is not compile-identity-checked, the branch is on a uniform (perfectly coherent), and one shader then serves both states so toggling charge never rebuilds a pipeline. `ForceControl` grew 25 → 29 scalars; **`FORCE_CONTROL_BYTES` 112 → 128**. It is now **registered in [verify-render-uniform-layouts.mjs](scripts/verify-render-uniform-layouts.mjs)** — it had been excluded on the grounds that its members are "baked into the shader from the compiler's layout", which is true of the agent `Control` uniform but WRONG for `ForceControl`: a fixed hand-written WGSL field list in one file plus a hand-written table of LITERAL indices (`u[0]`, `fl[6]`, …) in another is exactly the drift pair that harness exists for, and it feeds BOTH GPU force pipelines. (Registry entries gained an optional `structFile` for the two-file case.)
- **Measured layout fix** ([scripts/probe-graph-layout.mjs](scripts/probe-graph-layout.mjs), now driving the **REAL** WASM force pass over a real `createAgentStore` — it used to carry its own copy of the force loop, which cannot gate the product): overlap **99.2 % → 0.2 %**, nnb/bond **0.18 → 0.81** at the default 8× cutoff. The probe now **asserts** this (including that the charge-off baseline is STILL jammed — if that stops failing, the probe has stopped measuring the bug) and exits non-zero.
- **3D costs several times more — keep the cutoff tighter there.** The stencil is a 3×3×3 VOLUME, so candidates grow with the CUBE of the cutoff. Measured on a uniform packing at spacing = rest: 2D 124 cand/agent (1.8 ms/tick) at 4× rest and 427 (5.4 ms) at 8×; **3D 813 (11.8 ms) at 4× and 1728 (23.8 ms) at 8×** — at 8× in 3D the stencil already covers the entire population, i.e. it degenerates to all-pairs with none of the extra quality. **Start 3D at ~4× the bond rest length.**
- **Verified**: 29 library models byte-identical; `parity-agent-force.mjs` **20 checks** (11 new charge combos — charge on/off × 2D/3D × torus/bounded × collision on/off × charge-only — all 0 JS↔WASM mismatches) + the arity contract + **the bin-edge trap test with a live negative control** (at 0.9× cutoff the widened edge feels the force while the pre-L1 edge reads exactly 0); real GPU — all 8 shader variants (2D/3D × mirror × scatter) compile 0 errors / 0 validation errors, a real dispatch matches the analytic force to 2.2e-8 (f32) and is exactly antisymmetric, and **the B1 mirror and canonical pipelines are BIT-IDENTICAL with charge on** (maxDiff 0 over 8 agents); a live in-browser A/B on the shipped `Cubic GRA` (WASM agent target, 240 generations, 0 worker/console errors) — overlap **99.8 % → 14.3 %**, nnb/bond **0.07 → 0.467**. **That residual 14.3 % is the SECOND, independent cause** the impact map identified (§1.4): at 2278 agents a 220×220 torus gives 4.6 units/agent against a bond rest of 5 — the world is SATURATED and no repulsion strength can open it. Enlarging/unbounding the sample worlds is **L3's** scope (DC7).
- **Negative-controlled**: dropping the `− chargeMinC` term from the WASM emit makes every charge parity combo fail (1500-3000 mismatches); dropping one charge write from `uploadAgentForceControl` makes the uniform harness report `unwritten: chargeMaxD2@108`.

### Charge RANGE: Cutoff | Global (deterministic Barnes–Hut) — C10 / P11a (branch `GRA`)

`CenterBasedConfig.chargeRange?: 'cutoff' | 'global'` (absent ⇒ `cutoff` ⇒ **byte-identical**, no migration) + `chargeTheta?` (default 0.9, clamped `[MIN_CHARGE_THETA 0.1, MAX_CHARGE_THETA 1.5]`). Phase spec [HANDOFF_CLARITY_SIMPLIFICATION.md](docs/HANDOFF_CLARITY_SIMPLIFICATION.md) §C10, implementing [PROPOSAL_CLARITY_SIMPLIFICATION.md](docs/PROPOSAL_CLARITY_SIMPLIFICATION.md) **P11 item 1**; impact map + plan [PLAN_CLARITY_C10.md](docs/PLAN_CLARITY_C10.md)/`.html`.

**This is a different LAW, not a speed-up of the same one.** `global` drops the cutoff entirely (`min_c = 0`) and sums **every** pair through a Barnes–Hut octree; a model that switches follows a different trajectory and its `.gcaproj` records the choice, exactly as changing any other physics parameter does.

- **Approximate ≠ nondeterministic.** Same positions ⇒ same Morton codes ⇒ same order-canonical traversal ⇒ **bit-identical forces** on the CPU engines, so a fixed seed still replays and an Overseer sweep still reproduces. θ changes *which* law you run, not whether it repeats.
- **GLOBAL TAKES AN OPTIONAL CUTOFF (a later follow-up, shipped).** `chargeMaxDist` under
  `chargeRange:'global'` truncates the tree sum exactly the way the reference implementation
  (`calcMultibodyForce`) does: the coefficient becomes `1/(1+l²) − 1/(1+R²)` so it reaches zero
  CONTINUOUSLY at `R`, and nodes / whole leaves / individual points beyond `R` are culled at the
  same NODE granularity the reference uses. **Why it matters:** the far field of N distant nodes
  sums to ≈ `N/l`, which GROWS with the population — so the un-cut law inflates a *growing* graph
  without bound. **`chargeGlobalMaxDistOf` resolves absent/0 to `Infinity`, deliberately**: `l² <
  Infinity` is always true and `1/(1+Infinity) = 0`, and `x − 0 === x` bit-exactly, so the culled
  arithmetic COLLAPSES to the un-culled one with no second code path and no cross-target drift.
  (Contrast `chargeMaxDistOf`, the CUTOFF law's resolver, which derives `8 × rest` when unset —
  global has no derived default because "every pair" is the law C10 shipped.) Per target: **JS**
  emits the cull unconditionally (behaviour-identical at Infinity); **WASM** gates it at COMPILE
  time on a finite cutoff (`allocLocal` + instructions change the bytes, so an un-cut global model
  stays byte-identical — the `chargeOn` precedent) and allocates its `mass` temporary only then;
  **WGSL** gates at RUNTIME on the uniform (its text is not identity-checked, and `chargeMaxD2`
  uploads as f32 `Infinity`). `chargeBinEdgeOf` is UNCHANGED — global still never widens the hash
  stencil, because the octree carries it. Covered by 8 new `parity-agent-force` combos
  (2D/3D × torus/bounded × tight/loose × θ) plus a VALUE invariant asserting a world-sized cutoff
  is INERT (1.0% off the un-cut law), a tight one CHANGES the answer (98%), the traversal tracks
  the TRUNCATED sum far better than the un-cut one (37% vs 99%), and the result is MONOTONE in R.
  **Negative-controlled by source mutation**: disabling the WASM cull emit fails all 8 combos.
- **THE BENCHMARK GATE decided this ships enabled, and it inverted L1's prediction.** [probe-graph-layout.mjs](scripts/probe-graph-layout.mjs) grows the GRA blob at N ≈ 2.5k / 5k / 20k in a world scaled to the population (`side = √(N·(rest·1.45)²)`), same ticks + seed + splits, and compares the tuned 8×-rest cutoff against θ = 0.9 global. Global wins on **every** axis at **every** size — and is **cheaper**:

  | N | nnb/bond (cutoff → global) | overlap % (cutoff → global) | ms/tick (cutoff → global) |
  |---|---|---|---|
  | 2 500 | 0.53 → **0.83** | 16.9 → **4.2** | 7.15 → **4.33** (0.61×) |
  | 5 000 | 0.47 → **0.82** | 37.9 → **4.9** | 22.43 → **13.77** (0.61×) |
  | 20 000 | 0.37 → **0.81** | 82.1 → **4.4** | 254.74 → **186.35** (0.73×) |

  **The SHAPE is the point**: the cutoff law DEGRADES as N grows (nnb/bond 0.53 → 0.37, overlap 17 % → 82 %) while global holds flat (0.83 → 0.81, ~4 %). A finite cutoff cannot open a graph that outgrows it, however it is tuned — which is exactly the "new capability, not a speedup" claim. It is *cheaper* because at an 8×-rest cutoff the bin edge IS the cutoff, so the 3×3 stencil sweeps a 120×120 area in a dense world while the tree stays O(N log N). Six gate assertions in the probe hold this permanently. (No shipped model is retuned — the shipped-configs-are-deliberate rule.)
- **THE SEAM: ONE TypeScript build, three traversals.** `buildAgentOctree` ([agentEngine.ts](src/simulator/engine/agentEngine.ts)) builds the tree once per generation into plain typed arrays; JS reads them directly, the WASM force pass reads a COPY at baked offsets in the shared agent memory, and WebGPU reads an upload. The BUILD is where two implementations would drift (bbox reduction, float→int quantization, sort tie-break, split order) and it runs once per generation; the TRAVERSAL is the hot part and is pure arithmetic over shared bytes — the shape the force pass already keeps bit-identical. Exactly the `buildSpatialHash` precedent (built in TS, copied into WASM memory, uploaded to the GPU).
- **Determinism rests on four STRUCTURAL facts** (not on care): Morton quantization is a pure function of the positions; **the sort is ORDER-CANONICAL** — a stable LSD radix (3 × 10-bit passes) seeded from an id-ordered array realises `(morton, id)` order with no comparator, so no sort algorithm can change it; the build is a deterministic DFS with a **node-count CAP that degrades a node to a LEAF** (a leaf is *more* exact, so the cap can never make a result wrong — only slower — and it bites in the same place every run); and the traversal is a fixed-order skip-link walk (`nodeI` ascending, leaf points in sorted order), so the f64 accumulation order matches on JS and WASM.
- **Layout**: `AgentLayoutExtras.chargeTreeNodes` (from the shared `agentOctreeNodeReserve(maxAgents)` = `maxAgents + 64`) reserves 10 regions appended AFTER every existing one — 3 sorted-position runs (`maxAgents` f64 each) + 7 node runs (cx/cy/cz/ext f64, start/end/next i32). **0 ⇒ zero bytes ⇒ every cutoff/off model's layout, and therefore its WASM bytes, is unchanged.** The WebGPU side puts the tree in its OWN two buffers (bindings **7**/**8**, declared only when nodes are reserved — the Naga stripped-binding discipline), so the agent SoA runs are untouched.
- **WASM conditional arity gains a THIRD value**: 26 (charge off) / 30 (cutoff) / **32** (global, appending `treeNodeCount:i32, chargeTheta2:f64`). `emitForcePass` emits the tree traversal **INSTEAD of** the pair term (never both — `chargeParamsOf.doCharge` is FALSE under global, which is what stops the force being counted twice). The worker always passes all 32; extras past a module's arity are ignored, so the dangerous direction stays structurally impossible.
- **`chargeBinEdgeOf` returns 0 under global** — the stencil carries no charge, so widening it would be pure cost (and in 3D the candidate count grows with the CUBE of the edge). `doScan` is unchanged in shape; global simply does not join it, so a pure global-charge gas skips the neighbour pass entirely.
- **f64 ASSOCIATION ORDER IS LOAD-BEARING — the parity harness caught a real bug here.** JS evaluates `1 + a + b [+ c]` strictly left-to-right; folding it as `1 + (a + b + c)` in the WASM emit diverges by an ULP that the integrator amplifies (it surfaced as 4 mismatches in **2D bounded** while torus and 3D happened not to). Any new emitted arithmetic must mirror the JS ASSOCIATION, not just the value.
- **GPU residency is a BLOCKER under global** (`residencyModelBlockers` key `chargeGlobal`): the tree is CPU-built per generation, which is precisely the per-generation CPU touch point residency exists to remove. Surfaced in C1's readout and C3's diagnostics. **A GPU tree BUILD is a recorded follow-up, not a hidden gap.**
- **Self-interaction is not excluded** (the reference behaviour): a node containing the agent can pass the θ test, because the centre of mass can sit up to ≈ `extent·√3` from a contained point. Leaf-level self is *exactly* zero (`d = 0 ⇒ c·d = 0`), so the error is confined to the far field — which is what θ names. θ is clamped rather than validated (it is part of a declared law a file records, so it must resolve, never throw).
- **The tree is 3D-native**; a 2D model is the `z = 0` slice, so the octree degenerates to a quadtree with a constant z bit-plane — ONE build path, no 2D special case.
- **Torus**: every delta (node COM and leaf point) takes the SAME minimum-image fold as every other engine force. A node straddling the seam has a large extent, so it fails θ and is descended to leaves where the fold is exact — it degrades gracefully rather than silently.

## Layout Iterations — the solver-relaxation knob (branch `GRA`, L3)

**`CenterBasedConfig.layoutIterations`** runs the agent FORCE INTEGRATOR N times per generation. Absent / 1 ⇒ **exactly today's engine, byte-for-byte**. Resolved by ONE clamped resolver, `layoutIterationsOf(cfg)` ([centerBased.ts](src/model/centerBased.ts)), which every surface reads so the CPU and GPU paths cannot disagree about the count (clamps to `[1, MAX_LAYOUT_ITERATIONS = 32]`, floors, and treats non-finite / non-number as 1 — a hand-edited `.gcaproj` cannot smuggle a count in). Edited in **Properties → Bond-Graph Agents → Solver**.

**Why an engine knob and NOT a graph node** (Impact Map §1.6): how many times the *solver* iterates is numerical relaxation, not rule logic — the same category as the existing `positionalIterations`. Putting it in the graph would be like exposing an ODE's step count as a node. The rule's OWN cadence ("rewrite every Nth generation") IS model semantics and lives in the graph, as L2's `Agent Periodic Step`. The two compose: relaxation passes per rewrite = `period × layoutIterations`.

### THE invariant — once per generation stays once per generation
The loop is kept TIGHT around **[force pass → position commit]** and nothing else, so the **structural phase** — the bond request-queue drain, division, death, auto-bond — still runs exactly ONCE, after it. Draining per iteration would REPLAY every queued Form / Break / Rewire and corrupt the graph silently, with no error anywhere; that is the easiest way to break this feature and it is pinned twice (a source invariant + O6 on the shipped model). Also outside the loop: the spatial hash build, the compiled behaviour, and the graph-force reset.

- **The graph-authored Apply Force is NOT cleared between iterations** — it is a constant external force for that generation, so every iteration re-seeds from it.
- **The hash is built ONCE per generation** on every target: per-iteration displacement is far below one bin edge, and the per-gen GPU path uploads a CPU-built hash it cannot rebuild mid-encoder.
- **`age` advances exactly ONCE per generation.** Every force pass does `age += 1`; the CPU subtracts `iterations − 1` after the loop and the GPU relax-commit decrements as it goes (N passes, N−1 commits ⇒ net +1).
- **Growth ramps at `rate / iterations`.** The ramp is `radius += sign(dd)·rate` CLAMPED at the target and monotonic, so N steps of `rate/N` reach exactly `min(|dd|, rate)` toward the target — the same end radius as one step of `rate`, with no extra uniform, no second bind group and no per-target special case. `rate / 1` is exact, so the default path is untouched.

### Per target
- **JS + WASM** ([sim.worker.ts](src/simulator/engine/sim.worker.ts) `runAgentStep`): a `for (_lit …)` loop around the WASM force dispatch AND both verbatim JS arms, ending in `swapPositions`. **`x`/`y`/`z` are re-read at the top of every iteration** — `swapPositions` swaps the array REFERENCES on the JS path, so a stale local would integrate the previous iteration's buffer and silently freeze the layout.
- **WebGPU** ([agentWebgpuRuntime.ts](src/simulator/engine/agentWebgpuRuntime.ts)): a new **relax-commit** compute pass separates consecutive force passes, appended by ONE shared `encodeForceIterations` used by BOTH dispatch sites (`dispatchAgentStep` and `dispatchResidentBatch`), so they cannot disagree. It commits `xNext→x` (+z) and decrements `age`, and deliberately does **NOT** do what `posCommit` also does — zero the force accumulator (which would drop the generation's Apply Force after iteration 1) or bump the generation counter (which would make `Get Generation` tick `layoutIterations` times per generation, breaking the L2 semantics). It reads `highWater` from the **ForceControl** uniform (which both GPU paths write) so one pipeline serves both, and the alive mask so dead slots — which the force pass returns from before its own `age += 1` — are left alone. Built unconditionally (one tiny shader) but only ever DISPATCHED when `iterations > 1`; a build failure degrades to 1 iteration rather than to N uncommitted force passes.
