## WebGPU Compile Target (Wave 3)

**Status: functional.** WebGPU is the third compile target alongside JS (default) and WASM. The compiler emits a single WGSL shader module containing the `step` entry point + one `outputMapping_<sanitisedId>` per Attribute→Color mapping, dispatched as compute pipelines on the GPU. Verified on Game of Life (with macros), Coagulation, MNCA (model-attribute-driven trace gradient), and Wireworld (array-producing nodes + linked-frequency indicators) — paint, reset, play, save/load, indicator readback, stop events, GIF + WebM recording all work. Direct OffscreenCanvas render (transferControlToOffscreen + a `presentColors` compute pipeline) skips the per-step colors readback. GPU-side reductions cover eligible linked-indicator aggregations. Pipeline cache short-circuits rebuild when the WGSL source is byte-identical (`shaderHashOf` check at `sim.worker.ts:294`).

### Architecture
- `useWebGPU?: boolean` on `ModelProperties`. Mutually exclusive with `useWasm` enforced by the Engine segment in Properties → Execution → Grid engine and a worker-side safety net (WebGPU wins if both flags arrive true on a hand-edited file).
- `webgpuStopCheckInterval?: number` on `ModelProperties` (default 1) — opt-in throughput knob on WebGPU only. Worker checks the stop flag every K generations AND always on the last step of any batch (so the user never overshoots a stop event past the current play batch). K=1 preserves exact behaviour. JS / WASM ignore the setting.
- 4-file compiler under `src/modeler/vpl/compiler/webgpu/`:
  - `encoder.ts` — WGSL string helpers (bindings, struct decls, per-cell copy preamble, attr read/write helpers, PCG functions).
  - `layout.ts` — 8-binding GPU buffer layout (attrsRead/attrsWrite/colors/nbrOffsets/modelAttrs/indicators/rngState/control). Bool/int/tag/float attrs are stored as one u32 word per cell with bitcast on read/write. `nbrOffsets` holds only the per-neighbourhood (dRow, dCol) i32 pairs (a few KB total) — neighbour cell indices are computed inline by the WGSL `nbrCellIdx(cellIdx, baseOffset, k)` helper using grid-width/height/sentinel literals baked into each shader. Replaces the legacy per-cell `total × nbrSize` index table that hit multiple GB on huge grids (see docs/HUGE_GRID_OPTIMIZATIONS.md §2.1).
  - `emitter.ts` — `WgslEmitter` shell (legacy; current orchestrator builds lines directly).
  - `compile.ts` — orchestrator. Macro expansion (`expandMacros`) runs first to flatten the graph. Then `preEmitValueNodes` walks the flow chain to compile every referenced value node at the entry-point's top scope (avoids the "var declared in `if` branch but referenced in sibling `else` branch" WGSL scoping issue). Per-node dispatch via `VALUE_NODE_EMITTERS` and `FLOW_NODE_EMITTERS`.
- `src/simulator/engine/webgpuRuntime.ts` owns adapter/device/buffers/pipelines. `setupBuffersAndPipelines()` builds the step pipeline plus one pipeline per output mapping. Helpers: `uploadAttrs` / `uploadAttr`, `uploadNeighborOffsets`, `uploadModelAttrs`, `uploadActiveViewer`, `uploadIndicators`, `dispatchStep`, `dispatchOutputMapping`, `readbackAttrs`, `readbackColors`, `readbackIndicators`, `readbackStopFlag`, `seedRngState`.
- Worker integration:
  - `runStepWebGPU()`: resets stop flag, syncs per-generation indicators to GPU, dispatches step pipeline.
  - `runColorPassWebGPU()`: dispatches the active viewer's output mapping pipeline.
  - `finalizeStepWebGPU({needAttrs?, needColors?})`: async tail that reads back colors / indicators / stop flag (and optionally cell attrs for linked indicators or save state). Standalone integer/tag/bool indicators decode as bitcast<i32>; everything else as bitcast<f32>.
  - Mutation handlers (paint, importImage, reset, writeRegion, clearRegion) mutate CPU `readAttrs` then upload via `uploadAttrs` and dispatch `runColorPassWebGPU`.
  - `getState` does `readbackAttrs` first when `gpuOwnsAttrs`. `loadState` uploads everything after CPU restore.
  - On WebGPU init (`startWebGPUInit` then `setupBuffersAndPipelines`), the worker uploads CPU state, seeds per-cell RNG, dispatches an initial output mapping pass, reads back colors, and posts a `stepped` message so the canvas paints the initial state.

### Atomics
- Stop events: `atomicCompareExchangeWeak(&control.stopFlag, 0u, idxU)` — first-cell-wins matches JS/WASM semantics.
- UpdateIndicator (integer/tag): `atomicAdd` for increment/decrement, `atomicMax` / `atomicMin`. `bitcast<u32>(i32)` to encode.
- UpdateIndicator (bool): `atomicOr(&ind, 1u)` for `or` when value is true; `atomicAnd(&ind, 0u)` for `and` when value is false.
- UpdateIndicator (float): `loop { atomicLoad → bitcast<f32> → compute → bitcast<u32> → atomicCompareExchangeWeak; if exchanged break }`. CAS loop on the f32-bitcast u32 word.
- `toggle`/`next`/`previous` on indicators: rejected at compile time (order-dependent under parallel cell execution).

### Compile-time rejections
`detectWebGPUIncompatibilities()` and `detectWebGPUModelIncompatibilities()` in [nodeValidation.ts](src/modeler/vpl/nodes/nodeValidation.ts) catch async mode, the async-only nodes (`setNeighborhoodAttribute` / `setNeighborAttributeByIndex` / `markCellUpdated` / `setFacingOrientation` / `setNeighborOrientationByIndex` / `moveSelfToNeighbor`), and `updateIndicator` with `toggle`/`next`/`previous`. The variegated READ nodes + `setOrientation` + `lookupInteraction`/`interactionTableMap` + Init Event ARE supported on WebGPU. CaNode warning badges surface rejections in the modeler when `useWebGPU` is on. The compiler returns an `error` and the worker stays on JS.

### Aggregate / GroupOperator median + uniform random (FULL COVERAGE — DONE)
`aggregate.median` and `aggregate`/`groupOperator` uniform `random` now run on the WebGPU GRID target (they're per-cell-LOCAL + order-INDEPENDENT, already on JS/WASM — never fundamentals). [webgpu/compile.ts](src/modeler/vpl/compiler/webgpu/compile.ts) `emitAggregateOrCount`: a shared **`materialiseFoldInput`** lifts the value-input materialisation out of the `weightedRandom` block (single-array source / sub-attr-FILTERED nbr-path / multi-source scalars) into one f32 `var<function>` scratch (sized by `maxArraySize`), so median / uniform-random / weightedRandom stay in lockstep. **median** = per-thread insertion-sort the materialised prefix, then median-pick (empty 0; even = mean of two middles; odd = middle — matches AggregateNode JS). **random** = advance the per-cell PCG once (always, JS/WASM always-advance) → `idx = floor(u*len)` → clamp → pick; empty → index -1/result 0; result+index ports. The picked index DIFFERS cross-target by design (per-cell PCG vs shared xorshift32 — same documented statistical-parity stance as `getRandom`). Sub-attribute nbr-path filters non-matching neighbours so the sort/pick run over the filtered prefix. GPU-verified: both shaders compile 0 errors + run end-to-end (a median-of-Moore rule smooths a sparse field to death; a random-pick rule preserves density).

### Not implemented on WebGPU (compile-time rejected, worker falls back to JS) — the genuine fundamentals ONLY
- Async update mode and async-only nodes (`setNeighborhoodAttribute`, `setNeighborAttributeByIndex`, `markCellUpdated`, `setFacingOrientation`, `setNeighborOrientationByIndex`, `moveSelfToNeighbor`). Async = "a write is visible to a later cell this step" — fundamentally serial, no parallel-GPU representation. The user keeps async by picking WASM/JS.
- `updateIndicator` with `toggle` / `next` / `previous` (order-dependent non-commutative mutation of one shared accumulator by parallel writers — the lone node-op-level fundamental; or/and/max/min/inc/dec ARE supported via atomics).

These two are the **complete** WebGPU-grid reject set. f32 precision + per-cell PCG bar NO node.
- **Design study — could a mass-conserving MOVE run on WebGPU anyway?** [docs/INVESTIGATION_LATTICE_MOVERS.md](docs/INVESTIGATION_LATTICE_MOVERS.md) (+ `.html`): a two-phase `proposeMove` + engine resolve makes move-into-a-vacancy a CONFLICT problem instead of an ordering one, so it parallelises — measured exactly conserving, order-independent and deterministic. NOTHING SHIPPED; async itself stays a genuine fundamental.

### Known target-specific differences (intentional, documented)
- WGSL has no f64. Float arithmetic runs in f32 — small precision differences vs JS/WASM accumulate over many generations on chaotic models. Bit-exact parity is NOT a goal.
- RNG: WebGPU uses per-cell PCG state seeded from a global seed. JS/WASM use a single shared xorshift32 stream. Same global seed → different sequences. Statistical behaviour matches; deterministic replay across targets does not.

### Key gotchas
- **A WGSL FLOAT LITERAL IS PARSED AS f64 AND THEN RANGE-CHECKED AGAINST f32 — never hand-write a rounded f32::MAX** (a real shipped defect, 2026-07-31). Both WebGPU compilers seeded a `min`/`max` fold with `3.4028235e38`, the *rounded* spelling of f32::MAX. That decimal is **340282349999999991754788743781432688640**, which is LARGER than f32::MAX (340282346638528859811704183484516925440), so Naga rejects the WHOLE shader — `value … cannot be represented as 'f32'` — and the model **silently falls back off the WebGPU target** (`[agents] WebGPU runtime build failed, falling back to JS`). Use the shared **`WGSL_F32_MAX`** (`'3.4028234663852886e38'`, the shortest decimal that round-trips f32::MAX) exported from [webgpu/compile.ts](src/modeler/vpl/compiler/webgpu/compile.ts) — imported by [agentWebgpu/compile.ts](src/modeler/vpl/compiler/agentWebgpu/compile.ts) so the two cannot drift. It fed **6 emit sites** (cell-grid `aggregate`/`groupOperator` min+max; the agent `readCellsUnder` reduce, `groupOperator` best-of, and `aggregate` min+max). **Why it escaped every gate:** `check-compile-identity` HASHES emitted text without ever handing it to a device, and the one shipped model that used `aggregate.min` (`Cubic GRA`) ships on the WASM agent target. `Ant Necrophoresis` was latently broken the same way (a `readCellsUnder` `max` reduce). Guarded permanently by [scripts/verify-wgsl-float-literals.mjs](scripts/verify-wgsl-float-literals.mjs) — Tier A scans every shipped model's emitted WGSL (grid step + agent behaviour + agent OM + the force pass in all 4 variants; 160 surfaces) for any literal that does not fit f32, Tier B forbids the rounded spelling in `src/` outside its documenting comment, and `--self-test` is the negative control. **The general lesson: emitted text that compiles in TypeScript is not a shader that compiles on a device — a numeric constant crossing into WGSL must respect f32, not f64.**
- WebGPU types are NOT in the default DOM lib. The project uses `@webgpu/types` (dev dep) referenced via `/// <reference types="@webgpu/types" />` at the top of `webgpuRuntime.ts` — do NOT add `"types": ["@webgpu/types"]` to tsconfig.app.json because that switches off auto-loading of all OTHER `@types/*` packages.
- WGSL struct definitions must come BEFORE the `var` declarations that reference them. `Control` struct is emitted before `var<...> control: Control` in `emitBindings()`.
- WGSL `var`/`let` are block-scoped. Cross-branch references (a value computed in `then` cannot be read in `else`) used to be solved by an eager `preEmitValueNodes` pass that hoisted every value to function-top scope. Post-sinking (see "Value sinking" section below) the analyzer guarantees every value's emit scope dominates all its uses, so block-scoped declarations inside an `if`/`case` block work naturally for single-branch values, and multi-branch values keep their LCA at the parent (function-top in the worst case) for cross-branch visibility.
- Value emitters that resolve **array-port sources INSIDE their `routeEmissionForNode` wrapper** (e.g. `getRandom` "options", `aggregate`/`groupOperator` over multi-source scalars) violate the "inputs resolved upstream" contract. `compileValueNode` therefore pre-resolves an array port's **multi-source scalar** inputs BEFORE the wrapper (warming the cache at the proper scope). Without this, a CSE-shared `getConstant` (sink scope `CELL_TOP`) first compiled inside the wrapper lands in that node's temporary branch buffer, so a sibling switch case reading it hits `unresolved value '_v…'` at WGSL shader-compile (the kelp_war **`_ki10`** crash: options-mode `getRandom` fed by duplicate tag constants that CSE merged). Single array-PRODUCER sources are left to the emitter so `aggregate`/`groupOperator` **fusion** is preserved; `getVariable` is skipped (dual scalar/array, resolved at use site). WASM is immune (function-scoped locals); JS uses `branchValueLines` and was already correct here.
- Storage buffers must be ≥4 bytes. `layout.ts` clamps `attrsBytes` / `nbrBytes` to a 4-byte minimum so degenerate models don't fail buffer creation.
- Worker-side mutual-exclusion safety net: in `init` and `setUseWasm`/`setUseWebGPU` handlers, when both flags would be true the worker silently demotes WASM. Keep both UI and worker enforcement — UI for live edits, worker for legacy `.gcaproj` files saved before the radio existed.
- `gpuOwnsAttrs = true` after `runStepWebGPU` runs. Mutation handlers AND save/load MUST upload-after-write OR readback-before-read. CRITICAL distinction: handlers that overwrite ALL cells (reset, importImage) call full `uploadAttrs(rt, readAttrs)`. Handlers that touch only a subset of cells (paint, writeRegion, clearRegion) MUST patch the GPU buffer at per-cell offsets via `device.queue.writeBuffer(attrsBuf, byteOffset + idx*4, ...)` — full `uploadAttrs` would clobber the post-Play evolved state with the stale CPU mirror. The bug symptom is "brushing seems to reset the board to random/initial".
- The Resize button (`handleApplyDimensions`) calls `initWorkerWithDimensions(w, h)` directly with the new dimensions WITHOUT updating `model.properties.gridWidth/Height`. The compilers must therefore receive a `dimsModel` with overridden dimensions — passing the unmodified `model` makes `compileGraphWebGPU` bake the OLD `total` into the WGSL bounds check (`idx >= ${total}u`), causing only the first N cells of the new larger buffer to evolve. WASM is tolerant because it takes `total` as a runtime function arg. Symptom: half the grid shows live evolution, half stays at the initial randomize.
- `adapter.requestDevice()` defaults to a conservative 128 MB `maxStorageBufferBindingSize` even when the adapter supports 2 GB. Large grids (multi-attribute models at 5000²+) can exceed the default for the attrs / colors buffers. Request `requiredLimits` matching the adapter's max so larger grids work. `setupBuffersAndPipelines` also defensively checks each region against the device's actual `maxStorageBufferBindingSize` and throws a clear error before the lower-level GPU validation error fires (which is hard to attribute back to a specific buffer). The neighbour-index buffer is no longer a concern post-§2.1 — it now stores only the relative offsets (a few KB total).
- **`maxComputeWorkgroupsPerDimension` is 65535 — a FLAT 1-D `dispatchWorkgroups(ceil(total/64))` silently no-ops past ~4.19M cells** (= `65535 × 64`). No error is raised — the kernel simply never runs, so the **whole WebGPU sim goes blank** (step + colour pass + init + reductions all skipped) on any grid above the threshold: a 5000×5000 (25M) 2D grid OR a 3D volume past ~4.2M cells (the canonical repro was a **300×300×100 = 9M** 3D model — display blank, brushing appeared to "do nothing" because painted cells were never coloured). Requesting the adapter max for this limit doesn't help — 65535 IS the hardware/spec ceiling. **Fix: tile the dispatch into a 2-D workgroup grid** via `dispatchCells(pass, total, wg)` ([webgpuRuntime.ts](src/simulator/engine/webgpuRuntime.ts)) — `x = min(groups, 65535)`, `y = ceil(groups/65535)`, `dispatchWorkgroups(x, y)`. Used at ALL 5 per-cell dispatch sites (step / init / output-mapping ×2 / reductions); the present pass + glyph-clear are unaffected (texture-dim dispatch / `clearBuffer`). The per-cell shaders recover the linear index from the 2-D global id: `let idx = gid.y * (nwg.x * 64u) + gid.x;` with `@builtin(num_workgroups) nwg` — emitted by `emitEntryPoint` ([webgpu/encoder.ts](src/modeler/vpl/compiler/webgpu/encoder.ts)) for step/init/OM and by the reduction-shader builder ([webgpuReduce.ts](src/simulator/engine/webgpuReduce.ts)). **For grids ≤ 65535×64 cells `y==1` → `gid.y==0` → `idx==gid.x`, byte-behaviour-identical to the old 1-D path** (verified: a 40×40×12 model renders unchanged; the 9M model went from 0 → 3.6M rendered instances + brushes correctly post-step). The `64u` literal MUST track `@workgroup_size(64)` — change both together. Any NEW per-cell compute dispatch over `total` MUST go through `dispatchCells` + use this 2-D index recovery.
- **The dead CPU neighbour table is DROPPED on the WebGPU grid target (the wasm32-4-GiB grid-ceiling fix; branch `optimize`).** The worker's `wasmMemory` is ONE backing store shared by every target, and even on WebGPU `initGrid` used to reserve the FULL per-cell neighbour tables (`total × nSz × 4` — **2.81 GB at 300³ 26-Moore, 6.66 GB at 400³**) — the DOMINANT per-cell cost and what blows the 4 GiB `WebAssembly.Memory` cap (`value 127930 above the upper bound 65536` resizing the shipped Accretor to 400³). But the **WebGPU runtime NEVER reads that table** — the GPU computes neighbours inline in WGSL from the compact `nbrOffsets` buffer (§2.1); `runStep()` returns via `runStepWebGPU()` BEFORE ever calling `buildLoopArgs`. So on the WebGPU target the table is dead weight. **Fix ([sim.worker.ts](src/simulator/engine/sim.worker.ts), worker-only — no compiler touched → JS/WASM byte-identical):** the `init` handler computes **`nbrTableDropped`** = `msg.useWebGPU` (INTENT — the layout is baked here, before the async runtime is known to succeed) `&& gridCells && !SIE-on && !cpuIndexesNbr`, where **`cpuIndexesNbr` = does any COMPILED CPU function that runs on this target — init / gridInit / OM / inputColor, but **NOT the STEP** — index a neighbour table (`codeIndexesNeighbourTable`, regex `/nIdx_\w*\[/` over the code strings; a compiled param decl is `nIdx_<id>,` so `nIdx_<id>[` appears only at a real read site)**. When dropped, `computeMemoryLayout` gets `layoutNeighborhoods = []` (no nbr region) and `buildNeighborIndices` fills ONLY the constant-boundary sentinel (`fillBoundarySentinel`, uploaded to the GPU with the attrs) — `nbrIndices` stays `{}`, so `buildLoopArgs` pushes an `undefined` table arg the (guaranteed-non-indexing) CPU fns never read. **The STEP is deliberately EXCLUDED from the check** = its JS/WASM CPU fallback is the ONE reader we drop: a WebGPU model whose GPU runtime FAILS can no longer silently fall back to a CPU step (a grid too large for the GPU table is too large for JS/WASM anyway). `runStep` guards this — when `nbrTableDropped` it returns without running the JS/WASM step (transient no-op while the runtime inits; a genuine failure — `webgpuGridFailed`, set in every `startWebGPUInit` failure branch — surfaces a one-time clear "runs on WebGPU only" error). A soft **recompile** that ADDS a neighbour read to a CPU function while the table is already dropped can't reallocate; it posts a one-time "reload to apply" error. **Trade-off:** a WebGPU model on a non-WebGPU browser now surfaces that honest error instead of silently running the (impractical-at-scale) JS fallback. Measured ceiling: 300³ dead-table 2.81 GB → gone; **400³ (the user's error) now inits + plays; the WebGPU-target ceiling moves from ~320³ past ~860³** (bounded now by attrs+colours, not the table — 512³ hits the browser tab's contiguous-ArrayBuffer budget, a recoverable env limit, NOT the WASM cap). **Guarded by [scripts/verify-webgpu-nbr-table.mjs](scripts/verify-webgpu-nbr-table.mjs)** (layout-delta == Σ total·nSz·4; 400³/512³ dropped fits + full overflows the 65536-page cap; the Accretor's CPU fns don't index nbr → dropped; a synthetic neighbour-reading-init model → table KEPT). **NB the edge case: a WebGPU model with a Grid Init Event forces the CPU init path (`useWebGPUInit` false when `gridInitFn !== null`), so a per-cell Init Event that reads neighbours KEEPS the full table** — the `codeIndexesNeighbourTable(initCode)` arm covers exactly this; its full-table path is byte-identical to pre-change.
- **The dead CPU sync attribute WRITE buffer is DROPPED on the WebGPU grid target too (the 600³ sequel to the neighbour-table drop; branch `optimize`).** After the neighbour table is gone, the next dead-weight on a large 3D WebGPU grid is the CPU sync **double-buffer**: in sync mode `initGrid` reserves a SEPARATE per-attr `attrWriteOffset` region (the step reads `r_<attr>`, writes `w_<attr>`, then swaps). But on the **WebGPU target the STEP runs on the GPU** (`runStepWebGPU` does its OWN attrsBufA/B ping-pong), so the CPU `w_<attr>` region (≈9 B/cell for the Accretor = state+Boundary+Fade ≈ **1.9 GB at 600³**, ~30k of 89k pages) is never read/written — the residual dead weight that (after the nbr drop) still kept 600³ over the 4 GiB cap (`value 88990 above the upper bound 65536`). **Fix ([sim.worker.ts](src/simulator/engine/sim.worker.ts) + [wasm/layout.ts](src/modeler/vpl/compiler/wasm/layout.ts), no compiler EMIT touched → JS/WASM byte-identical, `check-compile-identity` clean on all 25 models):** the `init` handler computes **`attrWriteAliased`** = `msg.useWebGPU` (INTENT) `&& gridCells && !async`. Unlike `nbrTableDropped` this is **INDEPENDENT of what CPU functions read** — the ONLY reader that needs a distinct write buffer is the sync STEP, which never runs on WebGPU (so it's BROADER than `nbrTableDropped`, with its own flag). `computeMemoryLayout` gained a trailing `webgpuGridWriteAliased` param that reserves NO write region (`attrWriteOffset[id] = attrReadOffset[id]`, 0 extra bytes — the SAME aliasing the async + agents-only paths use), and `initGrid`'s attr-view loop sets `attrsB[id] = arrA` (write view === read view). **Correctness surface (all write FINAL values, correct with write===read):** `runInit` writes `r_` directly (its post-init `w→r` copy is a self-copy no-op); `runGridInit` likewise; paint/paintManual/writeRegion/clearRegion write the single shared buffer (`dstB[i]=v` becomes a redundant self-write) then upload/patch to the GPU; `resetGrid` fills both (same slot twice). The **STEP guard is shared with the nbr drop** — `runStep` returns early when `nbrTableDropped || attrWriteAliased` (transient no-op while the runtime inits; a genuine `webgpuGridFailed` surfaces the one-time honest "runs on WebGPU only" error, since a dropped-resource model can't fall back to the CPU step). **No WASM-desync risk**: on the WebGPU target SimulatorView sends EMPTY `wasmStepBytes`, so `tryInstantiateWasmModule` early-returns — no WASM module is instantiated against the (now-smaller) `wasmMemory`; `computeLayoutFromModel` (the WASM-compile layout) NEVER passes the alias flag → the WASM module keeps its separate write region → JS/WASM byte-identical. **Documented edge (accepted, same class as the STEP tradeoff):** a WebGPU model with a Grid Init Event (forces the CPU init path) whose per-cell Init Event READS-BACK a cell attribute would see intra-pass writes (r===w) — the Accretor's init only writes position-derived `border`/gridInit-scatters seeds (no attr read-back), so it is provably safe. **Verified in-browser (WebGPU, DISPLAYED):** 300³ plays unchanged (Gen 141, the dendritic accretion structure growing); resizing to **600³ now CLEARS the WASM cap** — `initGrid` succeeds (the `value 88990` error is GONE; the layout is 59327 ≤ 65536 pages), and on this test device the NEXT limit is the honest GPU-device `maxStorageBufferBindingSize` (2048 MB < the GPU's own 2471.9 MB attrs read+write ping-pong — a device-specific limit my fix cannot address, surfaced as a clear `[webgpu] init failed: Grid is too large for WebGPU on this device` message from `startWebGPUInit`, which runs AFTER `initGrid`). **Guarded by [scripts/verify-webgpu-attr-write.mjs](scripts/verify-webgpu-attr-write.mjs)** (layout-delta full−aliased == Σ writeable-attr-bytes at 300³/400³/600³; the aliased 600³ FITS the 4 GiB cap [59327p] while the full one OVERFLOWS [88990p — the exact reported error]; the aliased layout reserves NO separate write region while the full one does; the Accretor's worker predicate `attrWriteAliased === true`). **New practical WASM ceiling:** dropping the write buffer cuts the Accretor's WebGPU per-cell WASM cost from ~27 B/cell → ~18 B/cell, so the WASM-cap cube ceiling moves further past ~860³; the real-device ceiling is now GPU-storage-buffer-bound (~560³ on a 2048 MB device), NOT the WASM cap. **Next dead-weight follow-on (NOT done):** the async-only `orderArray` (`total×4`) + `skippedArray` (`total`) are reserved even in sync mode for layout stability — 5 B/cell dead on a sync WebGPU model; and the CPU `colours` buffer (4 B/cell, needed only for frame-mode readback) — both candidates if the WASM ceiling must move further, but out of scope here (600³ is already GPU-bound, not WASM-bound).
- DO NOT add fake/hardcoded "default viz" output shaders as placeholders for un-implemented per-node emit. The honest path: leave colors uninitialised on GPU, return a clear compile error, let the worker fall back to JS.
- Macros must be expanded BEFORE compile. `expandMacros` walks the graph, replaces each `macro` instance with the macroDef's internal nodes (prefixed ids) plus rewritten edges. Recursion guard depth=20 mirrors WASM. The compileValueNode / compileFlowChain code only sees flat post-expansion graphs.
- Vite serves stale dev-server modules aggressively when `@webgpu/types` arrives via reference. After heavy edits to the webgpu/ files, a hard reload is sometimes needed before the browser sees the new shader code.
- Under direct render, the visible canvas is `drawImage`'d from an OffscreenCanvas owned by the worker — main-thread `getImageData` on the visible canvas can return all-(0,0,0,0) even when the user sees content. Don't trust getImageData for verification under direct render; use `preview_screenshot` to read what the user actually sees.
- Soft-recompile direct-render: reusing the salvaged OffscreenCanvas across `startWebGPUInit`'s unconfigure+reconfigure-with-new-device leaves the canvas in a state where no subsequent `dispatchColorPassAndPresent` produces visible output (viewer switches and Play don't recover; manual Recompile button "works" only because it creates a fresh canvas via Phase 1/2). The main thread sets `recompilePendingCanvasRefresh.current = true` when sending a recompile under direct render; the useWebGPUStatus handler allocates a NEW canvas + `transferControlToOffscreen` + `attachCanvas` on the post-rebuild ack so Phase 2 commits a fresh canvas. Worker isn't torn down — all state survives.
