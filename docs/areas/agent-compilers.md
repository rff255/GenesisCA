### The agent compiler ([compile.ts](src/modeler/vpl/compiler/compile.ts))
- `compileAgentGraph(agentGraphNodes, agentGraphEdges, model) → { behaviourCode, divisionCode, initCode }` — a sibling of `compileGraph` that flattens macros / strips reroutes / runs accessor-CSE, finds the `behaviourStep` root, and emits the per-agent loop via the shared `compileRoot` + analysis passes. `divisionEvent` compiles to a SINGLE-agent function (`divisionCode`, run per daughter). `buildAgentLoopParams` ↔ the worker's `buildAgentLoopArgs` MIRROR exactly (same order — the desync hazard); `buildDivisionParams` ↔ `buildDivisionArgs` likewise. The agent roots + ALL agent read nodes (incl. the neighbour-access family + `getVelocity`/`getCurvature`) are `NEVER_INVARIANT`; `behaviourStep`/`divisionEvent`/`getSelfPosition`/`forEachBond`/`fieldGradient`/`getAgentPosition`/`getVelocity` are in `MULTI_OUTPUT_TYPES`. `SimulatorView.compileAgentModel` calls it; the init + recompile messages ship `agentBehaviourCode`/`agentDivisionCode`/`centerBased`. `compileHarness.compileAll` returns `js.agent.behaviourCode`.
- **Two latent compiler bugs the boids accumulators surfaced (BOTH affect any "accumulate-in-loop, read-after-loop" pattern on ALL THREE targets, not just agents):** (1) `accessorCSE` treated `getVariable` as pure → it merged an in-loop accumulator's `getVariable(v)` with the post-loop read (same purity key); `volatileHoist` then emitted the merged read at their common (dominating) scope = ABOVE the loop, reading the accumulator at its initial value. `getVariable` reads MUTABLE storage (like `getIndicator`) → now in `NEVER_PURE_TYPES` (also `getAgentAttribute`). (2) `volatileHoist`'s `usedVolatiles` recursed through a flow node's `next` continuation, so a value read AFTER a loop (`forEach.next → consumer`) was attributed to the loop and emitted BEFORE it — `next` is a SEPARATE scope member, so `usedVolatiles` skips the `next` port **of the scope member it is called on** (the `includeNext=false` top-level call). NB it must NOT skip next-chains reached through a BRANCH port — that over-skip was itself a bug, fixed later; see "Agent-compiler branch-scope + RNG-order fixes". Verified: lattice 4 baselines byte-identical; Amphiphile/Chromatography (array volatiles — position-independent) unaffected; boids polarization climbs 0.008 → 0.99.
- **forEachBond analyzer coverage (audit fix M1):** `forEachBond` was missing from `sinkAnalysis.walkFlowNode` and `volatileHoist.walkNode` (only `forEachInArray` was handled), so a Local-Variable accumulator mutated inside a bond loop was emitted ABOVE the loop and read its pre-loop value. Both analyzers now treat `forEachBond` exactly like `forEachInArray` (a `${nodeId}:body` scope + `next` at the parent), and `elementDependentsByForEach` is seeded for forEachBond's per-iteration outputs (`partnerId`/`restLength`/`currentLength`/`index`) so a value derived from them stays pinned in the loop. forEachInArray is byte-identical (the branches just add `|| 'forEachBond'`). Verified: a `forEachBond` accumulator now emits `_var_acc = (_var_acc + _v…_restLength)` INSIDE the bond `for` loop.
- **Get Nearby Agents 3D on the JS target (audit fix M3):** the JS `getNearbyAgents` was 2D-only (XY distance + 2D bin index) while its WASM emitter was 3D-aware → a 3D agent model got the wrong neighbour set on JS. The JS agent-loop ABI now threads `_hashNBinsZ`/`_hashBinSizeZ` (the trailing 3D block of `buildAgentLoopParams` ↔ `buildAgentLoopArgs`), and `GetNearbyAgentsNode` takes `ctx` and emits a 3D branch (dz distance + torus fold against `_fieldD`, 3×3×3 stencil, 3D bin index `(nbz*NBinsY+nby)*NBinsX+nbx`) when `ctx?.is3d`. 2D emit byte-identical.

### Phase F — PR6b-1: the WASM agent-loop ARCHITECTURE SKELETON (branch `agents_floating_cells`)
The FIRST internal split of capstone PR6b — proves the WASM agent loop ARCHITECTURE (memory sharing + the per-agent loop + dispatch + a few emitters) on a deterministic model BEFORE the large emitter port (PR6b-2 neighbour access → Boids; PR6b-3 field + division → Tissue).
- **A SEPARATE, minimal agent-WASM compiler** [src/modeler/vpl/compiler/agentWasm/compile.ts](src/modeler/vpl/compiler/agentWasm/compile.ts) — `compileAgentGraphWasm(nodes, edges, model, agentLayout)` → `{ bytes, pages, supportedTypes }`. It REUSES the pure lattice ENCODER (`../wasm/encoder.ts`) but emits its OWN self-contained module — NO coupling to the lattice `WasmCompileCtx`/layout. The lattice WASM compiler (`wasm/compile.ts`/`wasm/layout.ts`) is **byte-unmodified** (proven: `compileAll` lattice bytes string-equal before/after on GoL/Life3D/snake/Gray-Scott/Boids/Tissue/Chemotaxis). Front-end = the SAME `expandMacros → collapseReroutes → canonicalizeAccessorEdges` the JS agent compiler runs.
- **The module**: `import "env" "mem"` = the wasmBacked AgentStore memory (PR6a — reads/writes hit the SAME bytes the JS engine reads at the `computeAgentMemoryLayout` baked offsets); `import "env" "pow"/…/"tanh"` = the 7 host math funcs (same funcIdx convention as the lattice, POW=0..TANH=6, NUM_IMPORTED_FUNCS=7); **`export "behaviour"(highWater: i32)`** → the per-agent loop `for (idx=0; idx<highWater; idx++) { if (alive[idx]==0) continue; const colorIdx=idx*4; <value DAG + linear flow chain> }`. **AW-HASH minimal**: the supported set needs no neighbour query, so `behaviour` takes ONLY `highWater` (no hash-array copy yet — `getNearbyAgents` is excluded by the gate; PR6b-2 adds it).
- **The minimal emitter set** (reads/writes the AGENT offsets, NOT the lattice offsets): `behaviourStep` (myX/myY[/myZ]/myRadius/myArea/myAge value-outs via `f64.load` at the x/y/z/radius/age offsets + idx*8; myZ gated on `is3dModel`), `getSelfPosition` (X/Y[/Z]), `getRadius`, `applyForce` (read-modify-write `+=` into forceX/forceY[/forceZ]), `setTargetRadius` (`f64.store` into targetRadius); PLUS the layout-agnostic value/flow utility on the f64 stack/locals: `getConstant` (number/bool), `arithmeticOperator` (Math, incl. the host transcendentals + the `/`÷0→0 guard), `statement` (Compare, numerical), `logicOperator` (AND/OR/XOR/NOT), `conditional` (if/else), `sequence` (transparent). Single canonical supported set `AGENT_WASM_SUPPORTED_TYPES`.
- **The gate** `isAgentGraphWasmSupported(model)` — TRUE iff Agents enabled AND EVERY (flattened) agent-graph node is in the supported set (+ Compare numerical-only, Get Constant number/bool-only). The central, honest predicate `agentTargetOf(cfg, wasmSupported)` consults: `agentTarget==='wasm'` resolves to `'wasm'` ONLY when supported, else clamps to `'js'` (the clamp stays the safe default). PR6b-2/3 widen `AGENT_WASM_SUPPORTED_TYPES` with no other change.
- **Dispatch** ([sim.worker.ts](src/simulator/engine/sim.worker.ts)): SimulatorView's `compileAgentModel` resolves the target + compiles the bytes (it has the model) and ships `agentTarget`/`agentWasmBytes` in the init + recompile messages (mirroring lattice `wasmStepBytes`). The worker, when `agentTarget==='wasm'`, backs the store on a `WebAssembly.Memory` (`createAgentStore({ wasmBacked:true })`, the SAME `computeAgentMemoryLayout` the compiler used), `instantiateAgentWasm`s the module against that memory, and in `runAgentStep` calls `agentBehaviourWasmFn(highWater)` INSTEAD of the JS `agentBehaviourFn` — **the force pass / structural phase below is UNCHANGED** (reads the same views). Any WASM failure → null the fn → JS fallback. `initAgents`/reset/recompile re-instantiate against the fresh memory (the orphan-WASM discipline: a fresh `WebAssembly.Memory` drops the old fn).
- **Sample**: [scripts/gen-agent-wasm-drift.mjs](scripts/gen-agent-wasm-drift.mjs) → `public/models/Agent WASM Drift Test.gcaproj` — 16 compact-seeded agents spring toward the world centre (`(centre − pos)·k → applyForce`), no RNG / neighbours / bonds, momentum 0, 2D. The deterministic JS↔WASM parity vehicle (`agentTarget:'wasm'`).
- **Verified**: tsc -b + `npm run build` clean; lattice WASM bytes + JS-agent behaviourCode byte/string-identical before/after (7 models); the gate correctly accepts the drift model + rejects Boids (PR6b-1 only); **JS↔WASM bit-parity** — END-TO-END through the real worker: JS-target vs WASM-target runs → bit-identical x/y across all 16 agents (0 mismatches, 0 NaN, 0 errors).

### Phase F — PR6b-2: the WASM agent loop runs Boids (widened emitter set; branch `agents_floating_cells`)
The SECOND internal split of capstone PR6b. Widens the SEPARATE [agentWasm/compile.ts](src/modeler/vpl/compiler/agentWasm/compile.ts) so the **Boids — Flocking** sample runs on the WASM agent target with JS bit-parity. The lattice WASM compiler (`wasm/compile.ts`/`wasm/layout.ts`/`wasm/encoder.ts`) stays **byte-unmodified** (proven: `git diff` on `src/modeler/vpl/compiler/wasm` + `webgpu` is EMPTY; lattice GoL/Life3D compile clean on all 3 targets). The compiler now uses the byte-stable **`WasmEmitter`** abstraction (`../wasm/emitter.ts`, imported not modified) for clean local allocation + reuses the Expression AST emitter (`../expression/emitWasm.ts`).
- **Widened emitter set** (all read/write the AGENT offsets, mirroring the JS agent compiler 1:1): neighbour access — **`getNearbyAgents`** (fills a per-node scratch i32 id-array via the 3×3[×3] hash-bin stencil over the in-memory CSR hash + the all-pairs fallback, torus-wrapped exactly like the JS emit), **`forEachInArray`** (loops the scratch array, exposing element=agent-id + index as i32 locals), **`getAgentOffset`** (torus-shortest dX/dY[/dZ] + Distance via the world-bound fold), **`getVelocity`** (self when Agent unwired, else a neighbour Vx/Vy[/Vz]), **`getAgentPosition`** (X/Y[/Z]), **`getAgentRadius`**; **`getVariable`/`setVariable`** (SCALAR Local Variables = f64 function-locals, reset to initialValue at loop top — the boids cohesion/alignment/separation accumulators); **`expression`** (parsed AST → `emitWasm`); **`getRandom`** (float/integer/orientation/bool — NOT options mode); plus the PR6b-1 set (behaviourStep/getSelfPosition/getRadius/applyForce/setTargetRadius/getConstant/arithmeticOperator/statement/logicOperator/conditional/sequence).
- **AW-RNG** (B13 — the RNG-stream-divergence blocker): the shared xorshift32 `_rs` lives in an agent-memory cell (`layout.rngStateOffset`). The worker writes the global `rngState[0]` into the cell BEFORE the WASM `behaviour` call; the loop reads it once at function top (`_rs = u32[off] || 0x12345678`, mirroring JS exactly), advances per `getRandom` (same 13/17/5 constants on the in-register local), stores back at the end; the worker reads it back into `rngState[0]`. So a JS-target run and a WASM-target run advance the IDENTICAL stream. `getRandom` is emitted-once-per-agent (cached) → the RNG advances the same number of times as JS.
- **AW-HASH** (the keystone): the per-step spatial hash (`binStart`/`binAgents`) is **copied into reserved agent-memory views each step** (S10 — an O(nBins + liveCount) copy); the hash DIMENSIONS (valid flag + nBinsX/Y/Z + binSizeX/Y/Z + fieldW/H/D + torus flag) ride the **behaviour ARG list** (signature `(highWater, hashValid, nBinsX, nBinsY, nBinsZ : i32, binSizeX, binSizeY, binSizeZ, fieldW, fieldH, fieldD : f64, fieldTorus : i32)` — mirrored in `runAgentStep`, the ABI-mirror discipline). **Reserve bound + fallback**: `computeAgentMaxHashBins(W,H,D,range,defaultRadius,nbrQ)` (shared by compiler `agentMaxHashBinsForModel` + the worker `initAgents`) reserves `binStart` for the worst-case bin count (smallest bin edge, hard-capped 2²⁰); a per-step **fits-check** (`nBins+1 ≤ maxHashBins+1`) falls back to the JS behaviour fn for that step (warns once) — never silently wrong. `getNearbyAgents` writes its id-array to a per-node scratch slot (`AGENT_NEARBY_SCRATCH_SLOTS=4` reserved buffers of `maxAgents` i32; >4 nodes → gate rejects → JS). Both the RNG cell + hash + nearby-scratch are APPENDED to `computeAgentMemoryLayout` (existing offsets byte-identical → the drift-test path unaffected).
- **The gate** `isAgentGraphWasmSupported(model)` (the single source of truth `agentTargetOf` consults) now additionally requires: ≤ 4 `getNearbyAgents` nodes; every `forEachInArray.array` source is a `getNearbyAgents`; only SCALAR Local Variables (array variables + setArrayElement are PR6b-3); `getRandom` not options-mode. Field nodes / division-event / structural writes / `getCellAttribute` stay OUT → Chemotaxis (`secreteToField`) + Tissue (`getCellAttribute`) cleanly clamp to JS.
- **DEV `setRngSeed` worker message** (test-only, never sent by the app): forces the shared seed so a JS-target run + a WASM-target run advance the identical stream (the parity vehicle).
- **Verified**: tsc -b + `npm run build` clean; lattice byte-identity (zero `git diff` on `wasm`/`webgpu` compilers + GoL/Life3D compile clean ×3 targets); Boids `isAgentGraphWasmSupported===true` (2675-byte module, 11 node types); Chemotaxis/Tissue clamp to JS + run 0-error; **JS↔WASM bit-parity** — TWO pristine standalone workers (compact-seeded → deterministic, same RNG seed, momentum 0.9 full flocking), **N=200 steps, 260 agents → 0 diffs on x/y/vx/vy, maxAbs 0, 0 NaN** (positions bit-identical to full f64 precision); the PR6b-1 drift test still bit-exact (0 diffs/60 steps). NB: the parity test MUST use pristine standalone workers — the app-owned worker's `useEffect` re-init + the unserialized vx/vy (getState/loadState don't round-trip velocity, a PR4 gap) contaminate a same-worker JS-then-WASM comparison.

### Phase F — W1: the WASM FORCE PASS (the boost lever; plan `docs/PLAN_AGENT_WASM_WEBGPU.md`)
W1 ports the agent **force integrator** — the engine code that, even on the WASM agent target, ran in JS — to WASM. It is the HOTTEST per-step agent code (the per-neighbour-pair double loop): the 3×3(×3) hash-stencil neighbour pass (soft-sphere repulsion/adhesion + density) → bond springs → velocity integration (momentum, maxSpeed, drag, dt) → `xNext/yNext[/zNext]` → growth ramp. The handoff's PR6 intentionally kept it in JS to minimise the WASM surface; W1 is the deliberate delta.
- **A SECOND export `forcePass` in the SAME agent module** ([agentWasm/compile.ts](src/modeler/vpl/compiler/agentWasm/compile.ts) `emitForcePass`): a faithful byte-for-byte port of `runAgentStep`'s force loop ([sim.worker.ts](src/simulator/engine/sim.worker.ts)), reading/writing the wasmBacked AgentStore at the `computeAgentMemoryLayout` baked offsets — the SAME memory the JS engine reads (zero glue). It runs RIGHT AFTER the behaviour (same step), reusing the in-memory hash already copied in for `getNearbyAgents` (no extra copy). f64 throughout ⇒ JS↔WASM bit-exact. **The structural phase + the hash build STAY in JS** (run once per step, not per neighbour-pair); `swapPositions` (a copy-into under wasmBacked views, B10) commits the new positions as before.
- **2D vs 3D** is a SEPARATE verbatim code path (the `if (is3d)` split mirrors the JS loop — NOT a branchless always-0-dz body — so the 2D arithmetic + stencil count are identical). The hash path skips the alive check (`buildSpatialHash` only bins alive agents); the all-pairs fallback adds it. Density counts regardless of bonding; the soft-sphere force + bond springs + growth-ramp magnitude are gated on the resolved `bonding`/`growthRate` (which the worker already resolves with the `usesBondingPhysics` toggle).
- **Mirrored scalar-config ABI** (`FORCE_PASS_PARAMS` ↔ the worker's `agentForcePassWasmFn(...)` call in `runAgentStep` — the param↔arg pair, the silent-desync class): `(highWater, hashValid, nBinsX, nBinsY, nBinsZ : i32, binSizeX, binSizeY, binSizeZ : f64, dtOverEta, muR, muA, range, momentum, maxSpeed, growthRate : f64, W, H, D : f64, bonding, torus : i32)`. `dtOverEta = dt/eta` is PRECOMPUTED (one division, bit-identical to JS's per-iteration `(dt/eta)` since the operands are step-constant). `bonding` gates BOTH the soft-sphere force (JS `engineForces`) AND the bond springs; `growthRate` carries the bonding gate (0 when off).
- **The torus position wrap uses a host `env.fmod = (a,b)=>a%b` import** — the EXACT JS `%` (fmod). WASM has no f64 rem opcode, and reconstructing `a - trunc(a/b)*b` rounds twice (drift). A "skip the wrap when n ∈ [0,span)" fast path is ALSO not bit-exact (for a non-power-of-2 span, JS's `(n+W)` rounds, so `((n%W)+W)%W ≠ n` in the low bits even for in-range n — verified: it diverged at ~1e-12). The unconditional host-fmod is the only bit-exact path. `fmod` is an 8th func import at funcIdx `NUM_IMPORTED_FUNCS` (=7), appended AFTER pow..tanh (0..6) so those indices are unchanged; the two module funcs are then `behaviour` (funcIdx 8) + `forcePass` (funcIdx 9), exported by name (the funcIdx shift is invisible to the worker, which calls by name). An inline musl-style i64 fmod (avoids the host call) is deferred — it needs ~15 new i64 encoder ops, and the wrap is once per agent, not per neighbour pair.
- **Worker dispatch** ([sim.worker.ts](src/simulator/engine/sim.worker.ts) `runAgentStep`): `instantiateAgentWasm` now returns `forcePass` too (`agentForcePassWasmFn`, null on a behaviour-only module — nulled wherever `agentBehaviourWasmFn` is). After the WASM behaviour ran AND the in-memory hash was copied in this step (`forcePassReady`), the worker calls `agentForcePassWasmFn(...)` INSTEAD of the JS force loop (`if (ranForceWasm) {} else if (is3d) {...} else {...}`). Any WASM force-pass failure → null the fn + run the JS loop this step. The hash-overflow / behaviour-fallback paths set `forcePassReady=false`, so the force pass only runs when its in-memory hash is valid.
- **Verified** (a Node esbuild-bundled parity harness — DOM-free; the worker's force loop copied verbatim as the JS reference): **12/12 bit-parity variants — 0 mismatches, maxAbs 0, 0 NaN** over 60 steps × 200 agents across {2D, 3D} × {hash stencil, all-pairs fallback, torus, clamp, soft-sphere ON/OFF, maxSpeed cap, growth ramp grow+shrink}; an **end-to-end** `behaviour(WASM)+forcePass(WASM)` vs `behaviour+jsForceLoop` test — 0 diffs over 50 real steps (2D + 3D). `tsc -p tsconfig.app.json --noEmit` + `npm run build` clean. Lattice + JS-agent **byte-identity by construction** (only `agentWasm/compile.ts` + `sim.worker.ts` touched — the lattice/JS-agent compilers are untouched; `git diff --stat` = 2 files).
- **HONEST perf finding (the lever is small on this engine).** The plan hypothesised ~2–4× from the force pass. The measured **force-integrator-only** speedup (Node V8, hash build excluded) is **~1.0–1.25×**: ~1.25× in the clamp case, ~1.05–1.09× torus (the host-fmod boundary crossing — once per agent — erases part of the win), ~0.99× (a wash) for 3D-torus 2000 agents, up to ~1.15–1.17× at 10k. V8 already JITs this tight monomorphic numeric loop near-optimally, so the WASM win is modest — consistent with the plan's "neither target fixes a current bottleneck; both raise the ceiling," but BELOW its force-pass hypothesis. The port is bit-exact + zero-regression infrastructure (and worker-V8 / very-large-counts may differ from Node), but it is NOT the CA-grid-level speedup the goal sought for the FORCE LOOP specifically. (NB: the HEAVY-RULE benchmark below shows the boost DOES materialise for a heavy per-agent BEHAVIOUR rule — the force loop is just the wrong place to look.)

### Phase F — WASM AGENT WHOLE-TARGET PORT: full WASM agent coverage + JS bit-parity + the heavy-rule boost (branch `continue_agents`)
The full-coverage WASM agent push — `isAgentGraphWasmSupported` now accepts the ENTIRE agent-graph catalogue (the reject set is ZERO — WASM is Turing-complete + f64, so no node is un-portable), so a user picks the WASM agent target and models freely with **JS↔WASM bit-parity** (the f64 gold standard, UNLIKE WebGPU's f32/statistical parity). Touches ONLY `agentWasm/compile.ts` + `agentEngine.ts` + `sim.worker.ts` + `SimulatorView.tsx` (+ an `i32.trunc_sat` encoder const) — **lattice grid (2D+3D, all 3 targets) + the JS-agent + the WebGPU-agent compilers are byte-identical by construction** (`git diff --stat` vs the merge base touches none of them).
- **The WASM module = the BEHAVIOUR loop ONLY** (mirrors the WebGPU G4/G5 decision): the `divisionEvent` + `agentInit` roots stay JS-on-CPU (target-independent — the worker runs `agentDivisionFn`/`agentInitFn` over the SAME wasmBacked memory the WASM behaviour reads/writes, bit-exact). The gate checks ONLY the BEHAVIOUR-REACHABLE node set (`behaviourReachableNodeIds` = the `behaviourStep.do` chain + its transitive value cone), so a Tissue graph runs on WASM even though its divisionEvent subtree uses CPU-only nodes. `AGENT_WASM_CPU_ROOT_TYPES` (divisionEvent/agentInit/createAgent/addAgentToWorld) documents the JS-on-CPU set.
- **Added emitters** ([agentWasm/compile.ts](src/modeler/vpl/compiler/agentWasm/compile.ts)): the **field bridge** (sampleField/fieldGradient[central-diff]/readCellsUnder[r-disk]/affectCellsUnder/secreteToField[bilinear splat] — 2D, torus-folded), the **agent-array tier** (getAgentsAttribute gather / filterAgents / joinAgents[union+intersection] / pickRandomAgent / pickNRandomAgents[partial Fisher-Yates] / getBondedAgents, all skipping empty(-1)/dead/oob ids; aggregate[sum/product/min/max/average/median[insertion-sort]/and/or] / groupOperator[+ weightedRandom + uniform random + index/position] / groupCounting / groupStatement over arrays — scratch via a per-agent bump pointer), `getCellAttribute`/`getAgentAttribute`/`setAttribute`/`updateAttribute` on the agent SoA (typed by `agentAttrKind`), the **structural-WRITE** nodes (divideAgent/formBond/breakBond/killAgent → request-flag stores into shared agent memory — the heavy mutation is the CPU structural phase), the **setters** (setVelocity/setAttribute-by-id [then named `setAgentAttribute`]/setAgentsAttribute/setAgentPosition/Radius/Type — range+alive guarded), the **bond/self reads** (forEachBond[ragged bond loop]/getCurvature/getBondDegree/neighbourDensity), the **universal** value/flow nodes (switch[conditions+value, firstMatch+independent]/loop/valueSwitch[OP_SELECT relay]/getModelAttribute/lookupInteraction/interactionTableMap/proportionMap/interpolation/colorScale/categoricalColor/getColorConstant/arrayElement/arrayLength + getConstant tag + getIndicator/setIndicator/updateIndicator[ALL ops incl toggle/next/prev — the agent loop is SEQUENTIAL so these are well-defined, unlike WebGPU's parallel writers] + setCellLooks[plain, writes the agent colors buffer; glyph rejected — no per-agent glyph SoA]), and **array Local Variables** + setArrayElement.
- **External regions in agent memory** ([agentEngine.ts](src/simulator/engine/agentEngine.ts) `AgentLayoutExtras`): the cell field arrays (`_field_<id>`), model attributes, indicators, lookup tables ride NEW reserved regions appended to `computeAgentMemoryLayout` (after the PR6b-2 hash region, so existing offsets are byte-stable).
