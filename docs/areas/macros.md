## Macro System (Implemented)

### Architecture:
- MacroInput/MacroOutput are boundary nodes inside macro subgraphs (teal, `#00897b`)
- MacroInput has OUTPUT ports (data flows into subgraph); MacroOutput has INPUT ports (data flows out)
- Ports are dynamic — derived from `MacroDef.exposedInputs`/`exposedOutputs` at render time
- Port editing UI on boundary nodes: add/remove/rename ports, value/flow category selector
- Changes propagate automatically — MacroNode's external handles re-derive from the same MacroDef arrays
- Boundary nodes cannot be deleted (filtered in `handleNodesChange` and `deleteSelection`)

### Create Macro from Selection:
- Auto-creates MacroInput (left of bbox) + MacroOutput (right of bbox) inside the subgraph. **Boundary positioning uses the selection's FULL-extent bbox** (`bMinX/bMinY/bMaxX/bMaxY` via `nodeSize(n)` → `position + measured width/height`), NOT bare `position.x`: MacroInput's right edge sits `BOUNDARY_GAP` (120px) left of the bbox left edge (`x = bMinX − GAP − EST_BOUNDARY_W`), MacroOutput's left edge sits `BOUNDARY_GAP` right of the bbox right edge (`x = bMaxX + GAP`), both vertically centred on the bbox. **Vertical centring estimates each boundary node's height from its exposed-port count** (`estBoundaryH(portCount) = 46 + max(1,portCount)*22`) — applied per side (`exposedInputs.length` for MacroInput, `exposedOutputs.length` for MacroOutput) so a tall many-port boundary node still centres on the selection instead of riding high. The old code used `maxX + 100` on the rightmost node's *top-left corner*, so MacroOutput landed ON TOP of that node whenever it was wider than 100px (nearly always — the user's "boundary nodes on top of the graph" report). Positions are stored relative to the selection centroid (`avgX/avgY`) like the internal nodes. DEV-only `window.__openSelectionMenu(nodeIds, x, y)` test hook ([GraphEditor.tsx](src/modeler/vpl/GraphEditor.tsx)) opens the selection context menu (box-select can't be driven by synthetic events — same limitation as `__openConnectionDropMenu`).
- `exposedInputs[i].internalNodeId` points to MacroInput node ID (not the actual internal target)
- Bridging edges connect MacroInput output ports → original internal targets
- Bridging edges connect original internal sources → MacroOutput input ports
- **ONE exposed port per CONNECTED COMPONENT of the crossing edges, NOT one per crossing edge and NOT one per source** (**`groupCrossingEdges`** in [macroMoveScope.ts](src/modeler/vpl/macroMoveScope.ts) — the ONE definition of the rule, imported by Create Macro so it and the move-across-a-boundary gesture cannot drift). Treat the crossing edges as a **BIPARTITE graph** over (source port) × (target port) and emit one exposed port per connected component: outside the boundary every source in the component wires into that one port, inside it that one port reaches every target. So an INPUT port's fan-OUT lives INSIDE the def (one bridge per internal consumer) and its fan-IN lives OUTSIDE (several outer FLOW sources converging on it); an OUTPUT port is the mirror. **This SUBSUMES the earlier source-grouping rather than replacing it, and for a VALUE port it is provably the SAME grouping**: a value input is single-occupancy (`isValidConnection`), so on the input side every internal target has degree 1 and every component is a star centred on ONE outer source, and on the output side every outer value target has degree 1, so every component is a star centred on ONE internal source. Only FLOW, multi-occupancy on its inputs, can put several sources in one component — and that is exactly the convergence source-grouping could not express (the reported bug: two outer flow edges into one selected node's flow input produced TWO macro input ports where ONE, with both wires converging on it, was right).
- **⚠ THE LOSSLESSNESS GUARD — a component is merged only when it is COMPLETE BIPARTITE.** One port with sources S and targets T expands to the full product S × T, so merging a component whose edge set is not already that full product would silently INVENT a wire: with flow edges `A→X`, `B→X`, `A→Y` the component is {A,B}×{X,Y} but only 3 of the 4 pairs are real, and merging would add `B→Y`. `groupCrossingEdges` compares the distinct (source, target) pairs against `|S|·|T|` and, when they differ, falls back to grouping by SOURCE — always a star, therefore always lossless, and exactly what shipped before components. A value component can never take that branch (its components are stars already). Category is uniform within a component: every edge is flow→flow or value→value (validation rejects the mix) and two edges only ever join a component by SHARING a port, so the category propagates across it and is read once from the first member.
- External edges are sorted by `internalNode.position.y * 1000 + portIdx` BEFORE building exposedInputs/exposedOutputs, so port order matches the visual top-to-bottom layout instead of arbitrary edges-array order. Port index resolves via `def.ports.filter(p => p.kind === kind).findIndex(p => p.id === portId)`, falling back to MacroDef.exposedInputs/Outputs for nested macros. **A COMPONENT's order key is the MINIMUM of its members'**, so the port order still follows that layout — and a one-edge component is byte-identical to the pre-grouping result (same port id/label/category, same bridging-edge id `bridge_in_<macroId>_<i>`, same outer edge id `<macroNodeId>_ein_<i>`). Extra members take a `_<j>` suffix, and each side emits one edge per **DISTINCT** port (`sourceReps` / `targetReps`) rather than one per edge — so a fan-out-free macro is unchanged and a fan-out one is byte-identical to what source-grouping emitted.
- **`undoMacro` traces EVERY bridging edge on BOTH sides** (`.filter`, never `.find`). A boundary port legitimately fans out to several internal consumers AND, since the component rule, fans IN from several of them: an INPUT port may carry N outer feeders × M bridges (restored as the N×M product, which IS the original edge set because only a COMPLETE component is ever merged), and a MacroOutput INPUT port may take several internal sources when a flow component converged there. `.find` on either side silently dropped all but the first, so Undo Macro lost those wires — a latent bug on the input side (a hand-wired fan-out could already reach it) that Create Macro now produces routinely, and a real one on the OUTPUT side the moment output convergence became emittable. A VALUE port always has exactly one bridge on each side, so it is unchanged.
- **⚠ `expandMacros` COULD NOT EXPRESS A MULTI-FEEDER INPUT PORT — a LATENT COMPILER BUG, fixed here.** [macroExpand.ts](src/modeler/vpl/compiler/macroExpand.ts) built `extInMap` as ONE feeder per `targetHandle` and its `macroInput` arm `break`ed on the first matching port id, so a port fed by two outer edges kept exactly ONE of them: an entire flow path vanished at compile time, on **all three targets at once** (the pass is target-agnostic), with **no error anywhere**. That was reachable before this work — nothing stops a user hand-wiring a second flow edge into an existing instance's flow input — and Create Macro now emits it routinely. The arm now keys the map by PORT ID, holds an ARRAY of feeders, and loops over EVERY one, so a port with F feeders and B bridges expands to the F×B product — structurally symmetric with the `macroOutput` arm right below it, which already looped over every outer consumer. **The first feeder keeps the historical edge id**, so a single-feeder port is byte-for-byte unchanged. The `macroOutput` arm was verified (not assumed) to be ALREADY correct for several INTERNAL sources — it is driven by `def.edges`, so each such bridge visits it and emits its own edge per consumer; only its ids needed care (every push reused the outer edge's id, so two bridges produced two edges with the SAME id — harmless, since `buildAdjacency` maps by node+port and nothing in the compilers keys on an edge id, but a trap for any future consumer, so a second and later bridge now takes a `_s<n>` suffix). Verified: a fan-out macro's compiled JS step is **alpha-equivalent** (identical modulo the `m<instanceId>_` prefixes) to the same graph without the macro; and on the two-feeder flow shape the macro body is emitted in BOTH branch arms on JS (2× vs 1× for a one-feeder variant) while the WASM module grows 2520 → 2703 bytes and the WGSL 3853 → 4020 chars.
- **Gate**: [scripts/test-macro-expand.mjs](scripts/test-macro-expand.mjs) (32 checks) drives the SHIPPED module — the multi-feeder port, the F×B product, the unchanged single-feeder ids, both output shapes, nesting, and an unfed port — with a **negative control** (`--mutate`) that puts first-match-wins back and asserts the suite fails (8 failures), then restores.

### Default Macros & Import/Export:
- **`.gcamacro` file format** ([types.ts](src/model/types.ts) `MacroFile`): `{ schemaVersion: 1, name, description, macroDef: MacroDef, macroDefs?, references?, origin? }`. The last three are ADDITIVE + optional (see "Macro Reference Export" / "Macro Reference IMPORT resolution" below); the first four are the historical shape.
- **`fileOperations.ts` owns the format**: `buildMacroFile` / `parseMacroFile` / `readMacroFile` / `downloadMacroFile`. **⚠ `parseMacroFile` must NEVER gate on `schemaVersion`** — the format's only compatibility mechanism is "unknown keys are ignored" (which is exactly why an older build reads a file carrying `references` and imports it as it always did), and a strict version check would reject files a current build reads fine. Malformed optional fields are DROPPED, never thrown past the two named errors (`not valid JSON` / `missing or invalid macroDef field`).
- `public/macros/*.gcamacro` is auto-indexed into `public/macros/index.json` by `macrosLibraryPlugin()` in vite.config.ts (mirrors `modelsLibraryPlugin`). Palette's "Default Macros" section fetches from `index.json` and lists each one as draggable.
- Right-click macro node → "Export Macro…" downloads a `.gcamacro` (filename derived from macro.name).
- Right-click canvas → "Import Macro…" (top-level item) opens a hidden `<input type="file">` and inserts the imported macro at the right-click position.
- `cloneMacroWithFreshIds(raw)` in `src/model/macroImport.ts` is REQUIRED for any macro import path. Regenerates: MacroDef.id, every internal node.id (with parentId remap), every edge.id, MacroPort.internalNodeId references, AND `config.macroDefId` on `macroInput`/`macroOutput` boundary nodes (this last one is easy to forget — without it, boundary nodes still point at the old MacroDef and macros break across imports).
- `importMacro(raw): string` action on ModelContext wraps clone + addMacro and returns the new id.
- MacroNode `data.label` is the user-facing name shown above the "Macro" header. `createMacroFromSelection` sets it; palette drops and file imports also pass `name` as the label argument to `addNodeAtPosition`. Always set the label when creating a macro instance.
- Project Macros section in palette filters `model.macroDefs` to only those referenced by at least one MacroNode (in `model.graphNodes` OR in any `model.macroDefs[*].nodes`). Stale defs (last instance deleted) don't appear; no auto-cleanup of model state itself.

### Macro Reference Export (M1 — branch `tasks_batch_2026_08`)
A `.gcamacro` now CARRIES the model elements its nodes reference, so a macro dropped into another model can bring its attributes / neighborhoods / mappings / variables / indicators / sprites / face palettes along. Design authority: [docs/IMPACT_MAP_MACRO_REFERENCES.md](docs/IMPACT_MAP_MACRO_REFERENCES.md) (+ [PLAN_MACRO_REFERENCES.html](docs/PLAN_MACRO_REFERENCES.html)). **M1 is the EXPORT half only — import is byte-for-byte unchanged** (it reads `macroDef` and ignores the rest, exactly as an older build does); the import-resolution dialog (Import as new / Remap / Discard) is M2.
- **ZERO compiler impact, structurally** — every reference resolves to an ordinary model element and nothing here reaches a compiler. `check-compile-identity`: **31 models, all surfaces unchanged**, and that is a GATE, not an expectation.
- **[macroReferences.ts](src/model/macroReferences.ts) is the pure engine** (no DOM, no reducer, no React, so the Node harness drives the shipped code): `collectMacroExportDefs` → `collectMacroReferences` → `defaultSelection` / `pruneOrphanSelection` → `buildReferenceBundle`.
- **THREE carriers of a reference, and a value scan sees only the first** — this is the sharpest edge in the whole feature: (1) a config VALUE under a known key; (2) the id embedded in a config **KEY** (`_port_bondAttr_<attrId>` — Form Bond / Rewire Bond expose one port per bond attribute); (3) the id embedded in an **EDGE HANDLE** (`input_value_bondAttr_<id>` — a WIRED bond-attribute port has no `_port_` config key at all, so a config scan misses it entirely). The harness's negative controls run a value-only scan and assert it MISSES both.
- **`REFERENCE_KEYS` EXTENDS `danglingRefs`' `KEY_SPACE`** (which gained an `export` and nothing else) with `facingAttributeId` / `facePaletteId` / `presetId`. **The gate is deliberately NOT widened**: `facingSource.ts` skips a `facingAttributeId` that is not a live vector agent attribute and a dangling `presetId` only reaches the Overseer runtime — widening would turn two documented graceful skips into hard compile errors on models that run today. Spreading `KEY_SPACE` first means a future key added there is picked up here automatically; the harness asserts the containment.
- **`macroDefId` is deliberately absent from `REFERENCE_KEYS`** — a macro def is not a model element. Nested defs ride `MacroFile.macroDefs`, collected by the clipboard's own `collectMacroDefBundle` (**this also fixes F1: `exportMacro` used to write ONE def, so a macro instantiating another macro exported an instance pointing at nothing**).
- **DERIVED keys are excluded by an EXPLICIT list, never by the `_` prefix** — `_port_*` and `_varName_*` are user-authored inline values persisted in the model, and `_port_bondAttr_<id>` is carrier 2. `_sourceAttrId` is the trap: it IS an attribute id, but it is a compile-time CACHE of `variegatedCells.sourceAttributeId`.
- **The transitive closure is an ENUMERATED table** (`closureOf`), run to a fixpoint: attribute → sub-attribute parent / neighbourhood hint / lookup-table axis sources (tag attribute · face palette) / value-tag attribute / face-pattern assignments; mapping → linked attribute + C→A parameter tag attributes; indicator → linked attribute; variable → tag attribute; face pattern → its palette. **Deliberately NOT closed over**: `variegatedCells.sourceAttributeId`, `ModelProperties.*`, `centerBased.*`, presets — those are model CONFIGURATION, not element references (importing a face pattern must not drag the whole variegation setup).
- **Spaces are CLASSIFIED, not assumed**: resolution is a union over the lists a key may name, and the space recorded is whichever list actually held it — so an agent mapping's `linkedAttributeId` lands in `agentAttributes` and a cell mapping's in `attributes`.
- **Elements travel VERBATIM with their ids preserved.** No parallel display-metadata record (nothing to drift when a schema field is added), and preserving ids is what makes re-importing into the SOURCE model a provable no-op.
- **Presets are collected but never carried** (a `Preset` embeds a whole `SimulationState`; `.gcapreset` owns that transport) — surfaced in the dialog's "Cannot be carried" section rather than silently dropped, alongside any id that is ALREADY dangling in the source model.
- **[MacroExportDialog.tsx](src/components/MacroExportDialog.tsx)** — embed-by-DEFAULT with per-element opt-out (the decision that matters is at IMPORT, where the target model exists; the checkboxes are here for the one element that can be megabytes — a sprite — and for the deliberate reference-free template). Closure-pulled elements render indented under their requirer; unchecking a requirer prunes what only it needed (to a fixpoint), re-checking pulls its requirements back. Rendered from GraphEditor's own JSX beside `NameInputDialog` — **a child of the editor wrapper, NOT of `.react-flow__viewport`**, so its `position: fixed` card is not re-based by the viewport transform (the transformed-ancestor rule).
- **Two invariants held by construction, both asserted**: a macro that references nothing skips the dialog and writes the LEGACY 4-key file **byte for byte** (`origin` is written only alongside `references`/`macroDefs`, since it exists purely to caption the import dialog); and "Reference-free template" ⇒ all-discard ⇒ that same file.
- **Gate: [scripts/test-macro-references.mjs](scripts/test-macro-references.mjs)** — 79 checks over one synthetic model + a nested macro touching every id space: the whole key registry, both embedded-id carriers, nested-def walking, one fixture per closure row (incl. a **3-hop** chain node → lookup table → axis attribute → neighbourhood hint), the selection/prune semantics, and the file round trip (references + nested defs survive verbatim; an OLD-shape file loads; `schemaVersion: 99` still parses; malformed optional fields are dropped). **Negative-controlled by SOURCE MUTATION — 5 mutations, 5 caught**: drop the edge-handle pass, drop the key-embedded pass, make the closure one-hop, drop `presetId` from the registry, and classify every attribute as a cell attribute.

### Macro Reference IMPORT resolution (M2 - branch `tasks_batch_2026_08`)
The other half: importing a `.gcamacro` asks, per element the target model does NOT already have, **Import as new / Remap to existing / Discard** - and then rewrites the macro's subgraph so every id in it names something here. **Discard is exactly today's behaviour**, which is what makes the new path a strict superset. Same design authority as M1.
- **ZERO compiler impact, structurally** - `check-compile-identity`: **31 models, all surfaces unchanged**. A gate, not an expectation.
- **[macroImportPlan.ts](src/model/macroImportPlan.ts) is the pure engine** - `planImport(file, model)` then `applyImportPlan(plan, model)` returning `{ defs, elements, notices, counts }`. **DEVIATION from the impact map's D1**: these live in a SIBLING module rather than inside `macroReferences.ts` (already 500 lines), and `applyImportPlan` takes the MODEL rather than the defs (the plan already carries them). Both are pure/DOM-free, so the Node harness still drives the shipped code.
- **The rewrite returns BOTH halves, so the import is ONE atomic dispatch** (`IMPORT_MACRO_BUNDLE`, D9): ids are minted on the main thread by `applyImportPlan`, so the def rewrite and the elements agree without reading state back (the `FileMenu` `metaEdits` two-write discipline). The reducer appends per space, **MERGES `variegatedCells`** for palettes/patterns (F6 - there is no `ADD_FACE_PALETTE` action at all) and flips `isDirty` once. The caller already knows the new def id (`defs[0].id`).
- **THE ONE THING MOST LIKELY TO GO WRONG - a rewrite that walks `Object.entries(config)` and stops there.** Two of the three carriers are not values, both survive a value-only rewrite looking perfectly healthy, and the failure (a bond's initial value silently reverting to the attribute default) surfaces NOWHERE - no badge, no compile error, no console line. So the rewrite is **three passes**: config VALUES / the `_port_bondAttr_<id>` config **KEY** (renamed, value preserved) / the `input_value_bondAttr_<id>` edge **HANDLE**. Two harness checks and two source mutations exist for exactly this.
- **A FOURTH pass that is not about ids at all (D8).** A macro also stores values only meaningful RELATIVE to an element: a tag OPTION INDEX (`constValue`, `case_N_value`, `_port_x`/`_port_y`/`_port_y2`, `_port_value` and its multi-slot `_port_value_<i>`, `_port_bondAttr_<id>` on a tag bond attribute, and `partTag_<i>`, which is keyed BY index and must be PERMUTED), a neighbourhood tag NAME, an indicator CATEGORY, a face LABEL. All are re-derived **BY NAME**; **a name with no counterpart is LEFT AS STORED and REPORTED - never clamped to 0, never dropped** (a wrong-but-plausible tag value is the worst possible outcome; an out-of-range index renders as an unselected dropdown and an unknown tag name is already badged). The carrier table is written from the impact map's enumeration, **NOT copied from `ModelContext`'s three parallel tag cascades** - their coverage is asymmetric (F2b.2: the agent path never patches `updateAttribute` even though its own predicate matches it), and the harness asserts the case they miss. The same indices inside IMPORTED elements move too (`Attribute.parentValues` against a remapped parent; a tag `Variable.initialValue`).
- **The tag pass runs AFTER the id passes and keys off the TARGET id** - the config (and the `_port_bondAttr_` key) already names the remap target by then.
- **`planImport` CLONES the defs up front** (`cloneMacroWithFreshIds`, which also runs the node migrations, then `remapNestedMacroRefs` across the set so a nested macro instance names its freshly-imported def). So the reference rewrite lands on the MIGRATED form and **`cloneMacroWithFreshIds` needed no new parameter** (the impact map's subsystem 4 suggested one). Cancelling costs nothing - the clone is dropped, nothing was dispatched.
- **Collection resolves against a bundle-shaped VIEW of the file** (`bundleAsModel`), so ONE engine answers "what does this macro reference, which of those does the file carry, in which space, and what pulled it in" - including the closure BETWEEN carried elements.
- **Compatibility is per space and it gates the CANDIDATES, not just the suggestion** (D10): attributes must match `type` **and `isModelAttribute`**, mappings `isAttributeToColor`, variables `kind`+`dataType`, indicators `kind`; neighborhoods/sprites/palettes/patterns have no discriminator. An incompatible element is **not offered at all**, and a space with no compatible candidate renders Remap **disabled with its reason** rather than as an inert control. The suggestion is an exact name match (then case-insensitive) - always shown as "matched by name", never applied silently.
- **THE DIALOG OPENS ONLY WHEN THERE IS A DECISION** - `planNeedsDialog` is `rows.some(r => r.carried)`, not `rows.length > 0`. A row for a reference the file does NOT carry offers only Discard, so **every pre-M1 `.gcamacro` (the four shipped ones included) opens no dialog and imports on exactly the historical path**, dangling ids and amber badges and all; such rows are still SHOWN once the dialog is open for something else, so the user learns why a node arrived unwired.
- **Capability / topology mismatches WARN, never block** (D12): a bond attribute with Bonds off / an agent element with Agents off / a face palette with Variegation off imports anyway and says which Properties setting makes it live. **The import never flips a capability on** (asserted).
- **[MacroImportDialog.tsx](src/components/MacroImportDialog.tsx)** - rows grouped by space, a three-way segment per row, a same-space candidate `<select>`, live per-row warnings recomputed from the CHOSEN target (`remapWarnings` - the same helper `applyImportPlan` uses for its notices, so the preview and the report cannot disagree), an "Already present - nothing to do" summary, and a "N new / N remapped / N discarded / N warnings" footer. It **reuses `MacroExportDialog.module.css` verbatim** for the shared chrome (one source of truth for the two dialogs) and adds only its own controls; same placement rationale as the export dialog (a child of the editor wrapper, never of `.react-flow__viewport`).
- **The palette default-macro drop is deliberately NOT routed through this** - that is M3, per the impact map's phase boundary.
- **Gate: [scripts/test-macro-references.mjs](scripts/test-macro-references.mjs) grew 79 to 169 checks**, driving the **REAL reducer** (`modelReducer`, the `test-param-input-mappings` precedent). Tier B: export then import into an EMPTY model, all-new - every element lands in its space with a fresh id, all three carriers rewritten, every imported element's OWN references retargeted (sub-attribute parent, lookup-table axes, linked mapping/indicator, face-pattern assignment), and **the import adds NO badge the macro did not already carry in its home model** (a census diff, so a fixture node that badges anywhere is not mistaken for an import failure - while a DISCARDED reference is asserted to badge, because that IS today's behaviour). Tier C: remap onto same-named elements adds nothing and rewrites all three carriers to the target ids; a name match with the WRONG type is neither suggested nor offered; then D8, one fixture per carrier against a target whose options are **reordered with one option missing** (so an identity map fails). Tier D: discard-all leaves every config verbatim; re-import into the model just imported into adds nothing; a clean macro re-imported into its SOURCE model opens no dialog; a pre-M1 file opens no dialog; the gating warnings. **Negative-controlled by SOURCE MUTATION - 6 mutations, 6 caught**: drop the edge-handle pass / drop the key-rename pass / ignore type compatibility / clamp an unmatched tag option to 0 / keep the exported ids instead of minting fresh ones / forget the `variegatedCells` merge.
- **PROCESS WARNING: never `git checkout <file>` to revert a source mutation on an UNSTAGED file** - it restores from the INDEX and silently destroys the session's work. It happened again here (the whole `ModelContext` reducer edit). Copy the file aside and restore from the copy.

### Explicit Controls — a macro's INTERFACE on its closed instance (branch `explicit_controls`)

A macro instance renders only its PORTS, so every parameter buried inside the subgraph (a neighbourhood, a threshold, an attribute pick) needs a double-click, a hunt and a scope exit to change — and there is no way to say *"THESE three parameters are this macro's interface"*. **Explicit Controls** promote a chosen internal parameter to a named row on the CLOSED instance, so a macro reads as a component with knobs. Design authority: [docs/IMPACT_MAP_EXPLICIT_CONTROLS.md](docs/IMPACT_MAP_EXPLICIT_CONTROLS.md) + [PLAN_EXPLICIT_CONTROLS.md](docs/PLAN_EXPLICIT_CONTROLS.md) (+ `.html` mockup); shipped in four phases P1-P4.

**ZERO compiler impact, and it is STRUCTURAL rather than careful** — `check-compile-identity` reports **31 models, all surfaces unchanged** at every phase.

**Project structure note**: [src/modeler/vpl/widgets/CategoricalPaletteEditor.tsx](src/modeler/vpl/widgets/CategoricalPaletteEditor.tsx) is the shared palette widget the D11 round extracted out of CaNode — the `GradientStopsEditor` precedent, rendered by BOTH the in-node editor and the class-D facet control.

#### D1 — A CONTROL IS A REMOTE CONTROL, NEVER A COPY (the decision everything else falls out of)
A control stores **`{nodeId, configKey}`** and reads/writes `def.nodes[k].data.config[key]` **live**. There is exactly ONE storage location for a parameter, so:
- **no compiler learns the feature exists** — `expandMacros` flattens the def whose config the control already wrote, so every emit is byte-identical by construction;
- **"edit either side and the other shows it" needed NO propagation machinery** — P3's headline finding. A value copied onto the instance would have needed a sync direction, a conflict rule and a migration; a remote control needs none of the three.
- The instance is a **VIEW**: `resolveControlDescriptor` re-derives the widget from the target's CURRENT config on every render, so retyping the underlying attribute re-derives the row's widget with no stored state to invalidate (**D2/R4 — the widget kind is DERIVED, never stored**).

#### Schema ([types.ts](src/model/types.ts)) — four additive shapes, absent ⇒ today's files exactly, NO migration
`ControlTarget = {kind:'config', nodeId, configKey} | {kind:'control', nodeId, controlId}` (the second is chaining, D4) · `MacroControl {id, name, target, groupId?, description?}` · `MacroInterfaceGroup {id, name}` · `MacroDef.controls?` + `.groups?`. (**`MacroPort.groupId` was REMOVED by the D5b ordering round — ports are group-free and get a plain reorder instead.**)
- **`control.id` / `group.id` / a chained `controlId` are def-local and PRESERVED across clones** (the `MacroPort.portId` rule) — an OUTER def's chained target names them and both defs clone in ONE operation, which is exactly what keeps a chain resolving. **`target.nodeId` by contrast MUST go through the clone's `idMap`.**
- **⚠ R9 naming rule**: `stringifyCompact` inlines an array by its parent KEY NAME (`nodes` / `edges` / `coords`), so no sub-array in these records may carry one of those names. `controls` / `groups` pretty-print normally.

#### THE CLONE FIX (P1) — the failure mode is NOT "the interface vanishes"
`cloneMacroWithFreshIds` ([macroImport.ts](src/model/macroImport.ts)) is a hand-written 6-field literal with **no spread of `raw`**, and it sits on the path of every import / paste / independent-duplicate — so a new `MacroDef` field is **SILENTLY DROPPED**. It now carries `controls`+`groups` (conditional spreads, so a control-free def still clones with NO key) and remaps `target.nodeId` for BOTH target kinds. **R2 is the reason this matters**: without the remap the control SURVIVES with an un-remapped nodeId, resolves to a DIFFERENT internal node and silently edits the wrong parameter — plausible, wrong, no error anywhere. Pinned by a source-mutation control.

#### [explicitControls.ts](src/modeler/vpl/explicitControls.ts) — the ONE resolver, consumed by BOTH sides
`eligibleControlKeys` (what pick mode offers) · `describeKey` (what a row renders) · `resolveTarget` (walk a chain to its `{defId, nodeId, configKey}`) · `resolveControlDescriptor` · `applyControlValue` · `applyInterfaceEdit` (the ONE authoring mutation builder, a 9-arm `InterfaceEdit` union) · `interfaceRows`/`reorderInterface` and their two derivations `orderByGroup`/`groupSections` (ONE interface order shared by editor and instance) · `collapsedGroupIds`/`toggleCollapsedGroup`.
- **DUAL CONSUMPTION** (the `buildCensusPorts` / `buildInputParamPorts` / `applyLookupAxisPorts` discipline): **CaNode CALLS the resolver** rather than mirroring it, so "what pick mode offers" and "what the row renders" cannot drift.
- **D8 — REPORT, NEVER DROP**: an unresolvable control returns a descriptor with a `block` (`orphan-node` / `orphan-key` / `orphan-control` / `orphan-def` / `cycle` / `wired` / `scope-open`) and renders **DISABLED WITH ITS REASON** (`CONTROL_BLOCK_REASON`, ONE table). **`CONTROL_BLOCK_NEEDS_ATTENTION` is the BROKEN subset that rolls up onto the instance's amber badge** — `wired` and `scope-open` are legitimate, self-explaining states, and badging them would fire "something is wrong" on a healthy model.
- **D10 — graph-kind-aware scoping** (`ownAttrListFor` / `tagAttrScopeFor`, the CaNode precedents): an Agents-graph node's attribute list is `agentAttributes`, a Cells-graph node's is `attributes`. **R6 — the cross-graph scope caveat is DOCUMENTED, not fixed**: a def edited on one graph and instanced on the other resolves against the OPEN graph's scope.

#### The FOUR control CLASSES, and the ONE rule that decides membership
| class | what | source |
|---|---|---|
| **A** | inline port widgets (`_port_*`) | `inlineWidgetFor` — the adaptive kind (bool / tag / glyph / number), re-derived per render |
| **B** | declarative scalar config keys | **`SCALAR_CONFIG_KEYS`**, an ALLOWLIST over 40 node types |
| **C** | model-element pickers (`CLASS_C_KEYS` — the 11 id keys) | **`ELEMENT_CONFIG_KEYS`**, 32 `regElement(...)` registrations |
| **D** | MULTI-KEY EDITORS as **FACETS** (D11) — a Color Scale's gradient, a Categorical Color's palette, a Color Constant's RGB(A) | **`FACET_SPECS`**, an allowlist whose `read`/`write` **ARE the node's own exported pair** |

- **P1.2 — THE COUPLED-WRITE RULE, and it is why B is an allowlist**: a key whose in-node editor writes SEVERAL keys at once (retyping an attribute also resets `_port_value`, picking a tag attribute also re-bakes `_tagLen`) **cannot be faithfully driven by a one-key control**. Class B expresses that by OMISSION. **Class C needed an explicit `coupled: true` flag instead, because there the LIST is still shared** — the in-node picker must render the same options while the KEY stays unbindable. Six keys carry it: `updateAttribute.attributeId`, `updateIndicator.indicatorId`, `getModelAttribute.attributeId`, `getConstant.tagAttributeId`, `statement|switch.tagAttributeId`, `getNeighborIndexesByTags.neighborhoodId`. Enforced in BOTH `eligibleControlKeys` (never offered) and `describeKey` (a hand-edited one resolves `orphan-key`, so its write is inert).
- **⚠ CLASS D IS NOT AN EXCEPTION TO THAT RULE — IT IS ITS COMPLEMENT.** The rule forbids a control binding one **MEMBER** of a coupled write, and it still does: `isExcludedControlKey` refuses `stop_N_*` / `entry_N_*` / `default_*` / `stopCount` / `count` forever, and a hand-edited control naming one resolves `orphan-key`. A **FACET** binds the WHOLE editor and writes through the **node's own writer** — `writeColorScaleStops` / `writeCategoricalPalette` / `writeColorConstant`, the very functions the in-node editors call — so the config an instance edit produces is **byte-identical to the same edit made inside the macro, by construction**, and nothing can be half-written because the write is not decomposed at all. Three consequences: the **Option-A alpha gate comes free** (an opaque edit DELETES the `a` keys, so an instance edit cannot invent an alpha channel and turn a byte-identical model red); the two mechanisms **cannot overlap** (`applyControlValue` refuses a facet, `applyControlFacet` refuses a scalar AND refuses a value whose `widget` tag mismatches); and the instance renders the **SAME widget component** the node does (`GradientStopsEditor` / the extracted shared `CategoricalPaletteEditor` / `ColorField`).
  - **A facet REQUIRES its node to export a read/write PAIR** — that is what the allowlist is for, and it is why `_varName_*` (multi-key *and* structural: they relabel PORTS), the count steppers, the `attr_N` slot pickers and the lookup-table / sprite-sheet dialogs (which edit `Attribute` objects, not node config) stay out.
  - `ControlTarget` gains `{ kind:'facet', nodeId, facet }`; `ResolvedTarget` gains `facet?`. A facet is a **LEAF of `resolveTarget` exactly like a config key**, so chaining onto one needs no new recursion. `controlTargetOf(nodeId, row)` is the ONE place a row's shape decides the target's shape.
- **`elementOptionsFor(nodeType, configKey, model)` is the ONE option-list source** (P4's class-C extraction): the **39** in-node picker `<select>` bodies are now `{elementOptions('<key>')}`, so no inline list survives in CaNode and an instance-side `'element'` row cannot offer a different set. The shared list carries the FULL shape — the `— Select … —` placeholder, `setCellLooks`' `CURRENT_VIEWER_SENTINEL`, and `getIndicator`'s frequency-shaped / spatial entries as **`disabled` rows carrying their reason as a `title`** (`indicatorScalarBlocker`) — which is what makes the "no surviving inline list" grep meaningful.
  - **`attr_N` multi-attr slot pickers are deliberately OUT OF SCOPE** — a different indexed key family, not among the 11 `CLASS_C_KEYS`.
  - `ovReadIndicator` / `ovCollectSpatial` keep their own local `eligible` filters: those answer a DIFFERENT question (is the SELECTED indicator frequency-shaped) while their option lists come from the shared source.

#### Groups are SEPARATORS, and membership is POSITIONAL (D5b — the ordering round)
**The interface is ONE FLAT ORDERED LIST of controls and group SEPARATORS, and a control belongs to whichever separator it sits under.** The list is DERIVED, never stored: **`interfaceRows(controls, groups)`** emits *the ungrouped head, then each group's separator followed by its members*, and it is the ONE partition — the editor's drag list, the instance's `groupSections` and the plain `orderByGroup` member order are all built by calling it. Three orthogonal facts own it: the **`controls` array order** (order within a bucket) · the **`groups` array order** (order of the sections) · **`groupId`** (the BOUNDARY MARKER — *not* a second copy of the order; order and membership are different questions).
- **The invariant that makes "position ⇔ membership" a bijection**: every edit builder leaves `controls` **CANONICAL** (ungrouped head, then each group's members contiguously, in `groups` order) — exactly what `interfaceRows` emits, so `interfaceRows → reorderInterface` round trips as the identity. **`reorderInterface` IS the positional model**: scan the reordered rows, the "current group" is the last separator seen, stamp every member with it. A drag therefore writes the new position AND the `groupId` it implies, in one builder call — **there is no group dropdown any more**, which is the literal content of "separators, not memberships".
- **Dragging a SEPARATOR moves it ALONE and CAPTURES whatever now falls under it.** Deliberate: it is the one rule the model rests on, and it makes "drag the header up over two controls to capture them" a natural gesture, which a carry-your-members header makes impossible.
- **`group-remove` MERGES its members into the section ABOVE** (ungrouped when it was first) — under positional membership that IS "the separator was removed", and not one control changes row. (P2 cleared them to ungrouped, which would now make them jump to the top.)
- **PORTS are group-free.** A group's only visible form is a box around CONTROL rows and a handle cannot live in a box, so `MacroPort.groupId` was removed and ports get a **plain drag reorder** (`port-reorder`) — which is what the handle order always wanted. It re-keys by `portId`, so **`def.edges` comes back `===`** (F8).
- **Accepted limit, documented**: the ungrouped head is always FIRST, so "ungrouped controls after a group" is not expressible; a row dropped below the last separator joins that group.
- **The closed instance draws each group as a COLLAPSIBLE BOX, per INSTANCE.** State is **`_ctlCollapsed`** on the instance NODE's config (comma-joined ids — `NodeConfig` is scalars-only), `_`-prefixed and neither `_port_*` nor `_varName_*`, so accessor-CSE's purity filter drops it and it is additionally in `DISPLAY_ONLY_KEYS` (no control may bind it). Two LINKED instances share a `macroDefId` but never a node config — that is what makes collapse per-instance. The **ungrouped head is never collapsible** (nothing above it to collapse, and hiding it could make the whole interface unreachable), and an **EMPTY group draws no box** while staying a real, draggable separator in the editor.
- **⚠ Collapsing changes the node's SIZE, not its handle OFFSETS.** Vertical offsets are `PORT_TOP_BASE + i*portSpacing` over the port arrays, which a collapse does not touch (measured 7 / 28 / 50 px, unchanged); the node's WIDTH can shrink when the hidden rows were its widest content, carrying the right-edge OUTPUT handles horizontally — and a SIZE change is what React Flow's own ResizeObserver already re-measures. `updateNodeInternals` is only for the opposite case (offsets moving with no size change). *(This corrects P3's "changes only the HEIGHT" note.)*
- Both drag lists go through the SHARED **`useListReorder`** the model panels use; the rows live inside `.body`, which already carries `nodrag`, so React Flow never sees the gesture.

#### PICK MODE IS ONE MECHANISM FOR EVERY CLASS — an on-top hotspot (V6b, the overlay round)
**Every eligible parameter is offered by a semi-translucent, dashed button drawn ON TOP of its own widget.** This REPLACED V6's split (class A outlined in place; classes B/C in a separate LIST at the top of the body) — the user's objection was exact: *"some are not even in the same order shown in the node"*, so half the offer was presented in an order the node does not have. The classes differ only in where the widget is AUTHORED, so they must not differ in how it is OFFERED.
- **A POSITION SOURCE AND AN AUTHORITY, KEPT APART — the invariant.** Every widget carries an inert **`data-ctl-key`** attribute (a class-D multi-key editor BLOCK carries **`data-ctl-facet`**; a nested macro instance's own control row carries **`data-ctl-chain`**); a node-level layout effect measures those into node-local boxes; and **`partitionPickTargets(rows, measuredKeys, measuredFacets)`** ([explicitControls.ts](src/modeler/vpl/explicitControls.ts)) INTERSECTS them with `eligibleControlKeys`' output. **A marker can never ADD a target** — a COUPLED class-C picker is marked (it shares its element list) but never eligible, and it is dropped here. The two sides PARTITION the offer, so every parameter is offered exactly once.
- **⚠ FACETS ARE MEASURED IN THEIR OWN NAMESPACE, deliberately.** Folding them into `measuredKeys` would let a config key that happened to share a facet's name claim its hotspot — impossible today, but exactly the silent mis-binding the position/authority split exists to rule out. (Source-mutation-controlled: mixing the two sets fails M38/M39.)
- **WHY AN ATTRIBUTE AND NOT A WRAPPER COMPONENT**: the ~100 class-B/C widget sites are bespoke JSX hand-tuned inside flex rows: an attribute is inert (zero box-model change), one token per site, and greppable. A wrapper would have changed the layout at 100 sites for no benefit. **99 sites carry one**: 96 inserted by a conservative codemod over `<select|input|textarea|InlineNumberInput>` opening tags whose own text writes an eligible key, plus `VisionColorRow`'s row, the `cbx` helper (which covers `setAgentSprite`'s SIX facet checkboxes with one edit — the marker goes on the `<label>` ROW, since a hotspot the size of a 13px checkbox is not a target) and the class-A `.inlineWidgetWrapper` (**ONE site — the ports loop**). `InlineNumberInput` forwards a `'data-ctl-key'` prop onto its `<input>`, beside the existing `data-min`/`data-max` advisories.
- **⚠ TWO MEASUREMENT TRAPS, both real and both fixed here.** (1) `getBoundingClientRect` is POST-transform and React Flow scales the viewport, so the live zoom is derived **from the node itself** (`rootRect.width / root.offsetWidth`) — subscribing to the store's transform would re-render every node on every pan and zoom, which is exactly what the `connectedInputHandles` pub/sub exists to avoid. (2) `rootRect` is the **BORDER** box while an absolutely-positioned child's `left`/`top` resolve against the **PADDING** box, so without subtracting `root.clientLeft`/`clientTop` every hotspot lands **2px down and right** (the node's border) — measured, then fixed.
- **The measure runs on EVERY commit while armed** (a no-dep-array `useLayoutEffect`), which is what makes a hotspot track a widget that MOVED; only the armed def's nodes re-render at all, and a 0.5px-tolerant compare (`samePickRects`) returning the previous object breaks the measure→setState→measure loop. A `ResizeObserver` on the node root covers the layout changes no re-render announces.
- **The class-A widget is inert BY CONSTRUCTION** — the hotspot takes the pointer — so V6's inert pointer/click CAPTURE handlers and the `.pickable` outline are both GONE.
- **THE FALLBACK, and why it is not the list that was removed**: a parameter whose widget is NOT on screen right now — a WIRED port (which renders no widget at all, and keeps its `wired` flag), a collapsed formula editor, a widget hidden by `hiddenPorts` or a mode — has nothing to draw a hotspot over. Those are listed under a *"not shown on the node"* head, deliberately subordinate: they are genuinely bindable, so hiding them would put a real parameter out of reach. **A COLLAPSED NODE stays unpickable** (its branch returns before `.body` and never attaches the root ref) — P2's policy, unchanged.

#### Chaining (D4)
**Chaining**: pick mode on a nested macro INSTANCE offers that instance's own controls as bindable rows (`{kind:'control'}`), so an outer macro re-exposes an inner one's knob. Those rows get the SAME on-top hotspot (the row IS the widget), via `data-ctl-chain`. **Cycle-guarded** — `resolveTarget` carries a `seen` set keyed `defId::controlId` and a `CONTROL_MAX_CHAIN_DEPTH` (20, mirroring `expandMacros`' guard); **a would-be cycle renders DISABLED, not hidden**, so the author sees why. ⚠ The ✎-edit seed (pre-seeding `seen` with the control being re-bound) is load-bearing — without it a self-rebind resolves cleanly; pinned by a dedicated harness check.

### Undo Macro:
- Filters out boundary nodes and bridging edges when restoring
- Traces through bridging edges to find actual internal nodes for edge reconnection
- **Positioning** (`undoMacro` in GraphEditor.tsx): restored nodes are centered on the macro node by aligning the internal cluster's bounding-box center to the macro node's center (`offset = macroCenter − clusterCenter`). ### Macro Compilation (shared `expandMacros`, all three targets):
- **All three compilers flatten macros UP FRONT** via the shared `expandMacros` ([macroExpand.ts](src/modeler/vpl/compiler/macroExpand.ts)) before any analysis. Each `macro` instance is replaced by its MacroDef's internal nodes (ids prefixed `m<instanceId>_`) + rewritten bridge edges; boundary nodes (`macroInput`/`macroOutput`) are dropped; recurses with a depth-20 guard. After expansion NO `macro`/`macroInput`/`macroOutput` nodes remain, so sink analysis, loop-invariance, accessor-CSE AND volatile hoisting all see one uniform flat graph — there is no "inside a macro" special case on any target.
- **JS used to have a SEPARATE lazy macro-inliner** (`inlineMacroValues` / `inlineMacroFlow` / `inlineNestedMacroValues` + `emitMacroLine` + `expandingMacroDefs`) that ran NONE of those analyses on macro internals. It was DELETED in favour of `expandMacros` (call at the top of `compileGraph`, before reroute-collapse / linked-OM / CSE / `buildAdjacency`). This closed two real bugs: (a) the lazy flow-inliner never emitted a flow node's internal value-input deps (a macro of `getNeighbors→count → setVariable` referenced undeclared `_m…_count` vars); (b) macro internals bypassed sink/loop-invariance/volatile analysis entirely. The per-target macroDef-iteration pre-resolve loops (indicators/stopEvents/move/variegated/viewer-refs) and the per-macroDef reroute-collapse are gone too — the flattened top-level nodes cover everything.
- Bridge rewiring: MacroInput output ports → wired directly to the outer source feeding the matching instance port. MacroOutput inputs → the internal source is wired directly to each outer consumer of the macro instance's output port.
- `expandMacros` is a structural graph transform only — purely id-prefix + edge-rewrite, no per-target logic. The `forEachInArray`-body element-dependent analysis (`findElementDependents` / `forwardValueConsumersMulti`) now never sees a macro node (always flat), so its edge-map output-port discovery is only exercised by genuinely dynamic-output value nodes.

### Move a selection ACROSS a macro boundary (branch `macro_topology`)

Adding a node to an existing macro — or pulling one out — used to mean **Undo Macro** (which DESTROYS the def, losing every Explicit Control and group the author configured) + fix + re-create, or cut / enter / paste + hand-rewire every wire that crossed the boundary. The direct gesture: **a selected node's header carries a grip; dragging the selection by that grip onto a macro INSTANCE moves it INSIDE that macro, and — while editing a macro — dragging onto either BOUNDARY node moves it OUT.** Every existing connection is preserved by re-adjusting the topology. **ZERO compiler impact, structurally** — `git status` touches nothing under `src/modeler/vpl/compiler/` and no `.gcaproj` schema field; `check-compile-identity` reports **31 models, all surfaces unchanged**.

#### THE PORT RULE IS THE SHARED ONE, and this module OWNS its definition
**ONE exposed port per CONNECTED COMPONENT of the crossing edges** — `groupCrossingEdges` lives here and Create Macro imports it, so the two cannot drift (the rule itself, the value-is-a-star proof and the complete-bipartite losslessness guard are in the Create-Macro bullets above). An INPUT port's fan-OUT lives INSIDE the def (one bridge per internal consumer) and its fan-IN OUTSIDE (several outer flow feeders converging on it); an OUTPUT port is the mirror.

**REUSING AN EXISTING PORT IS PART OF THE SAME RULE, on BOTH sides.** A crossing edge whose component touches a port the def already has joins THAT port instead of minting a duplicate — by the SOURCE side (the outer feeder already crosses: move-in `needInput`, move-out `fromStaying`) **or by the TARGET side** (the internal consumer is already served: move-in `needOutput`, move-out `toStaying` — which is what lets a departing node become a second flow feeder converging on an existing input port instead of minting `in_1`). **Reuse is taken only when it stays LOSSLESS: the existing port's own set on the identity side must EQUAL the component's**, or the merge would make a pre-existing feeder reach a target it never fed. A VALUE port can never reach the reuse branch — the internal (or outer) value port it would have to share is already single-occupied — so only flow does, which is exactly the intent.

#### [macroMoveScope.ts](src/modeler/vpl/macroMoveScope.ts) is the PURE engine
DOM-free and dependency-light, so GraphEditor, the DEV hook and [scripts/test-macro-move-scope.mjs](scripts/test-macro-move-scope.mjs) all drive the SAME shipped code rather than a re-implementation. `moveIntoMacro` / `moveOutOfMacro` take `{ def, parentNodes, parentEdges, instanceNodeId, movingIds }` and return the new def + the new parent graph + the ports they ADDED and REMOVED; `filterMovableIds`, `stripControlsForNodes`, `countInstancesEverywhere` and `locateMacroInstance` are its helpers.

| direction | crossing edge | what happens |
|---|---|---|
| **IN** | `outer → moved` | a macro **INPUT** port — **REUSED** when that same outer `(source, sourceHandle)` already feeds this instance through some port |
| **IN** | `moved → outer` | a macro **OUTPUT** port, de-duplicated by the internal source |
| **IN** | `moved → instance.in_k` | the port's bridges become DIRECT internal edges; the port is **REMOVED** iff no OUTER feeder remains |
| **IN** | `instance.out_k → moved` | the port's internal source feeds the moved node directly; **REMOVED** iff no OUTER consumer remains |
| **OUT** | `MacroInput.in_k → moved` | the outer feeder wires STRAIGHT to the moved node; the port is **REMOVED** iff it has no OTHER internal consumer, else **KEPT** and it simply fans out to both |
| **OUT** | `moved → MacroOutput.out_k` | every outer consumer is rewired to the moved node; the port always goes (a MacroOutput input takes exactly ONE internal source, and it left) |
| **OUT** | `staying → moved` | a new (or REUSED) **OUTPUT** port carrying that inside source |
| **OUT** | `moved → staying` | a new **INPUT** port whose bridge feeds the stayer |
| both | `moved → moved` | travels unchanged |

- **"No remaining feeder" is a REAL test, not a foregone conclusion**: a value input has exactly one feeder (so it always goes), but a **FLOW** input legitimately takes several, and the surviving ones must keep the port — with the moved node's direct edges added ALONGSIDE the surviving bridge, which a flow input accepts.
- **A REMOVED PORT ID IS NEVER RE-ISSUED IN THE SAME MOVE.** `nextPortId` walks a set that only GROWS (every id the def ever had this operation), because re-issuing `in_1` for a different port while the caller is about to prune wires model-wide BY that id is exactly the silent-mis-wire the prune exists to prevent. Verified: a move-out that removes `in_0` and needs a new input port emits `in_1`.
- **Positions** convert by the `createMacroFromSelection` / `undoMacro` invariant — def position = `parentPos − instancePos` on the way in, `instancePos + defPos` on the way out — then the cluster is nudged BELOW the existing content if it would land on top of anything (landing on the boundary nodes, or on the instance, is the one placement that is not merely cosmetic).
- **Node-id collisions** regenerate the id and remap every edge endpoint. Essentially impossible (ids are timestamp+random) but free to make impossible.

#### LINKED INSTANCES — the sharp edge, handled asymmetrically
- **MOVE IN is ALLOWED.** Adding a port is safe for the siblings (they grow an unconnected port). **REMOVING one is not**: it leaves every OTHER instance — in every graph and every nested def — wired to a port that no longer exists. Those wires are dropped by the new **`PRUNE_MACRO_INSTANCE_EDGES`** reducer action, which reuses `patchAllEdges` (whose `drop` callback was widened to receive the TARGET node as well: an edge INTO an instance names the port on its target handle, one OUT of it on its source handle). The notice says how many sibling wires went.
- **MOVE OUT is REFUSED above ONE instance**, with a notice naming the count and pointing at the link badge's "Make Independent Copy" — pulling a node out would silently strip that computation from every other instance. That restriction is also what makes the instance uniquely findable: `currentScope` is a stack of DEF ids, not instance node ids, so `locateMacroInstance` scans all four stores for it. **`countInstancesEverywhere` is now a thin ALIAS for `macroImport.countMacroInstances`** — it kept its own copy while that one still walked only `graphNodes` + `macroDefs` (it predated the Agents and Overseer graphs), but two walks is exactly the drift this module warns about elsewhere, and the split shipped a real bug: the linked-copies BADGE used the narrow one and never appeared for a duplicate made on the Agents or Overseer graph. One walk now.

#### EXPLICIT CONTROLS stay consistent
Every control whose target names a DEPARTING node is removed, for **both** nodeId-bearing target kinds (`config` and `facet`) plus `control` (a chained target names a nested macro INSTANCE node, which can itself move) — through `applyInterfaceEdit`, the ONE authoring mutation builder, so the CANONICAL ordering of `controls`/`groups` survives and an emptied array comes back `undefined` (the pristine record shape). It runs in BOTH directions: on the def being LEFT for a move-out, and on the PARENT def for a move-in when the parent scope is itself a macro. A chained target in an OUTER def that pointed at a control removed here degrades to the documented `orphan-control` block, which the instance already surfaces.

#### The gesture ([CaNode.tsx](src/modeler/vpl/CaNode.tsx) + [GraphEditor.tsx](src/modeler/vpl/GraphEditor.tsx))
- The grip renders in the header **only while the node is SELECTED**, and carries **`nodrag`** — MANDATORY, because React Flow attaches its node drag NATIVELY on the node element, so `stopPropagation` on a React handler does NOT prevent it (the Expression width-grip / macro link-badge precedent). Verified: a full press-move-Escape gesture on the grip leaves the node's `transform` byte-identical.
- **A COLLAPSED node shows the grip too** — ONE `renderScopeGrip(collapsed)` helper, so the gesture (`onScopeGripDown`) is shared and only the PLACEMENT differs. Expanded: a flex child at the header's right edge. Collapsed: an **absolutely-positioned overlay on the node ROOT, centred just BELOW it** (`.scopeGripCollapsed`) — a collapsed strip is ~25px tall with no room in its header, and a collapsed **colour constant renders a 24px swatch with NO header at all**, so one overlay serves both collapsed shapes. It hangs BELOW because the top corners belong to the warning badge (`top:-7 right:-7`) and the port-count indicators (`top:-6`), and the left/right edges to the handles, which fan out past the node's own height once several ports are connected. Over the canvas rather than a coloured header, so it takes an opaque surface + border; its rules MUST follow `.scopeGrip`'s (same specificity, order decides). The two branches are mutually exclusive (`showExpanded`), so a hover-expanded collapsed node renders the header grip only — never both.
- **The drop target is resolved in FLOW COORDINATES** (`screenToFlowPosition` + node bounding boxes, last match wins), never `document.elementFromPoint` — that does not hit-test React Flow's transformed viewport in an occluded pane, which would make the gesture unverifiable.
- Affordances: every valid target gets a dashed accent outline (`scopeDropTarget`), the one under the cursor a solid ring (`scopeDropHover`), the carried nodes dim (`scopeMoving`). **Escape cancels.** A refusal is an in-app notice (`.scopeNotice`, top-centre, `pointer-events: none`, 6 s) — **never `window.alert`**, which blocks the render loop and every browser-eval harness with it.
- **Boundary nodes and the singleton event roots can never cross** (`MOVE_SCOPE_EXCLUDED_TYPES`), and an instance can never be dropped into itself.
- **`writeScopeNow`** writes the open canvas to the model synchronously (the `scheduleSync` routing, minus the 100 ms debounce) so the several dispatches a move makes all see a consistent model. For a move-OUT the DEF on screen is authoritative (its edits may not have synced), while the PARENT comes from the model.
- **DEV hook `window.__moveSelectionToScope(nodeIds, dropTargetNodeId)`** runs the SAME `performScopeMove` the drop calls (the `__openSelectionMenu` precedent) — a real pointer drag on the grip DOES work through CDP, but a synthetic one cannot start a React Flow-adjacent gesture reliably, and the hook is what makes the semantics assertable in one eval.

#### ⚠ UNDO IS SCOPE-LOCAL (documented, not fixed)
`graphHistory` holds ONE stack for the graph on screen and `clearHistory()` runs on every scope change, so **Ctrl+Z cannot reverse a cross-scope move** — it restores the canvas half only. Same shape as the documented "Make Independent Copy" undo asymmetry; fixing it needs a model-level undo, which this feature does not introduce.

### Linked vs Independent Copies (v1.16):
- **The data model already supports sharing** — a macro instance is just a graph node whose `config.macroDefId` points at a `MacroDef`. Two instances sharing one `macroDefId` are **linked** (mirror copies): the MacroDef is the single source of truth (edit-inside writeback via `updateMacro`; all three compilers expand by `macroDefs.find(d => d.id === macroDefId)`), so editing any instance's internals updates ALL of them with **zero compiler changes**. Independent copies each own a separate MacroDef.
- **Creation paths (intentionally mixed):** Palette "Project Macro" drop = **linked** (reuses the existing `macroDefId`); right-click → **Duplicate → "Duplicate Linked"** = **linked**; right-click → **Duplicate → "Duplicate Independent"** + copy/paste + default-macro drop + Create-from-selection = **independent** (clone the def via `importMacro`/`cloneMacroWithFreshIds`).
- **`duplicateNode(linked = false)`** in [GraphEditor.tsx](src/modeler/vpl/GraphEditor.tsx): when `linked && srcType === 'macro'` it SKIPS the def-clone block so the duplicate keeps the source `macroDefId`. The single-node context menu renders **Duplicate as a hover submenu for macro nodes** (`.contextSubmenuTrigger`/`.contextSubmenu`, same pattern as Align/Distribute) — "Duplicate Independent" calls `duplicateNode(false)`, "Duplicate Linked" calls `duplicateNode(true)`. Non-macro nodes get a plain "Duplicate" button (`duplicateNode()` → independent). Don't pass `duplicateNode` directly as an `onClick` handler (the event would land in `linked`).
- **Count badge** ([CaNode.tsx](src/modeler/vpl/CaNode.tsx), `.linkBadge`): rendered as the first child of the macro `.header` (left of the "MACRO" title), shown ONLY when `countMacroInstances(model, macroDefId) >= 2` (Blender-style — single-user macros show nothing). Click → `.linkMenu` popover → **"Make Independent Copy"** = `importMacro(srcDef)` then `updateNodeData(id, {config:{macroDefId: newId}})` for THIS node only; other linked instances stay on the original (their count decrements). Keeps the node's `data.label` (no rename/suffix).
- **`nodrag` gotcha:** the badge + popover live in the `.header`, which is a React-Flow drag handle (only the `.body` carries the `nodrag` class). Interactive elements in the header MUST add the `nodrag` class or mousing down on them initiates a node drag — `onMouseDown` `stopPropagation` does NOT prevent it because React Flow's d3-drag attaches a native listener on the node element that fires before React's root-delegated handler. (`.linkBadge` + `.linkMenu` both carry `nodrag`.)
- **`countMacroInstances(model, macroDefId, excludeNodeId?)`** in [macroImport.ts](src/model/macroImport.ts) is **THE ONE model-wide macro-instance walk**: `graphNodes` + `agentGraphNodes` + `overseerGraphNodes` + every `macroDefs[*].nodes`. Consumers: the count badge, `undoMacro`'s def-removal ref-check, and `countInstancesEverywhere` (macroMoveScope), which is now a thin ALIAS — so the badge and the move-across-a-boundary refusal can never disagree about how many instances exist. `excludeNodeId` skips one node by id (`undoMacro` needs it: the model's copy of the live graph can still hold the very node being undone, since the canvas→model sync is debounced).
  - **⚠ IT WALKED ONLY `graphNodes` + `macroDefs` UNTIL 2026-09** — it predated the Agents and Overseer graphs, and the resulting gap was a **shipped bug on THREE surfaces at once**: (1) a **Duplicate Linked made on the Agents or Overseer graph counted 1, so the badge never appeared** (the user-reported *"sometimes does not show the linked icon"*; measured A/B in one model — Cells 2 instances → two "2" badges, Agents 2 instances → **0 badges**); (2) a Cells+Agents linked PAIR showed no badge on **either** side; (3) `undoMacro` could `removeMacro` a def a linked instance on another graph was still using. **A NEW top-level graph store must be added to the `visit` list AND to every consumer's memo/effect dependency array** — a right answer that is never recomputed is the same bug wearing a different hat (see the next bullet).
  - **The badge's `useMemo` deps list every store the walk reads** (`graphNodes`, `agentGraphNodes`, `overseerGraphNodes`, `macroDefs`). CaNode re-renders on the ModelContext change regardless of its memo comparator, so **the dep array is the only thing gating the recount** — the shipped bug was both halves at once (the walk skipped those stores AND the memo never re-ran). The palette's Project-Macros "used" filter carries the same store list for the same reason (a macro instantiated only on the Overseer graph is not stale and must not vanish from the palette).
- **Undo asymmetry (accepted, harmless):** "Make Independent" does a model dispatch (`importMacro` → ADD_MACRO, sets `isDirty`) AND a graph-only node retarget. Ctrl+Z (graph-only history) reverts the retarget but leaves an **orphan MacroDef** — hidden from the palette (`usedMacroIds` filter) and never removed out from under a live instance by `undoMacro`'s ref-count. This exactly mirrors the existing independent-`duplicateNode` behavior. Don't build a combined ModelContext action (it would have to own React-Flow graph state).

### Thumbnails
- `ModelProperties.thumbnail?: string` stores a PNG/JPEG/GIF/WebP **or `video/webm`** data URL (≤2 MB, validated in [InfoPanelContent.tsx](src/modeler/panels/InfoPanelContent.tsx)). Travels inside `.gcaproj` — no sidecar for user-saved files. **The schema is unchanged (still one data URL string)**; WebM is accepted because the simulator RECORDS WebM, so a short recording is the most natural thumbnail a model can carry.
- **AN `<img>` CANNOT DISPLAY A WEBM — every render site MUST go through [`<ThumbMedia>`](src/components/ThumbMedia.tsx)**, the ONE place the branch lives (a `<video autoPlay loop muted playsInline>` vs an `<img>`; the caller's `className`/`style` apply to both, so sizing/`object-fit` rules are shared). `muted` + `playsInline` are REQUIRED for autoplay without a user gesture, and `controls` is deliberately absent (a thumbnail is decoration, not a player). The three consumers: the Info panel preview, the Models Library hover popover, and the standalone viewer's About panel. [thumbnail.ts](src/model/thumbnail.ts) owns `isVideoThumbnail` (`data:video/…` for embedded URLs, an exact `.webm` extension for library sidecars — NB `.webp` (still) and `.webm` (clip) differ only in the last character), plus the shared `THUMBNAIL_ACCEPT` / `THUMBNAIL_MAX_BYTES` / `THUMBNAIL_FORMATS_LABEL`.
- **The ONE graceful degradation: the presentation export's `og:image`.** [exportPresentation.ts](src/export/exportPresentation.ts) gates on `thumb.startsWith('data:image/')`, so a WebM thumbnail is simply SKIPPED for the social tags (a link scraper needs an image) while still travelling inside the embedded model and playing in the viewer's About panel. Verified through the real export: `og:title` present, `og:image`/`twitter:image` absent.
- `modelsLibraryPlugin` in `vite.config.ts` extracts `properties.thumbnail` from each library `.gcaproj` into `<file>.thumb.<ext>` sidecars, records the sidecar path in `index.json`, and sweeps stale `*.thumb.*` on every run. Sidecars are gitignored (`public/models/*.thumb.{png,jpg,jpeg,gif,webp,webm}`). **The extension list appears in FIVE places that must stay in sync**: the plugin's `cleanThumbnails` sweep regex, its `extractThumbnail` data-URL regex + ext map, the PWA `globPatterns` precache entry, the PWA `runtimeCaching` thumb regex, and `.gitignore`.
- Plugin runs only at `configureServer` / `closeBundle` — adding a thumbnail to a library `.gcaproj` while the dev server is running requires a restart before it shows up. **Pre-existing dev-server gotcha (bit the WebM verification):** a sidecar written during `configureServer` can miss Vite's initial public-dir scan, so on the FIRST dev start after a NEW sidecar appears the request falls through to the SPA `index.html` (`content-type: text/html`) instead of the file. A second restart fixes it; the production build is unaffected (it copies `public/` into `dist/`). If a thumbnail mysteriously 404s-as-HTML in dev, restart before debugging the code.
- `ModelsLibrary` renders a fixed-position TWO-PANE popover on `onMouseEnter` — [title + auto-scrolling description | thumbnail], both 320×240, side by side — centered ON the hovered card (both axes, overlaying it; viewport-clamped near edges; `pointer-events: none` keeps the card's hover + clicks working underneath); `image-rendering: pixelated` + `object-fit: contain` so small grid GIFs scale up crisply (a WebM clip inherits the same box + fit).

### Model creation date (`properties.createdDate`)
- **`ModelProperties.createdDate?: string`** — an ISO calendar date (`YYYY-MM-DD`) the AUTHOR sets in the Info panel ("Creation date", with **Today** / **Clear** buttons). Additive + optional, travels inside `.gcaproj` like the rest of the presentation metadata; **no migration** (old files simply have no date).
- **WHY AUTHORED AND NOT DERIVED — the bug this replaced.** The library card stamp + the Newest/Oldest sort used to read a plugin-emitted `modified` = the `.gcaproj`'s **file mtime**, which every build / checkout / `git switch` churns — so the date said "when this working copy was written", never "when the model was made", and the sort was meaningless. **Filesystem birthtime is no better** (a checkout recreates the file). There is no derivable ground truth on disk, so the date is a field, not an inference.
- **A model with NO date shows NO date** — the card omits the stamp entirely (and its tooltip), and the entry sorts **LAST in BOTH Newest and Oldest** (then by name; `byCreated` in [ModelsLibrary.tsx](src/library/ModelsLibrary.tsx)). Silence beats a misleading number, and an undated model has no place on a time axis.
- **[createdDate.ts](src/model/createdDate.ts) is the ONE parse/format module** (`parseCreatedDate` / `createdDateTimestamp` / `formatCreatedDate` / `todayCreatedDate`), shared by the library, the standalone viewer's About panel ("Created", rendered only when set) and the Info panel. **Two traps it exists to close:** `new Date('2026-04-07')` parses as **UTC** midnight and renders as the PREVIOUS day west of Greenwich (so it builds a LOCAL-midnight date from the components), and `toISOString()` for "today" is likewise UTC (so `todayCreatedDate` formats local parts). It also round-trip-validates the components, rejecting overflow dates the `Date` constructor would silently roll forward.
- **The Vite plugin (`modelsLibraryPlugin`) emits `createdDate` only when `properties.createdDate` matches `YYYY-MM-DD`**, and **omits the key otherwise** — so an unset/garbage value can never become a card stamp. `index.json` is build-generated + gitignored, so the field swap needed no back-compat shim. As with thumbnails, the plugin runs at `configureServer` / `closeBundle` — **editing a shipped model's date needs a dev-server restart** before the library reflects it.
- **The 29 shipped library models are stamped with their FIRST-ADDED commit date** (`git log --diff-filter=A --format=%as -- <file>`; **NOT `--follow`**, whose rename heuristic misattributes a new model to a similar deleted one — it dated four GRA samples two months early). Each **generator script carries the same date** as a `createdDate:` literal in its properties object, so a re-run preserves the stamp.

### Key Patterns:
- When adding new fields to CAModel type, always add migration guards in ModelContext's `createInitialState`
- `Attribute.boundaryValue?: string` (cell attrs only, shown in UI only when `properties.boundaryTreatment === 'constant'`). Worker's `buildNeighborIndices` writes `boundaryCellValue(attr) ?? defaultValue(attr)` into the sentinel cell at index `total`. WASM reads the same memory — no compile-path change needed.
- Align / Distribute submenu on the multi-selection context menu (`alignNodes(mode)` / `distributeNodes(axis)` in GraphEditor.tsx). Align modes: left/centerH/right, top/centerV/bottom. Distribute: sort by axis, fix first and last, equalize inter-node gaps. Uses the standard `pushCurrentSnapshot()` + `scheduleSync()` pattern.
- Node config UI: when a config field changes type (e.g., constType), reset dependent fields to prevent stale values
- Compiler: all value declarations hoisted to function scope (Pass 1) before control flow (Pass 2) to avoid block-scoping issues
- Web Worker in Vite: `new Worker(new URL('./file.ts', import.meta.url), { type: 'module' })` — no config needed
- Worker postMessage with transfer: use `{ transfer: [buffer] }` options format (not positional arg)
- ID generation: NEVER use counter-based IDs (`nextId++`) — they collide after page reload with saved models. Always use `Date.now().toString(36) + Math.random().toString(36).slice(2,5)`
- Worker message types: adding new messages requires updating the `WorkerMsg` union type in sim.worker.ts
- Vite base path: `const base = process.env.GHPAGES ? '/GenesisCA/' : '/'` — the production site is served at the ROOT of the custom domain **genesisca.online** (pinned by [public/CNAME](public/CNAME)), so the deploy ([deploy.yml](.github/workflows/deploy.yml)) builds with base `/` — the same as `npm run dev`, local `npm run build`/`preview`, and the Tauri shell. `GHPAGES` is an opt-in fallback: set it to rebuild under the `/GenesisCA/` subpath ONLY if the custom domain is removed and the bare `rff255.github.io/GenesisCA/` project URL is used directly. Don't hardcode `/GenesisCA/` for local builds.
- Reset must run one step via compiled stepFn so model-defined color mappings apply (not hardcoded fallback)
- Models Library: Vite plugin in vite.config.ts auto-generates `models/index.json` from `public/models/*.gcaproj` — no manual manifest; card metadata comes from `ModelProperties`
